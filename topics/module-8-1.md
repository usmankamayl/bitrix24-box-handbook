# Модуль 8.1: Авторизация в Bitrix24 REST API

## Теория

### Что такое Bitrix24 REST API?

**Bitrix24 REST API** — это HTTP-интерфейс для взаимодействия с Bitrix24 (облачная и коробочная версия). Позволяет:
- Управлять CRM (лиды, сделки, контакты, компании)
- Работать с задачами, календарем, дисками
- Создавать приложения для Bitrix24.Market
- Интегрировать внешние системы (1C, AmoCRM, телефония, и т.д.)

**Базовый URL облачного портала:**
```
https://ваш-домен.bitrix24.ru/rest/
```

### Типы авторизации в Bitrix24 REST API

#### 1. OAuth 2.0 (Для приложений)

**Когда использовать:**
- Создаете приложение для Bitrix24.Market
- Нужен доступ к нескольким порталам
- Требуется работа от имени пользователя

**Схема работы:**
```
1. Пользователь устанавливает приложение
2. Приложение получает код авторизации (authorization_code)
3. Обменивает код на access_token и refresh_token
4. Использует access_token для запросов (живет 1 час)
5. Обновляет access_token через refresh_token (живет бесконечно)
```

**Endpoints:**
```
Авторизация: https://oauth.bitrix.info/oauth/authorize/
Получение токена: https://oauth.bitrix.info/oauth/token/
```

**Параметры авторизации:**
- `client_id` — ID приложения (из маркетплейса)
- `client_secret` — секрет приложения
- `redirect_uri` — URL для редиректа после авторизации
- `scope` — права доступа (crm, task, user, etc.)

**Пример URL авторизации:**
```
https://oauth.bitrix.info/oauth/authorize/?client_id=APP_ID&response_type=code&redirect_uri=https://example.com/callback
```

**Получение токена:**
```php
POST https://oauth.bitrix.info/oauth/token/
  ?grant_type=authorization_code
  &client_id=APP_ID
  &client_secret=APP_SECRET
  &code=AUTHORIZATION_CODE
  &redirect_uri=https://example.com/callback
```

**Ответ:**
```json
{
  "access_token": "abc123...",
  "refresh_token": "xyz789...",
  "expires_in": 3600,
  "scope": "crm,task",
  "domain": "your-portal.bitrix24.ru",
  "member_id": "user123"
}
```

**Обновление токена:**
```php
POST https://oauth.bitrix.info/oauth/token/
  ?grant_type=refresh_token
  &client_id=APP_ID
  &client_secret=APP_SECRET
  &refresh_token=REFRESH_TOKEN
```

---

#### 2. Входящий Webhook (Incoming Webhook)

**Когда использовать:**
- Быстрая интеграция для одного портала
- Не требуется работа от имени конкретного пользователя
- Внутренние скрипты, интеграции

**Преимущества:**
- ✅ Простота настройки (1 минута)
- ✅ Не нужна регистрация приложения
- ✅ Токен не истекает (пока не удалите вебхук)
- ✅ Отлично для скриптов и внутренних интеграций

**Недостатки:**
- ❌ Привязан к одному порталу
- ❌ Работает от имени одного пользователя
- ❌ Нельзя публиковать в маркетплейс

**Как создать входящий вебхук:**
1. Зайти в Bitrix24 → Приложения → Вебхуки
2. Нажать "Добавить входящий вебхук"
3. Выбрать права доступа (CRM, задачи, диски и т.д.)
4. Получить URL вида:
```
https://your-portal.bitrix24.ru/rest/1/abc123xyz789/
```

**Структура URL:**
```
https://your-portal.bitrix24.ru/rest/{USER_ID}/{WEBHOOK_CODE}/
```

**Пример запроса:**
```php
GET https://your-portal.bitrix24.ru/rest/1/abc123xyz789/crm.lead.list.json
```

**С помощью PHP:**
```php
<?php
$webhookUrl = 'https://your-portal.bitrix24.ru/rest/1/abc123xyz789/';
$method = 'crm.lead.list';

$response = file_get_contents($webhookUrl . $method . '.json');
$data = json_decode($response, true);
```

---

#### 3. Исходящий Webhook (Outgoing Webhook)

**Когда использовать:**
- Bitrix24 должен СООБЩИТЬ вашему серверу о событии
- Реакция на события CRM (создание лида, изменение сделки)
- Триггеры для автоматизации

**Схема работы:**
```
1. В Bitrix24 настраивается исходящий вебхук на событие
2. При наступлении события Bitrix24 отправляет POST на ваш URL
3. Ваш сервер обрабатывает данные
```

**Как создать:**
1. Приложения → Вебхуки → Добавить исходящий вебхук
2. Выбрать событие (onCrmLeadAdd, onCrmDealUpdate, и т.д.)
3. Указать URL вашего сервера
4. Bitrix24 отправит туда POST при событии

**Пример данных от Bitrix24:**
```json
{
  "event": "ONCRMLEADADD",
  "data": {
    "FIELDS": {
      "ID": "123",
      "TITLE": "Новый лид"
    }
  },
  "ts": "1609459200",
  "auth": {
    "access_token": "...",
    "domain": "your-portal.bitrix24.ru"
  }
}
```

### Сравнение методов авторизации

| Критерий | OAuth 2.0 | Входящий Webhook | Исходящий Webhook |
|----------|-----------|------------------|-------------------|
| **Сложность настройки** | Высокая | Низкая | Средняя |
| **Регистрация приложения** | Требуется | Не требуется | Не требуется |
| **Работа с несколькими порталами** | ✅ Да | ❌ Нет | ❌ Нет |
| **Истечение токена** | Да (1 час) | Нет | N/A |
| **Публикация в маркетплейс** | ✅ Да | ❌ Нет | ❌ Нет |
| **Реакция на события** | Нет | Нет | ✅ Да |
| **Лучший вариант для** | Приложений | Скриптов | Триггеров |

### Структура REST-запроса

**Базовая структура:**
```
{BASE_URL}/{METHOD}.json?param1=value1&param2=value2
```

**Для OAuth 2.0:**
```
https://your-portal.bitrix24.ru/rest/{METHOD}.json
Headers: Authorization: Bearer {ACCESS_TOKEN}
```

**Для Webhook:**
```
https://your-portal.bitrix24.ru/rest/{USER_ID}/{WEBHOOK_CODE}/{METHOD}.json
```

**Методы HTTP:**
- `GET` — получение данных (список лидов, информация о сделке)
- `POST` — создание/изменение данных (добавить лид, обновить контакт)

**Формат ответа:**
```json
{
  "result": {
    /* данные */
  },
  "time": {
    "start": 1609459200.123,
    "finish": 1609459200.456,
    "duration": 0.333
  }
}
```

**Формат ошибки:**
```json
{
  "error": "INVALID_TOKEN",
  "error_description": "Токен доступа недействителен"
}
```

### Права доступа (Scope)

При создании приложения или вебхука нужно указать **scope** — набор прав:

| Scope | Описание |
|-------|----------|
| `crm` | Доступ ко всем данным CRM |
| `task` | Задачи и проекты |
| `user` | Пользователи и права |
| `calendar` | Календарь и события |
| `disk` | Диски и файлы |
| `telephony` | Телефония |
| `im` | Чат и мессенджер |
| `placement` | Встраивание в интерфейс |

**Принцип минимальных привилегий:**
Запрашивайте ТОЛЬКО те права, которые реально нужны приложению.

---

### Частые ошибки при авторизации

#### 1. `INVALID_TOKEN` или `expired_token`
**Причина:** access_token истек (живет 1 час)  
**Решение:** Обновить через refresh_token

#### 2. `INSUFFICIENT_SCOPE`
**Причина:** У токена нет прав для метода  
**Решение:** Пересоздать вебхук с нужными правами или запросить scope в OAuth

#### 3. `PAYMENT_REQUIRED`
**Причина:** Портал на тарифе, где REST API ограничен  
**Решение:** Upgrade тарифа Bitrix24

#### 4. `QUERY_LIMIT_EXCEEDED`
**Причина:** Превышен лимит запросов (обычно 2 req/sec для вебхуков, 50 для OAuth)  
**Решение:** Использовать batch-запросы или добавить задержки

## Вопросы для собеседования

### Вопрос 1: Какие типы авторизации поддерживает Bitrix24 REST API?

**Ответ:**
1. **OAuth 2.0** — для приложений, публикуемых в маркетплейс
2. **Входящий Webhook** — для быстрых интеграций одного портала
3. **Исходящий Webhook** — для получения событий от Bitrix24

OAuth используется для мультипортальных приложений, вебхуки — для внутренних интеграций.

---

### Вопрос 2: В чем разница между входящим и исходящим вебхуком?

**Ответ:**

**Входящий webhook:**
- ВЫ вызываете REST API Bitrix24
- Получаете постоянный URL с токеном
- Делаете запросы к Bitrix24 (crm.lead.list, и т.д.)

**Исходящий webhook:**
- Bitrix24 вызывает ВАШ сервер
- Вы указываете URL вашего сервера
- При событии (создание лида) Bitrix24 отправляет POST на ваш URL

---

### Вопрос 3: Как работает OAuth 2.0 в Bitrix24? Опишите flow авторизации.

**Ответ:**

**Шаги:**
1. Пользователь устанавливает приложение из маркетплейса
2. Bitrix24 редиректит на `redirect_uri` с параметром `code`
3. Приложение обменивает `code` на `access_token` и `refresh_token` через `https://oauth.bitrix.info/oauth/token/`
4. `access_token` используется для запросов (живет 1 час)
5. Когда токен истекает, обновляем через `refresh_token` (живет бесконечно)

**Важно:** 
- `access_token` передается в заголовке `Authorization: Bearer {TOKEN}`
- `refresh_token` нужно безопасно хранить на сервере

---

### Вопрос 4: Сколько живет access_token в OAuth 2.0? Как его обновить?

**Ответ:**

**Время жизни:** 1 час (3600 секунд)

**Обновление:**
```php
POST https://oauth.bitrix.info/oauth/token/
  ?grant_type=refresh_token
  &client_id=APP_ID
  &client_secret=APP_SECRET
  &refresh_token=REFRESH_TOKEN
```

**Ответ:**
```json
{
  "access_token": "new_token",
  "refresh_token": "new_refresh_token", // ВАЖНО: обновляется тоже!
  "expires_in": 3600
}
```

**Важно:** При обновлении `refresh_token` ТОЖЕ меняется! Сохраняйте новый.

---

### Вопрос 5: В каких случаях использовать OAuth 2.0, а в каких — Webhook?

**Ответ:**

**OAuth 2.0 использовать когда:**
- ✅ Создаете приложение для публикации в Bitrix24.Market
- ✅ Приложение должно работать с множеством порталов
- ✅ Нужна работа от имени конкретного пользователя
- ✅ Требуется соблюдение OAuth-стандарта

**Webhook использовать когда:**
- ✅ Быстрая интеграция для одного портала
- ✅ Внутренний скрипт или автоматизация
- ✅ Не планируется публикация в маркетплейс
- ✅ Нужно просто "дернуть API" без сложной авторизации

**Пример:** Синхронизация заказов с вашей CRM → Webhook. Приложение для 1000 порталов → OAuth.

---

### Вопрос 6: Как обработать ошибку INVALID_TOKEN?

**Ответ:**

**Причины:**
1. access_token истек (прошел час)
2. Токен был отозван (пользователь удалил приложение)
3. Неправильный формат токена

**Алгоритм обработки:**
```php
1. Получили INVALID_TOKEN или expired_token
2. Пытаемся обновить через refresh_token
3. Если обновление успешно → повторяем запрос с новым токеном
4. Если обновление не удалось → удаляем токены, требуем повторной авторизации
```

**Код:**
```php
try {
    $result = callBitrix24API($method, $params, $accessToken);
} catch (InvalidTokenException $e) {
    $newToken = refreshAccessToken($refreshToken);
    $result = callBitrix24API($method, $params, $newToken);
}
```

### Вопрос 7: Что такое scope в Bitrix24 REST API?

**Ответ:**

**Scope** — это набор прав доступа, которые запрашивает приложение.

**Основные scope:**
- `crm` — CRM (лиды, сделки, контакты, компании)
- `task` — задачи
- `user` — пользователи
- `calendar` — календарь
- `disk` — диски и файлы
- `telephony` — телефония

**При создании вебхука:** выбираете права через чекбоксы в UI  
**При OAuth:** указываете в параметре `scope` при авторизации

**Принцип:** Запрашивайте ТОЛЬКО необходимые права (принцип минимальных привилегий)

**Пример:**  
Если приложение работает только с лидами → scope=crm достаточно, не нужно запрашивать task, calendar, и т.д.

---

### Вопрос 8: Как Bitrix24 определяет от чьего имени выполняется запрос?

**Ответ:**

**OAuth 2.0:**  
Запрос выполняется от имени пользователя, который установил приложение (member_id в ответе токена)

**Входящий Webhook:**  
От имени пользователя, который создал вебхук (видно в URL `/rest/{USER_ID}/...`)

**Важно для прав:**
- Если пользователь не имеет доступа к сделке → API вернет ошибку доступа
- Для обхода используют webhook от имени администратора

---

### Вопрос 9: Какие лимиты на запросы в Bitrix24 REST API?

**Ответ:**

**Входящий Webhook (облако):**
- 2 запроса в секунду
- При превышении → ошибка `QUERY_LIMIT_EXCEEDED`

**OAuth 2.0:**
- Зависит от тарифа портала
- Обычно 50+ запросов в секунду

**Batch-запросы:**
- До 50 команд в одном batch
- Считается как 1 запрос к лимиту

**Решение для больших объемов:**
1. Использовать batch (до 50 запросов за раз)
2. Добавить задержки между запросами
3. Использовать очереди (Redis, RabbitMQ)
4. Переход на OAuth вместо webhook

---

### Вопрос 10: Можно ли использовать REST API в коробочной версии Bitrix24?

**Ответ:**

**Да, можно!** Но есть отличия:

**Коробка (self-hosted):**
- REST API доступен по умолчанию
- URL: `https://your-domain.com/rest/`
- Лимиты зависят от вашего сервера (не от Bitrix24)
- OAuth работает так же, но через ваш сервер

**Облако:**
- URL: `https://your-portal.bitrix24.ru/rest/`
- Лимиты 2 req/sec для webhook
- OAuth через `oauth.bitrix.info`

**Основное отличие:** В коробке вы контролируете лимиты и инфраструктуру.

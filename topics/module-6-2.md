# Модуль 6.2: Кейсы из реальной практики (уровень senior)

## Теория

### Что такое «кейс из практики» на собеседовании

Это не «какая функция делает X», а реальная больная ситуация, где нет одного правильного ответа. Интервьюер описывает инцидент или бизнес-требование и смотрит на ход рассуждений:

- Собираете ли вы требования до кода?
- Видите ли граничные случаи (ночная выгрузка, двойной клик, падение API)?
- Понимаете ли последствия решений (кеш → устаревание, очередь → задержка, лок → дедлок)?

Типичная ошибка мидла — сразу называть технологию («нужна очередь!»). Senior сначала уточняет объёмы, частоту, требования к консистентности — и только потом предлагает архитектуру.

### Кейс 1: «Импорт товаров из 1С убивает сайт»

**Ситуация:** ночная выгрузка 50К товаров из 1С через `iblock.ajax` / CommerceML. Пока идёт импорт — сайт лагает, фронтенд 500-ит, менеджеры жалуются.

**Вопросы senior-а перед решением:**

- Сколько записей и как часто? (50К раз в сутки vs 500 раз в минуту — разные архитектуры)
- Полная выгрузка или дельта? (полная каждый раз = ужасно)
- Что именно тормозит — запись в БД, пересчёт индексов, инвалидация кеша, фасетный индекс?

**Типовые причины и решения:**

| Причина | Решение |
|---------|---------|
| Полная выгрузка вместо дельты | `only_changes` в обмене, либо собственная дельта по `TIMESTAMP_X` |
| Каждая запись = `save()` с событиями | Отключить обработчики на время импорта, batch-insert |
| Перестроение фасетного индекса после каждой записи | `CIBlockElement::SetPropertyValuesEx` + `SetFacetIndex(false)` → один `Reindex` в конце |
| Сброс кеша на каждый элемент | Тегированный кеш + отложенная инвалидация |
| Импорт в пиковые часы | Перенести на ночь / cron, либо queue-worker с rate limit |
| `OnBeforeIBlockElementUpdate` с тяжёлой логикой | Проверка `$_REQUEST['type'] === 'catalog'` или флаг `IMPORT_MODE` |

**Senior-ответ:** «Сначала замеряю — SqlTracker на время импорта. Если боль в событиях — выключаю через флаг `$_SESSION['BX_IMPORT_MODE']` или передаю признак в `$arParams`. Если полная выгрузка — настраиваю дельту. Фасету и кеш — отложенная инвалидация. И обязательно: импорт идёт через отдельный скрипт-агент, не через веб.»

### Кейс 2: «Дубли заказов при двойном клике / ретрае платежа»

**Ситуация:** пользователь жмёт «Оформить» дважды (медленный интернет) — создаётся два заказа. Или платёжная система шлёт webhook дважды — заказ отмечается оплаченным дважды, менеджеру приходят два письма.

**Корень проблемы:** отсутствие идемпотентности.

**Решения:**

- **Уровень UI:** кнопка дизейблится после первого клика (не защита, но UX).
- **Уровень API:** уникальный `REQUEST_ID` (UUID с фронта) — сервер проверяет `Option` / отдельную таблицу: «этот request уже обработан?» → возвращает существующий заказ.
- **Уровень БД:** уникальный индекс по `XML_ID` или `external_id`.
- **Уровень webhook (PaySystem):** в `processRequest` проверка `isPayed()` *до* `setPaid()`; отдать 200 OK даже если уже оплачен (иначе ПС будет ретраить).

```php
// Идемпотентный webhook — паттерн, который ждут на собеседовании
public function processRequest(Payment $payment, Request $request): Result
{
    if (!$this->isSignatureValid($request)) {
        return $this->fail('invalid signature');
    }
    if ($this->isPayed($payment)) {
        // Уже обработано — НЕ ошибка, идемпотентность
        return new Result(); // 200 OK
    }
    // ... setPaid + save
}
```

### Кейс 3: «Заказ создался, но письмо/1С/склад не узнали»

**Ситуация:** на `OnSaleOrderSaved` навешаны 5 обработчиков: письмо клиенту, выгрузка в 1С, уведомление менеджеру в Slack, резерв на складе, SMS. Один падает (SMTP down) — падают все, или заказ «подвисает».

**Анти-паттерн мидла:**

```php
AddEventHandler('sale', 'OnSaleOrderSaved', function($event) {
    sendEmail();     // SMTP timeout 30с — пользователь ждёт
    exportTo1C();    // 1С упала → исключение → rollback заказа?!
    notifySlack();
});
```

Три проблемы: событие внутри транзакции → тяжёлая работа держит локи; исключение в одном обработчике ломает всех; синхронный вызов внешних API = медленный checkout.

**Senior-решение — transactional outbox / очередь:**

```php
// В событии — только запись в очередь (быстро, в той же транзакции)
AddEventHandler('sale', 'OnSaleOrderSaved', function($event) {
    $order = $event->getParameter('ENTITY');
    OutboxTable::add([
        'EVENT_TYPE' => 'order.saved',
        'ENTITY_ID' => $order->getId(),
        'PAYLOAD' => json_encode(['status' => $order->getField('STATUS_ID')]),
        'CREATED_AT' => new DateTime(),
    ]);
});

// Отдельный worker/агент разгребает очередь с retry + dedup
```

Плюсы: заказ сохранится даже если 1С лежит; каждый консьюмер независим; retry без влияния на checkout.

### Кейс 4: «Скидка применилась дважды / не туда»

**Ситуация:** маркетинг создал правило корзины «скидка 10% при сумме > 5000». Клиенты жалуются: скидка применяется к отложенным товарам, или суммируется с купоном, хотя не должна.

**Что проверяет кейс:** знание механизма скидок — приоритеты, условия применения, `MAX_DISCOUNT`, совместимость купонов, порядок калькуляции (`Discount` работает в `onAfterSaleOrderCreate`/`refreshOrderAjax`).

**Senior-ответ:** смотрю `b_sale_discount` — `PRIORITY`, `SORT`, `USE_COUPONS`; проверяю условия (`CondBsktAmtGroup`); тестирую через `CSaleDiscount::GetCoupons()` + `DiscountCouponsManager`. Кастомную логику — через событие `OnCondSaleControlBuildList` или собственный правила-класс, а не правкой корзины.

### Кейс 5: «Сайт упал после обновления модуля»

**Ситуация:** обновили `iblock` — сайт белый экран. Откатить нельзя (обновление необратимое).

**План:**

1. **Не паника, не «откатываем БД».** Логи: `/bitrix/modules/updater_partner.log`, php error_log.
2. **Белый экран → fatal error.** Включаем `display_errors` временно или смотрим error_log — обычно несовместимость кастомного кода с новым API.
3. **Проверка `updater`:** иногда обновление применилось частично — `updater.log` покажет где упало; докручиваем вручную через `php updater.php`.
4. **Профилактика:** staging-копия, `version` в `modules/`, lock-файл `.settings.php`.

**Senior-пойнт:** «У нас канареечный деплой — сначала staging с той же копией БД, прогоняем smoke-тесты (авторизация, каталог, оформление заказа), только потом прод.»

---

### Общая формула ответа на «кейс»

1. **Уточняю контекст:** объёмы, частота, критичность, SLA.
2. **Локализую:** замер (SqlTracker/XHProf/логи), а не гадание.
3. **Предлагаю 2 варианта** с trade-offs (быстрый фикс vs правильная архитектура).
4. **Называю риски:** что сломается при ×10 нагрузке, при падении внешнего сервиса.
5. **Метрика успеха:** «готово, когда checkout < 1.5с и ноль дублей за неделю».

## Вопросы для собеседования

1. **Что делать, если импорт из 1С лочит таблицу товаров?** — batch-запись, отключение событий, импорт в реплику/отдельную таблицу + swap.
2. **Как гарантировать exactly-once при webhook от платёжной системы?** — идемпотентный `processRequest`: проверка `isPayed()` до `setPaid`, dedup по `PS_INVOICE_ID` + `event_id`.
3. **Почему нельзя отправлять email синхронно в `OnSaleOrderSaved`?** — событие внутри транзакции, SMTP-timeout держит локи и замедляет checkout; исключение может откатить заказ.
4. **Как вы откатите плохой релиз модуля?** — VCS для кастомного кода, БД-бекап до обновления, staging-first, feature flags для новой логики.
5. **Кейс: «клиент оформил заказ, а оплата прошла через 10 минут — статус заказа?»** — заказ `N` + отдельное `Payment` со своим статусом; `processRequest` переводит `PAYED='Y'`, что триггерит `OnSaleOrderPaid`.

---

## Частые ошибки в ответах

- **«Перепишем на очередь»** — без уточнения объёмов. На 50 заказов/сутки очередь — overengineering.
- **«Добавим индекс»** — без `EXPLAIN` и знания selectivity.
- **«Это проблема 1С»** — senior смотрит со своей стороны: а что мы можем сделать с потреблением?
- **Отсутствие метрик** — «сделал быстрее» без «с 8с до 0.3с» звучит пусто.

# Модуль 13.4: Разбор реальных задач с собеседований

## Теория

Этот модуль — не новый API, а разбор типовых практических задач, которые
задают на собеседованиях Bitrix-разработчиков уровня middle+. Для каждой —
краткая формулировка, архитектурное решение и типичные ловушки, которые
собеседующий ждёт, что вы увидите. Реализация трёх из них — в
`examples/module-13-4/`.

### Классификация задач

| Тип задачи | Что проверяют | Примеры |
|---|---|---|
| **Алгоритмическая** | Умение работать с данными Bitrix-структуры без прямого SQL | "Дедупликация лидов", "Сводный отчёт по сделкам за период" |
| **Архитектурная** | Понимание масштаба и изоляции | "Multi-tenant приложение", "Синхронизация с внешним сервисом без блокировки CRM" |
| **Практическая** | Знание конкретных методов и их контрактов | "REST-робот", "Webhook с проверкой подписи", "Batch-импорт" |
| **Диагностическая** | Умение рассуждать о чужом коде | "Почему этот код дублирует сделки?", "Почему робот не срабатывает?" |

### Задача 1: Дедупликация лидов по телефону при импорте

**Формулировка:** "Есть CSV с 10 000 лидов, часть телефонов дублируются. Нужно импортировать только уникальные лиды. Как будете делать?"

Поверхностный ответ — `crm.lead.add` в цикле. Правильный — сначала `crm.duplicate.findbycomm` (поиск дублей в CRM до добавления), затем батчирование добавления.

```php
// До добавления проверяем — есть ли лид/контакт с таким телефоном
$dup = CRest::call('crm.duplicate.findbycomm', [
    'entity_type' => 'LEAD',
    'type' => 'PHONE',
    'values' => [$phone],
]);

if (!empty($dup['result']['LEAD'])) {
    // Лид с таким телефоном уже есть — пропускаем или обновляем существующий
    continue;
}
```

**Ключевой момент, который отличает сильный ответ:** не пытаться дедуплицировать только внутри CSV — дубликаты могут быть уже в CRM. `crm.duplicate.findbycomm` делает ровно то, что делает штатный механизм контроля дублей в интерфейсе, включая поиск по отформатированному номеру (Bitrix24 нормализует +7, 8, скобки и пробелы сам — не нужно писать свой нормализатор перед запросом).

**Ловушки:**
- Сравнивать телефоны как строки без нормализации — `8 (999) 123-45-67` и `+79991234567` для Bitrix24 — один и тот же номер, а для `==` — нет.
- Делать 10 000 отдельных `crm.lead.add` — упираетесь в rate limit (см. [8.3](module-8-3.md), batch — обязателен).
- Не учитывать, что `crm.duplicate.findbycomm` ищет по всем коммуникациям, включая `PHONE_WORK`, `PHONE_MOBILE` и т.д. — не только по `PHONE`.

### Задача 2: Отчёт "сумма закрытых сделок по менеджерам за месяц" без выгрузки в Excel

**Формулировка:** "Нужно вывести таблицу: менеджер — количество и сумма выигранных сделок за текущий месяц. Можно запросами к CRM, можно через BX24 — выбирайте сами."

Наивное решение — `crm.deal.list` с фильтром `STAGE_SEMANTIC_ID = 'S'` и `CLOSEDATE >= '2026-11-01'`, а затем группировка массива на PHP. Правильное — в зависимости от объёма:

```php
// Небольшой объём (тысячи сделок) — достаточно crm.deal.list + группировка на PHP
$deals = CRest::call('crm.deal.list', [
    'filter' => [
        'STAGE_SEMANTIC_ID' => 'S', // только успешно закрытые, не все закрытые
        '>=CLOSEDATE' => '2026-11-01',
        '<CLOSEDATE' => '2026-12-01',
    ],
    'select' => ['ASSIGNED_BY_ID', 'OPPORTUNITY', 'CURRENCY_ID'],
    'start' => -1, // обход пагинации в новом API — вместо самописного next/cursor
]);

$byManager = [];
foreach ($deals['result'] as $d) {
    $byManager[$d['ASSIGNED_BY_ID']]['count'] = ($byManager[$d['ASSIGNED_BY_ID']]['count'] ?? 0) + 1;
    $byManager[$d['ASSIGNED_BY_ID']]['sum'] = ($byManager[$d['ASSIGNED_BY_ID']]['sum'] ?? 0) + (float) $d['OPPORTUNITY'];
}
```

**Ключевые моменты сильного ответа:**
- `STAGE_SEMANTIC_ID = 'S'`, а не список конкретных `STAGE_ID` — если воронок несколько или стадии переименовали, код не ломается (см. [13.3](module-13-3.md)).
- `'start' => -1` — автоматическая итерация по пагинации, а не ручной обход `next`. В старом коде (`crm.deal.list` до ~2024 года) пагинация делалась через `start` параметр или `next` в ответе; сейчас `'start' => -1` делает то же, но с автоматическим курсором.
- Для большого объёма (сотни тысяч) честно сказать — `crm.deal.list` в цикле не подходит, нужен либо BI-коннектор (в Bitrix24.Enterprise), либо прямой запрос к реплике БД (коробка), либо собственная агрегирующая таблица, заполняемая событием `OnAfterCrmDealUpdate`.

### Задача 3: Обработчик входящего webhook, который не должен обрабатывать чужие запросы

**Формулировка:** "У вас есть endpoint `handler.php`, который принимает события от другого сервиса и создаёт сделки в CRM. Как защитить его от произвольных запросов?"

Проверка `application_token` (OAuth-приложение) или секрета в URL webhook — уже базовый ответ (см. [12.3](module-12-3.md)). Сильный ответ добавляет **подпись тела запроса**, потому что `application_token` сверяет только факт "запрос пришёл от Bitrix24", но ничего не говорит о том, что тело не подменили в пути или что обработчик не вызвали напрямую, минуя Bitrix24.

```php
// При установке Bitrix24 присылает application_token — сохраняем его.
// Для всех последующих вызовов handler.php сверяем его + целостность тела.
$auth = $_POST['auth'] ?? [];
$expected = $installation['application_token'] ?? null;

if (!$expected || !hash_equals($expected, $auth['application_token'] ?? '')) {
    http_response_code(403);
    exit;
}

// Дополнительно — проверка member_id: чужой портал, подделавший app_token,
// не сможет дёрнуть обработчик от чужого имени
if (($auth['member_id'] ?? '') !== $installation['member_id']) {
    http_response_code(403);
    exit;
}
```

**Ловушки:**
- Сравнение токенов через `==` вместо `hash_equals` — уязвимость timing-атаки (не критична для обычного скрипта, но маркер зрелости).
- Проверка только по IP-адресу Bitrix24 — IP могут меняться и не документированы как надёжный источник доверия; `application_token` — правильный механизм.
- Доверять `member_id` без дополнительной проверки — `member_id` не секретен, его можно подобрать.

### Задача 4: Сделка создаётся, но робот на нужной стадии не срабатывает

**Формулировка (диагностическая):** "Клиент пишет: 'робот на стадии "Согласование" не срабатывает, хотя сделка туда попадает'. Что проверять?"

Пошаговый чек-лист, который должен быть в голове на собеседовании:

1. **Триггер на стадии.** Роботы "при входе на стадию" срабатывают только если сделка физически *перешла* на эту стадию — если она была создана уже с этой стадией, "входа" не было. Проверить, не нужен ли робот "на стадии" или триггер по созданию.
2. **Условия робота.** Встроенное условие (см. [13.3](module-13-3.md)) может молча не пропускать сделку (например, "только если сумма > 0", а поле пустое).
3. **Права на робота.** Роботы, добавленные через REST (`bizproc.robot.add`), привязаны к `AUTH_USER_ID` — если у этого пользователя нет прав на изменение сделки, робот "тихо" не сработает.
4. **`bizproc.workflow.log`.** Найти экземпляр БП для этой сделки и посмотреть, на каком шаге он стоит — возможно, робот вообще не дошёл, потому что предыдущий шаг ещё не завершился.
5. **Кастомный робот не вызвал `bizproc.event.send`.** Если это ваш `HANDLER` — робот в логе БП будет стоять "В работе", пока ваш код не пришлёт `bizproc.event.send` (или `bizproc.activity.completed` для activity).

### Задача 5: Двусторонняя синхронизация без зацикливания

**Формулировка:** "Сделки синхронизируются между Bitrix24 и внешней системой в обе стороны. Как не получить бесконечный цикл, когда изменение в одной системе вызывает изменение в другой?"

Это один из самых популярных вопросов синьорского уровня. Правильный ответ — **флаг "это изменение пришло из синхронизации"**, а не догадки по содержимому:

```php
// При получении изменения от внешней системы помечаем сделку перед записью
// через кастомное поле UF_CRM_SYNC_SOURCE = 'external', чтобы обработчик
// OnAfterCrmDealUpdate знал, что изменение пришло из синхронизации, а не от пользователя

// В обработчике OnAfterCrmDealUpdate — проверяем источник
AddEventHandler('crm', 'OnAfterCrmDealUpdate', function ($fields) {
    if (($fields['UF_CRM_SYNC_SOURCE'] ?? '') === 'external') {
        // Это изменение пришло от внешней синхронизации — не отсылать обратно
        return;
    }
    enqueueSyncTask('deal', $fields['ID'], 'external');
});
```

Альтернативные/дополняющие подходы (на собеседовании полезно назвать и их):
- **Хэш последнего отправленного состояния** (см. [13.2](module-13-2.md)) — если пришедшее изменение идентично тому, что вы уже отправили, это "эхо" собственного обновления.
- **Транзакционный флаг в момент записи** (не сохранённый в БД) — `Bitrix24` сам не предоставляет `sync_source`, поэтому чаще используют сохранённое кастомное поле.

**Ловушка:** сравнивать пришедшее содержимое с текущим в CRM "по полям" — не гарантирует защиту, потому что внешняя система может вернуть нормализованные данные (другой формат телефона, округление числа), и сравнение не сработает.

### Частые ошибки при разборе задач

- Пытаться решить задачу "правильным API", когда собеседник ждёт архитектурный ответ — "как бы вы спроектировали" ≠ "какой метод вызвать".
- Молча решать "как написано", не уточняя масштаб: "сколько записей?", "какой лимит времени?", "как часто запускается?" — вопросы про объём меняют решение принципиально.
- Игнорировать пагинацию `crm.deal.list` и подобных — обычная проверка "а вы вообще пользовались API больше разового вызова".

## Вопросы для собеседования

**1. Как проверить, что лид с таким телефоном уже есть в CRM, до попытки добавить?**
`crm.duplicate.findbycomm` с `entity_type => 'LEAD'`, `type => 'PHONE'` — тот же механизм, что использует штатный контроль дублей в интерфейсе, включая нормализацию формата номера.

**2. Как сделать агрегацию (сумма/количество) по сделкам за период через REST без выгрузки в Excel?**
`crm.deal.list` с фильтром по `STAGE_SEMANTIC_ID` и диапазону `CLOSEDATE`, `'start' => -1` для автопагинации, группировка массива в PHP по `ASSIGNED_BY_ID`. При большом объёме — собственная агрегирующая таблица, заполняемая обработчиком `OnAfterCrmDealUpdate`.

**3. Почему `application_token` в событии недостаточен, если endpoint вызывается в обход Bitrix24?**
`application_token` подтверждает только, что запрос сформирован от имени вашего приложения. Дополнительная проверка `member_id` гарантирует, что это конкретный установленный портал, а не подделка — `member_id` не секретен и его можно подобрать, но вместе с `application_token` он подтверждает владельца запроса.

**4. Робот на стадии не срабатывает, хотя сделка туда попадает. Первые три вещи, которые проверяете?**
1) Запуск триггером "при входе" не срабатывает, если сделка была создана уже на этой стадии — нужен "на стадии" или другой триггер. 2) Встроенное условие робота молча отфильтровывает сделку. 3) `bizproc.workflow.log` для этой сделки — видно, дошёл ли процесс вообще до шага робота или застрял раньше.

**5. Как предотвратить бесконечный цикл двусторонней синхронизации (A → B → A → B → ...)?**
Флаг источника изменения: при записи изменения из внешней системы помечать объект кастомным полем (например, `UF_CRM_SYNC_SOURCE = 'external'`), а в обработчике `OnAfterCrmDealUpdate` — пропускать задачи с таким флагом и не отсылать изменение обратно.

**6. Какая разница между `'start' => -1` и ручным обходом `next` в `crm.deal.list`?**
`'start' => -1` — автоматическая итерация по пагинации в новом REST API (Bitrix24 сам перебирает страницы). `next` — ручное получение курсора из ответа и передача в следующий запрос — старый способ, требует самописного цикла.

# Модуль 12.1: Диски и файлы (disk.folder.*, disk.file.*)

## Теория

### Что такое «Диск» в Bitrix24

Диск — модуль хранения файлов в Bitrix24 (аналог Google Drive внутри портала). Физически файлы лежат в таблице `b_disk_object` + `b_disk_file`, сами бинарные данные — через модуль `main` (`CFile`, таблица `b_file`), то есть Диск — надстройка с правами, версиями, общими папками над общим файловым хранилищем Bitrix.

Три уровня сущностей:
- **Storage (хранилище)** — корневой контейнер. У каждого пользователя есть личное хранилище, у группы/проекта — групповое, у компании — общее хранилище «Диск компании».
- **Folder (папка)** — узел дерева внутри хранилища.
- **File (файл)** — конечный объект с версиями (`disk.file.getversions`), правами и ссылкой для шаринга.

### Получение хранилища

```php
$result = CRest::call('disk.storage.get', [
    'id' => $storageId,
]);
```

Чаще нужно хранилище текущего пользователя:

```php
$result = CRest::call('disk.storage.getforapp', []); // хранилище приложения (если нужно хранить служебные файлы)
```

Для личного диска пользователя явного метода «get my storage» нет напрямую в REST — обычно хранилище получают через `user.current` → далее работают с папками, либо хранят `STORAGE_ID` сразу после создания первой папки через `disk.storage.getlist` с фильтром по `ENTITY_TYPE = 'user'`.

### Работа с папками

```php
// Список подпапок/файлов
CRest::call('disk.folder.getchildren', [
    'id' => $folderId,
]);

// Создать подпапку
CRest::call('disk.folder.addsubfolder', [
    'id' => $folderId,
    'data' => ['NAME' => 'Договоры 2026'],
]);

// Получить метаданные папки
CRest::call('disk.folder.get', ['id' => $folderId]);

// Удалить (помещает в корзину, а не физически удаляет сразу)
CRest::call('disk.folder.deletetree', ['id' => $folderId]);
```

### Загрузка файла

Два основных способа — через REST webhook/приложение это почти всегда **base64**, так как многие интеграции шлют JSON:

```php
CRest::call('disk.folder.uploadfile', [
    'id'       => $folderId,
    'data'     => ['NAME' => 'contract.pdf'],
    'fileContent' => [
        'contract.pdf',
        base64_encode(file_get_contents('/tmp/contract.pdf')),
    ],
]);
```

Внутри коробки (не REST, а напрямую через D7/COM классы) загрузка идёт через `\Bitrix\Disk\Folder::uploadFile()`:

```php
$folder = \Bitrix\Disk\Folder::getById($folderId);
$folder->uploadFile(
    [
        'name' => 'contract.pdf',
        'tmp_name' => '/tmp/contract.pdf',
        'type' => 'application/pdf',
        'size' => filesize('/tmp/contract.pdf'),
    ],
    ['CREATED_BY' => $userId]
);
```

**Важный нюанс для собеседования:** `fileContent` в REST ограничен размером запроса (обычно безопасно до ~15-20 МБ, но зависит от конфигурации сервера и таймаута). Для больших файлов используют:
1. Загрузку по частям (chunked) — нестандартно, редко применяется.
2. Загрузку через веб-форму на сам портал (`disk.folder.uploadfile` с `controller` upload через браузер — метод `getUploadUrl`).
3. Для коробки — просто работу с файловой системой сервера напрямую.

### Методы работы с файлами

```php
CRest::call('disk.file.get', ['id' => $fileId]);

// Скачать — возвращает URL для скачивания (одноразовый/временный)
CRest::call('disk.file.get', ['id' => $fileId]); // поле DOWNLOAD_URL в ответе

CRest::call('disk.file.rename', ['id' => $fileId, 'newName' => 'new.pdf']);
CRest::call('disk.file.copy', ['id' => $fileId, 'targetFolderId' => $otherFolderId]);
CRest::call('disk.file.moveto', ['id' => $fileId, 'targetFolderId' => $otherFolderId]);
CRest::call('disk.file.delete', ['id' => $fileId]); // в корзину

// Внешняя ссылка на файл (публичный доступ)
CRest::call('disk.file.getExternalLink', ['id' => $fileId]);
```

### Права доступа на Диске

У каждого объекта Диска (`DiskObject`) есть права через ACL — `disk.folder.getrights` / `disk.folder.setrights` (в REST часто проще управлять через группы доступа, созданные на портале, а не байт-в-байт правами по ID). Уровни прав: `read`, `add`, `rename`, `delete`, `edit`, `edit_rights`.

В коробке права строятся через `\Bitrix\Disk\Security\AttachedObject` и таблицу `b_disk_object_right`. На практике для REST-интеграций проще:
- создать отдельную «Общую папку» (group storage) и управлять участниками группы,
- либо использовать персональный диск технического пользователя (бота/сервисного аккаунта), а делиться файлами через `disk.file.getExternalLink` или прикрепление к CRM-сущности (где права уже наследуются от прав на лид/сделку).

### Привязка файлов к CRM

Файлы, прикреплённые к лиду/сделке через стандартный интерфейс CRM, хранятся не в «Диске» пользователя напрямую, а в служебном хранилище CRM (`disk.storage` с `ENTITY_TYPE = 'crm'`), но физически это тот же модуль Disk. Программно прикрепить файл к сделке можно двумя путями:

1. Через `crm.deal.update` с полем типа `file` (если такое пользовательское поле создано):
```php
CRest::call('crm.deal.update', [
    'id' => $dealId,
    'fields' => [
        'UF_CRM_1234_FILE' => [
            'fileData' => ['contract.pdf', base64_encode($content)],
        ],
    ],
]);
```

2. Через создание файла на Диске и привязку (аттач) к таймлайну сделки:
```php
CRest::call('crm.timeline.comment.add', [
    'fields' => [
        'ENTITY_ID'   => $dealId,
        'ENTITY_TYPE' => 'deal',
        'COMMENT'     => 'Договор приложен',
        'FILES'       => [[ 'fileData' => ['contract.pdf', base64_encode($content)] ]],
    ],
]);
```

### Частые ошибки

- **Путают `disk.file.delete` с физическим удалением** — на самом деле это перенос в корзину, физическое удаление происходит позже через очистку корзины.
- **Пытаются загрузить файл больше лимита запроса целиком через fileContent** — получают таймаут или ошибку `413`.
- **Не проверяют права перед записью** — сервисный вебхук может не иметь прав на конкретную папку пользователя, получая `ACCESS_DENIED`.
- **Хранят DOWNLOAD_URL как постоянную ссылку** — он одноразовый/временный и устаревает, нужно запрашивать заново через `disk.file.get`.
- **Путают storage ID и folder ID** — у диска пользователя ID storage ≠ ID корневой папки, для операций с содержимым всегда нужен folder ID (`disk.storage.getchildren` -> ROOT_OBJECT_ID).

## Вопросы для собеседования

**1. Из каких сущностей состоит модуль «Диск» в Bitrix24?**
Storage (хранилище: личное, групповое, общее компании) → Folder (папка) → File (файл с версиями). Физические данные лежат в общей таблице `b_file` модуля `main`, Disk добавляет права, версионирование и дерево папок.

**2. Как загрузить файл размером 50 МБ через REST?**
Прямой `fileContent` в base64 для такого размера ненадёжен (таймауты, лимиты запроса). На практике — либо загрузка файла напрямую пользователем через веб-интерфейс портала, либо (для коробочной версии) работа с файловой системой сервера напрямую через `\Bitrix\Disk\Folder::uploadFile()`, минуя REST-лимиты.

**3. В чём разница между `disk.file.delete` и физическим удалением файла?**
`disk.file.delete` переносит объект в корзину (soft delete), запись остаётся в БД с флагом `deleted`. Полное удаление происходит либо вручную из корзины, либо автоматической очисткой по истечении срока хранения.

**4. Как привязать файл к сделке CRM программно?**
Через пользовательское поле типа «Файл» на сделке (`UF_CRM_*_FILE`) с передачей `fileData`, либо через вложение в комментарий таймлайна (`crm.timeline.comment.add` с полем `FILES`).

**5. Какие уровни прав существуют на объектах Диска?**
`read`, `add`, `rename`, `delete`, `edit`, `edit_rights` — управляются через ACL объекта (`b_disk_object_right`), в REST — чаще через участие в группе, владеющей хранилищем, а не ручное назначение прав по объекту.

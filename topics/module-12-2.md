# Модуль 12.2: Календарь и встречи (calendar.event.*)

## Теория

### Типы календарей в Bitrix24

- **user** — личный календарь сотрудника.
- **group** — календарь рабочей группы/проекта.
- **company_calendar** — общий календарь компании (отпуска, праздники, общие события).
- **location** — календари переговорных/ресурсов (бронирование помещений).

Каждое событие (`CCalendarEvent` / REST `calendar.event.*`) привязано к одному из типов через поля `type` и `ownerId`.

### Создание события

```php
$result = CRest::call('calendar.event.add', [
    'type'          => 'user',
    'ownerId'       => $userId,          // чей календарь
    'name'          => 'Встреча с клиентом',
    'description'   => 'Обсуждение условий договора',
    'from'          => '02.11.2026 15:00:00',
    'to'            => '02.11.2026 16:00:00',
    'section'       => $sectionId,        // ID секции календаря (можно получить через calendar.section.get)
    'is_meeting'    => 'Y',
    'attendees'     => [$userId, $managerId],
    'meeting'       => [
        'notify'    => 'Y',
        'reinvite'  => 'N',
    ],
    'remind' => [
        ['type' => 'min', 'count' => 15],
    ],
]);
```

Важные поля:
- `from` / `to` — в формате даты-времени портала (учитывают часовой пояс пользователя-владельца).
- `host` — организатор встречи (по умолчанию текущий пользователь).
- `attendees` — массив ID пользователей-участников; каждому автоматически создаётся копия события в его календаре со статусом приглашения.
- `meeting_status` — статус конкретного участника: `Y` (принял), `N` (отклонил), `Q` (ожидает ответа).

### Получение и изменение событий

```php
CRest::call('calendar.event.get', [
    'type'    => 'user',
    'ownerId' => $userId,
    'from'    => '01.11.2026',
    'to'      => '30.11.2026',
]);

CRest::call('calendar.event.update', [
    'id'     => $eventId,
    'fields' => ['name' => 'Перенесённая встреча', 'from' => '03.11.2026 10:00:00'],
]);

CRest::call('calendar.event.delete', ['id' => $eventId]);
```

### Напоминания

`remind` — массив напоминаний относительно начала события:
```php
'remind' => [
    ['type' => 'min', 'count' => 30],
    ['type' => 'min', 'count' => 10],
],
```
`type` может быть `min`, `hour`, `day`. Напоминания реализуются через системные уведомления и Push, обрабатываются агентом `CCalendarNotify::Send` в коробке.

### Синхронизация с внешними календарями (CalDAV)

Bitrix24 предоставляет CalDAV-эндпоинт для синхронизации с Google Calendar, Outlook, Apple Calendar. URL вида:
```
https://your-portal.bitrix24.ru/calendar/caldav/
```
с базовой авторизацией по логину/паролю или токену приложения. Для REST-интеграций CalDAV обычно не используют — это отдельный протокол, работающий параллельно с REST API и не требующий OAuth.

### Интеграция календаря с CRM

Встречи и звонки в CRM (раздел «Активности» / `crm.activity.*`) — это не то же самое, что события календаря, хотя тесно связаны. У сделки можно:

1. Запланировать активность типа "Встреча" через `crm.activity.add` с `TYPE_ID = 1` (Meeting) — она автоматически попадает и в календарь ответственного.
2. Либо напрямую создать `calendar.event.add` и привязать к сделке через поле `uf_crm_calendar_event` (если настроено) или просто хранить `EVENT_ID` в кастомном поле сделки для последующей синхронизации статуса.

Более частый сценарий на собеседовании — автоматическое планирование встречи при смене стадии сделки через обработчик `onCrmDealUpdate`, создающий `calendar.event.add` с `attendees = [responsibleId]`.

### Ограничения и нюансы

- Исходящий вебхук или приложение может создавать события **только от имени пользователя, авторизовавшего приложение**, либо через `ownerId`, если у приложения есть права на календарь этого пользователя (обычно административные вебхуки имеют доступ к любому `ownerId`).
- Часовые пояса: `from`/`to` передаются в локальном времени владельца календаря — при интеграции с внешними системами (где время в UTC) нужна явная конвертация, иначе встречи "уезжают" на несколько часов.
- Повторяющиеся события (`rrule`) задаются как в iCal (`FREQ=WEEKLY;COUNT=10` и т.д.) через поле `rrule`.

### Частые ошибки

- **Не учитывают часовой пояс пользователя** при массовом создании событий через интеграцию — встречи появляются не в то время.
- **Путают `crm.activity.add` (активность CRM) и `calendar.event.add` (событие календаря)** — это разные сущности с разным хранением, хотя визуально могут выглядеть похоже в интерфейсе.
- **Забывают `is_meeting = 'Y'` и `attendees`**, из-за чего приглашение не рассылается участникам.
- **Хранят только `EVENT_ID` без `ownerId`/`type`**, а эти поля обязательны для `calendar.event.get/update` — без них однозначно найти событие нельзя.

## Вопросы для собеседования

**1. Чем отличается событие календаря от активности CRM «Встреча»?**
Событие календаря (`calendar.event.*`) — запись в личном/групповом календаре пользователя, видна в разделе «Календарь». Активность CRM (`crm.activity.*`, тип Meeting) — задача-напоминание, привязанная к сделке/лиду в таймлайне CRM. При создании активности-встречи Bitrix24 автоматически создаёт и связанное событие календаря, но это две разные таблицы и две разные REST-сущности.

**2. Как пригласить несколько участников на встречу и получить статус их ответа?**
Передать `attendees` — массив ID пользователей — и `is_meeting = 'Y'`. Каждому участнику копируется событие с полем `meeting_status` (`Y`/`N`/`Q`), которое можно прочитать через `calendar.event.get` для этого пользователя.

**3. Какие типы владельцев календаря (`type`) существуют?**
`user` (личный), `group` (рабочая группа), `company_calendar` (общий компании), `location` (переговорные/ресурсы).

**4. Как настроить повторяющееся еженедельное событие на 10 недель?**
Через поле `rrule` в формате iCal: `rrule => ['FREQ' => 'WEEKLY', 'COUNT' => 10]` (в зависимости от версии REST — либо отдельными параметрами, либо строкой `FREQ=WEEKLY;COUNT=10`).

**5. Почему при интеграции время встреч может "съезжать" на несколько часов?**
Потому что `from`/`to` в calendar.event.* передаются в локальном времени владельца, а не в UTC. Если внешняя система отправляет время в UTC без конвертации в часовой пояс пользователя-владельца календаря, итоговое время будет смещено.

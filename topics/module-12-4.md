# Модуль 12.4: Миграция данных и импорт

## Теория

### Зачем нужна отдельная стратегия для массового импорта

Стандартные методы (`CIBlockElement::Add`, `crm.lead.add`, прямые `INSERT`) рассчитаны на единичные операции в рамках обычного веб-запроса. При импорте тысяч/десятков тысяч записей "в лоб" (цикл + `::Add`) типичные проблемы:

- Срабатывают все обработчики событий (`OnBeforeIBlockElementAdd`, `OnAfterAdd` и т.п.) на каждую запись — агенты пересчёта, переиндексация поиска, вебхуки во внешние системы — импорт замедляется многократно.
- Истекает `max_execution_time` веб-сервера — импорт обрывается на середине без транзакционного отката.
- Память PHP переполняется, если весь набор данных грузится в массив целиком.
- Повторный запуск импорта создаёт дубли, если нет проверки идемпотентности.

### Импорт в инфоблоки

Базовый паттерн с отключением лишней нагрузки на время импорта:

```php
\Bitrix\Main\Application::getInstance()->getConnection()->startTransaction();
try {
    // отключаем индексацию поиска на время импорта
    \CSearch::DeleteIndex('iblock', $iblockId);

    foreach ($rows as $row) {
        $element = new CIBlockElement();
        $id = $element->Add([
            'IBLOCK_ID' => $iblockId,
            'NAME'      => $row['name'],
            'CODE'      => $row['code'],
            'PROPERTY_VALUES' => $row['props'],
        ]);
        if (!$id) {
            throw new \Exception($element->LAST_ERROR);
        }
    }

    \Bitrix\Main\Application::getInstance()->getConnection()->commitTransaction();
} catch (\Exception $e) {
    \Bitrix\Main\Application::getInstance()->getConnection()->rollbackTransaction();
    throw $e;
}
```

**Важный нюанс для собеседования:** `CIBlockElement::Add()` сам по себе не атомарен и не обязан работать внутри транзакции корректно (часть внутренних операций инфоблоков исторически делает собственные commit'ы), поэтому транзакция вокруг цикла — не 100% гарантия отката при сбое. На практике чаще используют **батчи** (обработка пачками по 100-500 записей с логированием прогресса и возможностью продолжить с места обрыва) вместо расчёта на одну большую транзакцию.

Для производительности:
```php
// Разово выключаем обработку событий на время критичного импорта (осторожно! теряются побочные эффекты)
\Bitrix\Main\EventManager::getInstance()->removeEventHandler('iblock', 'OnAfterIBlockElementAdd', $callback);
```
или через настройку `~bx_no_accel` / отключение агентов индексации на время — зависит от задачи, обычно безопаснее не трогать события, а просто запускать импорт в фоне через агент/cron с увеличенным `max_execution_time`.

### Импорт в CRM с защитой от дублей

```php
// Проверка на дубль по email/телефону перед созданием лида
$dup = CRest::call('crm.duplicate.findbycomm', [
    'type'   => 'EMAIL',
    'values' => [$row['email']],
]);

if (empty($dup['result']['LEAD'])) {
    CRest::call('crm.lead.add', [
        'fields' => [
            'TITLE' => $row['title'],
            'NAME'  => $row['name'],
            'EMAIL' => [['VALUE' => $row['email'], 'VALUE_TYPE' => 'WORK']],
        ],
    ]);
}
```

Для массового импорта в CRM через REST — обязательно использовать **batch-запросы** (`CRest::callBatch`) пачками до 50 команд за вызов, с учётом общего лимита 2 запроса/сек для облачных вебхуков (см. модуль 8.3). Иначе импорт тысяч записей упрётся в `QUERY_LIMIT_EXCEEDED`.

```php
$commands = [];
foreach ($rows as $i => $row) {
    $commands["lead_$i"] = [
        'method' => 'crm.lead.add',
        'params' => ['fields' => $row],
    ];
}
$chunks = array_chunk($commands, 50, true);
foreach ($chunks as $chunk) {
    $result = CRest::callBatch($chunk);
    sleep(1); // пауза между батчами, чтобы не упереться в лимит
}
```

### Экспорт/импорт Highload-блоков

HL-блоки переносятся между окружениями в два шага:
1. **Структура** (поля) — либо вручную пересоздаётся через административный интерфейс/код `HighloadBlockTable::add()` + `UserFieldTable`, либо экспортируется через стандартный механизм экспорта настроек модуля `highloadblock` (XML-экспорт в административной панели, если доступен).
2. **Данные** — выгружаются построчно через `DataManager::getList()` целевого класса HL-блока в CSV/JSON, затем импортируются на новом окружении аналогичным батчевым циклом с `::add()`.

```php
$entity = Bitrix\Highloadblock\HighloadBlockTable::compileEntity($hlblock);
$entityClass = $entity->getDataClass();

$rows = [];
$res = $entityClass::getList(['select' => ['*']]);
while ($row = $res->fetch()) {
    $rows[] = $row;
}
file_put_contents('export.json', json_encode($rows));
```

### Миграция между окружениями (dev → staging → production)

Для коробочной версии стандартный путь:
1. **Код модулей/решения** — переносится через git/композер-пакеты, не через файловый бэкап базы.
2. **Структура данных** (инфоблоки, HL-блоки, пользовательские поля) — через `install/index.php` модуля (шаги `InstallDB`), либо через миграции Bitrix (`\Bitrix\Main\Update\Stepper`, механизм `local/php_interface/migrations` в современных решениях с `bitrix cli` / `bitrix-vm`).
3. **Контентные данные** — экспорт/импорт через `CIBlockElement::GetList` + `::Add` батчами, либо штатный модуль "Экспорт/Импорт" (CSV) для простых случаев без сложной структуры свойств.

Для облачной версии Bitrix24 полноценной "миграции между порталами" через REST нет — переносят данные только точечно (например, при смене CRM-системы на Bitrix24) через batch-импорт CRM-сущностей с маппингом внешних ID во `UF_CRM_*` поле (аналогично паттерну синхронизации из модуля 11.3).

### Производительность при массовом импорте — чеклист

- Импортировать **батчами**, а не по одной записи.
- Логировать прогресс (ID последней обработанной записи) — чтобы при сбое продолжить, а не начинать заново.
- Для CRM — всегда batch-запросы REST, с учётом rate limit.
- Для инфоблоков — по возможности отключать реиндексацию поиска на время импорта, запускать переиндексацию (`CSearch::Index`) один раз в конце.
- Проверять дубли **до** вставки (по уникальному внешнему ключу/email/телефону), а не чистить дубли после.
- Запускать длительный импорт не в веб-запросе, а через консольный скрипт или агент (cron) без ограничения `max_execution_time`.

### Частые ошибки

- **Импорт в веб-запросе без увеличения `max_execution_time`** — обрыв на середине, половина данных не импортирована.
- **Нет идемпотентности** — повторный запуск импорта (например, после сбоя) создаёт полные дубли вместо обновления существующих записей.
- **Импорт в CRM без batch** — быстро упирается в rate limit, импорт тысяч лидов растягивается на часы или падает по `QUERY_LIMIT_EXCEEDED`.
- **Не сохраняют маппинг "внешний ID → ID в Bitrix"** — при повторном импорте/обновлении невозможно понять, какая запись какой соответствует.
- **Забывают, что HL-блок — это две части (структура + данные)**, переносят только данные, не создав предварительно поля — импорт падает с ошибкой "неизвестное поле".

## Вопросы для собеседования

**1. Почему прямой цикл с `CIBlockElement::Add()` плохо подходит для импорта 10 000 записей?**
Каждый вызов триггерит полный набор событий инфоблоков (индексация, агенты, обработчики), что кратно замедляет импорт, плюс запрос рискует упереться в `max_execution_time` и оборваться без отката, оставив БД в промежуточном состоянии.

**2. Как защититься от создания дублей при повторном запуске импорта?**
Проверять наличие записи по уникальному внешнему идентификатору (email, телефон, внешний ID из исходной системы — через `crm.duplicate.findbycomm` для CRM или собственное поле `UF_EXTERNAL_ID`) **до** вставки, а при найденном дубле выполнять `update`, а не `add`.

**3. Какой лимит нужно учитывать при массовом импорте лидов через REST и как его обойти?**
Rate limit облачного Bitrix24 (обычно 2 запроса/сек на вебхук). Обходится через `batch`-запросы (`crm.lead.add` пачками до 50 команд за один HTTP-запрос) вместо отправки каждой записи отдельным вызовом.

**4. Из каких двух частей состоит перенос Highload-блока между окружениями?**
Структура (поля блока, `HighloadBlockTable` + `UserFieldTable`) и данные (строки таблицы). Сначала обязательно создаётся структура на целевом окружении, затем переносятся данные батчами — иначе импорт данных упадёт из-за отсутствия нужных полей.

**5. Почему длительный импорт лучше запускать не в обычном веб-запросе?**
Веб-запрос ограничен `max_execution_time` и таймаутом веб-сервера/прокси (обычно 30-60 сек), а консольный скрипт или агент (cron) могут выполняться сколь угодно долго, что безопаснее для импорта с десятками тысяч записей.

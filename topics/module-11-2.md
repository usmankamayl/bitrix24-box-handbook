# Модуль 11.2: Триггеры и условия в бизнес-процессах Bitrix24

## Теория

### Что такое триггер

**Триггер** — это событие, которое переводит сделку/лид на другую стадию или запускает роботов. В отличие от активити (которые *выполняют действие*), триггер *ждёт события* и реагирует на него.

**Штатные триггеры:**
- Входящее письмо / звонок / SMS
- Переход по ссылке из письма
- Заполнение CRM-формы
- Запись клиента на ресурс (ресурсное бронирование)
- Оплата счёта
- Задача завершена

**Пользовательский триггер** — собственное событие: «клиент подтвердил заказ в приложении», «заявка на кредит одобрена банком», «груз прибыл на склад» и т.д.

---

### Механика триггера

1. Триггер регистрируется в портале (`bizproc.activity.add` с `TYPE => 'TRIGGER'` или `bizproc.robot.add` для триггеров-роботов).
2. Пользователь добавляет его в «Триггеры» на стадии CRM — при переходе на стадию Битрикс начинает «ждать» событие.
3. Внешняя система вызывает `bizproc.event.send` или просто дергает `HANDLER` триггера — Битрикс переводит документ на целевую стадию и запускает привязанных роботов.

**Важно:** триггер не «делает работу» — он **оповещает БП о событии**. Перемещение по стадии и запуск роботов — отдельный этап.

---

### Регистрация триггера

Через `bizproc.activity.add` с `TYPE => 'TRIGGER'`:

```php
CRest::call('bizproc.activity.add', [
    'CODE' => 'BANK_APPROVED',
    'HANDLER' => 'https://myapp.com/trigger.php',
    'AUTH_USER_ID' => 1,
    'NAME' => 'Кредит одобрен банком',
    'DESCRIPTION' => 'Срабатывает, когда банк подтверждает заявку',
    'TYPE' => 'TRIGGER',
    'PROPERTIES' => [
        'APPROVED_SUM' => [
            'Name' => 'Одобренная сумма',
            'Type' => 'double',
            'Required' => 'N',
        ],
    ],
    'RETURN_PROPERTIES' => [
        'APPROVED_SUM' => ['Name' => 'Одобренная сумма', 'Type' => 'double'],
        'APPROVED_DATE' => ['Name' => 'Дата решения', 'Type' => 'datetime'],
    ],
    'DOCUMENT_TYPE' => ['crm', 'CCrmDocumentDeal', 'DEAL'],
]);
```

### Срабатывание: bizproc.event.send

Когда внешняя система решает, что событие наступило, она вызывает:

```php
CRest::call('bizproc.event.send', [
    'EVENT_TOKEN' => $eventToken,   // токен экземпляра ожидания
    'RETURN_VALUES' => [
        'APPROVED_SUM' => 500000,
        'APPROVED_DATE' => '2026-11-02 15:00:00',
    ],
    'LOG_MESSAGE' => 'Банк подтвердил заявку',
]);
```

**Откуда взять EVENT_TOKEN?** Когда Битрикс ставит триггер «в ожидание», он шлёт POST на `HANDLER` с параметрами — там и будет `event_token`. Приложение сохраняет его в БД (с привязкой к документу) и потом использует для `bizproc.event.send`.

Полный цикл:

```
[БП дошёл до триггера]
        ↓
Bitrix → POST handler.php {event_token, document_id}
        ↓
Приложение сохраняет токен в БД
        ↓
(внешняя система решает: событие наступило)
        ↓
Приложение → bizproc.event.send {event_token, RETURN_VALUES}
        ↓
Bitrix → запускает привязанные действия/роботов
```

### Условия (Conditions) в роботах и БП

**Условие** — фильтр, по которому Битрикс решает, запускать ли действие. Условия не создаются разработчиком как отдельная сущность — они настраиваются в интерфейсе конструктора и могут проверять:

- Значения полей документа (`UF_CRM_...`, `TITLE`, `OPPORTUNITY`)
- Результаты предыдущих действий/триггеров
- Результаты кастомного активити (то, что вернулось в `OUTPUT`)

**Программный способ добавить «умную» логику** — вернуть из активити/триггера вычисляемый параметр (`STATUS`, `SCORE`, `IS_VIP`), а в условии робота пользователь укажет: «если STATUS = vip → уведомить руководителя».

Это ключевая идея: **разработчик возвращает данные, пользователь строит логику**.

### Триггеры-роботы (bizproc.robot.add с USE_SUBSCRIPTION)

У `bizproc.robot.add` есть флаг `USE_SUBSCRIPTION`:

- `N` — робот выполняется сразу при переходе на стадию (обычное действие).
- `Y` — робот «подписывается» и ждёт, пока приложение завершит его через `bizproc.robot.completed`. Работает как триггер + активити одновременно: может ждать события и потом вернуть параметры.

```php
// Регистрация
CRest::call('bizproc.robot.add', [
    'CODE' => 'WAIT_CALLBACK',
    'HANDLER' => 'https://myapp.com/wait-callback.php',
    'AUTH_USER_ID' => 1,
    'NAME' => 'Ждать ответ клиента',
    'USE_SUBSCRIPTION' => 'Y',          // Ждём bizproc.robot.completed
    'RETURN_PROPERTIES' => [
        'CLIENT_ANSWER' => ['Name' => 'Ответ клиента', 'Type' => 'string'],
    ],
    'DOCUMENT_TYPE' => ['crm', 'CCrmDocumentDeal', 'DEAL'],
]);
```

### Ошибка в обработчике: bizproc.event.send с ошибкой

Если внешняя система хочет сообщить об ошибке:

```php
CRest::call('bizproc.event.send', [
    'EVENT_TOKEN' => $eventToken,
    'RETURN_VALUES' => [],
    'LOG_MESSAGE' => 'Банк отклонил заявку',
]);
```

БП завершит ожидание, но «пойдёт дальше». Если нужно остановить БП или перевести на стадию «Отказ» — пусть триггер возвращает `DECISION => 'rejected'`, а в условии робота/БП настраивается ветка.

### Вопросы для собеседования

**1. Чем триггер отличается от активити?**
Активити — действие (отправить SMS, создать документ). Триггер — ожидание события. Технически регистрируются одним методом `bizproc.activity.add`, но с разным `TYPE`. Активити завершается через `bizproc.activity.completed`, триггер «просыпается» через `bizproc.event.send`.

**2. Что такое EVENT_TOKEN и зачем он нужен в триггере?**
Токен, который Битрикс присылает при входе БП в состояние ожидания триггера. Приложение сохраняет его и позже вызывает `bizproc.event.send` с этим токеном — Битрикс понимает, какой именно экземпляр БП разбудить.

**3. Можно ли передать данные из внешней системы в БП через триггер?**
Да — через `RETURN_VALUES` в `bizproc.event.send`. Параметры должны быть объявлены в `RETURN_PROPERTIES` при регистрации. Дальше они доступны в условиях и подстановках следующих действий.

**4. Как триггер узнаёт, что событие наступило?**
Сам Битрикс не знает — это ответственность приложения. Внешняя система сама вызывает `bizproc.event.send` (например, по своему вебхуку от банка).

**5. Чем USE_SUBSCRIPTION='Y' отличается от обычного робота?**
Без подписки робот выполняется сразу при переходе на стадию. С подпиской — Битрикс ждёт, пока приложение завершит его через `bizproc.robot.completed`. Это способ сделать «ждущего робота».

**6. Что произойдёт, если событие никогда не наступит?**
БП будет висеть в ожидании триггера бесконечно (или до таймаута, если он настроен в шаблоне). Хорошая практика — ставить в БП параллельную ветку с паузой и действием «если N дней прошло — отменить/эскалировать».

**7. Можно ли удалить триггер, если он используется?**
`bizproc.activity.delete` удалит триггер — ожидающие экземпляры БП зависнут. Сначала убрать из всех шаблонов/стадий.

**8. Как реализовать «сценарий отклонения» через триггер?**
Вернуть в `RETURN_VALUES` параметр `DECISION` со значением `'rejected'` и настроить в БП условие на этот параметр. Не пытайтесь «упасть» триггером — он должен завершиться корректно с нужными данными.

**9. Чем триггер отличается от события REST (onCrmDealUpdate)?**
Событие REST — глобальное, приходит при каждом изменении сделки. Триггер — точечный, ждёт конкретного экземпляра БП на конкретной стадии. Они взаимодополняемы: приложение слушает onCrmDealUpdate, находит нужный `event_token` в своей БД и будит триггер.

**10. Что такое условие в конструкторе роботов и кто его пишет?**
Условие — это выражение вида «если поле X равно Y», которое настраивает пользователь портала в интерфейсе. Разработчик не «создаёт условия», он возвращает параметры (`OUTPUT`, `RETURN_VALUES`), на которые пользователь опирается.

---

### Частые ошибки

- ❌ **Триггер без `RETURN_PROPERTIES`.** Не сможете вернуть данные в БП.
- ❌ **Не сохранять `event_token`.** Потеряете связь — триггер невозможно «разбудить».
- ❌ **Завершать триггер активити-методом.** Для `TYPE => 'TRIGGER'` нужен `bizproc.event.send`, не `bizproc.activity.completed`.
- ❌ **Считать, что триггер «сам двигает сделку».** Триггер только сообщает о событии; перемещение по стадии делается отдельным роботом/действием.
- ❌ **Долгая обработка в handler триггера.** Та же ловушка с 30 секундами.

# Модуль 6.4: Архитектурные решения (уровень senior)

## Теория

### Что проверяет «архитектурная задача»

Это не «назови паттерн», а «спроектируй систему под требования». Интервьюер даёт бизнес-контекст и смотрит:

- Разделяешь ли ты слои (компонент → сервис → репозиторий)?
- Думаешь ли о границах (что в Bitrix, что вынести наружу)?
- Понимаешь ли, где нужна консистентность, а где eventual consistency?
- Можешь ли объяснить, почему выбрал именно это решение, а не другое?

Senior не говорит «нужен RabbitMQ» или «нужен Redis» — он спрашивает про объёмы, SLA, требования к консистентности, и уже потом выбирает инструмент.

### Три кита Bitrix-архитектуры

#### 1. Слои

```
Controller / Component  — входная точка, валидация, ответ
         ↓
       Service          — бизнес-логика (сложная, переиспользуемая)
         ↓
     Repository         — работа с хранилищем (ORM/SQL/кеш)
```

**Что где:**
- **Component** — `executeComponent`, `arResult`, включение шаблона. *Не* содержит бизнес-логику — только сбор данных.
- **Service** — `OrderService`, `DiscountService`, `SyncService` — переиспользуется в нескольких компонентах/контроллерах.
- **Repository** — `OrderRepository`, `ProductRepository` — скрывает `getList`/`load`/`save`, возвращает DTO или объекты.

**Почему:** тестируемость (можно мокнуть репозиторий), переиспользование (один сервис на 3 компонента), изменение хранилища без правки логики.

#### 2. Границы

Что живёт в Bitrix, что нет:

| Внутри Bitrix | Снаружи |
|---------------|---------|
| Каталог, заказы, корзина, пользователи | Тяжёлый поиск (Elasticsearch), ML-рекомендации |
| Кеш, события, агенты | Очереди сообщений (RabbitMQ), потоковая обработка |
| Компоненты, шаблоны, API | Микросервисы для высоконагруженных кусков |

**Принцип:** Bitrix отлично справляется с CRUD + ORM + события. Для сложного поиска, рекомендаций, очередей — используем его как *источник данных*, а тяжёлые операции выносим наружу через REST/webhook.

#### 3. Консистентность

- **Strong consistency** — внутри одной транзакции (заказ + платёж + отгрузка).
- **Eventual consistency** — через очередь/outbox (синхронизация с 1С, письма, Slack).
- **Compensation** — если вторая часть упала, компенсируем первую (отмена заказа при отказе оплаты).

### Типовые архитектурные кейсы

#### Кейс A: «Каталог с миллионом товаров тормозит»

**Формулировка:** стандартный `catalog.section` грузится 5 секунд, фильтр по свойствам — ещё медленнее. Как ускорить?

**Решение:**

- **Быстрый фикс:** `SqlTracker` → N+1 → `Runtime`/`with` → индексы → тегированный кеш.
- **Архитектурное решение:** если каталог > 500К и фильтры сложные — выносим поиск в **Elasticsearch**.
  - Bitrix остаётся источником истины (товары, цены, наличие).
  - ES индексирует по свойствам, цене, остатку — поиск/фильтрация через REST к ES, а не к MySQL.
  - Синхронизация: `OnAfterIBlockElementUpdate` → outbox → worker индексирует.
  - Отображение: компонент получает `ID`s из ES, потом `getList` в Bitrix для деталей.

**Senior-ответ:** «Для 50К товаров достаточно оптимизации запросов и кеша. Для 1М+ с фасетным поиском — ES отдельно, Bitrix как источник данных, синхронизация через outbox.»

#### Кейс B: «Склад + интернет-магазин — два источника остатков»

**Формулировка:** товар есть на складе и в магазине. Как показывать остаток? Как резервировать при заказе?

**Решение:**

- **Единый склад в Bitrix** — все остатки в `b_catalog_store_product`, суммарный остаток в `b_catalog_product.QUANTITY`.
- **Резерв при заказе** — `Order::save` → `OnSaleOrderSaved` → резервирование на складе (или через `CCatalogStoreDocs`).
- **Синхронизация с 1С** — не каждый заказ тянет остатки из 1С (медленно), а 1С пушит изменения в Bitrix через файл/REST.
- **Dedup и retry** — обязательно, иначе двойная резервация.

**Senior-пойнт:** «Не пытаюсь делать real-time остаток из 1С — 1С может быть недоступна. Bitrix держит актуальный остаток, 1С — мастер-система для закупки.»

#### Кейс C: «Фича для 10% пользователей — как выкатить безопасно?»

**Формулировка:** новый checkout — хотим тестировать на 10% трафика, потом 50%, потом 100%.

**Решение — feature flags:**

- **Простой вариант:** `Option::get('feature_checkout_v2', 'N')` — вкл/выкл глобально.
- **По пользователям:** `md5(USER_ID + 'feature_name') % 100 < rollout_percent` — детерминированное хеширование, один пользователь всегда в одной группе.
- **По кукам/сегментам:** `COOKIE['ff_checkout_v2']` — для A/B.
- **С метрикой:** логируем в аналитику «пользователь увидел фичу» + конверсия в заказ.

**Senior-пойнт:** «Фича-флаг должен уметь мгновенно выключиться без деплоя. И детерминированное хеширование — чтобы не мигать между старым и новым UI при обновлении страницы.»

#### Кейс D: «API для мобильного приложения + веб-версия»

**Формулировка:** нужно REST API для мобильного приложения и текущего SPA. Как строить?

**Решение:**

- **Общий слой:** `Service` + `Repository` — общие для web и API.
- **Контроллеры:** `Controller` для веб (HTML), `ApiController` для JSON — одни и те же сервисы.
- **Авторизация:** веб — `sessid` + куки, API — `Bearer token` (JWT или `b_user_access_token`).
- **Версии:** `/api/v1/orders` — при изменении формата не ломаем старые клиенты.
- **Rate limiting:** `Option` или Redis — защита от злоупотреблений.

**Senior-пойнт:** «API и веб — разные entry points, но общий domain layer. API возвращает DTO, не Entity — чтобы при изменении сущности не ломать мобильное приложение.»

### Как проектировать

1. **Требования → ограничения** — объём, частота, SLA, консистентность.
2. **Границы** — что Bitrix, что вынести.
3. **Слои** — Controller/Service/Repository.
4. **Состояние** — где данные живут, как синхронизируются.
5. **Отказоустойчивость** — что при падении? retry? compensation?

## Вопросы для собеседования

1. **Где живёт бизнес-логика в Bitrix?** — в `Service`/`Repository`, не в `template.php` и не в `component.php` (компонент только собирает данные).
2. **Когда выносить в Elasticsearch?** — при >500К записей с сложными фильтрами/поиском по тексту.
3. **Как синхронизировать остатки с 1С?** — 1С пушит дельту в Bitrix (файл/REST), Bitrix — мастер для фронта.
4. **Feature flag — как выключить без деплоя?** — `Option` + админ-переключатель, детерминированный rollout по `USER_ID`.
5. **API для мобилки — DTO или Entity?** — DTO — стабильный контракт, Entity меняется при рефакторинге.

## Частые ошибки

- **«Сразу в очередь»** — на 10 заказов в сутки очередь — overengineering.
- **«Всё в компоненте»** — не тестируется, не переиспользуется.
- **«Real-time из 1С»** — 1С лежит → сайт лежит. Bitrix держит копию.
- **«JSON в БД — просто»** — не индексируется, не фильтруется. Только для payload событий.

# Модуль 6.1: Типичные задачи на собеседовании (уровень senior)

## Теория

### Что проверяют на собеседовании Bitrix-разработчика

Задачи делятся на 4 типа:

1. **Оптимизация** — «у нас страница грузится 10 секунд, что делать?». Проверяют: умеете ли вы *диагностировать*, а не только «добавить кеш». Ожидают: SqlTracker, N+1, индексы, композит, кеш с тегами.
2. **SQL и выборки** — «выбери заказы за последний месяц с суммой > 1000, сгруппируй по менеджеру». Проверяют знание D7 ORM (`getList`, `RuntimeEntity`, `Expr`) и понимание JOIN/GROUP BY.
3. **Архитектура / паттерны** — «как организовать синхронизацию с 1С?». Проверяют понимание очередей, идемпотентности, событийной модели, разделения ответственности.
4. **Code review / найди баг** — показывают кусок кода с типичной ошибкой (N+1, утечка при транзакциях, небезопасная фильтрация).

Senior отвечает не «какой функцией», а «как бы я это делал в проде, с подводными камнями».

---

### Типичная задача 1: медленный список заказов

**Формулировка:** «Есть список заказов, грузится 8 секунд. 5000 заказов, выводим по 20. Что делать?»

**Ход рассуждения senior-а:**

1. **Сначала диагноз, потом лечение.** Включаем `SqlTracker`, смотрим: 1 тяжёлый запрос или 200 маленьких?
2. **N+1 внутри цикла** — классика. `foreach ($orders as $o) { $o->getBasket(); $o->getPropertyCollection(); }` — каждый вызов = запрос.
3. **Пагинация** — `LIMIT 20 OFFSET 40000` на большой таблице всё равно сканирует 40K строк. Решение — курсорная пагинация (`WHERE ID < :last_id ORDER BY ID DESC LIMIT 20`).
4. **Кеш** — только после того, как запрос оптимален. Кешировать плохой запрос — прятать проблему.
5. **Индексы** — смотрим `EXPLAIN`: `USER_ID + DATE_INSERT` — кандидат в составной индекс.

**Чего не стоит говорить:** «поставим Redis» — кеш это не решение, а маскировка.

### Типичная задача 2: «дай ID всех заказов со статусом N и суммой > X за 30 дней»

Проверяет знание D7 `getList`:

```php
$result = \Bitrix\Sale\Order::getList([
    'select' => ['ID'],
    'filter' => [
        'STATUS_ID' => 'N',
        '>=DATE_INSERT' => new \Bitrix\Main\Type\DateTime('-30 days'),
        '>PRICE' => 1000,
    ],
    'limit' => 20,
    'offset' => 0,
    'order' => ['ID' => 'DESC'],
]);
```

Что дополнительно спрашивают:

- **`>PRICE` — почему строкой `'>'`?** — D7 использует префиксы: `>`, `>=`, `<`, `<=`, `!=`, `!` (NOT), `%` (LIKE), `><` (BETWEEN), `=@` (IN), `!@` (NOT IN).
- **Как посчитать SUM?** — `'select' => ['SUM' => new \Bitrix\Main\DB\SqlExpression('SUM(PRICE)')]` или `RuntimeEntity`.
- **Почему не `fetchAll()` на 5000?** — memory limit, надёжнее `while ($row = $result->fetch())` или `fetchObject()`.

### Типичная задача 3: «два менеджера одновременно меняют статус заказа»

Проверяет понимание конкурентности:

- `Order::load` → `setField` → `save()` — **last write wins**. Если оба читают версию V, потом пишут — теряются данные.
- Решения:
  - **Optimistic locking** — проверка `VERSION` или `DATE_UPDATE` перед `save()` («read-modify-write with check»).
  - **Pessimistic** — `SELECT ... FOR UPDATE` в транзакции (`$connection->startTransaction()` + `lock()`).
  - **Атомарные операции** — `UPDATE ... SET counter = counter + 1` вместо `counter = :value`.
  - **Очередь** — все изменения через `sync_queue`, worker обрабатывает по одному.

### Типичная задача 4: «найди баг»

Классика:

```php
// БАГ 1: N+1 в цикле
$orders = Order::getList(['select' => ['ID'], 'limit' => 100]);
while ($o = $orders->fetch()) {
    $order = Order::load($o['ID']);         // запрос
    echo $order->getBasket()->count();      // ещё запрос
}

// БАГ 2: save() в событии
AddEventHandler('sale', 'OnSaleOrderSaved', function($event) {
    $order = $event->getParameter('ENTITY');
    $order->setField('COMMENTS', 'x');
    $order->save();                          // рекурсия / дедлок
});

// БАГ 3: IDOR
$order = Order::load($_REQUEST['id']);
echo $order->getPrice();                     // любой чужой заказ

// БАГ 4: SQL-инъекция в legacy-коде
$DB->Query("SELECT * FROM b_sale_order WHERE ID = " . $_GET['id']);

// БАГ 5: кеш без тегов
$cache->set('order_'.$id, $order);           // при изменении заказа — stale навсегда
```

### Как отвечать

Формула ответа:

1. **Что вижу** — короткая диагностика.
2. **Что бы сделал** — 2-3 подхода с trade-offs.
3. **Что проверил бы** — метрика/тест.
4. **Подводные камни** — что сломается при масштабировании.

Пример (задача «медленная страница»):

> «Сначала SqlTracker — понять, один тяжёлый запрос или N+1. Если N+1 — переделываю `getList` с `select` через связи или `BatchLoad`. Если один тяжёлый — смотрю `EXPLAIN`, добавляю составной индекс. Затем проверяю пагинацию — большой `OFFSET` заменяю курсором. И только потом, если запрос оптимален, добавляю кеш с тегами на `b_sale_order`. Готово, когда page time < 300мс без кеша.»

## Вопросы для собеседования

1. **Как найти N+1 в компоненте?** — SqlTracker, лог запросов, XHProf. Ожидают: «не гадаю — замеряю».
2. **`Order::load` vs `Order::getList`** — когда что? `load` — полный объект со всеми коллекциями, `getList` — плоские строки для списков.
3. **Как добавить условие по связанному полю?** — через `RuntimeEntity` или `filter => ['USER.ACTIVE' => 'Y']` если связь в `select`.
4. **Что такое `PageNavigation` vs `LIMIT/OFFSET`?** — одинаковый SQL, но PageNavigation даёт интерфейс; проблема большого OFFSET решается курсором, а не другой пагинацией.
5. **Когда нужна транзакция?** — когда несколько пишущих операций должны быть атомарны (заказ + отгрузка + оплата). Не «везде» — транзакции держат локи.
6. **Как избежать дубля заказа при двойном клике «Оформить»?** — идемпотентность: уникальный ключ `REQUEST_ID`, проверка перед `save()`, либо `INSERT ... ON DUPLICATE KEY`.
7. **Почему `OnSaleOrderSaved` опасен?** — в нём нельзя `save()` сущности, и он внутри транзакции — тяжёлая работа (письмо, API) делается через `CAgent`.
8. **Чем `getList` отличается от `GetList`?** — D7 (новая ORM, объекты, `select`/`filter`/`order`/`limit`/`offset`) vs старый `CSaleOrder::GetList` (arOrder/arFilter/arSelect, legacy).

## Частые ошибки в ответах

- **«Сразу кеш»** — кеш это отложенное решение, не диагностика.
- **`fetchAll()` на большой выборке** — память.
- **«Транзакции везде»** — транзакция на чтении не нужна, на записи — только когда нужна атомарность.
- **«Поле через `get()` без проверки»** — `get()` вернёт `null` для несуществующего поля, `getField` бросит исключение.
- **Проверка `is_object` после `load`** — `Order::load` возвращает `null` или объект, проверяйте `if (!$order)`.

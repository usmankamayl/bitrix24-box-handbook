# Модуль 1.8: Result, Exception и обработка ошибок

## Теория

> Подраздел закрыт целиком: блок A — `Result`, `Error`, `ErrorCollection` как
> контракт возврата; блок B — исключения, их иерархия, транзакции и логирование;
> блок C — как из этого сделать ответ наружу без утечек и без потери смысла.
> Задача не «узнать, что есть класс Result», а научиться выбирать механизм до
> написания кода и не терять ошибку по дороге.

### Границы темы

| Тема | Где |
|---|---|
| `Request`, `HttpRequest`, чтение входных данных | 1.7 |
| Заголовки, статусы, `FinalActions`, буферизация | 1.5, 1.7 блок B |
| ORM: сущности, `getList`, поля, отношения | модуль 2 |
| Транзакции и конкурентность в деталях | модуль 2, модуль 13 |
| `Engine\Controller`, `ActionFilter`, JSON-экшены | модуль 5 |
| Логи, мониторинг, алерты как процесс | модуль 13 |
| Права и CSRF как механизм | модуль 7 |

Здесь — только механизм ошибок: кто их производит, в каком виде, кто ловит и что
из них делает.

## Блок A. Результат как контракт

### A0. Два механизма, и это не «вкусовщина»

В D7 одновременно живут `Result` и исключения. Разница не стилистическая, а в
том, **кто обязан обработать ошибку**:

| Признак | `Result` | Исключение |
|---|---|---|
| Ожидаемая ситуация? | да (валидация, правило бизнеса, «не найдено») | нет (баг, отказ инфраструктуры) |
| Кто обрабатывает | вызывающий код, обязательно и явно | любой уровень выше, часто глобальный обработчик |
| Что будет, если забыть | тихо продолжится выполнение с невалидным состоянием | падение запроса с 500 и записью в лог |
| Цена забывания | испорченные данные, которые никто не заметил | видимая поломка, но без порчи данных |
| Годится для UI | да (сообщения по полям) | нет (нечего показать пользователю) |

Формулировка, по которой выбирают на практике:

> `Result` — когда «так бывает»: пользователь ввёл плохой email, заказ уже
> оплачен, товара нет на складе, объекта нет по этому ID.
> Исключение — когда «так быть не должно»: файла нет там, где он обязан быть,
> модуль не установлен, БД недоступна, в метод передали массив вместо строки.

Второе правило, которое ломают чаще: **не смешивать в одном методе**. Функция,
которая возвращает `Result` и при этом бросает исключение на «плохих» данных,
заставляет вызывающего писать и `if`, и `try` — и он забудет одно из двух.

Есть третья категория, которую надо знать, потому что она встречается в ядре:
**ORM возвращает `Result`, но на неверный запрос бросает исключение**. Это не
непоследовательность, а то же разделение: «строка не прошла бизнес-правило» —
результат, «в `select` указано несуществующее поле» — программная ошибка
(см. A5).

### A1. Анатомия `Result`

`Bitrix\Main\Result` (с 12.0.7) — маленький объект, и весь его контракт — семь
методов:

| Метод | Что делает | Замечание |
|---|---|---|
| `isSuccess(): bool` | успешен ли | единственный правильный способ проверить |
| `addError(Error $error): $this` | добавляет ошибку | принимает **объект**, не строку |
| `addErrors(array $errors): $this` | добавляет массив `Error` | не сливает `data` (см. A4) |
| `getErrors(): Error[]` | все ошибки | массив объектов |
| `getError(): ?Error` | первая ошибка или `null` | удобно для лога, опасно для UI |
| `getErrorMessages(): string[]` | только тексты | для `implode` / быстрого лога |
| `getErrorCollection(): ErrorCollection` | коллекция для передачи в контроллер | с 15.5.9 |
| `setData(array $data): $this` / `getData(): array` | полезная нагрузка | `getData` с 14.0.6 |

Чего в `Result` **нет**, и на этом ловятся:

- **Нет `addData()`.** Только `setData()`, и он **заменяет** массив целиком, а не
  дополняет. Код, который «аккуратно накапливает» через `setData` в цикле,
  оставляет в результате последний кусок.
- **Нет `getData()['key'] = ...` по ссылке** — `getData()` возвращает копию
  массива (PHP копирует по значению), запись в неё ничего не меняет в результате.
- **Нет `__toString()`.** `echo $result` — фатал. В шаблоне нужен
  `implode(', ', $result->getErrorMessages())`.
- **Нет автоматической связи между `data` и успехом.** Можно получить
  `isSuccess() === false` и непустой `getData()` одновременно — например, если
  данные положили до проверки. Правило: `getData()` читают **только** после
  `isSuccess()`.

И главная ловушка, которая живёт в проде годами:

```php
if ($result = $someService->doIt()) {   // ВСЕГДА true: объект truthy
    // «успех», даже если isSuccess() === false
}
```

`Result` — объект, объектов с «ложным» значением в PHP нет. Проверка `if
($result)` не проверяет ничего. Это не стилистика: код молча едет по ветке
успеха и, например, отправляет письмо «ваш заказ принят» на провалившийся заказ.
Тот же дефект в форме `if (!$result)` — ветка ошибки не выполнится никогда.

### A2. `Error`: сообщение, код и данные

```php
new Error(
    'Товара не хватает на складе',
    'INSUFFICIENT_STOCK',                    // код: строка или int
    ['available' => 5, 'requested' => 10]    // customData: что угодно
);
```

| Метод | Что возвращает | Для чего |
|---|---|---|
| `getMessage(): string` | текст для человека | UI, письмо |
| `getCode(): int\|string` | машинный код | ветвление логики, HTTP-статус, i18n |
| `getCustomData(): mixed` | произвольные данные | поля формы, числа, id |
| `__toString()` | текст ошибки | `implode` по массиву объектов |
| `jsonSerialize()` | `Error` — `JsonSerializable` | сериализация без ручной сборки |
| `createFromThrowable(\Throwable $e): static` | ошибка из исключения | граница «исключение → результат» |

Три правила про коды, без которых `Result` бесполезен:

1. **Код — часть контракта, текст — нет.** Текст меняют редактором, переводят
   через `Loc::getMessage()`, сокращают для мобильного клиента. Логика ветвится
   по `getCode()`, а не по `strpos($message, 'нет на складе')`.
2. **Код стабилен и в верхнем регистре**, без пробелов: `ORDER_NOT_FOUND`,
   `STATUS_TRANSITION_DENIED`, `INSUFFICIENT_STOCK`.
3. **Код — строка или int** (`getCode(): int|string`). Код, который когда-то был
   int, а потом стал строкой, ломает строгие сравнения `=== 0`. Сравнивать через
   `(string)` или держать один тип во всём модуле.

`customData` — не свалка. Разумное использование: какие поля не прошли
(`['field' => 'email']`), сколько осталось (`['available' => 5]`), какой id уже
занят (`['existing_id' => 42]`). Это то, из чего клиент строит подсветку полей и
что нельзя восстановить из текста.

### A3. `ErrorCollection`

`Bitrix\Main\ErrorCollection` нужен ровно в одном месте — на границе с D7:
контроллер и часть API принимают/возвращают коллекцию, а не `Result`.

| Метод | Что делает |
|---|---|
| `add(Error[] $errors): void` | добавить массив ошибок |
| `setError(Error $error, $offset = null): void` | добавить одну |
| `getErrorByCode(string\|int $code): ?Error` | найти по коду — то, чего нет в `Result` |
| `isEmpty(): bool` | пусто ли |
| `toArray()` / `getValues()` | массив значений |
| `clear()` | очистить |

Коллекция наследует `Dictionary` — значит `ArrayAccess`, `Iterator`, `Countable`,
`JsonSerializable`. Отсюда `count($collection)` и `foreach` работают, а
`$collection[0]` — работает, но полагаться на индекс не надо.

Практическая разница с `Result`: **у коллекции есть `getErrorByCode()`**. Если
логике нужно спросить «была ли конкретная ошибка» (например, `DUPLICATE` →
`409`, а всё остальное → `422`), то либо так, либо `foreach` по `getErrors()` с
ручным сравнением кодов.

Мостик между ними односторонний: `Result::getErrorCollection()` есть,
`ErrorCollection::getResult()` — нет. Из коллекции обратно в `Result` —
`$result->addErrors($collection->getValues())`.

### A4. Композиция: как один `Result` собирается из других

Стандартный сценарий: сервис вызывает три подсервиса, каждый вернул свой
`Result`, надо вернуть один.

```php
$result = new Result();

$validation = (new OrderInputValidator($input))->validate();
if (!$validation->isSuccess()) {
    return $result->addErrors($validation->getErrors());
}

$stock = $this->stock->reserve($orderId);
if (!$stock->isSuccess()) {
    return $result->addErrors($stock->getErrors());
}

$result->setData(['reserved' => $stock->getData()['reserved']]);

return $result;
```

Что здесь важно и что ломают:

- **`addErrors()` не сливает `data`.** Данные дочернего результата надо переносить
  руками и только осознанно.
- **Ранний `return` — правильно.** Собирать все ошибки сразу имеет смысл только
  на уровне валидации полей формы. Смешивать «email плохой» и «склада нет» в
  одном ответе — значит показать пользователю ошибку, которую он не может
  исправить.
- **Потеря контекста.** `addErrors()` копирует объекты `Error`, но не говорит, кто
  именно их произвёл. Если в ответе клиенту нужно различать слои — добавляй
  префикс в код (`STOCK_INSUFFICIENT`) или в `customData` (`['source' =>
  'stock']`), а не полагайся на порядок ошибок.
- **`getErrors()` — массив, а не «первая ошибка».** `implode(', ',
  $result->getErrorMessages())` допустим в логе, но не в UI: пользователю нужен
  список по полям.
- **`getErrors()[0]` без проверки `isSuccess()`** — в PHP 8 это warning
  «Undefined array key 0» и `null->getMessage()` → фатал. Частый дефект в
  обработчиках, которые «всегда получают хотя бы одну ошибку».

### A5. ORM: результат и исключение в одном API

ORM (`DataManager` и наследники) — главный источник обоих механизмов в реальном
коде:

| Операция | Возвращает | Бросает |
|---|---|---|
| `add(array $data)` | `ORM\Data\AddResult` (`getId()`, `getPrimary()`, `getObject()`) | `Exception` |
| `update($id, array $data)` | `UpdateResult` | `Exception` |
| `delete($id)` | `DeleteResult` | `Exception` |
| `getList(array $params)` | `ORM\Query\Result` (курсор, не `Main\Result`) | `ArgumentException`, `ObjectPropertyException`, `SystemException` |
| `getById($id)` | то же | то же |

Практические следствия:

- **Ошибки записи — в `getErrors()` результата.** У ORM-результатов `getErrors()`
  возвращает не только `Error`, но и `ORM\EntityError` / `ORM\Fields\FieldError`
  — наследники `Error` с полем/сущностью внутри. Код, который ждёт именно
  `Bitrix\Main\Error` в `instanceof`, обычно проходит (наследование), но код,
  который читает `getCustomData()`, может получить не то, что ожидал.
- **`getList()` падает исключением, а не возвращает пустой результат.** Опечатка в
  `select` — `ObjectPropertyException`, неверный оператор фильтра —
  `ArgumentException`. Пустой массив строк и «неверный запрос» — разные вещи, и
  ORM это различает.
- **`add()` коммитит сразу.** Никакой отложенности: если после `add()` код упал,
  запись осталась. Отсюда — транзакция (B4).
- **`update()` по несуществующему ID не обязательно ошибка.** Проверять
  «обновилось ли» через `isSuccess()` недостаточно: результат может быть успешным
  при нуле затронутых строк. Надёжный приём — читать обратно в той же транзакции
  и сверять ожидаемое с фактическим (это и делает задача 3).

### A6. `Result` не заменяет валидацию

`Result` — контейнер для ошибок, а не механизм их обнаружения. Частая ошибка
дизайна: сервис «возвращает Result» и внутри делает `if (empty($data['email']))`,
`filter_var`, проверки диапазонов — то есть валидатор, размазанный по трём
уровням. Правильное деление:

- **валидатор** — принимает массив, возвращает `Result` с ошибками по полям;
- **доменный сервис** — принимает уже провалидированные данные, возвращает
  `Result` с ошибками правил (`STATUS_TRANSITION_DENIED`);
- **репозиторий/ORM** — возвращает свой `Result` или бросает исключение.

Один `Result` на выходе, но три разных источника и три разных набора кодов.
Клиент по коду понимает, что делать: `EMAIL_INVALID` — исправить поле,
`STATUS_TRANSITION_DENIED` — обновить страницу, `INTERNAL` — повторить позже.

## Блок B. Исключения

### B0. Иерархия: что ловить и что называть в `catch`

Всё D7 растёт из одного класса:

```
\Throwable
├─ \Exception
│  └─ Bitrix\Main\SystemException        — базовый для D7
│     ├─ Bitrix\Main\ArgumentException   — неверные входные параметры
│     │  ├─ ArgumentNullException
│     │  ├─ ArgumentOutOfRangeException
│     │  └─ ArgumentTypeException
│     ├─ Bitrix\Main\DB\Exception
│     │  ├─ DB\ConnectionException       — нет соединения
│     │  └─ DB\SqlException              — ошибка выполнения запроса
│     ├─ Bitrix\Main\IO\IoException
│     │  ├─ FileNotFoundException
│     │  ├─ FileOpenException
│     │  ├─ FileDeleteException
│     │  └─ InvalidPathException
│     ├─ Bitrix\Main\Config\ConfigurationException
│     ├─ Bitrix\Main\Security\SecurityException
│     │  └─ Security\Sign\BadSignatureException
│     ├─ Bitrix\Main\AccessDeniedException
│     ├─ Bitrix\Main\ObjectException
│     │  ├─ ObjectNotFoundException
│     │  └─ ObjectPropertyException
│     ├─ Bitrix\Main\NotSupportedException
│     ├─ Bitrix\Main\NotImplementedException
│     └─ Bitrix\Main\LoaderException
└─ \Error                                 — TypeError, ValueError, …
```

Выводы, которые надо помнить:

| Что в `catch` | Что поймает | Когда правильно |
|---|---|---|
| `\Throwable` | всё, включая `TypeError` | граница запроса, транзакция, «не дать упасть наружу» |
| `\Exception` | только исключения | **никогда** для «поймать всё»: PHP 8 бросает `TypeError` в код, который вызывает методы у `null` |
| `SystemException` | ошибки D7 | когда обрабатываешь именно API ядра |
| `SqlException` | ошибка БД | тонкая настройка: повтор запроса, разбор дубликата |
| `LoaderException` | модуль не подключён | проверка окружения на входе |

`catch (\Exception $e) {}` в PHP 8 — это дыра: пустой `catch` без `\Throwable`
пропускает мимо себя `TypeError` из `$repository->get($id)->getId()`, и запрос
падает уже вне понятной логики ошибок.

### B1. Где исключение обязательно

Три места, где `Result` не подходит и не надо пытаться его приспособить:

1. **Конструктор и сеттеры.** Объект, который создали «с ошибкой», — это объект в
   невалидном состоянии. Если конструктор не смог, он бросает
   `ArgumentException`, а не возвращает `Result` (вернуть его из конструктора
   нельзя).
2. **Проверка окружения на входе.** `Loader::includeModule('iblock')` вернул
   `false` — модуль не установлен, работать нечем. Это не «ошибка пользователя»,
   это сломанная конфигурация: бросай `LoaderException` или отдавай `500`.
   Тут же — обязательная зависимость, отсутствие которого делает бессмысленной
   всю страницу.
3. **Инфраструктурный сбой.** БД недоступна, файл не открылся, внешний сервис
   ответил таймаутом. Возвращать `Result` с ошибкой «нет соединения» — значит
   заставить каждый вызов проверять `isSuccess()`, чтобы отличить «нормальный
   отказ бизнеса» от «всё сломано». Такое пробрасывают наверх и превращают в
   `500` один раз, на границе.

Отдельный, очень частый на практике случай — **смешанный API**. `Loader`:

```php
if (!Loader::includeModule('iblock')) {
    // false: модуль не установлен — штатная проверка
}

Loader::includeModule('iblok');   // опечатка → LoaderException «Module iblok is not installed»
```

То есть одна и та же функция и возвращает `false`, и бросает исключение — в
зависимости от того, «модуль есть в поставке, но не установлен» или «такого
модуля не существует». Поэтому `if (!Loader::includeModule(...))` **не
закрывает** опечатку: код упадёт исключением, не дойдя до `if`.

### B2. Как ловить, чтобы не потерять

Правила, каждое — из реального дефекта:

- **`catch (\Throwable $e)`, а не `\Exception`** — на границе запроса и вокруг
  транзакции.
- **Не глотать.** `catch` без тела или с `// TODO` — это тихая потеря ошибки:
  пользователь видит «успех», в логе пусто, данные не записались. Минимум —
  лог. Часто — `throw` дальше.
- **Не терять предыдущее исключение.** `throw new \RuntimeException('Ошибка')`
  внутри `catch` убивает стек и причину. Нужно
  `throw new \RuntimeException('Ошибка сохранения заказа', 0, $e);`.
- **Порядок `catch` — от частного к общему.** `SqlException` раньше
  `SystemException`, иначе ветка для БД недостижима.
- **`finally` — для освобождения.** Закрыть файл, вернуть блокировку, откатить
  транзакцию, если она ещё открыта.
- **Не превращать исключение в `Result` без причины.** Если вызывающий всё равно
  не может ничего сделать («БД лежит»), `Result` только размазывает обработку.
- **Не логировать и не показывать одно и то же дважды.** Граница запроса: лог —
  подробно, ответ — коротко.

Граница «исключение → результат» уместна в одном случае: когда наверх (в UI или
в API) нельзя отдавать исключение, но нужно отдать корректный отказ.

```php
try {
    $order = $this->repository->getById($id);       // может бросить ObjectNotFound
} catch (ObjectNotFoundException $e) {
    return (new Result())->addError(new Error('Заказ не найден', 'ORDER_NOT_FOUND'));
}
```

Здесь `ObjectNotFoundException` — деталь реализации репозитория, а
`ORDER_NOT_FOUND` — часть контракта сервиса. Превращение оправдано: снаружи
сервиса про исключения знать не должны.

### B3. Логирование: что писать и что не писать

| Пишем | Не пишем |
|---|---|
| код ошибки, id сущности, действие | пароль, токен, номер карты |
| класс исключения + сообщение | полный `$_POST` формы |
| `file:line` первой строки своего кода | персональные данные целиком |
| trace — в файл, не в ответ | trace в JSON клиенту |

Инструменты:

- `AddMessage2Log($message, $moduleId)` — legacy-функция, но работает везде и
  пишет в файл, заданный константой `LOG_FILENAME` (в `dbconn.php` по умолчанию
  `/bitrix/modules/error.log`). Для быстрой диагностики в Box — самый короткий
  путь.
- `Bitrix\Main\Diag\Logger` — D7-путь с уровнями и обработчиками
  [проверить: наличие и API в твоей версии; проба `practice-1-result-probe`
  печатает `class_exists` и список методов].
- `$e->getTraceAsString()` — только в файл. В ответ клиенту — никогда: там
  абсолютные пути, имена таблиц и структура кода.

### B4. Транзакции: где `Result` перестаёт быть достаточным

`Bitrix\Main\DB\Connection` (получается через
`Application::getConnection()`):

```php
$connection = \Bitrix\Main\Application::getConnection();
$connection->startTransaction();

try {
    // ... записи через ORM или $connection->queryExecute()
    $connection->commitTransaction();
} catch (\Throwable $e) {
    $connection->rollbackTransaction();
    throw $e;
}
```

Пять фактов, без которых транзакция в Битриксе не работает как ожидается:

1. **`commitTransaction()` и `rollbackTransaction()` возвращают `void`.** Никакого
   `if ($connection->commit())`.
2. **ORM внутри транзакции участвует в ней автоматически** — отдельного
   «транзакционного соединения» нет, оно одно на запрос.
3. **`startTransaction()` внутри уже открытой транзакции — это `SAVEPOINT`,** не
   вложенная транзакция. Внутренний `rollbackTransaction()` откатит только до
   точки сохранения, внешние данные останутся. Из этого следует: сервис,
   который «на всякий случай» открывает транзакцию, не ломает вызывающего — но и
   не даёт ему атомарности, на которую тот рассчитывает.
4. **`Result` с ошибкой внутри транзакции не откатывает ничего.** Если
   `$stock->update()` вернул `isSuccess() === false`, а код просто вернул
   `Result` из метода — транзакция осталась открытой, и `commit` может прийти
   позже (или соединение закроется с неявным откатом). Правило: **внутри
   транзакции любая ошибка превращается в исключение**, а `Result` собирается
   уже снаружи.
5. **`ddl` и MyISAM не транзакционны.** `CREATE TABLE`, `ALTER` и таблицы
   MyISAM откату не подлежат. Транзакция защищает данные, а не схему.

Шаблон, который надо довести до автоматизма:

```php
$connection->startTransaction();
try {
    $result = $this->writeA();
    if (!$result->isSuccess()) {
        throw new OperationFailed($result);   // свой класс, несущий Result
    }
    $result = $this->writeB();
    if (!$result->isSuccess()) {
        throw new OperationFailed($result);
    }
    $connection->commitTransaction();
} catch (\Throwable $e) {
    $connection->rollbackTransaction();
    throw $e;
}
```

`OperationFailed` (свой класс с `getResult()`) — потому что нести `Result`
через исключение иначе нечем: `Error` — не `Throwable`, а бросать
`\Exception('ошибка')` без кодов значит потерять коды, по которым наружу
строится ответ.

### B5. Исключения в фоновых механизмах

Агенты, обработчики событий и очереди — место, где необработанное исключение
проявляется не сразу:

- **Агент.** Если метод агента бросил исключение, запрос агента падает; агент
  при этом не «теряется», а остаётся и будет запущен снова (следующий хит
  cron/хит пользователя) — то есть ошибка повторяется, пока её не заметят
  [проверить: точное поведение `NextExec` при фатале в твоей версии]. Логирование
  внутри агента — обязательное, иначе это «тихий» цикл.
- **Обработчик события.** Исключение из `OnBeforeIBlockElementAdd` прерывает
  добавление, из `OnAfter...` — уже после записи, и откатить её нельзя (событие
  постфактум). Отсюда правило: проверки, которые должны запретить операцию,
  живут в `OnBefore`; в `OnAfter` ошибка только логируется.
- **Очередь/отложенные события.** `CEvent::Send` может отложить письмо; падение
  после постановки в очередь означает письмо, которое уйдёт позже — это нормально,
  но знать надо.

## Блок C. Наружу: из `Result` в HTTP

### C0. Маппинг кодов, а не текстов

Граница API — единственное место, где решается HTTP-статус. Не в сервисе, не в
валидаторе: они не знают про HTTP.

| Ситуация | Код ответа | Что в теле |
|---|---|---|
| Провал валидации | `422` | список `{code, message, field?}` |
| Некорректный запрос (битый JSON, неверный тип) | `400` | один код |
| Нет авторизации | `401` | один код |
| Нет прав / CSRF | `403` | один код |
| Объект не найден **или чужой** | `404` | один код |
| Конфликт состояния (уже закрыт, уже существует) | `409` | код + `customData` |
| Непредвиденное | `500` | `INTERNAL`, без деталей |

Маппер — таблица «код ошибки → статус», а не `if (strpos(...))`:

```php
private const STATUS_BY_CODE = [
    'VALIDATION_FAILED'       => 422,
    'EMAIL_INVALID'           => 422,
    'REQUEST_NOT_FOUND'       => 404,
    'ACCESS_DENIED'           => 404,   // чужой объект не подтверждаем
    'STATUS_TRANSITION_DENIED'=> 409,
    'ALREADY_CLOSED'          => 409,
];
```

Неизвестный код → `422` (если ошибка пришла из `Result`) или `500` (если это
исключение). Отдельно: **`404` вместо `403` для чужого объекта** — `403`
подтверждает, что объект существует.

### C1. Что нельзя отдавать наружу

- `$e->getMessage()` от `SqlException` — там текст SQL и имя таблицы.
- `$e->getTraceAsString()` — пути, имена классов, структура.
- Полный `Result::getErrorMessages()` без чистки — в них могут быть внутренние
  сообщения («Unknown field definition `IBLOCK_ID`»).
- Разницу между «не найдено» и «не ваше» — см. C0.

Правильный ответ на непредвиденное:

```php
$errorId = bin2hex(random_bytes(8));                 // корреляция с логом
AddMessage2Log('[' . $errorId . '] ' . get_class($e) . ': ' . $e->getMessage()
    . "\n" . $e->getTraceAsString(), 'mycompany.api');

http_response_code(500);
header('Content-Type: application/json; charset=UTF-8');
echo \Bitrix\Main\Web\Json::encode([
    'status'    => 'error',
    'errors'    => [['code' => 'INTERNAL', 'message' => 'Внутренняя ошибка. Код: ' . $errorId]],
], JSON_UNESCAPED_UNICODE);
```

Клиент получает код, поддержка по нему находит запись в логе. Пользователь не
видит ни таблиц, ни путей.

### C2. Частичный успех — не `Result`

Отдельный реальный сценарий, который `Result` не описывает: импорт 5000 строк,
из них 37 с ошибками. Вопрос не «успех или нет», а «сколько и какие».

`Result` тут работает плохо: он бинарен. Правильная форма — свой объект-отчёт:

```php
final class ImportReport
{
    public int $created = 0;
    public int $updated = 0;
    public int $skipped = 0;
    /** @var array<int, array{line:int, code:string, message:string}> */
    public array $errors = [];

    public function addError(int $line, Error $error): void
    {
        $this->errors[] = [
            'line'    => $line,
            'code'    => (string)$error->getCode(),
            'message' => $error->getMessage(),
        ];
    }

    public function hasErrors(): bool
    {
        return $this->errors !== [];
    }
}
```

Внутри по строкам — обычный `Result` от ORM/валидатора, снаружи — отчёт.
HTTP-статус такого эндпоинта — `200` (запрос обработан), а результат — в теле:
`{"created": 4963, "errors": [...]}`. `207`/`422` здесь вводят в заблуждение:
клиенту нужно продолжить импорт, а не считать запрос провалившимся.

Правило выбора: **бинарен ли исход для вызывающего?** Да — `Result`. Нет —
свой отчёт со счётчиками.

### C3. Антипаттерны

| Код | Что не так | Последствие |
|---|---|---|
| `if ($result = $service->run())` | объект всегда truthy | успех на провале |
| `catch (\Exception $e) {}` | глотание + не ловит `TypeError` | тихая потеря данных |
| `$result->getErrors()[0]->getMessage()` без `isSuccess()` | пустой массив | warning + фатал в PHP 8 |
| `new Error($e)` | в `$message` ждут строку | `TypeError` |
| `getData()` без проверки успеха | данные могут быть от неудачной ветки | запись мусора |
| `throw new \Exception('Ошибка')` внутри `catch` | потерян `$previous` | стек и причина исчезли |
| `commitTransaction()` без `try` | исключение между `start` и `commit` | открытая транзакция, блокировки |
| `Result` вместо исключения для «БД недоступна» | каждый вызов обязан проверять | ошибка конфигурации не видна мониторингу |
| `getMessage()` в JSON ответа | утечка SQL/путей | раскрытие внутренностей |
| `403` для чужого объекта | подтверждение существования | утечка через перебор ID |
| код ошибки int, а сравнение строкой (`=== '0'`) | типы не совпали | ветка не срабатывает |
| один `Result` на 5000 строк импорта | бинарность | не видно, что именно упало |

### C4. Box vs Cloud

- **Box:** доступно всё — `AddMessage2Log`, свои файлы логов, транзакции, свои
  эндпоинты, `LoaderException` при отсутствии модуля.
- **Cloud (Bitrix24):** кода на сервере нет, `Result` встречается в REST-ответах
  и в приложениях; транзакции и файловые логи недоступны, диагностика — через
  REST-ответы (`error`, `error_description`) и журнал событий приложения.
  Внутри собственного приложения на своём хостинге механика та же, что в Box.
- **Разница в поведении ошибок:** в облаке ошибка приложения возвращается
  структурой `{error, error_description}`, а не HTTP-статусом — тот же принцип
  «код важнее текста», другая упаковка.

### C5. Что проверить пробой

Все утверждения с `[проверить]` и вообще всё поведение `Result` на твоей версии
ядра проверяет `examples/module-1-8/practice-1-result-probe/probe.php`:
матрица `method_exists()`, поведение `addErrors`, truthiness результата,
`getError()` при нескольких ошибках, `Error` в JSON, `Loader::includeModule` с
опечаткой в имени, `update()` по несуществующему ID. Для закрытия подраздела
проба не обязательна — она нужна, когда повторяешь это на незнакомой версии.

## Вопросы для собеседования

**Junior**

1. Чем `Result` отличается от исключения и когда что выбирают?
   *(`Result` — ожидаемый отказ, обрабатывает вызывающий; исключение —
   программная ошибка или сбой, ловится выше.)*
2. Как правильно проверить успех операции? *(Только `isSuccess()`. `if ($result)`
   всегда true.)*
3. Что вернёт `getErrorMessages()` и чем это отличается от `getErrors()`?
   *(Массив строк против массива объектов `Error` с кодами и `customData`.)*
4. Зачем нужен код ошибки, если есть текст?
   *(Текст меняют и переводят; логика и HTTP-статус строятся по коду.)*
5. Почему `catch (\Exception $e) {}` — плохо? *(Глотает ошибку и не ловит
   `TypeError` в PHP 8.)*

**Middle**

6. `$result->addErrors($other->getErrors())` — что произойдёт с `data` дочернего
   результата? *(Ничего: `addErrors` переносит только ошибки.)*
7. `setData()` вызываетcя дважды. Что в результате? *(Второй массив заменит
   первый целиком.)*
8. `Loader::includeModule('iblok')` — что вернёт? *(Бросит `LoaderException`:
   такого модуля нет. `false` — когда модуль существует, но не установлен.)*
9. `update()` по несуществующему ID вернул `isSuccess() === true`. Это баг?
   *(Нет: ORM не считает нулевое число затронутых строк ошибкой. Нужна проверка
   чтением обратно.)*
10. Где ставить `commitTransaction()`, если внутри несколько операций, каждая из
    которых возвращает `Result`? *(После проверки всех `isSuccess()`; любая
    ошибка внутри — исключение и `rollback`.)*
11. `startTransaction()` внутри уже открытой транзакции — что это?
    *(`SAVEPOINT`; внутренний `rollback` откатит только до него.)*
12. Как отдать клиенту `422` с ошибками по полям, если сервис вернул `Result`?
    *(Маппинг код → статус; в теле `{code, message}`; текст `Error` не содержит
    SQL.)*

**Senior**

13. Сервис пишет в две таблицы и возвращает `Result`. Как сделать операцию
    атомарной, не протекая деталями БД в вызывающий код?
    *(Транзакция внутри сервиса; ошибки ORM → исключение с `Result` внутри;
    снаружи — снова `Result`. Транзакция не должна «висеть» после `return`.)*
14. Почему `Result` плохо подходит для импорта на 5000 строк и что вместо него?
    *(Бинарность: нужен отчёт со счётчиками и ошибками по строкам; `200` со
    статистикой в теле.)*
15. Обработчик `OnAfterIBlockElementAdd` бросил исключение. Что уже нельзя
    отменить и как проектировать такой код? *(Элемент записан; запреты — только
    в `OnBefore`; в `OnAfter` — лог и компенсация.)*
16. Клиент жалуется, что «иногда приходит 200, а данных нет». Назови три
    механизма, которые дают такой симптом. *(`if ($result)`; `getErrors()[0]` в
    try/catch, который вернул «успех»; транзакция без `commit`; ответ собран до
    записи.)*
17. Как вы построите контракт ошибок API, чтобы через год можно было менять
    тексты? *(Стабильные коды, `customData` для полей, маппинг кодов в статусы,
    коды — часть документации и тестов, тексты — ресурсы `Loc`.)*

### Критерии приёмки

- Все четыре задачи запускаются на твоей коробке; вывод приложен по желанию —
  он не влияет на зачёт.
- Контрольное задание: названы все пять дефектов, у каждого — причина,
  последствие и условие проявления, а не «так не пишут».
- Ни в одном решении нет `if ($result)` и `getErrors()[0]` без `isSuccess()`.
- В эндпоинте нет `getMessage()` исключения в теле ответа и нет `403` для
  чужого объекта.
- Транзакция: `commit` после проверок, `catch (\Throwable)` → `rollback` →
  `throw`; ни одного `return` между `startTransaction()` и `commit`.
- Ты объясняешь на память: почему `addErrors` не переносит `data`, что делает
  `startTransaction()` внутри транзакции, и что вернёт `Loader::includeModule`
  с опечаткой в имени модуля.

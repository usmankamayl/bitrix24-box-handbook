# Модуль 12.3: Права доступа и безопасность

## Теория

Тема объединяет два уровня: **права доступа внутри CRM/портала** (кто что видит и может менять) и **безопасность интеграций** (защита вебхуков, приложений, компонентов от атак).

### Права доступа в CRM

CRM Bitrix24 строит права на трёх уровнях детализации:
1. **Тип доступа** — чтение, запись, удаление, экспорт, импорт, доступ к списку прав и т.д. (отдельно для лидов, сделок, контактов, компаний).
2. **Уровень охвата** — «личные» (`CRM_PERM.*_PERSONAL`), «подразделение» (отдел), «подразделение с подчинёнными», «все» (`CRM_PERM.*_ALL`).
3. **Статус/стадия** — права могут различаться для записи в разных статусах воронки (например, менеджер не может редактировать сделку после перехода в "Успешно").

Роли настраиваются в интерфейсе CRM: **Настройки → Права доступа → Роли доступа**. Программно это таблицы `b_crm_perms`, доступ проверяется через `\Bitrix\Crm\Security\Permissions`. Через REST узнать права пользователя на конкретную сущность можно методом:

```php
CRest::call('crm.lead.fields', []); // поле прав напрямую не отдаёт
CRest::call('user.access', ['filter' => ['USER_ID' => $userId]]); // роли/группы, в которые входит пользователь
```

На практике, если нужно проверить "может ли пользователь X менять сделку Y" в обработчике события, чаще проверяют через `CCrmPerms::GetUserPermissions($userId)` → `CCrmDeal::CheckUpdatePermission($dealId, $permissions)` (коробочный API, в облаке — аналогично через соответствующие классы модуля crm).

### Группы пользователей и права в «коробке» (D7)

В коробочной версии (self-hosted) права строятся через модуль `main`:
- `CGroup` — группы пользователей (не путать с рабочими группами Bitrix24!).
- `CUser` — пользователи, привязка к группам через `b_user_group`.
- Права на модули/разделы настраиваются через **Группы прав** (`b_module_group`) — какая группа какие действия может делать в каком модуле (например, права на административный раздел, на конкретный инфоблок).
- Права на инфоблок: `CIBlockRights`, задаются по группам и операциям (чтение, запись, премодерация и т.д.) отдельно для каждого инфоблока.

```php
$rights = new CIBlockRights();
$rights->SetRights(BLOCK_ID, [
    [
        'GROUP_CODE' => 'G2', // ID группы пользователей
        'TASK_ID'    => 7,     // например, "чтение"
    ],
]);
```

### OAuth scopes и приложения

При установке локального/облачного приложения Bitrix24 запрашивает набор **scope** — областей доступа (`crm`, `disk`, `calendar`, `task`, `user_basic` и т.д.), которые пользователь (администратор) подтверждает при установке. REST-методы, выходящие за пределы разрешённых scope, вернут ошибку `insufficient_scope`.

- Входящий вебхук создаётся с конкретным набором прав (выбираются вручную при создании) — хорошая практика: давать вебхуку **минимально необходимый** набор прав (принцип наименьших привилегий).
- `application_token` — уникальный токен приложения, передаётся во всех событийных callback-запросах (`ONAPPINSTALL`, `ONCRMDEALADD` и т.д.) — обязательно должен проверяться на бэкенде перед обработкой события, иначе любой внешний запрос с правильным URL сможет сымитировать событие Bitrix24.

### Проверка подписи/токена входящего вебхука

```php
if (!hash_equals($_REQUEST['auth']['application_token'] ?? '', $storedApplicationToken)) {
    http_response_code(403);
    die('Forbidden: invalid application_token');
}
```

Для событий, присылаемых через `event.bind`, в теле запроса приходит `auth[application_token]` — именно по нему проверяется подлинность отправителя, а не по IP (IP у облачного Bitrix24 не гарантированно статичен).

### Безопасность входящих/исходящих вебхуков

- **Входящий вебхук** (входящая интеграция, "дыра" в портал снаружи) — URL содержит секретный код: `https://portal.bitrix24.ru/rest/1/xxxxxxxxxx/`. Код по сути пароль — хранить в `.env`/секретах, никогда не коммитить в репозиторий, ограничивать набор доступных методов при создании.
- **Исходящий вебхук/приложение** — Bitrix24 стучится к вам, важно: проверять `application_token`, по возможности ограничивать по диапазону IP Bitrix24 (документированы официально, но могут меняться — не единственная защита), использовать HTTPS.
- Ротация ключей: если ключ входящего вебхука скомпрометирован — пересоздать вебхук (старый сразу отзывается).

### CSRF и `sessid` в коробке

В коробочной версии (не REST, а административный/публичный раздел) Bitrix генерирует `sessid` (`bitrix_sessid()`) для защиты от CSRF — все формы, изменяющие данные (POST-запросы, AJAX), обязаны передавать и проверять `check_bitrix_sessid()`. Без этого запрос будет отклонён ядром.

```php
if (!check_bitrix_sessid()) {
    ShowError('Неверный sessid');
    return;
}
```

### XSS и защита компонентов

- Шаблоны компонентов обязаны экранировать вывод пользовательских данных (`htmlspecialcharsbx()`), особенно если данные идут из пользовательских полей, комментариев, инфоблоков с публичным редактированием.
- Параметры компонента, попадающие в SQL-фильтр (например, кастомный `arFilter`), нельзя подставлять напрямую из `$_REQUEST` без фильтрации через `CUtil::JSEscape`/приведение типов — иначе риск SQL-инъекции (хотя `CIBlockElement::GetList` использует подготовленные условия, кастомные `\Bitrix\Main\Entity\Query` с сырыми строками — уязвимы).
- Для публичных форм обязательна капча (`CCaptcha`) и валидация на сервере, не только на клиенте.

### Частые ошибки

- **Не проверяют `application_token`** во входящих обработчиках — классическая дыра, позволяющая подделать событие извне.
- **Дают входящему вебхуку права "на всё"**, хотя интеграции нужен доступ только к `crm` — при утечке URL компрометируется весь портал.
- **Путают права CRM (бизнес-уровень) с правами группы пользователей (административный уровень)** — это разные механизмы, настраиваются в разных местах.
- **Забывают `check_bitrix_sessid()`** в кастомных AJAX-обработчиках коробки — уязвимость к CSRF.
- **Хранят вебхук-URL в публичном JS-коде фронтенда** — секрет утекает в исходники страницы.

## Вопросы для собеседования

**1. Что такое `application_token` и зачем он нужен?**
Уникальный секретный токен приложения/вебхука, который Bitrix24 передаёт в каждом событийном callback-запросе. Проверка этого токена на бэкенде подтверждает, что запрос действительно пришёл от Bitrix24, а не был подделан третьей стороной, знающей публичный URL обработчика.

**2. Чем права CRM отличаются от прав группы пользователей в коробке?**
Права CRM — бизнес-уровень: кто видит/редактирует конкретные лиды/сделки, с детализацией "личные / отдел / все". Права группы пользователей (`CGroup`, `b_module_group`) — административный уровень: доступ к разделам/модулям системы в целом (например, к административной панели или конкретному инфоблоку), не привязан к стадиям воронки.

**3. Почему вебхуку стоит выдавать минимальный набор прав?**
Принцип наименьших привилегий: если URL вебхука скомпрометирован (утёк в логи, в публичный код, в чат), ущерб ограничен только теми методами/правами, которые были явно разрешены при создании вебхука, а не всем порталом.

**4. Что такое `check_bitrix_sessid()` и когда он нужен?**
Проверка CSRF-токена сессии в коробочной версии — обязательна для всех изменяющих данные POST/AJAX-запросов в административной и публичной части сайта, чтобы запрос не мог быть подделан со стороннего сайта через автоматическую отправку формы от имени залогиненного пользователя.

**5. Как ограничить права инфоблока для конкретной группы пользователей программно?**
Через класс `CIBlockRights::SetRights()`, передав массив `GROUP_CODE` (код группы, например `G2`) и `TASK_ID` (ID операции: чтение, запись, премодерация и т.д.) для конкретного `BLOCK_ID`.

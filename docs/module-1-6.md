# Модуль 1.6: Автозагрузка, namespace и Composer

## Теория

> Черновик: блок A (механика автозагрузки). Блок B (Composer в проекте:
> установка, конфликт загрузчиков, деплой, безопасность) — следующим куском.
> Разделы «Вопросы для собеседования» и «Практические задачи» заполняются на
> этапах 6 и 3.

### Границы темы

Здесь — как имя класса превращается в путь к файлу в Bitrix, кто и в каком
порядке регистрирует загрузчики, и когда вместо `Loader` нужен Composer.
Не разбираются: компоненты (1.2), `Application`/`Context`/`Request` (1.7),
`Result`/исключения (1.8), установка модулей через `install/index.php`
(модуль 14), opcache как отдельная тема (модуль 4).

### A0. Задача, которую решает автозагрузка

Без автозагрузки класс нужно объявить до первого использования:

```php
require_once $_SERVER['DOCUMENT_ROOT'] . '/local/php_interface/classes/StringHelper.php';
```

Три следствия, которые и породили автозагрузку:

1. Порядок. Если `StringHelper` использует `ArrayHelper`, `require` должен идти
   раньше — граф зависимостей руками.
2. Точки входа. Класс, подключённый в `index.php`, не существует в
   `/local/ajax/*.php`, в агенте, в CLI-скрипте. Каждая новая точка входа —
   новый набор `require`.
3. Дубли. Два `require_once` с разными путями к одному классу (симлинк,
   относительный путь) — `Fatal error: Cannot declare class`.

PHP решает это через стек автозагрузчиков:

```php
spl_autoload_register(callable $loader);   // добавляет в стек
spl_autoload_functions();                  // весь стек, в порядке вызова
```

Ключевая механика, которую часто путают: PHP вызывает загрузчики **по
очереди**, пока один из них не создаст класс. Загрузчик, который «ничего не
нашёл», обязан просто вернуть управление. Загрузчик, который бросил исключение
или сделал `require` несуществующего файла, **прерывает всю цепочку** — до
следующего загрузчика дело не дойдёт.

Namespace сам по себе PHP никуда не маппит. `MyCompany\Helpers\StringHelper` —
это просто имя с префиксом в виде строки; путь к файлу строит конкретный
загрузчик по своему правилу. В Bitrix правила три (карта, namespace→каталог,
модульный префикс), четвёртое — PSR-4 из Composer.

### A1. Порядок старта: кто регистрирует загрузчики

Официальная последовательность инициализации пролога
(`docs.1c-bitrix.ru/pages/framework/request-lifecycle.html`), только то, что
касается классов:

1. `/bitrix/modules/main/lib/loader.php` — класс `Bitrix\Main\Loader`.
   Единственный класс D7, который подключается напрямую, до всего остального.
2. `/bitrix/modules/main/include/autoload.php` — здесь:
   - `Loader::registerNamespace('Bitrix\Main', $moduleRoot . '/lib')` и
     пачка вендорских namespace из `main/vendor` (`Psr\Log`, `PHPMailer\PHPMailer`,
     `Monolog`, `GeoIp2`, `PhpParser`, `Recurr` …);
   - `Loader::registerNamespace('Bitrix\UI', DOCUMENT_ROOT . '/bitrix/modules/ui/lib')`;
   - `spl_autoload_register([Loader::class, 'autoLoad'])` — вот момент, с
     которого `Loader` вообще участвует в поиске классов;
   - `Loader::registerAutoLoadClasses('main', [...])` — карта ~200 самых
     горячих классов ядра (ключи в нижнем регистре).
3. `/bitrix/modules/main/tools.php` — глобальные функции.
4. `dbconn.php` → `constants.php` → объект `$DB` → `after_connect_d7.php`.
5. Определение сайта: `SITE_ID`, `LANGUAGE_ID`, `SITE_CHARSET`.
6. `/local/php_interface/init.php` (если нет — `/bitrix/php_interface/init.php`),
   затем `/local/php_interface/<SITE_ID>/init.php`.
7. Сессия → `OnPageStart` → **создание `$USER` и авторизация** → шаблон сайта →
   `OnBeforeProlog` → проверка прав → буферизация → `OnProlog`.

Отсюда три практических факта.

**`init.php` выполняется до `$USER`.** Между п. 6 и п. 7 стоит создание
пользователя. Код, который в момент подключения `init.php` дёргает
`$USER->IsAuthorized()` или `$USER->GetID()`, получает `false`/`0`, а не
текущего пользователя. Регистрировать обработчики в `init.php` можно и нужно —
они вызовутся позже, когда `$USER` уже есть. Выполнять проверки прав прямо в
теле `init.php` — нельзя.

**`init.php` — это каждый запрос.** Публичная страница, AJAX, REST, агент,
CLI-скрипт `php -f`, cron. Всё, что там подключено, компилируется и
исполняется столько раз, сколько было запросов. Файл на 2000 строк с
`file_get_contents` в теле — это налог на весь сайт. Композитный сайт пролог
выполняет (кешируется уже результат), так что `init.php` в композите
отрабатывает тоже.

**Проверка прямого вызова.** П. 1–3 выставляет `B_PROLOG_INCLUDED`; файлы,
которые должны работать только внутри пролога, начинаются с:

```php
if (!defined('B_PROLOG_INCLUDED') || B_PROLOG_INCLUDED !== true) {
    die();
}
```

### A2. Алгоритм `Loader::autoLoad`

`Loader::autoLoad(string $className)` вызывается на каждый неразрешённый класс.
Порядок проверок (по исходнику `loader.php`, версия ядра 25.x):

1. **Карта классов.** `self::$autoLoadClasses[strtolower(ltrim($className,'\\'))]`.
   При регистрации ключ тоже приводится к нижнему регистру и обрезается слева
   `\` — то есть регистр в ключе карты не важен, `bitrix\main\application` и
   `Bitrix\Main\Application` — одна запись. Путь из карты.
2. **Namespace-префиксы** из `registerNamespace()`. Префикс отрезается, остаток
   имени превращается в путь; из нескольких подходящих префиксов побеждает
   самый длинный — реализацию сопоставления смотри в `loader.php` под свою
   версию [проверить] (`registerNamespace` — строка ~323, `autoLoad` — ~440).
3. **Модульный префикс** — без всякой регистрации: первые два сегмента имени
   дают ID модуля, остальное — путь внутри модуля. Официальный пример из
   документации:

   | Класс | Файл |
   |---|---|
   | `\Bitrix\Main\IO\File` | `/bitrix/modules/main/lib/io/file.php` |
   | `\Bitrix\IBlock\Section\Type` | `/bitrix/modules/iblock/lib/section/type.php` |
   | `\QSoft\Catalog\Tools\File` | `/bitrix/modules/qsoft.catalog/lib/tools/file.php` |

   `Vendor\Module` → `vendor.module`. Это и есть причина, по которой файлы в
   `lib/` модулей называются **в нижнем регистре**: `ElementTable` →
   `elementtable.php`.
4. **Фолбэк для `*Table`**: если `footable.php` не найден, загрузчик пробует
   `foo.php` — наследие старой раскладки ORM.
5. **Защита от подстановки в имени класса.** Если имя содержит что-то кроме
   `[a-zA-Z0-9_\\/]` — загрузчик молча выходит. Иначе `__construct`-подобные
   трюки с `..` в имени класса дали бы include произвольного файла. При этом
   имя класса — не пользовательский ввод, но правило полезно помнить: любой
   автозагрузчик, который строит путь из строки, обязан её валидировать.
6. `require_once` найденного файла.

**Критично для прод-сервера.** `Loader` приводит к нижнему регистру не только
имя класса, но и путь файла. Значит `Loader::registerNamespace('MyCompany',
'/local/php_interface/classes')` для класса `MyCompany\Helpers\StringHelper`
ищет `classes/helpers/stringhelper.php`. На Windows (регистронезависимая ФС)
это находит `Helpers/StringHelper.php` и «работает»; на Linux в проде —
`Class not found`. Это первая по частоте причина «у меня работало, на сервере
нет».

Следствие: `registerNamespace` годится для файлов в нижнем регистре (как в
`lib/` модулей). Для PSR-4 с CamelCase-именами файлов нужен Composer — он
единственный, кто ищет файл по имени класса без приведения регистра.

### A3. Пять способов зарегистрировать свой класс

| Способ | Где регистрируется | Как ищет файл | Когда выбирать |
|---|---|---|---|
| `Loader::registerAutoLoadClasses($module, $map)` | `init.php`, `include.php` модуля | ключ = имя класса (без учёта регистра), значение = путь | 1–10 классов, горячий путь, нужен предсказуемый O(1) |
| `Loader::registerNamespace($ns, $dir)` | `init.php`, `include.php` | префикс → каталог, путь в нижнем регистре | группа классов из одного каталога, файлы в нижнем регистре |
| Модульный префикс | ничего не регистрируется | `Vendor\Module\...` → `local/modules/vendor.module/lib/...` | свой модуль: единственный вариант, который переживает перенос между проектами |
| Composer PSR-4 | `local/composer.json` + `require autoload.php` | имя класса → путь без изменений | сторонние библиотеки, PSR-4, автозагрузка тестов |
| `require_once` руками | где угодно | — | только для файлов без классов и точек входа |

```php
// /local/php_interface/init.php
use Bitrix\Main\Loader;

// 1. Карта. $module = null — класс не принадлежит модулю.
Loader::registerAutoLoadClasses(null, [
    'MyCompany\\Helpers\\StringHelper' => '/local/php_interface/classes/Helpers/StringHelper.php',
]);

// 2. Namespace → каталог. Файлы должны быть в нижнем регистре:
//    /local/php_interface/classes/helpers/stringhelper.php
Loader::registerNamespace('MyCompany\\Legacy', Loader::getDocumentRoot() . '/local/php_interface/classes/legacy');

// 3. Модуль: регистрация не нужна вообще, если имя совпадает с ID модуля.
//    local/modules/mycompany.tools/lib/helper.php  →  \MyCompany\Tools\Helper
```

`registerAutoLoadClasses` при ошибке бросает `\Bitrix\Main\LoaderException`
(класс объявлен в том же `loader.php`). Практический смысл: файл из карты не
обязан существовать в момент регистрации — он подключается при первом
обращении. Опечатка в пути не проявится, пока класс не понадобится, и вылезет
`Fatal error` в самом неудобном месте.

**Антипаттерны, которые встречаются в проектах:**

```php
// плохо: свой autoload.php поверх ядра
spl_autoload_register(function ($class) {
    $path = __DIR__ . '/' . str_replace('\\', '/', $class) . '.php';
    if (file_exists($path)) require $path;
});
```

Почему плохо: (а) не учитывает `local`/`bitrix`, модульные префиксы и карту
ядра — то есть дублирует `Loader` и расходится с ним в поведении; (б) порядок
в стеке не определён, и при совпадении имён побеждает случайный загрузчик;
(в) `file_exists` на каждый класс без мемоизации. Если очень нужен свой
загрузчик — `Loader::registerHandler(callable)` встраивает его в цепочку
`Loader`, а не рядом.

```php
// плохо: require в каждом файле
require_once __DIR__ . '/../../classes/Helpers/StringHelper.php';
```

Относительный путь ломается при переносе файла, а `__DIR__` в шаблоне
компонента указывает на шаблон, а не на корень.

### A4. `include.php` модуля и `Loader::includeModule`

`Loader::includeModule('mycompany.tools')` подключает
`/local/modules/mycompany.tools/include.php` (если каталога в `/local/` нет —
`/bitrix/modules/...`) и помечает модуль загруженным в `$loadedModules`.
Повторный вызов — no-op.

В `include.php` модуль делает то, что должно произойти при его подключении:
регистрирует namespace/классы, навешивает обработчики событий, объявляет
константы. Классы из `lib/` при этом находятcя по модульному префиксу **даже
без** `includeModule` — файл просто подключается по пути. Но работать такой
класс может некорректно: не выполнена инициализация модуля, не подключены его
ORM-таблицы, не зарегистрированы события.

Отсюда правило: `Loader::includeModule()` — не «подключить класс», а
«подключить модуль». Возвращает `bool`; для партнёрских модулей с демо-режимом
есть `includeSharewareModule()`, возвращающий `MODULE_NOT_FOUND`,
`MODULE_INSTALLED`, `MODULE_DEMO`, `MODULE_DEMO_EXPIRED`. Для кода, где
отсутствие модуля — ошибка, есть `requireModule()` — бросает исключение
(поведение переключается `setRequireThrowException()`).

### A5. Стоимость и диагностика

- Промах автозагрузки дешевле, чем кажется, но не бесплатен: до нескольких
  `file_exists` + `require_once`. В цикле на 1000 элементов с промахом на
  каждом — это уже заметно. Регистрируйте то, что используется часто; официальная
  документация прямо говорит, что редкие классы регистрировать не нужно.
- `class_exists($name)` по умолчанию **запускает** автозагрузку;
  `class_exists($name, false)` — только проверяет объявленные классы. Второй
  вариант нужен, когда проверка идёт в горячем цикле или когда загрузка класса
  имеет побочные эффекты.
- Автозагрузчик не должен делать I/O: ни запросов в БД, ни HTTP, ни чтения
  настроек. Он вызывается в момент, когда приложение уже частично
  инициализировано, и падение внутри загрузчика не перехватывается.
- Диагностика в одну строку на любой странице:

```php
print_r(spl_autoload_functions());
```

Покажет фактический стек: замыкания, `[Loader::class, 'autoLoad']`, объект
`Composer\Autoload\ClassLoader` — и порядок, в котором они будут вызваны.

### A6. Симптом → причина → где смотреть

| Симптом | Причина | Где смотреть |
|---|---|---|
| Локально работает, на сервере `Class not found` | регистр в пути (`registerNamespace` + CamelCase-файлы), регистр файла на Linux | `spl_autoload_functions()`, `ls` каталога |
| `Class not found` только в AJAX/агенте/CLI | регистрация сделана не в `init.php`, а в шаблоне/странице | точка входа, `init.php` |
| `Fatal: Cannot declare class` | класс объявлен из двух разных файлов: `autoload.files` Composer + карта/`lib` | `composer.json` секция `autoload.files` |
| Класс не найден после `composer dump-autoload -o` | classmap собран до появления файла | пересобрать автозагрузку, не коммитить `vendor/composer/*` вслепую |
| Обработчик не срабатывает | зарегистрирован после события (в `init.php` порядок важен) или модуль не подключён | `EventManager::getInstance()->getEvents()` |
| `$USER` пустой в коде `init.php` | `init.php` выполняется до авторизации | п. 6 и 7 в A1 |

### B. Composer в Bitrix-проекте

#### B1. Зачем он вообще нужен, если есть `Loader`

`Loader` решает «найти свой класс в проекте». Composer решает «притащить чужой
код с зависимостями»: разрешение версий, `composer.lock`, автозагрузка
сторонней библиотеки, которая ничего не знает про Bitrix и раскладывает файлы
по PSR-4. Писать `require_once` на библиотеку из 40 файлов — не вариант;
копировать её в `/local/php_interface/classes` — тоже (обновлять руками,
лицензии, конфликты).

Практическая граница: **свой код — `Loader` (модуль или карта), чужой код —
Composer**. Смешивать (свой код через Composer PSR-4) можно, и это часто
удобно, но тогда надо понимать порядок загрузчиков (B3).

#### B2. Где живёт `composer.json`

| Вариант | Плюсы | Минусы |
|---|---|---|
| `composer.json` в корне документ-рута, `vendor/` там же | «как в обычном PHP» | `/vendor/` и `/composer.json` доступны по HTTP — перечисление зависимостей и чтение исходников; `/vendor/` внутри публичного каталога |
| `/local/composer.json` + `/local/vendor/` | всё в одном месте, `vendor` уже вне шаблонов сайта, легко бэкапить и переносить | `/local/vendor/` всё ещё под документ-рутом — нужен запрет на уровне веб-сервера |
| вне документ-рута (`../composer.json`) | ничего не отдаётся по HTTP | нужно помнить путь; на части хостингов нельзя выйти выше `DOCUMENT_ROOT` |

Что реально надо сделать в любом варианте — запретить отдачу:

```apache
# /local/.htaccess — Apache
<IfModule mod_authz_core.c>
    Require all denied
</IfModule>
```

```nginx
# nginx: .htaccess не читается, правило нужно в конфиге сайта
location ~ ^/local/(vendor|composer\.(json|lock)) {
    deny all;
    return 404;
}
```

Проверка: `curl -I https://site.local/composer.json` и
`curl -I https://site.local/local/vendor/autoload.php` должны давать `403`/`404`,
а не `200`. На nginx отсутствие правила — типовая дыра: файлы на месте и
отдаются.

#### B3. Два загрузчика: кто кого перекрывает

Порядок регистрации в стеке `spl_autoload`:

1. `Loader::autoLoad` — регистрируется в `/bitrix/modules/main/include/autoload.php`
   на этапе 2 пролога;
2. `Composer\Autoload\ClassLoader` — регистрируется, когда вы делаете
   `require .../vendor/autoload.php` в `init.php` (этап 6).

Следствия:

- **Класс ядра подменить Composer-пакетом нельзя.** Для `Bitrix\*` первым
  сработает `Loader`, класс уже объявлен, Composer не вызовется. Это не
  «защита», это порядок — но он спасает от части инцидентов.
- **Класс проекта, объявленный в двух местах, — ошибка проектирования.**
  Победит тот загрузчик, что раньше в стеке; второй станет мёртвым кодом. При
  этом `Fatal: Cannot declare class` случается не «когда-нибудь», а когда оба
  загрузчика всё же сработают: карта отдала файл, а Composer подключил тот же
  класс через `autoload.files` (eager-подключение).
- **`require autoload.php` должен идти до первого использования классов
  проекта в `init.php`.** Если в теле `init.php` выше вызова
  `new MyCompany\Service(...)` — `Class not found`. Регистрация обработчиков
  ниже — не проблема: обработчик выполнится позже.

```php
// /local/php_interface/init.php
use Bitrix\Main\Loader;

$autoload = Loader::getDocumentRoot() . '/local/vendor/autoload.php';
if (is_file($autoload)) {           // без composer install проекта не убиваем
    require_once $autoload;
}
```

`is_file()` здесь не украшение: на чистом деплое без `composer install`
безусловный `require` даёт `Fatal error` до `header.php` — белый экран без
шанса увидеть ошибку в браузере.

В ядре есть `Loader::includeComposerAutoload()` — метод существует
(документирован в API `Bitrix\Main\Loader`), но что именно он сканирует,
зависит от версии ядра: посмотри реализацию в своём
`/bitrix/modules/main/lib/loader.php` (`grep -n includeComposerAutoload`)
перед тем как полагаться на него. Явный `require` в `init.php` предсказуем и
работает на любой версии — поэтому в примерах используется он.

#### B4. Секции `autoload` и их цена

| Тип | Как работает | Когда |
|---|---|---|
| `psr-4` | namespace-префикс → каталог, файл = имя класса, **регистр сохраняется** | свой код, сторонние библиотеки |
| `psr-0` | устаревший, подчёркивания в имени класса → путь | легаси-пакеты |
| `classmap` | скан каталога, карта класс → файл | код без namespace (`C*`, legacy), сторонние SDK |
| `files` | подключается **всегда и сразу**, на каждом запросе | функции, константы; для классов — почти всегда ошибка |

`psr-4` — единственный тип, который решает проблему регистра из A2: файл
`Helpers/StringHelper.php` находится по классу `MyCompany\Helpers\StringHelper`
без приведения к нижнему регистру.

`files` опасен именно в Bitrix: если тот же класс зарегистрирован в карте
`Loader` или лежит в `lib/` модуля, получаем двойное объявление. И ещё: `files`
исполняется на каждом запросе, включая AJAX — туда не кладут ничего, кроме
нескольких функций.

#### B5. Конфликт версий с ядром

Ядро несёт **свои копии** популярных библиотек внутри
`/bitrix/modules/main/vendor/` и регистрирует их namespace:
`Psr\Container`, `Psr\Log`, `Psr\Http\Message`, `Psr\Http\Client`,
`Http\Promise`, `PHPMailer\PHPMailer`, `GeoIp2`, `MaxMind\Db`, `PhpParser`,
`Recurr`.

Так как `Loader` стоит в стеке раньше Composer, пакет `psr/log` из
`composer.json` **не будет использован** — класс `Psr\Log\LoggerInterface`
возьмётся из ядра. Практика:

- не требовать эти пакеты напрямую, если они нужны только как транзитивная
  зависимость — Composer поставит свою копию, она просто не загрузится;
- проверять `composer why psr/log` при странных `Class not found` в
  сторонней библиотеке;
- при обновлении ядра версия встроенной библиотеки меняется — код, завязанный
  на конкретную версию, ломается «сам».

#### B6. Оптимизация и деплой

- `composer dump-autoload` — генерация карты PSR-4 (поиск по префиксам, до
  нескольких `file_exists` на класс).
- `composer dump-autoload -o` (`--optimize`) — карта «класс → файл» из скана
  каталогов: быстрее, но **заморожена**. Добавил класс — в dev-окружении он
  не найдётся, пока не пересоберёшь. Отсюда правило: `-o` на деплое, обычная
  автозагрузка в разработке.
- `-a` (`--classmap-authoritative`) — Composer ищет только в карте и не
  ходит по файловой системе. Классы Bitrix в эту карту не попадают, но это
  безопасно: Composer вернёт «не нашёл», и PHP вызовет следующий загрузчик —
  `Loader`. Выигрыш — на проектах, где Composer-классов много.
- Деплой: `composer.lock` в репозитории; на сервере
  `composer install --no-dev --optimize-autoloader`; `vendor/` в git — на
  усмотрение команды (без него деплой зависит от доступа к Packagist).
- `config.platform.php` в `composer.json` — фиксирует версию PHP для разрешения
  зависимостей, когда локально 8.3, а на коробке 8.1. Без него `composer
  install` на сервере отвалится на `requires php >=8.3`.
- `vendor/composer/*` руками не править: следующий `composer install` затрёт,
  а причина конфликта останется.

#### B7. Box vs Cloud

- **Box:** полный контроль — свой `composer.json`, свой `vendor/`, конфиг
  nginx/Apache, `opcache`, CI.
- **Cloud:** файловая система управляется платформой, `/bitrix/` менять нельзя,
  свои зависимости ставятся в `/local/`; часть настроек веб-сервера
  недоступна — запрет на `/local/vendor/` может быть не вашим решением.
  Проверяй фактическую доступность URL, а не наличие `.htaccess`.

### Практические задачи

Решения — в `examples/module-1-6/`. Каждая папка самодостаточна: файлы для
копирования в `/local/`, страница для проверки и `README.md` с порядком
запуска. Задачи идут по возрастанию: карта → диагностика → модуль → Composer.

#### Задача 1. Helper-класс с автозагрузкой через карту (20–30 мин)

`task-string-helper/`. Класс `MyCompany\Helpers\StringHelper` в
`/local/php_interface/classes/Helpers/` (CamelCase — осознанно, это карта, а не
namespace-префикс), регистрация в `init.php` через
`Loader::registerAutoLoadClasses(null, [...])`, страница с примерами вызовов.

Проверить: страница работает и до, и после подключения `header.php`; карта
содержит ровно одну запись на класс; `php -l` чистый.

#### Задача 2. Диагностика автозагрузки (20–30 мин)

`task-probe/`. Скрипт, который на живой коробке показывает: фактический стек
`spl_autoload_functions()`, путь `Loader::getDocumentRoot()` против
`$_SERVER['DOCUMENT_ROOT']`, резолвинг трёх классов (ядро, модуль, свой),
стоимость промаха (`class_exists` на 1000 несуществующих имён с автозагрузкой
и без неё), и предупреждение про регистр ФС.

Сдать: вывод скрипта и один вывод, сделанный после `var_dump(class_exists(...,
false))` — разница должна быть видна.

#### Задача 3. Свой модуль с `lib/` (40–60 мин)

`task-module/`. Модуль `mycompany.tools`: `local/modules/mycompany.tools/`,
`include.php`, `install/index.php` (DoInstall/DoUninstall), класс
`MyCompany\Tools\StringHelper` в `lib/tools/stringhelper.php` — файл в нижнем
регистре, namespace из двух сегментов совпадает с ID модуля.

Проверить: класс находится **без** регистрации (модульный префикс); после
`Loader::includeModule('mycompany.tools')` модуль виден в
`ModuleManager::isModuleInstalled()`; при `includeModule` = `false` код не
падает, а обрабатывает отсутствие модуля.

#### Задача 4. Composer PSR-4 (30–40 мин)

`task-composer/`. `/local/composer.json` с `psr-4` на `MyCompany\` →
`php_interface/classes/`, подключение `autoload.php` в `init.php` с `is_file()`,
запрет на `/local/vendor/` и `/local/composer.json`, страница проверки того же
`StringHelper`, но уже через Composer.

Проверить: `curl -I` на `composer.json` и `vendor/autoload.php` даёт `403`/`404`;
класс находится с CamelCase-файлом; после `composer dump-autoload -o` и
добавления нового класса старый поиск ломается — увидеть и объяснить.

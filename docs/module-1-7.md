# Модуль 1.7: Application, Context, Request, Response

## Теория

> Подраздел закрыт целиком: блок A — как ядро собирает контекст, чем
> `HttpRequest` отличается от `Request`, откуда брать параметры; блок B —
> как отдаётся ответ и почему `HttpResponse` в обычной странице не виден.
> Детали `Engine\Controller` — модуль 5, здесь только контракт.

### Границы темы

Здесь — объекты, которыми ядро описывает входящий запрос и окружающую его
среду: `Application`, `Context`, `Request`, `HttpRequest`, `Server`. Плюс
дисциплина чтения входных данных: что считать доверенным, что проверять, где
экранировать.

Что здесь **не** разбирается:

| Тема | Где |
|---|---|
| Пролог/эпилог, буферизация, `RestartBuffer`, композит | 1.5 |
| Автозагрузка и `init.php` как точка инициализации | 1.6 |
| `Result`, `Error`, исключения | 1.8 |
| Компоненты и их параметры (`$arParams`) | 1.2 |
| `Engine\Controller`, `ActionFilter`, JSON-экшены — подробно | модуль 5 |
| CSRF/сессии как механизм безопасности — подробно | модуль 7 |
| REST и `Bitrix\Rest` | модуль 8 |

Здесь `check_bitrix_sessid()` и `htmlspecialcharsbx()` — только как часть
контракта «как читать параметр», без разбора их внутренностей.

### A0. Зачем вообще контекст, если есть `$_GET`

Пять проблем суперглобальных массивов, из-за которых ядро завело `Context`:

1. **Неявная зависимость.** Функция, читающая `$_POST['email']` внутри,
   выглядит как `validate(): Result`, но требует конкретного окружения. Юнит-тест
   на неё невозможен без подмены глобалов.
2. **Нет типа.** `$_GET['id']` — это `string`, `array` или «ключа нет».
   Три разных значения в одной переменной.
3. **`$_REQUEST` — сюрприз конфигурации.** Его состав зависит от
   `variables_order` и `request_order` в `php.ini`. На одном сервере там
   GET+POST+Cookie, на другом только GET+POST. Код, читающий `$_REQUEST`,
   меняет поведение от настроек хостинга.
4. **Тело читается один раз и не тем API.** JSON-POST не попадает в `$_POST`
   вообще, а `php://input` для `multipart/form-data` отдаётся пустым.
5. **Нет точки расширения.** Прокси, CLI, агент, тест, подзапрос — у каждого
   свой способ получить «текущий запрос». Без абстракции получается пять
   разных реализаций в одном проекте.

`Context` решает ровно это: один объект на запрос, внутри — снимок входных
данных и ссылки на инфраструктуру (соединение, кеш, сессия, сайт). Не решает:
валидацию (её нет), экранирование (его нет) и права (их нет).

### A1. `Application` — инфраструктурный фасад, а не контейнер

`Bitrix\Main\Application` — синглтон, который создаётся в прологе. Через него
получают доступ к инфраструктуре запроса:

| Метод | Что возвращает | Когда нужен |
|---|---|---|
| `getInstance()` | тот же объект | всегда, вместо `new` |
| `getContext()` | `Bitrix\Main\Context` | запрос, ответ, сессия, сайт |
| `getConnection()` | `Bitrix\Main\DB\Connection` | ORM-запросы, транзакции, `$connection->getSqlHelper()` |
| `getCache()` | `Bitrix\Main\Data\Cache` | кеш на файлах/в `cache`-хранилище |
| `getManagedCache()` | `Bitrix\Main\Data\ManagedCache` | тегированный кеш (`clearByTag`) |
| `getSession()` | сессия | чтение/запись, закрытие сессии |

Чем `Application` **не** является:

- **Не DI-контейнером.** Здесь нет `get('service')` и автовайринга. Сервисы
  передаются аргументами конструктора; `Application` — только инфраструктура.
- **Не `$APPLICATION`.** `$APPLICATION` — глобальный объект `CMain` (страница,
  заголовок, шаблон, `ShowHead()`, `SetTitle()`). `CMain` и `Application` живут
  одновременно и это разные вещи. Проба из практики печатает `CMain ===
  Application` → `false`, чтобы это не оставалось теорией.
- **Не «текущей страницей».** `GetCurPage()` — это `CMain`, а не контекст.

Отдельно: `Application::getInstance()` вызывается в прологе **до**
`/local/php_interface/init.php`. Значит в `init.php` контекст уже есть, а
`$USER` — ещё нет (см. 1.6, A1). Типичная ошибка — строить в `init.php` логику
«если авторизован», получая `false` на каждом запросе.

### A2. `Context` — срез окружения одного запроса

`Context::getCurrent()` — короткий путь, эквивалентный
`Application::getInstance()->getContext()`. Внутри — семь вещей:

| Метод | Класс (в своей версии проверить пробой) | Что это |
|---|---|---|
| `getRequest()` | `Bitrix\Main\HttpRequest` | входные данные текущего запроса |
| `getResponse()` | `Bitrix\Main\HttpResponse` | объект ответа (в обычной странице почти не используется) |
| `getServer()` | `Bitrix\Main\Server` | `$_SERVER` в виде объекта, `ArrayAccess` |
| `getSession()` | `Bitrix\Main\Session\Session` [проверить] | сессия, та же, что в `$_SESSION` |
| `getLanguage()` | `Bitrix\Main\Localization\Language` [проверить] | язык (`LANGUAGE_ID`) |
| `getSite()` | `Bitrix\Main\Site\Site` [проверить] | текущий сайт (`SITE_ID`, `DIR`, `SERVER_NAME`) |
| `getEnvironment()` | `Bitrix\Main\Environment` | значения из `.settings.php` (окружение, не HTTP) |

Практическая ценность последних двух строк: `getEnvironment()` — единственный
штатный способ прочитать настройки из `.settings.php` (`get('exception_handling')`,
`get('crypto')`, `get('session')`) без `include` файла руками. Значения
окружения — не HTTP-данные, и в `Request` их искать бессмысленно.

`Context::getCulture()` (форматы даты/числа) есть не во всех версиях —
проверяется пробой, а не памятью.

### A3. Как ядро собирает контекст и почему это снимок

Порядок, который важен:

1. Пролог (`/bitrix/modules/main/include.php` и далее) поднимает автозагрузку,
   подключает `init.php`.
2. `Application::getInstance()` создаёт единственный экземпляр и **один раз**
   собирает `Context`. Конструктор `HttpRequest` получает массивы `$_SERVER`,
   `$_REQUEST`, `$_GET` [проверить: `main/lib/application.php`, момент вызова].
3. Дальше весь запрос — страница, компоненты, AJAX, агент — работает с этим же
   объектом.

Из «один раз» следуют четыре следствия, которые надо знать наизусть.

**1. Request — снимок, а не окно в `$_GET`.** Массивы переданы по значению
(PHP копирует по записи), поэтому:

```php
// Контекст уже собран прологом.
$_GET['filter'] = 'подмена';          // правка суперглобала
$request->getQuery('filter');         // исходное значение, не «подмена»
```

Обратное тоже верно: фильтр, который «чистит» `$_POST` в обработчике события,
не влияет на `$request->getPost()` — и наоборот. Проба (`task-context-probe`)
показывает это двумя строками вывода, а не обещанием.

**2. `$_REQUEST` — не источник.** Из-за `request_order` состав разный, а
`Request::get()` имеет собственный порядок источников, который тоже деталь
реализации. Читать надо `getQuery()` или `getPost()` — явно и по имени.

**3. Контекст существует и там, где HTTP нет.** Скрипт `php -f`, CLI-команда,
агент — `Context::getCurrent()` вернёт объект, но `getRequestMethod()` будет
пустым, `getQuery()` — всегда `null`, `getServer()` — без HTTP-заголовков.
Код, который на верхнем уровне модуля безусловно дёргает `getHeader()`, в CLI
падает или молча получает `null`.

**4. Память.** Копия `$_POST` на запросе с большой формой — это второй экземпляр
массива в памяти. Не аргумент против `Request`, но аргумент против «прочитать
всё в массив и передать дальше» на больших выгрузках.

### A4. `Request` и `HttpRequest`: где какой

Иерархия простая и её спрашивают:

```
Bitrix\Main\Request            — базовый: query, post, files, cookies, get()
  └─ Bitrix\Main\HttpRequest   — + Server, заголовки, метод, URI, isPost/isAjaxRequest
```

| Возможность | `Request` | `HttpRequest` |
|---|---|---|
| `getQuery()`, `getPost()`, `getFile()`, `getCookie()` | да | да |
| `get()`, `getQueryList()`, `getPostList()` | да | да |
| `getRequestMethod()`, `getRequestUri()`, `isPost()` | зависит от реализации [проверить] | да |
| `getServer()` (объект `Server`) | нет | да |
| `getHeader()` / `getHeaders()` | нет (в базовом) [проверить] | да (`getHeaders()` — в свежих ядрах) |
| `isAjaxRequest()`, `isHttps()` | нет | да в `HttpRequest` [проверить] |

Отсюда правило типизации, которое отличает аккуратный код от «работает у меня»:

- **Валидатор, сервис, доменный код принимают массив или `Request`.** Не
  `HttpRequest`: сервису не нужны заголовки и метод, а в CLI/тесте
  `HttpRequest` не собрать.
- **`HttpRequest` живёт в точке входа**: страница, эндпоинт, контроллер,
  middleware. Там же — проверка метода, CSRF, чтение тела.
- **Если в сигнатуре метода появился `HttpRequest` у класса, который считает
  бизнес-логику, — это сигнал, что слой поехал.**

### A5. Откуда брать параметры

Контракт из четырёх шагов, и он не обсуждается:

1. **Получить** значение по имени из конкретного источника.
2. **Проверить тип** (`is_string`, `is_array`, `filter_var`), а не приводить.
3. **Нормализовать и провалидировать** (trim, lowercase, диапазон, формат).
4. **Использовать.** Экранирование — не здесь, а в контексте вывода.

| Источник | API | Что реально приходит | Ловушка |
|---|---|---|---|
| Query | `$request->getQuery('id')` | `string` \| `array` \| `null` | `?id[]=1` даёт массив; `?id=` — пустая строка, а не `null` |
| Тело формы | `$request->getPost('id')` | то же | `max_input_vars` (по умолчанию 1000) молча обрезает большие формы |
| JSON-POST | `file_get_contents('php://input')` + `Json::decode()` | массив/`null` | в `$_POST` ничего; `check_bitrix_sessid()` не работает |
| Заголовки | `$request->getHeader('X-Foo')` | `string` \| `null` | `Content-Type`/`Content-Length`/`Authorization` приходят без префикса `HTTP_` |
| Cookie | `$request->getCookie('NAME')` | `string` \| `null` | клиент подделывает; значение — сырое, не раскодированное `Web\Cookie` |
| Файлы | `$request->getFile('file')` | структура `$_FILES` | «файла нет» — это `error = 4`, а не пустой `tmp_name` |
| Путь | `$request->getRequestUri()` | `string` | URL-декодирование, `//`, `..`, UTF-8 — разбирать до использования |
| Всё сразу | `$request->get('id')` | что-то из query/post | порядок источников — деталь реализации; не использовать |

Типовые дефекты чтения, каждый из которых реально приводит к багу:

```php
// 1. Приведение вместо проверки: (int)'12abc' === 12, (int)[] === 1
$id = (int)$request->getQuery('id');

// 2. Массив там, где ждали строку: TypeError в mb_strlen()
$q = $request->getQuery('q');          // ?q[]=a

// 3. Точка и пробел в имени параметра превращаются в подчёркивание
//    ?a.b=1  ->  $_GET['a_b'], а getQuery('a.b') вернёт null

// 4. Дубли ключей: ?id=1&id=2 -> последнее значение, без предупреждения
```

Правильный минимум для одного параметра:

```php
$raw = $request->getQuery('id');

if ($raw === null) {
    // параметра нет — это не ошибка формата, а другой сценарий
} elseif (!is_string($raw)) {
    // ?id[]=1 — отказ, а не «первое значение массива»
} else {
    $id = filter_var($raw, FILTER_VALIDATE_INT, ['options' => ['min_range' => 1]]);
    if ($id === false) { /* 400 */ }
}
```

Про `getPostList()`/`getQueryList()`: они возвращают `Bitrix\Main\Type\ParameterDictionary`
[проверить], у которого есть `get($name)` и `toArray()`. Полезно, когда полей
много и нужен весь набор сразу (например, прогон через валидатор).

Отдельно — то, что путают чаще всего: **валидация и экранирование — разные
слои**. `htmlspecialcharsbx()` на входе означает, что в БД лежит `&quot;`, а в
шаблоне значение экранируется второй раз. `strip_tags()` на входе — потеря
данных: пользователь не сможет сохранить текст с `<`, а XSS всё равно
появится в другом контексте (`href`, JS, атрибут).

### A6. Заголовки, тело, файлы

**Заголовки.** `getHeader('X-Requested-With')` — это чтение
`$_SERVER['HTTP_X_REQUESTED_WITH']`. Три исключения из правила:

- `Content-Type` и `Content-Length` PHP кладёт в `$_SERVER` как `CONTENT_TYPE` и
  `CONTENT_LENGTH`, без `HTTP_`. `getHeader('Content-Type')` должен находить
  оба варианта — проверяется пробой, а не верой.
- `Authorization` часто срезается веб-сервером: Apache+CGI/FastCGI требует
  `CGIPassAuth On` или `RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]`,
  nginx — `fastcgi_param HTTP_AUTHORIZATION $http_authorization`. Если
  `getHeader('Authorization')` пуст при живом токене, виноват не Битрикс.
- Заголовки `X-Forwarded-For`/`X-Real-IP` подставляются клиентом. Доверять им
  можно только если запрос пришёл от своего прокси; иначе IP в логах и
  rate-limit — подделка.

`isAjaxRequest()` — удобный признак, но **не** контроль доступа: заголовок
ставит клиент.

**Тело.** JSON не попадает в `$_POST`. Читается так:

```php
$raw = file_get_contents('php://input');
$data = $raw !== '' ? \Bitrix\Main\Web\Json::decode($raw) : null;
```

`Json::decode()` бросает `Bitrix\Main\ArgumentException` на битом JSON (в
отличие от `json_decode()`, который вернёт `null` и оставит причину в
`json_last_error()`). Для эндпоинта это удобнее: одно исключение вместо двух
проверок. Ограничение размера тела — `post_max_size`: при превышении `$_POST`
пуст, а `php://input` может быть пуст тоже, и без проверки `Content-Length`
клиент получит «неверные данные» вместо «слишком большой запрос».

**Файлы.** «Пользователь не выбрал файл» — это `error = UPLOAD_ERR_NO_FILE (4)`,
а не пустой `tmp_name`. Проверять надо `error`, потом `is_uploaded_file()` и
`move_uploaded_file()`; `MAX_FILE_SIZE` из формы — подсказка клиенту, а не
защита.

### A7. Cookie и сессия: где `Request` заканчивается

`getCookie('NAME')` читает `$_COOKIE` как есть. Битрикс умеет подписывать и
шифровать cookie через `Bitrix\Main\Web\Cookie` — если значение клали через
этот класс, читать надо им же, иначе получите закодированную строку.

CSRF-токен:

- `bitrix_sessid()` — текущий `sessid`;
- `bitrix_sessid_post()` — скрытое поле в форме;
- `check_bitrix_sessid()` — проверка, читает `sessid` из `$_GET`/`$_POST`
  **глобалов**, не из `Request`. Поэтому в JSON-эндпоинте она не сработает:
  тело не разобрано в `$_POST`, и `sessid` надо сравнить вручную через
  `hash_equals((string)bitrix_sessid(), $sessid)`.

### A8. `Response`: почему в обычной странице его не видно

`Context::getResponse()` возвращает `Bitrix\Main\HttpResponse`, но классический
поток страницы им не пользуется: `CMain` пишет заголовки через `header()` и
`CHTTP::SetStatus()`, а тело — в выходной буфер (`RestartBuffer`,
`OnEndBufferContent` — см. 1.5). `HttpResponse` реально работает в
D7-контроллерах: экшен возвращает значение, ядро превращает его в ответ
(`Response\Json` и родственные классы [проверить под версию]).

Практический вывод для этой темы: **не смешивать**. Если точка входа —
страница, ответ отдаётся средствами `CMain`; если эндпоинт — явные
`http_response_code()` + `header()` до первого вывода, либо контроллер D7.
Один ответ на запрос, заголовки — до вывода, `exit` — после `FinalActions()`.

### A9. Антипаттерны

| Код | Что не так | Чем заменить |
|---|---|---|
| `$_GET['id']`, `$_POST['x']` в глубине кода | неявная зависимость, нет типа | `getQuery()`/`getPost()` в точке входа, дальше — массив |
| `$_REQUEST['x']` | состав зависит от `php.ini`, cookie-инъекция | `getQuery()` / `getPost()` явно |
| `$request->get('x')` | неясно, откуда значение | явный источник |
| `(int)$request->getQuery('id')` | `'12abc'` → 12, `[]` → 1 | `filter_var(FILTER_VALIDATE_INT)` |
| `htmlspecialchars()` на входе | двойное экранирование, мусор в БД | экранирование в шаблоне |
| `isAjaxRequest()` как проверка прав | заголовок ставит клиент | проверка прав + CSRF на сервере |
| чтение `php://input` внутри метода валидатора | валидатор знает про HTTP | тело читается в точке входа |
| `exit`/`die` в середине эндпоинта | обрывает `FinalActions`, статистику, события | `FinalActions()` затем `exit` |

### A10. Box vs Cloud

- **Box:** контекст, `Request`, свои эндпоинты в `/local/`, доступ к `$_SERVER`
  и заголовкам как есть. Основная масса проблем — настройки веб-сервера
  (`Authorization`, `fastcgi`, `post_max_size`).
- **Cloud (Bitrix24):** файловой системы сайта нет, `/local/` нет, свои
  HTTP-эндпоинты не разворачиваются. Вход — REST и приложения; внутри
  приложения на сервере (если есть свой хостинг) механика та же, что в Box.
  Правки `HttpRequest`/`Context` в облаке недоступны — ни `init.php`, ни
  переопределения.

### A11. Что проверить на своей коробке

Всё, что помечено `[проверить]`, подтверждается одним запуском
`examples/module-1-7/task-context-probe/probe.php`: он печатает реальные классы

## Блок B. Ответ

### B0. Три режима ответа, и они не смешиваются

| Режим | Кто формирует ответ | Инструменты |
|---|---|---|
| Страница с шаблоном | `CMain` + выходной буфер | `SetTitle`, `SetPageProperty`, `AddChainItem`, `CHTTP::SetStatus`, `LocalRedirect` |
| Endpoint без шаблона (`/local/api/*`, `/local/ajax/*`) | точка входа и только она | `http_response_code()`, `header()`, `Json::encode()`, `exit` или `FinalActions()` |
| D7-контроллер (`Engine\Controller`) | ядро по возвращённому значению | возврат массива/`ErrorCollection`/объекта ответа |

Ошибка новичка — смешать: страница печатает HTML до `header()`, эндпоинт
вызывает `$APPLICATION->SetTitle()` (это в пустоту), контроллер пытается
`echo` внутри экшена. Каждый режим отвечает одним способом.

### B1. Заголовки и статус — только до первого вывода

После первого байта тела `header()` и `http_response_code()` молча ничего не
делают: PHP выдаст warning, а клиент получит `200` с телом ошибки. Диагностика:

```php
if (headers_sent($file, $line)) {
    // $file:$line — где именно начался вывод (BOM, пробел до <?php, echo в init.php)
}
```

Отсюда же правило «нет `echo` до конца вычислений» в эндпоинте: сначала
собирается ответ, потом ставится статус, потом печатается тело.

`CHTTP::SetStatus('404 Not Found')` — легаси-путь, но именно он дружит с
шаблоном сайта и `define('ERROR_404', 'Y')` (см. 1.5). В эндпоинте без шаблона
достаточно `http_response_code(404)`.

### B2. Тело ответа: JSON

```php
http_response_code(422);
header('Content-Type: application/json; charset=UTF-8');
header('X-Content-Type-Options: nosniff');
echo \Bitrix\Main\Web\Json::encode(['success' => false, 'errors' => $errors], JSON_UNESCAPED_UNICODE);
exit;
```

Три вещи, которые делают JSON-ответ предсказуемым:

- `Content-Type` с `charset` — иначе браузер и часть клиентов читают тело как
  `text/html`;
- `nosniff` — запрет на «угадывание» типа;
- `Json::encode()` вместо `json_encode()` — согласованная обработка UTF-8 и
  исключений на некорректных данных.

Обратный путь (`Json::decode()` на входе) бросает `Bitrix\Main\ArgumentException`
на битом JSON — это удобнее `json_decode()` + `json_last_error()`.

### B3. Завершение запроса

| Способ | Что делает | Когда |
|---|---|---|
| `exit` / `die` | обрывает всё немедленно | в эндпоинте после явных заголовков и тела |
| `CMain::FinalActions()` | отдаёт буфер и доводит эпилог: статистика, отложенные события, `OnEpilog` | в AJAX-ветке компонента, где ответ собирался через буфер |
| `LocalRedirect()` | ставит `Location` и завершает | редирект, в том числе после POST |

`die()` в середине логики — дефект: письма и события, накопленные в
`b_event`/очередях, не будут обработаны до следующего запроса, а статистика
потеряется. В 1.5 это разобрано по фазам.

### B4. `Engine\Controller` — контракт, без внутренностей

Контроллер D7 (`\Bitrix\Main\Engine\Controller`, интерфейс
`Controllerable`) отличается от эндпоинта тем, что **экшен ничего не печатает и
не ставит заголовки** — он возвращает значение:

```php
use Bitrix\Main\ErrorCollection;

public function saveAction(array $data): array|ErrorCollection
{
    $result = (new RegistrationValidator($data))->validate();

    if (!$result->isSuccess()) {
        // ErrorCollection ядро превратит в {"status":"error","errors":[...]}
        return $result->getErrorCollection();
    }

    return ['success' => true, 'data' => $result->getData()];
}
```

Обрати внимание на сигнатуру: валидатор принимает массив, а не `HttpRequest`.
Экшен — единственное место, где живёт HTTP; дальше данные уже нормализованы.

Практические следствия, которые ломают интеграции:

- **HTTP-код по умолчанию `200` и на ошибку.** Клиент обязан смотреть поле
  `status` в теле, а не код ответа. Если нужен HTTP-статус — это отдельный
  объект ответа, а не голый массив [проверить под версию].
- **CSRF у контроллера свой** — фильтр `ActionFilter\Csrf` [проверить], а не
  `check_bitrix_sessid()` в теле экшена.
- **Request у контроллера — `$this->getRequest()`**; глобалы там не нужны.

Детали (`configureActions()`, префильтры, `ActionFilter`, `Binder`, права) —
модуль 5. Здесь важно одно: **режим ответа выбирается до написания кода**, а не
подбирается по ходу.

### B5. Ошибки в ответе

- Пользователю — код и короткое сообщение; стектрейс, SQL и пути — только в лог
  (`AddMessage2Log()` или `Diag\Logger`).
- `500` — для непредвиденного, `422` — для проваленной валидации, `400` — для
  некорректного запроса, `403` — нет прав/CSRF, `404` — объект не найден **или
  чужой**.
- Тело ошибки не должно подтверждать существование чужого объекта: разные
  ответы на «нет такого» и «не ваш» — утечка.

## Практические задачи

Решения — в `examples/module-1-7/`. Каждая папка самодостаточна: файлы для
копирования в проект и `README.md` с порядком запуска. Задачи идут по
возрастанию: проба → GET → POST-форма → JSON-эндпоинт → контрольное задание.

### Задача 1. Проба контекста (20–30 мин)

`task-context-probe/probe.php` → `/local/tools/context-probe.php`.

Скрипт печатает: классы `Application`/`Context`/`Request`/`Response`/`Server`,
матрицу `method_exists()` для своей версии ядра, доказательство «Request —
снимок», таблицу источников (`getQuery`/`getPost`/`get`), маппинг заголовков,
повторное чтение `php://input`, структуру `getFileList()`.

Запуск — тремя запросами, каждый проверяет своё:

```bash
# 1. query + cookie
curl -s 'http://b24.local/local/tools/context-probe.php?probe_a=1&probe_both=from_query' \
     -b 'probe_cookie=cookie_value'

# 2. тот же URL, но POST: probe_both задан в двух местах
curl -s -X POST -d 'probe_both=from_post&probe_only_post=1' \
     'http://b24.local/local/tools/context-probe.php?probe_a=1&probe_both=from_query'

# 3. JSON-тело + ajax-заголовок
curl -s -X POST -H 'Content-Type: application/json' -H 'X-Requested-With: XMLHttpRequest' \
     -d '{"probe_both":"from_json"}' \
     'http://b24.local/local/tools/context-probe.php'
```

Сдать: вывод всех трёх запросов и три вывода, сделанных по своему выводу:

1. какие методы из матрицы в твоей версии отсутствуют;
2. что вернул `getQuery()` после правки `$_GET` — и почему;
3. какой источник предпочёл `get()` для `probe_both` и почему на это нельзя
   опираться в коде.

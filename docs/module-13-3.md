# Модуль 13.3: Кастомизация воронок и бизнес-процессов

## Теория

Базовая механика роботов, триггеров и custom activity уже разобрана в [7.3](module-7-3.md), [7.4](module-7-4.md), [11.1](module-11-1.md) и [11.2](module-11-2.md). Этот модуль — про то, что из этого складывается на практике: программное управление воронками через REST, собственный робот (не activity — это разные сущности), управление уже запущенными экземплярами бизнес-процессов и типичные ловушки, в которые попадают даже опытные разработчики.

### Воронки через REST: `crm.dealcategory.*`

Воронка (категория сделок) создаётся и управляется не только руками в интерфейсе, но и программно — это нужно, например, при автоматическом онбординге нового направления бизнеса или при миграции данных.

```php
// Создать новую воронку
$category = CRest::call('crm.dealcategory.add', [
    'fields' => ['NAME' => 'Оптовые продажи'],
]);
$categoryId = $category['result']['CATEGORY_ID'];

// Стадии создаются отдельно, через crm.dealcategory.stage.add —
// пустая воронка по умолчанию получает только служебные "Новая" и "Успешно"/"Провалено"
CRest::call('crm.dealcategory.stage.add', [
    'fields' => [
        'ENTITY_ID' => 'DEAL_STAGE_' . $categoryId,  // особенность: ID статусной сущности = DEAL_STAGE_<ID воронки>
        'NAME' => 'Согласование цены',
        'SORT' => 20,
    ],
]);
```

**Частая ловушка:** поле `ENTITY_ID` для стадий — не просто `CATEGORY_ID`, а строка `DEAL_STAGE_<ID>` (для воронки по умолчанию, `CATEGORY_ID = 0`, это будет `DEAL_STAGE`, без суффикса). Перепутать это — классическая ошибка, из-за которой стадия создаётся "в никуда".

### Перенос сделки между воронками программно

```php
function moveDealToCategory(string $accessToken, int $dealId, int $targetCategoryId, string $targetStageId): void
{
    // Нельзя просто поменять CATEGORY_ID — STAGE_ID из старой воронки
    // не существует в новой и Bitrix24 либо откажет, либо сделка "потеряется"
    // на несуществующей стадии. Менять нужно оба поля одним вызовом.
    CRest::call('crm.deal.update', [
        'id' => $dealId,
        'fields' => [
            'CATEGORY_ID' => $targetCategoryId,
            'STAGE_ID' => $targetStageId,
        ],
    ]);
}
```

Это же является ответом на частый вопрос собеседования: "почему при автоматическом переносе сделки в другую воронку она пропадает из канбана?" — потому что `STAGE_ID` остался от старой воронки и не соответствует ни одной стадии новой.

### Семантические статусы vs конкретные ID стадий

Жёстко прописывать `STAGE_ID = 'C2:NEW'` в коде робота или обработчика — хрупко: пользователь переименует/удалит/добавит стадию в интерфейсе, и строковый ID (который генерируется автоматически при создании, например `C2:UC_8X3F2A`) перестанет существовать, а код продолжит ссылаться на несуществующую стадию.

Вместо этого Bitrix24 даёт **семантику** стадии — `SEMANTICS` (`P` — в работе, `S` — успешно завершена, `F` — провалена):

```php
$stages = CRest::call('crm.dealcategory.stage.list', ['id' => $categoryId]);

foreach ($stages['result'] as $stage) {
    if ($stage['SEMANTICS'] === 'S') {
        $successStageId = $stage['STATUS_ID']; // независимо от того, как стадия называется и переименована ли она
        break;
    }
}
```

На собеседовании это маркер понимания темы на уровень выше "я вызывал REST": код, который ищет стадию по `SEMANTICS`, не ломается при переименовании или добавлении новых промежуточных стадий пользователем воронки — а код с захардкоженным `STAGE_ID` ломается.

### Собственный робот vs собственное activity — в чём разница

Оба регистрируются через REST, но решают разные задачи и у них разный контракт:

| | Custom Activity (`bizproc.activity.add`) | Custom Robot (`bizproc.robot.add`) |
|---|---|---|
| Где доступен | Только в конструкторе бизнес-процессов (полный БП с ветвлением) | В простом автоматическом действии на стадии канбана ("роботы") |
| Набор параметров | Сложные (`PROPERTIES` с типами, условные поля) | Упрощённый список полей, без ветвления внутри самого робота |
| Возврат результата | Может возвращать значения для использования в последующих шагах БП | Просто завершает выполнение (успех/ошибка), без output-переменных для БП |
| Сложность разработки | Выше — нужно продумывать `ReturnProperties`, диалоговые окна настроек | Ниже — обычно подходит для простых "выполнить действие и всё" |

```php
// Регистрация простого робота — например, "Перевести сделку в другую воронку"
CRest::call('bizproc.robot.add', [
    'CODE' => 'move_to_category',
    'HANDLER' => 'https://yourapp.example.com/robot-handler.php',
    'AUTH_USER_ID' => 1,
    'USE_SUBSCRIPTION' => 'Y', // обязательное поле для роботов из REST-приложений
    'NAME' => 'Перевести в воронку "Оптовые продажи"',
    'CODE' => 'move_to_wholesale',
    'PROPERTIES' => [
        'target_category' => [
            'Name' => 'ID целевой воронки',
            'Type' => 'int',
            'Required' => 'Y',
        ],
    ],
]);
```

Когда Bitrix24 доходит до этого робота на стадии, он отправляет POST-запрос на `HANDLER` с данными сделки и значениями `PROPERTIES` — обработка идентична обработчику custom activity из [11.1](module-11-1.md), но контракт ответа проще.

### Управление уже запущенными экземплярами БП

Изменение шаблона бизнес-процесса в конструкторе **не затрагивает** уже выполняющиеся экземпляры — они продолжают работать по снимку схемы, который был на момент их запуска. Это частый источник путаницы: "я поправил шаг в БП, а старые заявки всё равно идут по старой логике".

```php
// Список выполняющихся экземпляров конкретного шаблона — для диагностики
$instances = CRest::call('bizproc.workflow.instances', [
    'filter' => ['TEMPLATE_ID' => $templateId],
]);

// Принудительное завершение зависшего экземпляра (например, из-за упавшего
// custom activity, который не прислал bizproc.event.send с результатом)
CRest::call('bizproc.workflow.kill', ['id' => $workflowInstanceId]);

// История выполнения конкретного экземпляра — какие шаги пройдены,
// на каком шаге сейчас стоит, какие были ошибки
$log = CRest::call('bizproc.workflow.log', ['id' => $workflowInstanceId]);
```

Отсюда вытекает практика: при значимом изменении логики БП (не косметика, а смена набора шагов) — не редактировать существующий шаблон "на горячую", а создавать новую версию и переключать на неё новые сделки, дав старым экземплярам доработать на прежней схеме. Иначе можно получить зависшие процессы, которые ссылаются на удалённый из схемы шаг.

### Кастомизация через условия на роботах (без написания кода)

Не каждая кастомизация требует REST-разработки. Встроенные роботы поддерживают **условия запуска** — это первое, что стоит предложить на вопрос "как сделать Х" на уровне middle: иногда достаточно штатных средств.

```php
// Добавление робота "Изменить стадию" с условием через REST
// (то же самое можно сделать руками в конструкторе, здесь — для массовой настройки)
CRest::call('crm.automation.rule.add', [
    'entityTypeId' => 2, // сделки
    'categoryId' => $categoryId,
    'rule' => [
        'name' => 'bizproc.activity.crm.changestate',
        'parameters' => [
            'TARGET_STATUS_ID' => $targetStageId,
        ],
        'condition' => [
            'condition-item' => [
                'field' => 'OPPORTUNITY',
                'logic' => 'greaterOrEquals',
                'value' => 1000000,
            ],
        ],
    ],
]);
```

### Частые ошибки

- **Хардкод `STAGE_ID`/`STATUS_ID`** вместо поиска по `SEMANTICS` — ломается, когда пользователь переименовывает или перестраивает воронку.
- **Смена `CATEGORY_ID` без одновременной смены `STAGE_ID`** — сделка "теряется" в новой воронке на несуществующей стадии.
- **Путаница `ENTITY_ID` для стадий** (`DEAL_STAGE_<ID>` вместо просто `<ID>`) при программном создании воронки.
- **Редактирование шаблона БП "на горячую"** при изменении набора шагов — уже запущенные экземпляры могут сослаться на удалённый шаг и зависнуть.
- **Регистрация custom activity вместо робота** (или наоборот) не по задаче, а "как привычнее" — activity избыточно сложна для простого действия на стадии, а робот не подходит, если нужно ветвление и работа с переменными БП.
- **Отсутствие `bizproc.workflow.kill`-санации зависших процессов** — если custom activity по какой-то причине никогда не присылает `bizproc.event.send`, экземпляр БП висит "В работе" бесконечно, засоряя статистику и(или) блокируя повторный запуск БП для той же сделки, если шаблон не allow-параллелен.

## Вопросы для собеседования

**1. Почему нельзя просто изменить `CATEGORY_ID` сделки через REST без изменения `STAGE_ID`?**
`STAGE_ID` — строка вида `C<ID воронки>:<код>`, специфичная для конкретной воронки. После смены `CATEGORY_ID` старый `STAGE_ID` не существует в новой воронке, и сделка оказывается на несуществующей стадии — обычно это выглядит как "сделка пропала из канбана".

**2. Как написать код, который находит "финальную успешную" стадию воронки, не завязываясь на конкретный `STAGE_ID`?**
Запросить стадии воронки через `crm.dealcategory.stage.list` и искать стадию с `SEMANTICS = 'S'` (успешно завершена) — это не меняется при переименовании стадий пользователем, в отличие от жёстко прописанного `STAGE_ID`.

**3. В чём принципиальная разница между custom activity и custom robot на уровне контракта разработки?**
Activity предназначена для полноценного конструктора БП — поддерживает ветвление, возвращаемые значения (`ReturnProperties`) для использования на следующих шагах. Робот — для простой автоматизации на стадии канбана, без вывода переменных для последующих шагов и без ветвления внутри себя.

**4. Что происходит с уже запущенными экземплярами бизнес-процесса, если изменить шаблон в конструкторе?**
Ничего — уже выполняющиеся экземпляры продолжают работать по снимку схемы на момент своего запуска. Изменения применяются только к новым запускаемым экземплярам. При значимых изменениях шаблона (не косметических) практика — создавать новую версию БП, а не редактировать старую "на горячую".

**5. Как диагностировать "зависший" бизнес-процесс, который не двигается по шагам?**
`bizproc.workflow.instances` с фильтром по `TEMPLATE_ID` для списка выполняющихся экземпляров, `bizproc.workflow.log` для истории конкретного экземпляра (какие шаги пройдены, на каком стоит). Частая причина зависания — custom activity, которая так и не прислала `bizproc.event.send` с результатом выполнения.

**6. Нужно ли всегда писать custom activity/робот для кастомизации воронки, или есть более простой путь?**
Не всегда — встроенные роботы поддерживают условия запуска (`crm.automation.rule.add` с `condition`), и значительную часть "если сумма сделки больше X — сделать Y" можно настроить штатными средствами без разработки.

# Модуль 6.3: Code Review примеры (уровень senior)

## Теория

### Что такое «code review» на собеседовании

Интервьюер показывает кусок кода (50–150 строк) и просит:
- «Что здесь не так?»
- «Как бы ты это переписал?»
- «На что обратил бы внимание при ревью?»

Это проверка не только знания API, но и *чувства кодового запаха* — умение увидеть проблему, которую автор не заметил.

### Три уровня ревью

| Уровень | Что смотрим | Пример |
|---------|-------------|--------|
| **Баги** | Не работает, сломается на проде | N+1, SQL-инъекция, race condition |
| **Производительность** | Работает, но медленно | fetchAll на 50К, кеш без TTL, запросы в цикле |
| **Архитектура** | Работает, но не масштабируется | Бизнес-логика в шаблоне, нет идемпотентности, нет абстракции |

Senior ревьюит все три уровня, не только «работает ли». Мидл говорит «выглядит ок» если код запускается.

### Методология ревью

1. **Прочитай как пользователь** — что этот код *должен* делать? (не как программист — как человек, который не писал этот код).
2. **Найди входные точки** — `$_REQUEST`, `$_GET`, `$_POST`, `$arParams`, `$arResult`.
3. **Проследи данные** — где они валидируются? где могут быть инъекцией?
4. **Найди циклы и запросы** — N+1, `fetchAll`, вложенные `foreach` с БД.
5. **Найди сохранение** — `save()`, `Add()`, `Update()` — проверь транзакции, события, idempotency.
6. **Найди кеш** — есть ли TTL, теги, инвалидация?
7. **Найди права** — `IsAuthorized`, `GetID`, владелец, группы.

### Чек-лист для ревью Bitrix-кода

```
□  Входные данные: экранированы? приведены к типу? валидированы?
□  SQL: есть ли конкатенация? подготовленные выражения?
□  Циклы: есть ли запросы внутри foreach/while?
□  Память: fetchAll на больших данных? генераторы для >10К?
□  Кеш: TTL? теги? что при инвалидеции?
□  События: save() внутри события? рекурсия?
□  Транзакции: несколько пишущих операций? атомарность?
□  Права: проверка владельца? IsAuthorized? sessid?
□  Ошибки: try/catch? Result? silent fail?
□  Логирование: можно ли понять, что упало, через час?
```

### Типичные находки в Bitrix-коде

#### Баги

- `Order::load($_GET['id'])` без проверки `USER_ID` → IDOR.
- `$_REQUEST['email']` → `setField('EMAIL', ...)` без `checkEmail()` → инвалидный email в заказе.
- `OnSaleOrderSaved` → `Order::save()` → рекурсия.
- `if (!$order)` после `load()` — правильно. `if ($order === false)` — неправильно, `load` возвращает `null`.

#### Производительность

- `foreach` + `getList` внутри → N+1.
- `fetchAll()` на таблице с 100К строк → memory limit.
- Кеш `TTL=0` или `TTL=31536000` без тегов → устаревание навсегда.
- `while($row = $result->fetch()) { Order::load($row['ID']) }` — load всего объекта для вывода одного поля.

#### Архитектура

- Бизнес-логика в `template.php` — пересчёт скидок, проверка прав.
- Нет разделения на слои: компонент + сервис + репозиторий смешаны.
- Нет идемпотентности: двойной клик = два заказа.
- Нет мониторинга: `try { ... } catch (Exception $e) { }` — silent fail.

---

### Формула ответа при ревью

> «Первое — [критичный баг], потому что [сценарий]. Второе — [производительность]. Третье — [архитектура]. Как перепишу: [вариант]. Что проверю: [метрика/тест].»

Не «всё плохо», не «всё хорошо» — конкретные пункты с обоснованием.

## Вопросы для собеседования

1. **Что проверяешь в первую очередь в API-эндпоинте?** — входные данные (экранирование, тип, диапазон), права (владелец, sessid), идемпотентность.
2. **Как проверить, нет ли N+1, не запуская код?** — ищем `foreach`/`while` с `load()`/`getList()`/`query()` внутри.
3. **Что опасного в `fetchAll()`?** — память. На 10К записей — OOM. Альтернатива: `while(fetch)` или `fetchObject()` с фильтрацией.
4. **Почему `if ($order)` после `load()` — правильно, а `if ($order === false)` — нет?** — `load` возвращает `Order|null`, не `false`. Проверка `=== false` пропустит `null`.
5. **Что такое «business logic in template» и почему это плохо?** — шаблон должен только рендерить. Логика в шаблоне = не тестируема, дублируется, ломается при смене шаблона.

## Частые ошибки в ревью

- **«Всё ок, если работает»** — ревью не только на баги, но и на поддерживаемость.
- **«Переписал бы всё»** — ревью не для переписывания, а для минимальных безопасных изменений.
- **«Это стилистика»** — в проде стилистика (имя переменной) — не баг, но несоответствие PSR/стандарту проекта — замечание.
- **Не назвать приоритет** — «критичный баг» vs «незначительное улучшение» — разные вещи.

## Практические задачи

- **Задача 1:** `component-review` — разбор плохого компонента списка заказов: N+1, IDOR, логика в шаблоне.
- **Задача 2:** `api-handler-review` — разбор плохого REST-эндпоинта: SQL-инъекция, отсутствие идемпотентности, silent fail.
- **Задача 3:** `integration-review` — разбор плохой интеграции с внешним API: нет таймаута, нет retry, нет circuit breaker.

## 1. Что такое 1С-Битрикс и Bitrix Framework

### 1.1. Основные понятия

1С-Битрикс: Управление сайтом — CMS, построенная на Bitrix Framework. Она предоставляет готовые механизмы для создания и управления сайтами:

- управление контентом;
- пользователи и группы;
- права доступа;
- инфоблоки;
- интернет-магазин;
- поиск;
- кеширование;
- административная панель;
- система компонентов и модулей.

Bitrix Framework — PHP-фреймворк и набор инфраструктурных механизмов, на которых построена CMS. Он включает систему модулей, API ядра, компоненты, события, механизмы работы с данными, кеширование и другие инструменты.

Важно различать три понятия:

| Понятие                       | Что означает                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| Bitrix Framework              | Программная платформа и API                                                          |
| 1С-Битрикс: Управление сайтом | CMS, использующая Framework                                                          |
| Bitrix24                      | Отдельный продукт для CRM, совместной работы и автоматизации; существует Cloud и Box |

Bitrix24 Box использует собственную серверную инфраструктуру и API Bitrix, но не следует автоматически считать, что все механизмы и API CMS доступны в нём одинаково.

### 1.2. Основные особенности Bitrix Framework

- Модульная архитектура: функциональность распределена по модулям.
- Компонентная архитектура: повторно используемые блоки интерфейса.
- Событийная модель: возможность реагировать на события ядра и модулей.
- API для работы с данными: ORM D7, инфоблоки, пользователи, заказы и другие сущности.
- Механизмы кеширования и оптимизации.
- Поддержка обратной совместимости со старым API.

Практический вывод: разработчик Bitrix должен понимать не только PHP, но и правила работы платформы. Код, который корректен с точки зрения PHP, необязательно корректен с точки зрения Bitrix.

## 2. D7: что это и зачем появилось

### 2.1. Определение D7

D7 — новое поколение API ядра Bitrix, которое постепенно внедрялось начиная с версии 14.0.0.

D7 — это не отдельный фреймворк и не обозначение версии PHP. Это набор новых API и архитектурных подходов, которые развивают и во многих областях заменяют старые механизмы.

D7 предоставляет:

- пространства имён (`namespace`);
- классы и статические методы;
- автозагрузку классов;
- ORM;
- сервисы приложения;
- объектные механизмы работы с запросами и контекстом;
- новую систему событий в соответствующих частях ядра.

### 2.2. Старое API и D7

В Bitrix до сих пор сосуществуют старое API и D7. Нельзя утверждать, что старое API полностью удалено или что все старые классы имеют прямую замену в D7.

Пример:

Старый подход:

```
<?php

$filter = [
    'ACTIVE' => 'Y',
];

$res = CIBlockElement::GetList(
    [],
    $filter,
    false,
    false,
    ['ID', 'NAME']
);

while ($element = $res->Fetch()) {
    echo $element['NAME'];
}
```

Современный подход с ORM:

```
<?php

use Bitrix\Iblock\Elements\ElementNewsTable;

$result = ElementNewsTable::getList([
    'select' => ['ID', 'NAME'],
    'filter' => [
        '=ACTIVE' => 'Y',
    ],
]);

while ($element = $result->fetch()) {
    echo $element['NAME'];
}
```

Второй пример предполагает, что для инфоблока существует соответствующий ORM-класс и правильно настроена его связь с инфоблоком.

Необходимо понимать:

- `CIBlockElement` — старый API инфоблоков.
- `ElementNewsTable` — ORM-класс, который может быть сгенерирован для конкретного инфоблока.
- Не каждый старый API имеет универсальную D7-замену.
- В реальном проекте выбор API зависит от задачи, версии ядра и доступных механизмов.

### 2.3. Преимущества D7

| Возможность  | Практическая польза                                |
| ------------ | -------------------------------------------------- |
| Namespace    | Удобная организация классов                        |
| Autoload     | Автоматическое подключение классов                 |
| ORM          | Работа с таблицами через объектную модель          |
| Result       | Стандартизированная обработка результатов операций |
| EventManager | Работа с событиями через современный API           |
| Application  | Доступ к сервисам приложения                       |
| Context      | Работа с контекстом выполнения                     |

Важно: D7 не означает полную совместимость с PSR и не гарантирует, что каждый API ядра использует одинаковые архитектурные принципы. Нужно ориентироваться на документацию конкретного класса и метода.

## 3. Структура проекта Bitrix

### 3.1. Основные директории

Типичная структура проекта:

```
/project
│
├── bitrix/
│   ├── admin/
│   ├── components/
│   ├── modules/
│   ├── php_interface/
│   ├── templates/
│   └── ...
│
├── local/
│   ├── components/
│   ├── modules/
│   ├── php_interface/
│   ├── templates/
│   ├── include/
│   └── ...
│
├── upload/
├── index.php
├── .htaccess
└── ...
```

Назначение основных директорий:

| Директория              | Назначение                                  |
| ----------------------- | ------------------------------------------- |
| `/bitrix/`              | Файлы ядра и поставляемых модулей           |
| `/local/`               | Пользовательская разработка и расширения    |
| `/upload/`              | Загруженные файлы                           |
| `/bitrix/modules/`      | Модули системы                              |
| `/bitrix/components/`   | Стандартные компоненты                      |
| `/local/components/`    | Пользовательские компоненты                 |
| `/local/modules/`       | Пользовательские модули                     |
| `/local/templates/`     | Шаблоны сайта                               |
| `/local/php_interface/` | Пользовательская конфигурация и обработчики |

### 3.2. Почему пользовательский код размещают в `/local/`

Главное правило: не изменять файлы ядра без крайней необходимости.

Если разработчик изменяет файлы внутри `/bitrix/`, обновление платформы может перезаписать его изменения.

Для собственного кода предназначена директория `/local/`.

Пример:

```
/local/
├── components/
│   └── company/
│       └── news.list/
│
├── modules/
│   └── company.integration/
│
├── php_interface/
│   ├── init.php
│   └── include/
│       ├── events.php
│       └── helpers.php
│
└── templates/
    └── company/
```

При этом `/local/` — не универсальный механизм переопределения любого файла. Приоритет пользовательских файлов зависит от конкретного механизма поиска и подключения в Bitrix.

### 3.3. `/local/` и `/bitrix/`: что важно помнить

1. Код проекта по возможности размещаем в `/local/`.
2. Файлы ядра не редактируем.
3. Пользовательские компоненты и модули размещаем в соответствующих директориях `/local/`.
4. Переопределение стандартного поведения выполняем предусмотренными платформой механизмами.
5. После обновления ядра проверяем совместимость пользовательского кода.

Вопрос на собеседовании: почему нельзя просто изменить стандартный компонент в `/bitrix/components/`?

Ответ: изменение ядра или поставляемого компонента может быть потеряно при обновлении. Лучше использовать копирование компонента в `/local/components/` и поддерживаемые механизмы переопределения.

## 4. Модульная архитектура

### 4.1. Что такое модуль

Модуль — логически самостоятельная часть платформы, которая предоставляет определённую функциональность.

Примеры стандартных модулей:

| Модуль          | Назначение                             |
| --------------- | -------------------------------------- |
| `main`          | Базовая инфраструктура ядра            |
| `iblock`        | Инфоблоки                              |
| `catalog`       | Каталог товаров                        |
| `sale`          | Интернет-магазин и заказы              |
| `crm`           | CRM в соответствующих продуктах Bitrix |
| `highloadblock` | Highload-блоки                         |

Модуль может содержать:

- PHP-классы;
- ORM-сущности;
- обработчики событий;
- административные страницы;
- языковые файлы;
- установщик;
- файлы конфигурации.

### 4.2. Подключение модуля

Для подключения модуля используется:

```
<?php

use Bitrix\Main\Loader;

if (!Loader::includeModule('iblock')) {
    throw new RuntimeException(
        'Модуль iblock не установлен или недоступен'
    );
}
```

Метод `Loader::includeModule()`:

1. Проверяет доступность модуля.
2. Подключает его необходимые файлы.
3. Обеспечивает доступ к его API.

Возвращает `true` или `false`.

Важный момент: подключение модуля не означает, что конкретный метод или класс доступен в любой версии ядра. Нужно учитывать версию платформы.

### 4.3. Проверка доступности класса

Для работы с классами D7 используется автозагрузка. В стандартном случае не нужно вручную подключать PHP-файл класса через `require`.

```
<?php

use Bitrix\Main\Loader;
use Bitrix\Main\Application;

if (!Loader::includeModule('main')) {
    throw new RuntimeException('Модуль main недоступен');
}

$request = Application::getInstance()
    ->getContext()
    ->getRequest();
```

В большинстве штатных сценариев `main` уже загружен к моменту выполнения пользовательского кода, поэтому повторная проверка обычно не нужна. Пример показывает связь основных классов.

## 5. Автозагрузка классов и пространства имён

### 5.1. Что такое namespace

Пространства имён позволяют организовывать классы и избегать конфликтов имён.

Например:

```
<?php

namespace Company\Integration;

class ApiClient
{
    public function send(): void
    {
        // Логика отправки запроса
    }
}
```

Использование:

```
<?php

use Company\Integration\ApiClient;

$client = new ApiClient();
$client->send();
```

Полное имя класса:

```
Company\Integration\ApiClient
```

### 5.2. Автозагрузка в Bitrix

Автозагрузка позволяет PHP находить и подключать файл класса при первом обращении к нему.

В Bitrix D7 для этого предусмотрен `Bitrix\Main\Loader`.

Пример регистрации собственного класса:

```
<?php

use Bitrix\Main\Loader;

Loader::registerAutoLoadClasses(
    null,
    [
        'Company\\Tools\\StringHelper' =>
            '/local/php_interface/lib/StringHelper.php',
    ]
);
```

Файл:

```
<?php

namespace Company\Tools;

class StringHelper
{
    public static function normalize(string $value): string
    {
        return trim($value);
    }
}
```

Использование:

```
<?php

use Company\Tools\StringHelper;

$value = StringHelper::normalize('  Bitrix  ');
```

Здесь:

- `registerAutoLoadClasses()` регистрирует соответствие имени класса и пути к файлу;
- `null` означает регистрацию без привязки к конкретному модулю;
- класс подключается автоматически при обращении к нему.

В современных проектах также может использоваться Composer с PSR-4. Это отдельный механизм автозагрузки, который можно применять совместно с Bitrix, если проект правильно настроен.

Не путай:

- `namespace` — логическая область имён;
- `use` — импорт имени класса или пространства имён;
- `autoload` — механизм загрузки файла класса;
- `require/include` — непосредственное подключение PHP-файла.

## 6. Файл `init.php`

### 6.1. Назначение

`init.php` — специальная точка подключения пользовательского PHP-кода при инициализации Bitrix.

Обычно пользовательский файл находится здесь:

```
/local/php_interface/init.php
```

В нём часто регистрируют:

- обработчики событий;
- подключение небольших конфигурационных файлов;
- регистрацию собственных автозагрузчиков;
- начальную настройку пользовательского кода.

Пример:

```
<?php

require_once __DIR__ . '/include/events.php';
require_once __DIR__ . '/include/autoload.php';
```

А в `events.php`:

```
<?php

use Bitrix\Main\EventManager;

$eventManager = EventManager::getInstance();

// Регистрация обработчиков событий
```

### 6.2. Что не следует делать в `init.php`

Не нужно превращать `init.php` в файл, содержащий всю бизнес-логику проекта.

Плохие практики:

- выполнять тяжёлые SQL-запросы на каждом запросе;
- отправлять HTTP-запросы к сторонним API;
- выполнять длительные циклы;
- создавать сложные сервисы непосредственно в файле инициализации;
- хранить весь код проекта в одном файле.

Хорошая практика — использовать `init.php` как точку регистрации и подключения.

### 6.3. Важная особенность

В типовой конфигурации Bitrix используется один пользовательский `init.php` — в `/local/php_interface/` либо в `/bitrix/php_interface/`.

Если существует `/local/php_interface/init.php`, он используется вместо стандартного пользовательского файла `/bitrix/php_interface/init.php`, а не автоматически дополняет его.

Поэтому при переносе проекта важно проверить, где находится фактически используемый файл и какие подключения в нём присутствуют.

## 7. Жизненный цикл HTTP-запроса

Это одна из важнейших тем для понимания архитектуры Bitrix.

### 7.1. Общая схема

## Жизненный цикл запроса

1. HTTP-запрос

   Браузер отправляет запрос на сервер.
2. Веб-сервер

   Nginx или Apache передаёт выполнение PHP.
3. Точка входа

   Выполняется `index.php` или другой PHP-скрипт.
4. Пролог Bitrix

   Инициализируется ядро, загружаются необходимые части окружения, подключается пользовательская инициализация.
5. Обработка запроса

   Выполняется код страницы, компоненты, контроллеры или другие обработчики.
6. Формирование ответа

   Формируется HTML, JSON или другой ответ.
7. Завершение

   Выполняются завершающие действия и отправляется HTTP-ответ клиенту.

Это упрощённая схема. Реальный порядок зависит от точки входа, типа запроса, режима работы и используемых механизмов ядра.

### 7.2. Пролог и эпилог

В Bitrix существуют механизмы подключения пролога и эпилога.

Типичный шаблон страницы:

```
<?php

require($_SERVER['DOCUMENT_ROOT'] . '/bitrix/header.php');

$APPLICATION->SetTitle('Моя страница');

?>

<h1>Содержимое страницы</h1>

<?php

require($_SERVER['DOCUMENT_ROOT'] . '/bitrix/footer.php');
```

`header.php` подключает пролог и начинает формирование страницы.

`footer.php` подключает эпилог и завершает её формирование.

Внутри пролога инициализируется окружение Bitrix, в том числе выполняются предусмотренные системой пользовательские подключения.

Не следует путать подключение `header.php` с обычным подключением HTML-шапки: это часть механизма жизненного цикла страницы.

### 7.3. Глобальный объект `$APPLICATION`

В классическом сценарии работы сайта доступен глобальный объект `$APPLICATION`.

Он предоставляет методы для управления параметрами страницы, например:

```
<?php

$APPLICATION->SetTitle('Каталог');
```

В D7 есть и современные способы доступа к сервисам ядра, но глобальный `$APPLICATION` продолжает использоваться в проектах Bitrix.

## 8. Application, Context, Request и Response

Эти классы — основа работы с окружением приложения в D7.

### 8.1. Application

Класс:

```
Bitrix\Main\Application
```

Представляет приложение и предоставляет доступ к основным сервисам.

Получение экземпляра:

```
<?php

use Bitrix\Main\Application;

$application = Application::getInstance();
```

Пример получения контекста:

```
<?php

$context = Application::getInstance()->getContext();
```

Важно: `Application` — не контейнер DI в полном смысле слова и не замена архитектурному слою приложения. Это инфраструктурный объект ядра.

### 8.2. Context

Класс:

```
Bitrix\Main\Context
```

Контекст содержит информацию о текущем выполнении приложения.

Через него можно получить:

- Request;
- Response;
- Server;
- информацию о текущем окружении.

Пример:

```
<?php

use Bitrix\Main\Application;

$context = Application::getInstance()->getContext();

$request = $context->getRequest();
$response = $context->getResponse();
$server = $context->getServer();
```

### 8.3. Request

Класс:

```
Bitrix\Main\HttpRequest
```

Представляет HTTP-запрос.

Пример получения параметров:

```
<?php

use Bitrix\Main\Application;

$request = Application::getInstance()
    ->getContext()
    ->getRequest();

$search = $request->getQuery('search');
```

Для POST:

```
<?php

$name = $request->getPost('name');
```

Для метода запроса:

```
<?php

$method = $request->getRequestMethod();
```

Для проверки AJAX-запроса:

```
<?php

$isAjax = $request->isAjaxRequest();
```

Важное правило безопасности: Request только предоставляет входные данные. Сам по себе он не гарантирует, что данные валидны, безопасны или соответствуют бизнес-правилам.

### 8.4. Валидация входных данных

Нельзя считать данные безопасными только потому, что они получены через `getQuery()` или `getPost()`.

Пример:

```
<?php

$rawId = $request->getQuery('id');

$id = filter_var(
    $rawId,
    FILTER_VALIDATE_INT,
    [
        'options' => [
            'min_range' => 1,
        ],
    ]
);

if ($id === false) {
    throw new InvalidArgumentException('Некорректный ID');
}
```

Нужно различать три операции:

| Операция      | Назначение                               |
| ------------- | ---------------------------------------- |
| Валидация     | Проверка соответствия формату и правилам |
| Нормализация  | Приведение к ожидаемому виду             |
| Экранирование | Безопасный вывод в конкретный контекст   |

Не нужно пытаться «очистить от XSS» все данные на входе. Экранирование выполняется при выводе в зависимости от контекста: HTML, HTML-атрибут, JavaScript, URL и так далее.

### 8.5. Response

Класс:

```
Bitrix\Main\HttpResponse
```

Представляет HTTP-ответ.

Пример:

```
<?php

use Bitrix\Main\Application;

$response = Application::getInstance()
    ->getContext()
    ->getResponse();

$response->setStatus(200);
$response->addHeader('Content-Type', 'text/plain; charset=UTF-8');
$response->setContent('OK');
$response->send();
```

Этот пример демонстрирует базовый API ответа. В реальном проекте необходимо учитывать, кто управляет отправкой ответа, не отправлять его повторно и корректно завершать выполнение сценария.

Для JSON-ответа:

```
<?php

use Bitrix\Main\Web\Json;

$data = [
    'success' => true,
    'message' => 'Операция выполнена',
];

$json = Json::encode($data);
```

Кодирование данных в JSON — ещё не полноценный HTTP-ответ. Необходимо также корректно установить Content-Type и статус ответа.

## 9. Result и Exception: обработка ошибок

### 9.1. Зачем нужны Result

В D7 многие операции возвращают объект `Bitrix\Main\Result` или его наследника.

Это позволяет передавать результат выполнения вместе с информацией об ошибках.

Пример:

```
<?php

use Bitrix\Main\Result;
use Bitrix\Main\Error;

function validateEmail(string $email): Result
{
    $result = new Result();

    if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
        $result->addError(
            new Error('Некорректный email')
        );
    }

    return $result;
}
```

Использование:

```
<?php

$result = validateEmail('test@example.com');

if (!$result->isSuccess()) {
    foreach ($result->getErrors() as $error) {
        echo $error->getMessage();
    }
}
```

### 9.2. Когда использовать Exception

Исключения предназначены для ситуаций, когда нормальное выполнение операции невозможно и ошибка должна быть передана выше по стеку вызовов.

Пример:

```
<?php

function divide(int $a, int $b): float
{
    if ($b === 0) {
        throw new InvalidArgumentException(
            'Деление на ноль невозможно'
        );
    }

    return $a / $b;
}
```

Обработка:

```
<?php

try {
    $result = divide(10, 0);
} catch (InvalidArgumentException $exception) {
    // Логирование или формирование ответа
}
```

### 9.3. Result и Exception — не конкуренты

| Result                                      | Exception                                                |
| ------------------------------------------- | -------------------------------------------------------- |
| Описывает результат операции                | Сообщает об исключительной ситуации                      |
| Удобен для ожидаемых ошибок бизнес-операции | Удобен для прерывания нормального выполнения             |
| Может содержать несколько ошибок            | Передаёт одну исключительную ситуацию                    |
| Требует проверки `isSuccess()`              | Требует обработки через `try/catch` на подходящем уровне |

Нельзя утверждать, что в D7 все методы возвращают `Result` или что исключения больше не используются.

Правило: изучай контракт конкретного метода — что он возвращает и какие исключения может выбросить.

## 10. Безопасность при работе с запросами

Даже на базовом уровне разработчик должен понимать основные угрозы.

### 10.1. SQL Injection

Нельзя напрямую подставлять пользовательские данные в SQL-запрос.

Плохо:

```
<?php

$id = $_GET['id'];

$sql = "SELECT * FROM users WHERE ID = $id";
```

Правильно — использовать ORM или подготовленные запросы с параметрами.

В Bitrix при работе с D7 ORM предпочтительно использовать `getList()` с фильтрами, а не собирать SQL вручную.

### 10.2. XSS

Нельзя выводить пользовательские данные в HTML без контекстного экранирования.

Плохо:

```
<?php

echo $_POST['name'];
```

Лучше:

```
<?php

use Bitrix\Main\Text\HtmlFilter;

echo HtmlFilter::encode($name);
```

`HtmlFilter::encode()` подходит для HTML-текста. Для JavaScript, URL и других контекстов нужны соответствующие методы защиты.

### 10.3. CSRF

CSRF — атака, при которой злоумышленник пытается заставить авторизованного пользователя выполнить нежелательное действие.

Для форм Bitrix следует использовать штатный механизм проверки сессии:

```
<?php

if (
    $_SERVER['REQUEST_METHOD'] === 'POST'
    && check_bitrix_sessid()
) {
    // Обработка формы
}
```

При выводе формы:

```
<?php

echo bitrix_sessid_post();
```

Для AJAX и собственных контроллеров нужно корректно организовать передачу и проверку токена.

### 10.4. Проверка прав доступа

Нельзя считать, что пользователь имеет право выполнять действие только потому, что он авторизован.

Нужно проверять:

1. Авторизован ли пользователь.
2. Имеет ли он право выполнять операцию.
3. Имеет ли он доступ к конкретной сущности.
4. Допустима ли операция с точки зрения бизнес-правил.

Проверка прав должна выполняться на сервере, а не только скрытием кнопок в интерфейсе.

## 11. Организация собственного кода

### 11.1. Не смешивать разные уровни ответственности

Даже небольшой проект желательно разделять на логические части.

Например:

```
/local/
└── php_interface/
    ├── init.php
    ├── include/
    │   ├── events.php
    │   └── autoload.php
    └── lib/
        └── Company/
            └── Tools/
                └── StringHelper.php
```

Здесь:

- `init.php` — точка входа пользовательской инициализации;
- `include/` — подключения и регистрация инфраструктуры;
- `lib/` — классы проекта.

Для более крупных проектов лучше создавать собственный модуль в `/local/modules/`, а не бесконечно расширять `php_interface`.

### 11.2. Что должно быть в сервисе

Сервис — класс, который отвечает за определённую бизнес-операцию.

Например:

```
<?php

namespace Company\Integration;

use Bitrix\Main\Result;
use Bitrix\Main\Error;

class CustomerService
{
    public function validateName(string $name): Result
    {
        $result = new Result();

        if (trim($name) === '') {
            $result->addError(
                new Error('Имя обязательно для заполнения')
            );
        }

        return $result;
    }
}
```

Это небольшой пример организации кода. В реальном проекте сервис может взаимодействовать с ORM, внешними API и другими компонентами системы.

Главный принцип: не размещать всю бизнес-логику в `init.php`, шаблонах компонентов или обработчиках событий.

## 12. Типичные ошибки начинающего Bitrix-разработчика

| Ошибка                                     | Почему это плохо                             |
| ------------------------------------------ | -------------------------------------------- |
| Изменять файлы `/bitrix/`                  | Изменения могут потеряться при обновлении    |
| Помещать весь код в `init.php`             | Сложно поддерживать и тестировать            |
| Подключать все модули подряд               | Лишняя нагрузка и зависимости                |
| Считать D7 полной заменой старого API      | Не все старые механизмы имеют замену         |

| Считать Request безопасным                 | Данные всё равно нужно проверять             |
| Экранировать данные только при записи      | Защита должна учитывать контекст вывода      |
| Проверять права только на фронтенде        | Запрос можно отправить напрямую              |
| Использовать глобальные переменные повсюду | Сильная связанность и сложность тестирования |
| Не учитывать версию ядра                   | API и доступные методы могут отличаться      |

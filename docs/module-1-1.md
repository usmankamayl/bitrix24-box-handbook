# Модуль 1.1: Структура Bitrix Framework и основы D7

## Теория

### Границы темы

Этот подраздел — карта платформы: из чего состоит продукт, из чего состоит
проект, что такое D7 и где он заканчивается, как устроены модули и
пользовательская инициализация. Задача — чтобы ты мог зайти в незнакомый
проект и за 10 минут сказать, что там есть и где что лежит.

Что здесь **не** разбирается:

| Тема | Где |
|---|---|
| Компоненты, шаблоны, `result_modifier` | 1.2 |
| Агенты, cron, фоновые задачи | 1.3 |
| События как механизм (старое API и `EventManager`) | 1.4 |
| Пролог/эпилог, `header.php`/`footer.php`, композит | 1.5 |
| Автозагрузка, namespace, Composer — подробно | 1.6 |
| `Application`/`Context`/`Request`/`Response` — подробно | 1.7 |
| `Result`, `Exception`, обработка ошибок — подробно | 1.8 |
| Кеширование | модуль 4 |
| Разработка модулей для Box и миграции | 14.1 |

Здесь автозагрузка и `init.php` даны только как контракт: «что это и зачем»,
без разбора механизма. Так же `Application` — только как точка входа в сервисы.

> **О версии.** Конкретные имена файлов и внутренний порядок вызовов в ядре
> менялись: `SM_VERSION` 12.5 и `SM_VERSION` 24.x — разные исходники при той же
> архитектуре. Всё, что помечено `[проверить]`, проверяется тремя командами на
> своей коробке (см. задачу 1). Механизмы, которые здесь описаны как правило
> (приоритет `/local`, `init.php`, `install/index.php`), стабильны с 8–10 версий.

### 1. Три продукта, которые путают на первом собеседовании

| Понятие | Что это | Что важно |
|---|---|---|
| **Bitrix Framework** | PHP-платформа: ядро, модули, ORM, события, кеш, компоненты | Это API. Лицензии и редакции к ней не относятся |
| **1С-Битрикс: Управление сайтом** (БУС) | CMS на этом Framework: сайты, инфоблоки, магазин | Продукт. Состав модулей зависит от редакции |
| **Bitrix24** | Отдельный продукт: CRM, задачи, чат, автоматизация | Два исполнения: **Cloud** (SaaS) и **Box** (на своём сервере) |

Практические следствия, которые спрашивают:

- **Редакция БУС определяет состав модулей.** «Старт» и «Бизнес» — один и тот же
  код ядра, но разные наборы модулей и разные права. Код, который «работает
  у меня», на редакции ниже может упасть на `Loader::includeModule()` без
  модуля. Поэтому результат подключения проверяют, а не игнорируют.
- **Cloud ≠ Box.** В облаке Bitrix24 нет ни файловой системы сайта, ни `/local/`,
  ни `CModule`, ни `install/index.php`. Кастомизация — REST API, приложения,
  бизнес-процессы, роботы. В Box есть ядро и модули, но продуктовая надстройка
  другая: наличие модуля `sale` не означает, что там лежат компоненты магазина
  из БУС.
- **«У меня Битрикс» — это не ответ.** Первый вопрос на проекте: БУС или Б24,
  Box или Cloud, редакция, версия ядра.

### 2. Что такое D7 и чем он не является

D7 — поколение API ядра, которое вводилось с версии **14.0.0** и вводится до сих
пор. Это не версия PHP, не отдельный фреймворк и не «новый Битрикс».

Что даёт D7:

- пространства имён и автозагрузку (`Bitrix\Main\Loader`);
- ORM (`DataManager`, `getList()`, `Query`, поля-объекты);
- `Bitrix\Main\Result` / `Error` / `ErrorCollection` как стандарт результата;
- `EventManager` — событийная модель в новом виде;
- `Application`, `Context`, `Request`, `HttpResponse`;
- `Bitrix\Main\Web\{Json, Http\Client, Cookie, Uri}`, `Bitrix\Main\Type\{Date, DateTime}`;
- `Bitrix\Main\Config\Configuration`, `Bitrix\Main\DB\Connection`, `Bitrix\Main\IO`;
- `Bitrix\Main\Diag\Logger`, `Bitrix\Main\Localization\Loc`.

Чем D7 **не** является:

- **Не полной заменой старого API.** У части механизмов замены нет вообще
  (см. таблицу ниже).
- **Не PSR-совместимым фреймворком.** Автозагрузка похожа на PSR-4, но это не
  PSR-4; DI-контейнера нет; `Application` — не контейнер, а инфраструктурный
  объект.
- **Не гарантией единообразия.** Внутри `Bitrix\Main` есть классы, написанные
  в разные годы и по-разному. Контракт читается по конкретному классу, а не по
  namespace.

### 3. Карта «старое → D7»: где замена есть, где нет

Это самая частая точка, где джуна ловят. Утверждение «всё старое API
устарело, пиши на D7» — неверно.

| Старое | D7-замена | Комментарий |
|---|---|---|
| `CIBlockElement::GetList()` | `Bitrix\Iblock\Elements\ElementXxxTable` (генерируется для инфоблока), `Bitrix\Iblock\ElementTable` | Замена частичная: свойства, разделы, торговые предложения, сложные фильтры — всё равно через legacy-API инфоблоков. Полноценного D7-API инфоблоков нет |
| `CIBlockSection::GetList()` | `Bitrix\Iblock\SectionTable` | То же: только базовые выборки |
| `CModule::IncludeModule()` | `Bitrix\Main\Loader::includeModule()` | Полная замена, оставлено для совместимости |
| `CDatabase` / `$DB->Query()` | `Bitrix\Main\Application::getConnection()` → `Bitrix\Main\DB\Connection` | Полная замена; но `$DB->RunSQLBatch()` в установщиках модулей используется до сих пор |
| `$USER` / `CUser` | `Bitrix\Main\UserTable` — только данные | Авторизация (`Authorize`, `IsAuthorized`) — legacy. Замены нет |
| `CFile::*`, `CFile::SaveFile()` | `Bitrix\Main\IO\File`, `Bitrix\Main\File` | Замена частичная: `CFile` до сих пор используется в компонентах и инфоблоках |
| `CEvent`, `CEventLog` | `EventManager` (`send`/`addEventHandler`), `CEventLog` | События почты — `EventManager`; журнал событий (`CEventLog::Add`) остался legacy |
| `CAgent::AddAgent()` | — | Замены нет, агенты по-прежнему `CAgent` |
| `$APPLICATION` (`CMain`) | `Bitrix\Main\Application` — только сервисы | `SetTitle`, `AddChainItem`, `IncludeComponent`, `RestartBuffer` — по-прежнему `$APPLICATION` |
| `CBitrixComponent` | — | Компоненты не переписаны на D7; внутри компонента D7 используется для данных |
| `install/index.php` модуля (`CModule`) | — | Замены нет и не планируется: это контракт установщика |
| `CUserTypeEntity`, `CUserFieldEnum` | `Bitrix\Main\UserField*` | Замена частичная |

Вывод, который нужно уметь сформулировать: **новый код пишется на D7 там, где
D7 есть; legacy остаётся там, где контракт не имеет замены.** Смешивать их
в одном файле нормально, если граница проходит по слою: например, установщик на
`CModule`, а вся логика модуля — на D7.

### 4. Структура проекта

Типичный корень коробочного сайта:

```
/ (DOCUMENT_ROOT)
├── bitrix/
│   ├── .settings.php          конфиг ядра: БД, кеш, сессии, ошибки
│   ├── .settings_extra.php     переопределения, не перезаписываемые обновлением
│   ├── admin/                  скрипты админки
│   ├── components/             поставляемые компоненты (bitrix:*)
│   ├── modules/                поставляемые модули (main, iblock, sale, crm, ...)
│   ├── templates/              поставляемые шаблоны (.default)
│   ├── php_interface/          dbconn.php (legacy), init.php (устаревшая точка), include/
│   ├── cache/, managed_cache/, stack_cache/, backup/   служебные каталоги
│   ├── updates/                история обновлений и скрипты
│   └── urlrewrite.php          точка входа для ЧПУ
├── local/
│   ├── modules/                свои модули: vendor.module
│   ├── components/             свои компоненты: vendor/name
│   ├── templates/              свои шаблоны сайта
│   ├── php_interface/          init.php, include/, свои классы
│   ├── js/, css/, images/      свои статические ресурсы
│   └── logs/                   свои логи (закрыть от HTTP)
├── upload/                     загруженные файлы: iblock/, resize_cache/, uf/
├── index.php, .htaccess, urlrewrite.php, 404.php
```

| Каталог | Назначение | Правило |
|---|---|---|
| `/bitrix/` | ядро и поставляемые модули/компоненты/шаблоны | не редактировать |
| `/local/` | вся пользовательская разработка | код проекта только здесь |
| `/upload/` | файлы, загруженные через сайт | публичный, отдаётся веб-сервером |
| `/bitrix/.settings.php` | конфигурация ядра | читать первым при разборе проекта |
| `/bitrix/cache`, `/managed_cache`, `/stack_cache` | кеш | чистить при отладке; не хранить там своё |
| `/bitrix/backup` | бэкапы из админки | не место для боевых данных |

Что важно про `/upload/`: он доступен по HTTP напрямую, веб-сервер отдаёт файлы
без участия PHP. Поэтому туда нельзя класть ничего приватного (логи, выгрузки,
документы клиентов) — это делают **вне** `DOCUMENT_ROOT` или закрывают
конфигом веб-сервера.

### 5. `/bitrix/` и `/local/`: правила, которые не обсуждаются

1. Файлы в `/bitrix/` не редактируются. Обновление ядра перезапишет изменения
   без предупреждения. Восстановление — сравнение с дистрибутивом, то есть
   ручная работа на боевом сайте.
2. Пользовательский код живёт в `/local/`. Поиск идёт сначала в `/local/`,
   потом в `/bitrix/` (`Loader::getLocal()` — та же логика для одиночных файлов).
3. Приоритет `/local` — это механизм, а не пожелание. Компоненты
   (`/local/components`), шаблоны (`/local/templates`), модули
   (`/local/modules`), `init.php` — всё ищется сначала локально. `[проверить]`
   на своей версии: `Loader::getLocal('/bitrix/header.php')` в отладочной точке.
4. Переопределение — не «правка», а «копия + поддерживаемый механизм»: копия
   компонента в `/local/components`, свой шаблон в
   `/local/templates/<шаблон>/components/<namespace>/<имя>`, обработчик события
   вместо правки класса.
5. Не всё переопределяется копированием. Компонент, у которого внутри
   `CBitrixComponent::includeComponentClass()` или жёсткие пути, копируется
   вместе с классом; модуль ядра не переопределяется вообще — только события,
   наследование и свои обёртки.

Вопрос, который задают почти всегда: **почему не поправить компонент прямо в
`/bitrix/components/bitrix/`?**

Ответ: потому что обновление ядра заменит файлы, и правка исчезнет; потому что
следующий разработчик не найдёт изменений (git в `/bitrix/` обычно не
ведётся); потому что при обновлении компонента конфликт проявится как «код
пропал» без ошибки. Правильно — копия в `/local` или свой шаблон компонента.

### 6. `.settings.php`: конфиг, который читают первым

`/bitrix/.settings.php` — конфигурация ядра для D7. Ключевое:

| Ключ | Что настраивает |
|---|---|
| `connections` | подключение к БД: класс соединения, хост, логин, пароль, БД. Legacy-аналог — `bitrix/php_interface/dbconn.php` |
| `cache` | тип кеша: `A` (авто), файлы, memcache, redis, apcu; `sid`, `ttl` |
| `session` | режим сессий (`N` — штатные, `A` — в БД и т.п.), lifetime |
| `exception_handling` | `debug`, `log` (файл), обработчики, показ ошибок |
| `cookies` | `cookie_domain`, `cookie_secure` |
| `crypto`, `pull`, `loggers`, `smtp`, `routing` | соответствующие подсистемы |

`.settings_extra.php` мержится поверх `.settings.php`; его используют, чтобы
локальные переопределения не затирались при обновлении. Флаг `readonly => true`
в `.settings.php` запрещает ядру перезаписывать файл из админки.

Практика: пароль БД лежит в `.settings.php` открытым текстом. Файл не
коммитят в публичный репозиторий; при переносе проекта между окружениями
правят именно его. `[проверить]` на своей версии: часть установок дополнительно
держит `bitrix/php_interface/dbconn.php` для legacy-совместимости.

### 7. Модуль — единица функциональности

Модуль — самостоятельная часть платформы с идентификатором, установщиком и
своим API. Всё, что делает ядро, разложено по модулям: `main`, `iblock`,
`catalog`, `sale`, `crm`, `bizproc`, `highloadblock` и десятки других.

**Идентификатор модуля.** Для своих модулей — `vendor.module`: строчные латинские
буквы, цифры, `_`, точка-разделитель. Идентификатор попадает в `b_module`, в
путь `/local/modules/<id>/` и в имя класса установщика: точки заменяются на
подчёркивания (`mycompany.orders` → `class mycompany_orders extends CModule`).

**Структура своего модуля:**

```
/local/modules/mycompany.orders/
├── include.php              подключается при Loader::includeModule()
├── install/
│   ├── index.php            класс mycompany_orders extends CModule
│   ├── version.php          ['VERSION' => '1.0.0', 'VERSION_DATE' => '...']
│   ├── db/
│   │   ├── install.sql      CREATE TABLE ...
│   │   └── uninstall.sql    DROP TABLE ...
│   ├── components/          компоненты модуля (копируются в /local/components)
│   └── lang/ru/index.php    тексты установщика
├── lang/ru/                  тексты модуля (Loc::loadMessages)
├── lib/                      классы модуля (namespace из id)
├── admin/                    страницы админки (копируются в /bitrix/admin)
├── options.php               настройки модуля в админке
└── default_option.php        значения по умолчанию для настроек
```

**Установщик.** Это единственное место, где `CModule` уместен: у
`install/index.php` нет D7-замены. Контракт:

| Метод | Что делает | Когда вызывается |
|---|---|---|
| `DoInstall()` | сценарий установки | по кнопке «Установить» |
| `InstallDB()` | таблицы, инфоблоки, HL-блоки, демо-данные | из `DoInstall` |
| `InstallFiles()` | копирование компонентов/шаблонов/`admin` | из `DoInstall` |
| `InstallEvents()` | регистрация обработчиков | из `DoInstall` |
| `DoUninstall()` | сценарий удаления | по кнопке «Удалить» |
| `UnInstallFiles()`, `UnInstallEvents()`, `UnInstallDB()` | обратные операции | из `DoUninstall` |

Два правила, которые проверяют на собеседовании:

- **Порядок.** Установка: файлы → БД → события → `ModuleManager::registerModule()`.
  Удаление: обратный. Регистрация модуля **последней**: если она пройдёт, а
  `InstallDB()` упадёт, получится «модуль есть, таблиц нет».
- **Идемпотентность.** `$DB->RunSQLBatch()` возвращает `false` при успехе и
  **массив ошибок** при провале — проверять `!== false`, а не «истинность».
  `CREATE TABLE IF NOT EXISTS` + повторная установка не должны падать.
  Обработчики перед регистрацией снимают (`unRegisterEventHandler`) — иначе
  повторная установка даёт два обработчика на одно событие.

Проверка и версии:

```php
use Bitrix\Main\Loader;
use Bitrix\Main\ModuleManager;

if (!Loader::includeModule('sale')) {
    throw new RuntimeException('Модуль sale не установлен');
}

if (!ModuleManager::isModuleInstalled('crm')) { /* ... */ }

if (version_compare(ModuleManager::getVersion('sale'), '20.0.0', '<')) {
    throw new RuntimeException('Нужен sale >= 20.0.0');
}
```

`Loader::includeModule()` — не «подключить файл класса». Он проверяет, что модуль
установлен (запись в `b_module`), подключает его `include.php` и `lib/autoload.php`,
регистрирует namespace модуля на `lib/` и возвращает `bool`. Файлы модуля могут
лежать на диске и при этом не быть установленным модулем — тогда вернётся `false`.

**Модуль ≠ компонент.** Модуль — серверная функциональность: таблицы, API,
обработчики, права. Компонент — блок интерфейса с параметрами и шаблоном.
Компонент может требовать модуль; модуль компонентом не является.

### 8. `init.php` и автозагрузка: контракт

`/local/php_interface/init.php` — точка подключения пользовательского кода,
которая выполняется при инициализации ядра (из `prolog_before.php`).

Что нужно знать на уровне 1.1:

- Если существует `/local/php_interface/init.php`, он используется **вместо**
  `/bitrix/php_interface/init.php`, а не вместе с ним. При переносе проекта это
  первое, что проверяют: где фактически выполняется инициализация.
- В `init.php` место регистрации: обработчики событий, автозагрузка своих
  классов, подключение небольших конфигов. Не место: бизнес-логика, запросы к
  БД на каждом хите, HTTP-вызовы к внешним API, тяжёлые циклы.
- `init.php` выполняется на каждом обычном хите. На **композитной** странице,
  отданной из кеша, пролог не запускается — значит, и `init.php` тоже. Всё, что
  должно работать всегда (например, обработка входящего вебхука), в пролог не
  кладут. `[проверить]` на своей коробке: включить композит и посмотреть, растёт
  ли лог из `init.php`.
- Порядок «`init.php` → авторизация `$USER` → события страницы» зависит от
  версии ядра. Признак, который считается «уже доступным» в `init.php`,
  проверяется экспериментом, а не по памяти.

Три способа получить автозагрузку своих классов (подробно — 1.6):
`lib/` внутри модуля, `Loader::registerNamespace()`,
`Loader::registerAutoLoadClasses()`. Плюс Composer — отдельный механизм,
который с Bitrix совместим, но требует `composer dump-autoload` и дисциплины
по namespace.

`Loader::includeModule()` в `init.php` не вызывают «на всякий случай»: он
подключает модуль со всеми его обработчиками и влияет на весь хит. Делать это
надо там, где модуль действительно нужен.

### 9. Алгоритм «10 минут на чужой проект»

Порядок, который экономит часы:

1. **`.settings.php`** — БД, тип кеша, `exception_handling.debug`, домен cookie.
2. **`local/php_interface/init.php`** и `local/php_interface/include/` — что
   регистрируется на каждом хите.
3. **`local/modules/`** — какие модули свои, что они добавляют, есть ли
   `install/version.php`.
4. **`local/components/` и `local/templates/`** — что переопределено.
5. **`urlrewrite.php`** (в корне и в `/local`) — какие URL на какие файлы
   ведут.
6. **Правки в `/bitrix/`** — главный признак беды. Смотреть даты модификации
   файлов и сравнивать с дистрибутивом; при наличии git — `git log -- bitrix/`.
7. **Обработчики событий** — где лежат: `b_module_to_module` в БД (старое API)
   и `EventManager` (D7). Проверять оба места, иначе «событие не срабатывает».
8. **Кеш** — `/bitrix/cache` и `/bitrix/managed_cache`; при «изменения не
   применяются» первым делом сбрасывать кеш, но причину искать в коде.

Задача 1 ниже — это тот же алгоритм, оформленный в работающий скрипт.

### 10. Гигиена кода: 10 правил с причинами

| Правило | Причина |
|---|---|
| Код проекта — только в `/local/` | обновление ядра не должно его касаться |
| Бизнес-логика — не в `init.php`, не в шаблоне компонента | не тестируется, не переиспользуется, ломает вёрстку |
| Свой код — в модуль, когда он перерос `php_interface/lib` | модуль ставится/удаляется, версионируется, имеет права и язык |
| `Loader::includeModule()` с проверкой результата | «модуль есть у меня» ≠ «модуль есть на этом сайте» |
| Версия ядра и модуля — проверкой, не предположением | API отличается между версиями, демо ограничено |
| Не использовать глобальные `$APPLICATION`, `$USER` внутри сервисов | не тестируется, скрытая зависимость от запроса |
| Вывод — через `htmlspecialcharsbx()` (или контекстное экранирование) | XSS; экранирование делается при выводе, не при сохранении |
| Права и CSRF — на сервере, в начале обработчика | скрытая кнопка — не защита; GET-действия обходит любой краулер |
| Кеш сбрасывать при записи в сущность | иначе «данные не меняются» — и это баг, а не фича |
| Правки в `/bitrix/` — только через тикет с обоснованием | иначе они бесследно исчезнут |

## Вопросы для собеседования

Формат: сначала отвечаешь сам, потом сверяешься. Ответы — не «определения из
документации», а то, что реально ждут на проекте.

### Junior

**1. Что такое Bitrix Framework и чем он отличается от «1С-Битрикс: Управление
сайтом»?**

**Ответ.** Framework — платформа: ядро, модули, ORM, события, кеш, компоненты,
API. «Управление сайтом» — CMS, построенная на этом Framework: она даёт
инфоблоки, магазин, админку, шаблоны. Разница прикладная: Framework — это то,
против чего ты пишешь код; CMS — продукт, который на нём собран. Bitrix24 —
третий продукт, отдельно, в двух исполнениях: Cloud (SaaS) и Box (свой сервер).

**2. Что такое D7?**

**Ответ.** Поколение API ядра, вводимое с версии 14.0.0: namespace, автозагрузка,
ORM, `Result`, `EventManager`, `Application`/`Context`/`Request`/`Response`,
`Type`, `Web`. Это не версия PHP и не отдельный фреймворк. D7 внедрён частично:
старое API (`CIBlockElement`, `CUser`, `CAgent`, `$APPLICATION`) никуда не делось.

**3. Зачем нужна директория `/local/`?**

**Ответ.** Для пользовательского кода, который не должен пострадать при
обновлении ядра. Ядро ищет файлы сначала в `/local/`, потом в `/bitrix/` —
поэтому там размещают компоненты, шаблоны, модули и `init.php`. Править
`/bitrix/` нельзя: обновление перезапишет файлы молча.

**4. Где размещаются пользовательские компоненты, модули и шаблоны?**

**Ответ.** Компоненты — `/local/components/<vendor>/<name>/`, модули —
`/local/modules/<vendor>.<module>/`, шаблоны сайта — `/local/templates/<id>/`.
Шаблон компонента внутри шаблона сайта —
`/local/templates/<id>/components/<namespace>/<name>/<template>/`.

**5. Что такое модуль Bitrix?**

**Ответ.** Самостоятельная часть платформы с идентификатором (`sale`, `iblock`,
`mycompany.orders`), установщиком и своим API. Модуль содержит таблицы, классы,
обработчики, языковые файлы, страницы админки. Пока модуль не установлен
(нет записи в `b_module`), его классы и API недоступны.

**6. Что делает `Loader::includeModule()`?**

**Ответ.** Проверяет, что модуль установлен, подключает его `include.php` и
`lib/autoload.php`, регистрирует namespace модуля на каталог `lib/` и
возвращает `bool`. Это не подключение файла класса: файлы на диске могут быть,
а модуль — не установлен, и метод вернёт `false`.

**7. Чем `CModule::IncludeModule()` отличается от `Loader::includeModule()`?**

**Ответ.** По сути ничем: `CModule` — legacy-обёртка над тем же механизмом,
оставленная для совместимости. В новом коде используют `Loader`; в старом коде
и в чужих модулях встречается `CModule`, и это не повод его «чинить» без задачи.

**8. Где находится `init.php` и что в нём делают?**

**Ответ.** `/local/php_interface/init.php` (реже —
`/bitrix/php_interface/init.php`). Там регистрируют обработчики событий,
автозагрузку своих классов, подключают небольшие конфиги. Если файл есть в
`/local/`, он заменяет версию из `/bitrix/`, а не дополняет её.

**9. Куда нельзя писать код?**

**Ответ.** В `/bitrix/` — обновление затрёт. В `/upload/` — каталог публичный,
файлы отдаются веб-сервером напрямую. В `/bitrix/cache`, `managed_cache`,
`stack_cache` — это кеш, его чистит ядро. Ещё нельзя считать «своим» файл
чужого модуля: для этого есть события и наследование.

**10. Как узнать версию ядра и версию модуля?**

**Ответ.** Версия ядра — константа `SM_VERSION`. Версия модуля —
`Bitrix\Main\ModuleManager::getVersion('main')`. На собеседовании это проверяют
потому, что половина «работает у меня, не работает у клиента» — разные версии.

**11. Что такое `.settings.php`?**

**Ответ.** Конфигурация ядра: подключение к БД, тип кеша, настройки сессий,
обработка ошибок, домен cookie. Лежит в `/bitrix/.settings.php`; рядом
`.settings_extra.php` для локальных переопределений. Legacy-аналог части
настроек — `bitrix/php_interface/dbconn.php`.

**12. Чем модуль отличается от компонента?**

**Ответ.** Модуль — серверная функциональность: таблицы, API, обработчики,
права, установка/удаление. Компонент — блок интерфейса: параметры, шаблон,
`result_modifier`, кеш. Компонент может требовать модуль (например, `sale`),
модуль компонентом не является и в интерфейсе не выводится.

### Middle

**1. Какие механизмы реализуют приоритет `/local/` над `/bitrix/`?**

**Ответ.** `Loader::getLocal()` — ищет файл сначала в `/local`, потом в
`/bitrix`. Для компонентов и шаблонов — собственные механизмы поиска
(`CBitrixComponent::initComponent`, поиск шаблона сайта). Для `init.php` —
проверка наличия файла в `prolog_before.php`. Для модулей — проверка каталога
`/local/modules/<id>` перед `/bitrix/modules/<id>`. Общее правило: приоритет
локального — не «так принято», а реализованный в коде порядок поиска.

**2. Почему при повторной установке модуля появляются двойные обработчики и как
это предотвратить?**

**Ответ.** `install/index.php` при установке вызывает
`$em->registerEventHandler()`; повторная установка (после неудачной или после
переустановки без удаления) добавляет вторую запись в `b_module_to_module`.
Событие начинает выполняться дважды: двойная запись в лог, два письма, двойное
списание. Лечится так: перед регистрацией снимать обработчик
(`unRegisterEventHandler`) или сначала вызывать `UnInstallEvents()`. В
установщике порядок «снять → поставить» обязателен, потому что установка может
прерваться на середине.

**3. Как сделать установку модуля идемпотентной?**

**Ответ.** Схема — `CREATE TABLE IF NOT EXISTS`; данные — проверка перед
вставкой (`getList` с `limit 1`), а не `INSERT` вслепую; обработчики — снять
перед регистрацией; `ModuleManager::registerModule()` повторно не вредит, но
версию в `b_module` надо обновлять осознанно. Проверка `$DB->RunSQLBatch()`
идёт на `!== false`: при успехе метод возвращает `false`, при ошибке — массив.

**4. Что произойдёт, если удалить модуль без `UnInstallDB()`?**

**Ответ.** Модуль снимется с регистрации (`b_module`), файлы могут остаться,
таблицы останутся. `Loader::includeModule()` начнёт возвращать `false`, код,
который его результат не проверял, упадёт на отсутствующем классе. Повторная
установка может упасть на `CREATE TABLE`, если он без `IF NOT EXISTS`.
Отдельная проблема — данные-сироты: таблицы с ПД остаются без владельца и без
UI.

**5. Как модуль узнаёт о необходимости обновить схему при выходе новой версии?**

**Ответ.** Через `install/version.php` и код обновления: при установке новой
версии поверх старой установщик сравнивает версию в `b_module` с версией из
файла и выполняет `ALTER`-скрипты. В самодельных модулях это делают руками в
`InstallDB()` по шагам или отдельным runner'ом миграций. `install.sql` — не
миграция: он выполняется один раз и схему после изменения `getMap()` не
обновляет.

**6. Как проверить наличие модуля и его минимальную версию?**

**Ответ.** `ModuleManager::isModuleInstalled('sale')` — установлен ли;
`Loader::includeModule('sale')` — установлен и подключён (это то, что нужно
перед использованием API); `version_compare(ModuleManager::getVersion('sale'),
'20.0.0', '<')` — версия. Проверять надо оба условия: модуль может быть
установлен, но не подключён, а версия — ниже требуемой.

**7. Где хранить свой код: `php_interface/lib` или свой модуль?**

**Ответ.** `php_interface/lib` — для небольших проектов: несколько классов,
хелперы, один-два обработчика. Модуль — когда есть свои таблицы, права, языки,
страницы админки, настройки, установка/удаление, переиспользование на других
проектах. Признак, что пора в модуль: код начал обрастать `install`-логикой и
`options.php`, либо его копируют между сайтами.

**8. Как переопределить шаблон стандартного компонента, не трогая ядро?**

**Ответ.** Создать шаблон сайта или использовать существующий и положить
шаблон компонента в
`/local/templates/<шаблон>/components/<namespace>/<имя компонента>/<шаблон>/`.
Правки шаблона (`template.php`, `style.css`, `result_modifier.php`) там
переживут обновление. Если нужна правка PHP-логики компонента — копия
компонента в `/local/components/` (или наследование класса компонента), тогда
обновление ядра её не затронет, но и исправления ядра в неё не придут.

**9. Почему код из `init.php` может «не работать» на композитном сайте?**

**Ответ.** При композите страница отдаётся из кеша до запуска пролога: PHP
ядра не выполняется вообще, `init.php` тоже. Всё, что должно срабатывать
всегда (приём вебхука, запись статистики, реакция на внешний запрос),
выносится в отдельную точку входа или в динамическую область, а не в пролог.

**10. Как найти все обработчики события в чужом проекте?**

**Ответ.** Два места: `b_module_to_module` (старое API, `AddEventHandler`) и
код с `EventManager::getInstance()->addEventHandler()` (D7) — обычно в
`init.php` и в `include.php` модулей. Плюс `GetModuleEvents()` в рантайме как
диагностика. Если смотреть только `init.php`, половину обработчиков не найти —
модули регистрируют свои через установщик.

**11. Как вывести JSON-ответ из скрипта Bitrix?**

**Ответ.** Не подключать `header.php`/`footer.php`; подключить пролог
(`prolog_before.php`) или, если нужно только API, использовать отдельную точку
входа. Затем выставить `Content-Type: application/json`, статус, тело через
`\Bitrix\Main\Web\Json::encode()`, и убедиться, что ответ отправляется один раз
(второй `send()` после вывода — ошибка). Кодирование в JSON само по себе
HTTP-ответом не является: заголовки и статус ставятся отдельно.

**12. Что проверять в проекте перед тем, как что-то менять?**

**Ответ.** Где фактически выполняется `init.php`; установлены ли нужные модули
и их версии; какие обработчики уже висят на нужном событии; тип кеша и
включён ли композит; правились ли файлы в `/bitrix/`; есть ли тестовый стенд и
бэкап. Без этих пяти ответов любая правка — лотерея.

### Senior

**1. Как организовать архитектуру приложения поверх Bitrix Framework?**

**Ответ.** Слоями с явными границами: точка входа (страница, компонент,
контроллер, агент) → сервис/use case → репозиторий (ORM, инфоблоки, legacy) →
инфраструктура (кеш, события, HTTP). Точка входа отвечает только за разбор
запроса и вывод; бизнес-правила — в сервисах, которые не знают про
`$APPLICATION` и `$USER`; доступ к данным — в репозиториях, чтобы legacy
`CIBlockElement` не расползался по коду. Bitrix не навязывает эту структуру,
поэтому её приходится держать самому — через namespace, DI в конструкторах и
запрет на статику внутри сервисов.

**2. Как изолировать бизнес-логику от статических API ядра?**

**Ответ.** Через адаптеры и инъекцию: сервис принимает интерфейсы
(`UserProvider`, `OrderRepository`, `Clock`), а реализации внутри вызывают
`UserTable`, `OrderTable`, `new DateTime()`. Статика `Loader`, `Application`,
`EventManager` остаётся в инфраструктурном слое — в фабриках, точках входа,
обработчиках. Тогда юнит-тесты не требуют поднятого ядра, а замена источника
данных не переписывает бизнес-логику. Граница прагматичная: 100% изоляция в
Bitrix недостижима и не нужна — достаточно, чтобы сервисы не зависели от
глобальных `$APPLICATION`/`$USER`.

**3. Как проектировать код под разные версии ядра?**

**Ответ.** Feature-detect вместо `version_compare` там, где это возможно:
`class_exists()`, `method_exists()`, проверка констант. Где нужна версия —
`ModuleManager::getVersion('main')` и явная проверка с понятной ошибкой, а не
молчаливый fallback. В `.description.php`/README модуля — минимальные версии.
Для своих зависимостей — Composer, но с оговоркой: `vendor/` в Bitrix обычно
кладётся в `/local/` и требует `autoload.php` в `init.php`.

**4. Как обновление ядра ломает пользовательский код и как это ловить?**

**Ответ.** Ломается в трёх местах: правки в `/bitrix/` (исчезают), наследование
внутренних классов ядра (меняется сигнатура), использование недокументированных
методов и свойств. Ловится так: staging с той же версией ядра, перед обновлением
— `git status` по `/bitrix/` (должен быть чистым), после — прогон критичных
сценариев и лог `exception_handling`. Композитный кеш после обновления
сбрасывается, иначе видны старые ошибки.

**5. Как безопасно переопределить стандартную функциональность?**

**Ответ.** По возрастанию инвазивности: свой шаблон компонента → копия
компонента в `/local/components` → обработчик события, меняющий данные
(`OnBeforeIBlockElementAdd` и т.п.) → наследование класса компонента/модуля →
своя обёртка над API. Чего не делать: править ядро, подменять классы через
`class_alias`, патчить через `!defined('B_PROLOG_INCLUDED')`-хаки. Каждый
уровень надо уметь обосновать: копия компонента означает, что исправления
ядра в него не придут.

**6. Как делать миграции схемы в Bitrix?**

**Ответ.** `install.sql` — это не миграция, а начальная схема. Дальше нужен
версионируемый механизм: собственный runner (таблица версий + набор
SQL/PHP-шагов), `sprint.migration` на проектах, где он принят, или шаги в
`InstallDB()` по версиям. Требования: идемпотентность, откат (down-миграция
или бэкап), запрет ручных правок БД на боевом, прогон миграций в деплое, а не
«руками в админке».

**7. Как тестировать код, который использует Bitrix?**

**Ответ.** Разделить на уровни. Юнит: сервисы без статики ядра (PHPUnit,
моки интерфейсов). Интеграционные: с поднятым ядром, `prolog_before.php` в
bootstrap, тестовая БД; проверяют ORM, события, права. E2E — по критичным
сценариям через HTTP. `$APPLICATION`/`$USER` в тестах подменяются или
изолируются на уровне точки входа. Полный «чистый» unit-тест компонента в
Bitrix нецелесообразен: компонент — это вывод.

**8. Что мешает «чистой архитектуре» в Bitrix и как с этим жить?**

**Ответ.** Глобальные `$APPLICATION`/`$USER`, статические фасады
(`Loader`, `Application`, `EventManager`), legacy-API с глобальным состоянием,
кеш, привязанный к URL, и композит, который выполняет код только при промахе
кеша. Жить с этим — значит держать границы: вся статика в одном слое, сервисы
на интерфейсах, точки входа тонкие, кеш — явная зависимость, а не «само
получится».

## Практические задачи

Задачи идут от «осмотреться на новом проекте» к «переписать чужой код».
Готовые решения — в `examples/module-1-1/`, но сначала делай сам: проверка
закрывается объяснением, а не чтением эталона.

### Задача 1. Разведка незнакомого проекта

**Ситуация.** Тебя позвали на коробочный сайт на БУС. Доступа к репозиторию
нет, есть только FTP/SSH и админка. Нужно за 10 минут понять, что здесь есть
и где что лежит, ничего не меняя.

**Что сделать.** Написать служебную страницу `local/tools/probe.php`, которая
выводит:

1. версию ядра (`SM_VERSION`) и версии установленных модулей;
2. какой `init.php` фактически работает — `/local/` или `/bitrix/`;
3. есть ли `.settings.php` и что в нём задано для кеша и `exception_handling`
   (без паролей и логинов);
4. какие свои модули лежат в `/local/modules/` и есть ли у них `install/version.php`;
5. есть ли свои компоненты и шаблоны в `/local/`;

   (`main:OnPageStart`, `iblock:OnBeforeIBlockElementAdd`).

**Требования.** Доступ — только администратору; страница не должна ничего
писать и менять; пароли и ключи не выводятся; после работы файл удаляется.

**Критерии приёмки.** Страница открывается под админом и отдаёт 403/редирект

### Задача 2. Свой модуль с установщиком

### Задача 3. Копия вместо правки ядра

**Ситуация.** Заказчик: «в форме заявки надо убрать поле и поменять подписи».

тебя правил `template.php` прямо там, и после обновления правки исчезли.

**Что сделать.** Восстановить правки «правильно» и объяснить письменно, почему
так:

1. определить, какой шаблон компонента фактически используется (шаблон сайта →

переживают сброс кеша; объяснение содержит цену решения (обновления компонента
не придут автоматически).

### Задача 4. Legacy → D7 без изменения поведения

**Ситуация.** Есть рабочий скрипт:

```php
<?php
require_once $_SERVER['DOCUMENT_ROOT'] . '/bitrix/modules/main/include/prolog_before.php';

CModule::IncludeModule('iblock');

$q = $_GET['q'];
$res = CIBlockElement::GetList(
    ['SORT' => 'ASC'],
    ['IBLOCK_ID' => 5, 'ACTIVE' => 'Y', '%NAME' => $q],
    false,
    false,
    ['ID', 'NAME']
);

while ($el = $res->Fetch()) {
    echo '<a href="/catalog/' . $el['ID'] . '/">' . $el['NAME'] . '</a><br>';
}
```

**Что сделать.** Переписать так, чтобы:

- точка входа была корректной для страницы (пролог + эпилог, заголовок, шаблон);
- входные данные валидировались и не попадали в вывод без экранирования;
- `%NAME` сохранил семантику поиска по подстроке (`%` ставится оператором, а не
  вручную в значение);
- выборка была ограничена (`nTopCount`/`limit`);
- и при этом **не** сломалась совместимость: если для инфоблока нет
  ORM-класса, `CIBlockElement` остаётся, а D7 используется там, где он есть
  (`Loader`, `Request`, `Application`).

**Что обязательно объяснить.** Какие строки остались legacy и почему: замена
`CIBlockElement::GetList()` на `ElementTable` меняет контракт (нет свойств,
другой формат фильтра `%NAME`, нет `DETAIL_PAGE_URL`), поэтому «переписать
всё на D7» здесь — не улучшение.

**Критерии приёмки.** Поведение совпадает на тех же данных; пустой `q` не даёт
LIKE `%%`; вывод экранирован; в объяснении названы минимум три места, где
замена на D7 изменила бы поведение.

### Задача 5. Code review

**Ситуация.** Пришёл код на ревью. Нужно найти проблемы и объяснить каждую
в формате «ошибка → причина → последствие → исправление».

```php
<?php
require($_SERVER['DOCUMENT_ROOT'] . '/bitrix/modules/main/include/prolog_before.php');

$APPLICATION->SetTitle('Отчёт');

    false,
    false,

echo '<h1>Отчёт за период</h1>';

file_put_contents(

```

**Что искать.** Минимум шесть проблем; в этом фрагменте их восемь. Отдельно

поддерживаемость.

**Критерии приёмки.** Найдено не менее шести проблем, у каждой — конкретное
исправление; отдельно указано, что здесь нельзя «починить» заменой на D7.

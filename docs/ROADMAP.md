# Программа подготовки PHP / Bitrix24 Box Developer

**Цель:** самостоятельная подготовка к работе и техническим собеседованиям
на позицию PHP-разработчика Bitrix24 Box.

**Формат:** теория → архитектура → практика → edge cases → Code Review →
контрольное задание.

**Использование:** каждый модуль самодостаточен и может быть передан
отдельно в новой сессии. Прогресс отмечается чекбоксами внутри модуля.

## Как пользоваться программой

### Правило нумерации (главное)

Материалы по модулям 1–14 и подразделам `X.1–X.4` уже написаны и лежат в
`docs/module-X-Y.md` и `examples/module-X-Y/`. Поэтому:

-   **Номер готового модуля и готового подраздела не меняется никогда.**
-   Новая тема получает **следующий свободный номер внутри модуля**:
    `1.5`, `1.6`, `2.5`, `6.5`, `14.5` и т. д. — то есть всегда после
    существующих `X.1–X.4`.
-   Если новая тема логически должна изучаться раньше готовой, она всё
    равно получает номер **позже**, а порядок изучения задаётся пометкой в
    тексте раздела (например, «при повторном прохождении читать до 14.1»).
-   Новые модули добавляются только **в конец**, с номером больше
    последнего существующего (сейчас это 15–20).
-   Один подраздел = файл `docs/module-X-Y.md` и, если есть практика,
    каталог `examples/module-X-Y/`.

Итог: старые конспекты и примеры остаются валидными, меняется только
программа, а не имена файлов.

### Статусы прогресса

Для каждого модуля три независимых статуса:

``` text
- [ ] Теория
- [ ] Практика
- [ ] Проверка (Code Review + контрольное задание)
```

-   `[ ]` — не начато;
-   `[~]` — в процессе;
-   `[x]` — завершено и проверено.

**Правило:** `[x]` за теорию не ставится. Только после проверки практики
и способности объяснить решения.

Исключение для уже написанных модулей 1–13 и блока 14.1–14.4: `[x]` у
теории и практики означает «материал создан и пройден по старому плану»,
а `[ ] Проверка` — её по новым критериям ещё не проводили.

### Как передавать модуль в новую сессию

Каждый модуль оформлен как самостоятельный блок: номер, теория, практика,
контроль, критерии освоения. Достаточно скопировать заголовок модуля и
его содержимое — этого хватит, чтобы продолжить работу без контекста
предыдущих сессий.

### Правила обучения

-   Каждый модуль начинается только после закрытия предыдущего (по
    чекбоксам).
-   Теория не сокращается до пересказа — разбираются внутренние механизмы
    Bitrix.
-   Примеры приближены к production, с указанием версии ядра и
    ограничений API.
-   Ошибки и альтернативные решения разбираются, а не только правильный
    код.
-   Практика и контрольное задание выдаются вместе с рабочим решением —
    осознанное решение для экономии времени: код изучается самостоятельно.
    Проверку закрывает не чтение решения, а способность объяснить его и
    изменить под новое условие.
-   Code Review объясняет ошибку, причину, последствие и способ
    исправления.
-   Практика без проверки не считается завершённой.

-   **17.5.** ADR и технический долг: фиксация решения, рассмотренных
    альтернатив и последствий; где хранить ADR в проекте; code review как
    контроль накопления долга; когда долг допустим осознанно.

DDD, Clean Architecture и Event-driven Architecture изучаются как
инструменты выбора решений, а не как обязательная архитектурная догма для
каждого Bitrix-проекта.

### Практика

-   Рефакторинг процедурного PHP.
-   Выделение бизнес-сервиса.
-   Разделение Controller / Service / Repository.
-   Проектирование интерфейсов и зависимостей.
-   Рефакторинг обработчика события.
-   Архитектурное ревью с объяснением компромиссов.

-   Составить реестр технического долга своего модуля с приоритетами и

### Контроль

## 5. Работа с документацией, версиями и сообществом

### Документация и версии

-   Проверять документацию именно для используемой версии ядра.
-   Различать документированные публичные API и внутренние классы.
-   Не считать наличие класса гарантией стабильности контракта.
-   Проверять сигнатуры, возвращаемые значения и исключения.
-   Для CRM API учитывать различия legacy и Factory/Service.
-   Проверять поведение на тестовой коробке до внедрения в production.
-   Не копировать примеры из интернета без проверки версии и контекста.
-   Не редактировать `/bitrix/` и ядро ради быстрого исправления: любая
    правка ядра теряется при обновлении и не диагностируется по исходникам.
    Точки расширения — события, `/local/`, собственный модуль.
-   Для PostgreSQL отдельно проверять прямые SQL-запросы и специфичные для
    СУБД конструкции.

### Как проверять версию ядра

-   `SM_VERSION` — версия продукта.
-   `\Bitrix\Main\ModuleManager::getVersion('main')` — версия модуля.
-   `class_exists()` + сверка с документацией — доступность класса.
-   `method_exists()` — доступность метода в конкретной версии.

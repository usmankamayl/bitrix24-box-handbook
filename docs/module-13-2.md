# Модуль 13.2: Интеграция со сторонними сервисами (AmoCRM, 1C, др.)

## Теория

На собеседовании редко спрашивают "как вызвать метод AmoCRM" — спрашивают, как вы спроектируете **надёжную** синхронизацию между двумя независимыми системами, которые ничего не знают друг о друге, могут временно лежать, и в которых одна и та же сущность имеет два разных ID. Это архитектурная тема, а не справочник по чужому API.

### Общая проблема любой интеграции: сопоставление сущностей

У сделки в Bitrix24 есть `ID = 142`. У того же клиента в AmoCRM — `ID = 9981`. В 1С — свой `ДокНомер`. Без явной таблицы соответствия вы не сможете понять при повторном обмене, что это один и тот же объект, и будете плодить дубли.

```sql
-- Таблица соответствия ID между системами — сердце любой интеграции
CREATE TABLE entity_mapping (
    id INT AUTO_INCREMENT PRIMARY KEY,
    entity_type VARCHAR(32) NOT NULL,       -- 'deal', 'contact', 'product'
    bitrix_id INT NOT NULL,
    external_system VARCHAR(32) NOT NULL,   -- 'amocrm', '1c'
    external_id VARCHAR(64) NOT NULL,
    last_synced_hash VARCHAR(64) NULL,      -- см. ниже: для определения, что реально изменилось
    updated_at DATETIME NOT NULL,

    UNIQUE KEY uniq_bitrix (entity_type, bitrix_id, external_system),
    UNIQUE KEY uniq_external (entity_type, external_system, external_id)
) ENGINE=InnoDB;
```

Два уникальных индекса — не избыточность: первый не даёт создать вторую запись-соответствие для уже привязанной сделки Bitrix24, второй — не даёт привязать один и тот же внешний объект к двум сделкам одновременно.

### Идемпотентность — без неё интеграция рано или поздно задвоит данные

Сеть ненадёжна: ответ от AmoCRM может не дойти до вас (таймаут), хотя сделка там уже создана. Если вы в этом случае просто повторите запрос на создание — получите дубль. Идемпотентная операция — та, которую можно безопасно повторить с тем же результатом.

```php
function syncDealToExternal(int $bitrixDealId, ExternalCrmClient $client, PDO $pdo): string
{
    $existing = findMapping($pdo, 'deal', $bitrixDealId, $client->systemName());

    $deal = CCrmDeal::GetByID($bitrixDealId);
    $payload = mapDealFields($deal);

    if ($existing) {
        // Сущность уже привязана — всегда UPDATE, никогда повторный CREATE
        $client->updateDeal($existing['external_id'], $payload);
        return $existing['external_id'];
    }

    // Перед созданием — на случай, если прошлая попытка создала запись,
    // но ответ не дошёл (таймаут) — пробуем найти по уникальному внешнему признаку
    $found = $client->findDealByExternalRef('bitrix_deal_id', $bitrixDealId);

    $externalId = $found['id'] ?? $client->createDeal($payload + ['bitrix_deal_id' => $bitrixDealId]);

    saveMapping($pdo, 'deal', $bitrixDealId, $client->systemName(), $externalId);
    return $externalId;
}
```

Ключевой приём: при создании объекта во внешней системе туда же пишется исходный `bitrix_deal_id` как кастомное поле. Это даёт возможность для **любого** будущего запроса найти "а не создавали ли мы уже это" — даже если ваша таблица `entity_mapping` была потеряна или рассинхронизировалась.

### Как не слать лишние запросы: хэш содержимого

При периодической синхронизации (крон раз в 5 минут, "просканировать все сделки, изменённые со времени последнего запуска") наивный подход — всегда отправлять `UPDATE` во внешнюю систему. Проблема: это расходует rate limit впустую, если реально ничего не изменилось (например, `TIMESTAMP_X` обновился из-за правки несвязанного поля).

```php
function syncIfChanged(array $deal, ExternalCrmClient $client, PDO $pdo, array $mapping): void
{
    $payload = mapDealFields($deal);
    $hash = md5(json_encode($payload));

    if ($hash === $mapping['last_synced_hash']) {
        return; // содержимое идентично тому, что уже отправлено — пропускаем
    }

    $client->updateDeal($mapping['external_id'], $payload);
    updateMappingHash($pdo, $mapping['id'], $hash);
}
```

### Направление синхронизации и разрешение конфликтов

Частый вопрос: "что если сделку одновременно изменили и в Bitrix24, и в AmoCRM?" Универсального правильного ответа нет — есть три стратегии, и на собеседовании важно уметь их назвать и обосновать выбор:

1. **Одностороння синхронизация (master/slave).** Одна система — источник истины (обычно 1С для товаров/остатков, Bitrix24 для статусов сделки). Конфликтов в принципе не возникает, т.к. вторая система только читает.
2. **Last-write-wins.** Побеждает более свежее по времени изменение (`updated_at`). Просто в реализации, но можно молча потерять изменения, если часы систем рассинхронизированы — на практике для этого применяют единый источник времени (например, время сервера синхронизации, а не время клиента).
3. **Разделение полей по владельцу.** Например, цену и остаток товара всегда диктует 1С, а статус сделки и комментарии менеджера — всегда Bitrix24. Конфликтов нет, потому что поля не пересекаются по "владельцу записи".

Для CRM-интеграций (AmoCRM ↔ Bitrix24) на практике почти всегда выбирают **одностороннюю** синхронизацию с одним источником правды, потому что двусторонняя синхронизация с произвольным разрешением конфликтов — источник большинства продакшен-багов такого рода интеграций.

### Обмен с 1С: протокол CommerceML

1С:Предприятие и Bitrix24/Bitrix-коробка по умолчанию общаются через стандарт **CommerceML 2** (XML) поверх HTTP-протокола обмена `1C-Bitrix: Управление сайтом` (он же протокол `CommerceML`/`import.php`). Это не REST и не JSON — исторически сложившийся XML-формат с собственной последовательностью запросов.

Последовательность обмена (упрощённо):

```
1C → сайт: ?type=catalog&mode=checkauth       → сайт отвечает success\nИмя_сессии\nЗначение_сессии
1C → сайт: ?type=catalog&mode=init            → сайт сообщает лимит размера файла
1C → сайт: ?type=catalog&mode=file&filename=... → сайт принимает файл за файлом (import1.xml, offers1.xml...)
1C → сайт: ?type=catalog&mode=import&filename=... → сайт разбирает присланный XML и применяет изменения
1C → сайт: ?type=sale&mode=query              → сайт отдаёт накопленные заказы в формате CommerceML
1C → сайт: ?type=sale&mode=success             → сайт помечает заказы как выгруженные (чтобы не выгрузить повторно)
```

Файл `import1.xml` — товары и их свойства (группы, картинки), `offers1.xml` — цены и остатки отдельно от товаров (чтобы можно было выгружать остатки часто, без перевыгрузки всей номенклатуры).

```xml
<!-- offers1.xml — фрагмент: только цены/остатки, без описаний -->
<КоммерческаяИнформация>
  <ПакетПредложений>
    <Предложения>
      <Предложение>
        <Ид>00000001</Ид>
        <Количество>42</Количество>
        <Цены>
          <Цена>
            <ИдТипаЦены>b7c3...</ИдТипаЦены>
            <ЦенаЗаЕдиницу>1990.00</ЦенаЗаЕдиницу>
            <Валюта>RUB</Валюта>
          </Цена>
        </Цены>
      </Предложение>
    </Предложения>
  </ПакетПредложений>
</КоммерческаяИнформация>
```

На стороне Bitrix24 (коробка) этот протокол уже реализован модулем `catalog`/`sale`, писать парсер вручную в современных проектах обычно не нужно — но понимать его шаги важно, чтобы диагностировать "обмен с 1С оборвался на файле offers3.xml" или "заказы из 1С не попадают выгрузкой обратно".

Для **облачного** Bitrix24 (не коробки) прямого XML-обмена CommerceML нет — интеграция с 1С там обычно делается через REST API (`crm.deal.add`, `catalog.product.*`) с собственным мостом-скриптом на стороне 1С или промежуточным сервером, который транслирует CommerceML в REST-вызовы.

### AmoCRM REST API: ключевые отличия от Bitrix24 REST

| | Bitrix24 | AmoCRM |
|---|---|---|
| Авторизация | OAuth 2.0 или webhook | OAuth 2.0 (long-lived access+refresh) |
| Пакетные запросы | `batch` (до 50 команд, 1 слот лимита) | `/api/v4/leads` с массивом в body (до 50 объектов за раз) |
| Кастомные поля | `UF_CRM_*`, строготипизированные | `custom_fields_values`, идентификатор поля из `/api/v4/leads/custom_fields` |
| Вебхуки о событиях | `event.bind` на конкретное событие | единая подписка на Webhooks API с массивом событий |

```php
// Пример: создание сделки в AmoCRM с привязкой к Bitrix24 через кастомное поле
function createAmoDeal(string $accessToken, int $bitrixDealId, array $fields): int
{
    $ch = curl_init('https://yourdomain.amocrm.ru/api/v4/leads');
    curl_setopt_array($ch, [
        CURLOPT_RETURNTRANSFER => true,
        CURLOPT_POST => true,
        CURLOPT_HTTPHEADER => [
            'Authorization: Bearer ' . $accessToken,
            'Content-Type: application/json',
        ],
        CURLOPT_POSTFIELDS => json_encode([[
            'name' => $fields['title'],
            'price' => $fields['opportunity'],
            'custom_fields_values' => [[
                'field_id' => AMOCRM_BITRIX_ID_FIELD_ID, // заранее созданное кастомное поле
                'values' => [['value' => (string) $bitrixDealId]],
            ]],
        ]]),
    ]);
    $raw = curl_exec($ch);
    curl_close($ch);

    $data = json_decode($raw, true);
    return $data['_embedded']['leads'][0]['id'];
}
```

### Очередь и повторные попытки — интеграция не должна тормозить основной процесс

Если синхронизация с AmoCRM/1С вызывается синхронно внутри обработчика `onCrmDealUpdate` (см. [8.4](module-8-4.md)), то недоступность внешнего сервиса (их плановые работы, сетевой сбой) превращается в недоступность вашего CRM для пользователя — сохранение сделки будет висеть, пока не истечёт таймаут HTTP-запроса.

Правильный паттерн — событие только **ставит задачу в очередь**, а сама отправка во внешнюю систему выполняется отдельным воркером/агентом с ретраями:

```php
// В обработчике события — только постановка в очередь, без сетевых вызовов
AddEventHandler('crm', 'OnAfterCrmDealUpdate', function ($fields) {
    enqueueSyncTask('deal', $fields['ID'], 'amocrm');
});

// Отдельный крон-агент — читает очередь, пробует синхронизировать, считает попытки
function processSyncQueueAgent(): string
{
    $tasks = getPendingSyncTasks(limit: 20);

    foreach ($tasks as $task) {
        try {
            syncDealToExternal($task['entity_id'], getAmoCrmClient(), getPdo());
            markTaskDone($task['id']);
        } catch (Throwable $e) {
            // Экспоненциальный backoff по числу попыток, не бесконечно —
            // после N неудач задача помечается failed и требует ручного разбора
            markTaskFailed($task['id'], $e->getMessage(), maxAttempts: 5);
        }
    }

    return '\\processSyncQueueAgent();';
}
```

Это тот же принцип, что и агенты из [1.3](module-1-3.md) — асинхронная обработка защищает основной пользовательский поток от деградации стороннего сервиса.

### Частые ошибки

- **Нет таблицы соответствия ID** — при повторном обмене система создаёт дубли вместо обновления существующих записей.
- **Создание объекта во внешней системе без идемпотентной проверки** — при таймауте сети повторный запрос создаёт дубль.
- **Синхронная отправка во внешний сервис прямо в обработчике события CRM** — недоступность стороннего API блокирует сохранение сделки в Bitrix24.
- **Отсутствие ретраев с ограничением попыток** — либо задача теряется при первом же сбое, либо (в другую крайность) ретраится бесконечно и забивает очередь.
- **Двусторонняя синхронизация без явного владельца поля** — конфликтующие правки в обеих системах перезаписывают друг друга непредсказуемо.
- **Игнорирование лимита batch в AmoCRM (50 объектов) и в Bitrix24 batch (50 команд)** — попытка отправить больше в одном запросе просто игнорируется или обрезается API.

## Вопросы для собеседования

**1. Зачем нужна отдельная таблица соответствия ID (`entity_mapping`), а не хранение внешнего ID прямо в сделке Bitrix24?**
Отдельная таблица позволяет хранить соответствия для нескольких внешних систем одновременно, не требует изменения структуры CRM-сущности и упрощает массовые операции (поиск по внешней системе, аудит несинхронизированных записей) без полного сканирования CRM.

**2. Как сделать создание сущности во внешней системе идемпотентным, если ответ на запрос создания не дошёл из-за таймаута?**
Перед повторной попыткой создания искать во внешней системе объект по заранее записанному туда уникальному признаку источника (например, кастомное поле `bitrix_deal_id`) — если найден, использовать его ID вместо создания нового.

**3. Почему синхронизацию лучше вызывать не напрямую в обработчике события CRM, а через очередь и отдельный воркер?**
Прямой синхронный вызов делает время ответа обработчика (и, соответственно, сохранения сделки для пользователя) зависимым от доступности и скорости стороннего API. Очередь с воркером изолирует сбои внешнего сервиса от основного пользовательского потока.

**4. Какие есть стратегии разрешения конфликтов при двусторонней синхронизации и какая предпочтительнее для CRM-интеграций?**
Одностороння синхронизация (один источник истины), last-write-wins по времени изменения, разделение полей по владельцу. Для CRM-интеграций (AmoCRM ↔ Bitrix24) обычно выбирают одностороннюю синхронизацию — она исключает конфликты в принципе.

**5. Чем протокол обмена с 1С (CommerceML) принципиально отличается от REST API Bitrix24/AmoCRM?**
CommerceML — это XML-протокол с собственной последовательностью запросов (checkauth → init → file → import → query → success), а не произвольные REST-вызовы. Товары и остатки передаются раздельными файлами (`import*.xml` и `offers*.xml`), чтобы часто меняющиеся остатки можно было выгружать без перевыгрузки полного каталога.

**6. Зачем при периодической синхронизации хранить хэш последнего отправленного состояния объекта?**
Чтобы не отправлять `UPDATE` во внешнюю систему, если реальных изменений в синхронизируемых полях не было (например, обновилась только служебная метка времени) — это экономит лимит запросов и уменьшает нагрузку на оба сервиса.

**7. В чём разница между выгрузкой каталога (`import*.xml`) и выгрузкой предложений (`offers*.xml`) в CommerceML?**
`import*.xml` содержит описания товаров (название, свойства, картинки, группы) — меняется редко. `offers*.xml` содержит только цены и остатки — меняется часто (несколько раз в день). Разделение позволяет выгружать актуальные остатки без перевыгрузки всего тяжёлого каталога.

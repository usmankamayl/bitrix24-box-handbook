# Модуль 11.4: Webhook и входящие данные в Bitrix24

## Теория

### Два вида webhook в Bitrix24

Путаница между ними — классический вопрос на собеседовании:

| | **Входящий вебхук** | **Исходящий вебхук** |
|---|---|---|
| Что это | URL-ключ для вызова REST-методов извне | Endpoint Bitrix24, который сам дёргает ваш сервер при событии |
| Кто инициатор | Внешняя система → Bitrix24 | Bitrix24 → ваш сервер |
| Где настраивается | Разработчикам → Вебхуки → Входящий вебхук | `event.bind` через REST или приложение |
| Авторизация | Токен в URL (`/rest/USER_ID/TOKEN/method`) | `application_token` в payload для проверки |
| Права | Фиксированные при создании (crm, task, user, ...) | В рамках приложения/вебхука |
| Лимиты | ~2 rps | Зависит от тарифа |

**Запомнить:** входящий = ты звонишь в Bitrix, исходящий = Bitrix звонит тебе.

---

### Входящий вебхук (inbound webhook)

#### Создание

В портале: **Разработчикам → Другое → Входящий вебхук** → выбрать права (crm, task, im, user, ...) → получить URL вида:

```
https://your.bitrix24.ru/rest/1/abc123def456/
```

Где `1` — ID пользователя, `abc123def456` — секретный токен.

#### Вызов методов

Любой REST-метод вызывается по этому URL:

```bash
curl -X POST "https://your.bitrix24.ru/rest/1/abc123def456/crm.deal.get" \
     -d "ID=123"
```

```php
// PHP-эквивалент
$ch = curl_init('https://your.bitrix24.ru/rest/1/abc/crm.deal.get');
curl_setopt_array($ch, [
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_POST => true,
    CURLOPT_POSTFIELDS => http_build_query(['ID' => 123]),
]);
$resp = json_decode(curl_exec($ch), true);
```

#### Особенности

- **Без OAuth** — никаких токенов обновлять не нужно, токен «вшит» в URL.
- **Права ограничены** — только те скоупы, которые выбраны при создании.
- **Не может вызывать методы, требующие авторизации приложения** — например, `placement.bind`, `bizproc.*` частично (зависит от версии).
- **URL = секрет.** Если утечётся — пересоздать.
- **Один вебхук = один пользователь.** Действия выполняются от его имени.

#### Когда использовать

- Скрипты-миграции и разовая автоматизация
- Простые интеграции: cron-выгрузка, импорт, отчёты
- Внутренние инструменты, где OAuth избыточен

**Не подходит для:** публичных приложений, многопользовательских сценариев, Marketplace-решений.

### Исходящий вебхук / события (outbound webhook, events)

Bitrix24 сам делает POST на ваш URL при наступлении события. Регистрируется через `event.bind`:

```php
CRest::call('event.bind', [
    'event'      => 'onCrmDealAdd',          // имя события
    'handler'    => 'https://myapp.com/h.php',
    'auth_type'  => 0,                        // 0 — OAuth (приложение), 1 — incoming webhook
    'event_type' => 'online',                 // 'online' или 'offline'
    'auth'       => 'my-secret-token',        // application_token — вернётся в payload
]);
```

#### Популярные события

- `onCrmDealAdd`, `onCrmDealUpdate`, `onCrmDealDelete`
- `onCrmLeadAdd`, `onCrmContactAdd`, `onCrmCompanyAdd`
- `onTaskAdd`, `onTaskUpdate`, `onTaskCommentAdd`
- `onVoximplantCallStart`, `onVoximplantCallEnd`
- `onAppInstall`, `onAppUninstall`
- `onBizProcWorkflowStart`, `onBizProcWorkflowEnd`

Список: `events` метод.

#### Payload обработчика

```php
// POST handler.php
$_REQUEST = [
    'event' => 'onCrmDealUpdate',
    'event_handler_id' => '42',
    'data' => [
        'FIELDS' => ['ID' => 123],
    ],
    'ts' => '1699000000',
    'auth' => [
        'application_token' => 'my-secret-token',
        'access_token' => 'xxx',      // для OAuth-приложения
        'refresh_token' => 'yyy',
        'domain' => 'your.bitrix24.ru',
        'member_id' => 'z1',
    ],
];
```

**Проверка `application_token`** — обязательна: иначе кто угодно сможет подделать запрос.

#### event_type: online vs offline

- `online` — событие приходит сразу, в реальном времени.
- `offline` — события накапливаются и приходят пачкой при следующем онлайн-вызове. Для редких/некритичных событий.

#### Отписка

```php
CRest::call('event.unbind', [
    'event' => 'onCrmDealUpdate',
    'handler' => 'https://myapp.com/h.php',
]);
```

### Безопасность входящих данных

1. **HTTPS только.** Никогда не принимайте на HTTP — токены и данные в открытом виде.
2. **Проверка `application_token`.** Всегда сверяйте с ожидаемым.
3. **Проверка `domain`/`member_id`.** Если приложение на несколько порталов — убедитесь, что это «свой».
4. **Валидация входных данных.** `ID` приводить к int, текст — escape для SQL/вывода.
5. **Rate limiting на своей стороне.** Ваш endpoint — публичный, защититесь от флуда.
6. **Не логировать секреты.** В лог пишите ID, event — но не `access_token`.

### Типичные сценарии

#### Сценарий 1: Синхронизация сделки из CRM в Slack

- `event.bind` на `onCrmDealAdd` + `onCrmDealUpdate`
- Handler проверяет `application_token`, забирает сделку через `crm.deal.get` и постит в Slack webhook.

#### Сценарий 2: Входящий вебхук для мобильного приложения

- Мобильное приложение дергает `/rest/1/token/crm.lead.add` при заполнении формы.
- На вебхуке включён скоуп `crm`.
- Лид создаётся от имени пользователя с ID=1.

#### Сценарий 3: Цепочка «событие → активити → внешний API»

- Событие `onCrmDealUpdate` → handler → ставит задачу в очередь
- Worker → внешний API → обратно в Bitrix через входящий вебхук.

---

### Сравнение: входящий вебхук vs OAuth-приложение

| | Входящий вебхук | OAuth-приложение |
|---|---|---|
| Установка | Один клик в админке | Регистрация, flow получения токена |
| Токен | В URL, не меняется | access_token истекает, refresh_token |
| Права | Фиксированы, минимальны | Запрашиваются при установке |
| Масштаб | Один портал, один пользователь | Много порталов, multi-tenant |
| Marketplace | Нет | Да |
| Использование | Скрипты, cron, внутренние | Приложения, продукт |

### Вопросы для собеседования

**1. Чем входящий вебхук отличается от исходящего?**
Входящий — URL-ключ, по которому внешняя система вызывает REST-методы Bitrix24. Исходящий — endpoint, который Bitrix24 сам дергает при событии. Первый «принимает» вызовы наружу из вашей системы, второй — «шлёт» события к вам.

**2. Почему входящий вебхук не подходит для публичного приложения?**
URL токена уникален для одного портала и одного пользователя — нельзя раздать клиентам, нет OAuth-обновления, нет разграничения прав по пользователям. Для публичного — OAuth-приложение.

**3. Как проверить, что POST на handler действительно от Bitrix24?**
По `auth.application_token` — секрет, который вы передали при `event.bind`. Дополнительно проверять `auth.domain` / `member_id`.

**4. Что делать, если handler события недоступен?**
Bitrix24 не гарантирует доставку — событие может быть потеряно. Поэтому критичные данные получайте через polling-запросы (cron), а события используйте как ускоритель. Либо держите очередь и делайте reconciliation раз в N минут.

**5. Чем online и offline события отличаются?**
Online — немедленно при каждом изменении. Offline — накапливаются и приходят пачкой при первом же вызове вашего endpoint. Для мониторинга в реальном времени — online, для некритичной статистики — offline.

**6. Что важно сделать в handler события в первую очередь?**
Проверить `application_token`, быстро ответить `200 OK`, положить задачу в очередь. Не делать долгую работу в handler — события могут приходить часто.

**7. Как отписаться от события?**
`event.unbind` с тем же `event` и `handler`, что были при `event.bind`. При деинсталляции приложения (`onAppUninstall`) — отписаться от всех событий и удалить свои сущности.

**8. Как создать лид через входящий вебхук?**
`POST /rest/USER_ID/TOKEN/crm.lead.add` с `fields[TITLE]`, `fields[NAME]`, `fields[PHONE]`. Вебхук должен иметь скоуп `crm`.

**9. Какие данные приходят в `data` у события?**
Зависит от события. Для `onCrmDeal*` — `data.FIELDS.ID` и (у `*Update`) изменённые поля. Для `onTask*` — `data.FIELDS.ID`, иногда ещё. Не рассчитывайте на полный объект — делайте `crm.deal.get` по ID, чтобы получить актуальные данные.

**10. Как избежать двойной обработки одного события?**
События могут приходить дублями. Делайте обработчик идемпотентным: проверяйте по ID сущности + timestamp или ведите таблицу обработанных `event_id`/`event_handler_id + ts`.

---

### Частые ошибки

- ❌ **Долгий handler события.** Если handler висит — последующие события таймаутят.
- ❌ **Нет проверки `application_token`.** Любой может шарить по вашему endpoint.
- ❌ **Логирование `access_token`.** Секрет в логах — утечка.
- ❌ **Считать, что событие = гарантированная доставка.** Нет — нужен polling/reconciliation.
- ❌ **Дубли из-за отсутствия идемпотентности.**
- ❌ **Не отписываться при деинсталляции.** Мусорные события летят в никуда.
- ❌ **Делать `crm.deal.get` синхронно в handler.** Лучше положить ID в очередь и ответить.

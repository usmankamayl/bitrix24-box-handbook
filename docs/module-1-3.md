# Модуль 1.3: Агенты и cron в Bitrix Framework

## 🎯 Цели модуля

После изучения модуля вы сможете:

- объяснить, как работают агенты;
- различать периодические и непериодические агенты;
- добавлять, изменять и удалять агентов;
- передавать параметры в методы агентов;
- понимать различия между запуском на хитах и через cron;
- настроить перенос всех агентов на cron;
- обрабатывать ошибки и проектировать надёжные фоновые задачи.

> **О версиях.** Материал опирается на традиционный публичный API `CAgent`. Особенности подключения ядра и настройки cron необходимо сверять с установленной версией модуля `main`. Актуальность изменений отдельных релизов на 4 ноября 2026 года без проверки установленного ядра не гарантируется.

# 📖 1. Что такое агенты

**Агент** — это зарегистрированная в Bitrix задача, которую ядро должно вызвать при наступлении времени её выполнения.

Агенты используются для:

- очистки устаревших данных;
- обработки очередей;
- отправки уведомлений;
- синхронизации с внешними системами;
- обновления статистики;
- подготовки отчётов.

Обычно агент представляет собой вызов функции или статического метода:

```php
\MyCompany\Project\Agents::heartbeat();
```

В записи агента хранятся, в частности:

| Поле | Назначение |
|---|---|
| `NAME` | PHP-выражение вызова агента |
| `MODULE_ID` | ID модуля, подключаемого перед вызовом |
| `ACTIVE` | Активность агента |
| `IS_PERIOD` | Правило расчёта следующего запуска |
| `AGENT_INTERVAL` | Интервал в секундах |
| `NEXT_EXEC` | Запланированное время следующего запуска |
| `LAST_EXEC` | Время последнего выполнения |
| `SORT` | Порядок обработки |

**Агенты не являются отдельными постоянно работающими процессами.** Чтобы агент выполнился, механизм проверки агентов должен быть запущен — например, при обращении к сайту или из cron.

По документации Bitrix Framework агенты выполняются **однопоточно**: если агент работает дольше 10 минут, система блокирует его повторный запуск (защита от дублирования), другие агенты и процессы это не затрагивает. Практический вывод: десятиминутная блокировка не заменяет ни собственный lock, ни идемпотентность — она покрывает только случай «тот же агент ещё выполняется в этом же механизме».

Ещё два следствия однопоточности:

- долгий агент задерживает остальные агенты, наступившие в этой же проверке;
- параллельный запуск того же агента из cron и с хита может произойти до истечения 10 минут — если конфигурация допускает оба источника.

# 📖 2. Две независимые характеристики агента

Важно не смешивать:

1. **Источник запуска проверки агентов:** хиты или cron.
2. **Правило расчёта следующего запуска:** `IS_PERIOD = Y` или `N`.

Это разные настройки.

## 2.1. Запуск на хитах

Проверка агентов инициируется при обработке обращений к сайту.

Особенности:

- выполнение зависит от посещений;
- при отсутствии запросов агент может запускаться с задержкой;
- работа агента может увеличивать время обработки запроса;
- тяжёлые задачи способны ухудшать отклик сайта.

## 2.2. Запуск через cron

Системный планировщик запускает PHP-скрипт, который загружает ядро и вызывает проверку агентов.

Особенности:

- нет зависимости от посещений;
- агент не выполняется внутри пользовательского HTTP-запроса;
- задержка зависит от частоты cron, нагрузки и состояния системы;
- сохраняется конкуренция за ресурсы сервера и БД.

> Cron запускает **проверку агентов**, а не обеспечивает точное время начала и успешное завершение каждого агента.

## Сравнение

| Параметр | На хитах | Через cron |
|---|---|---|
| Зависимость от посещений | Есть | Нет |
| Предсказуемость запуска | Ниже | Выше |
| Работа внутри HTTP-запроса | Возможна | Нет |
| Нагрузка на сервер и БД | Есть | Есть |
| Гарантия успешного выполнения | Нет | Нет |
| Типичное применение | Небольшие некритичные задачи | Регулярные фоновые задачи |

# 📖 3. Периодические и непериодические агенты

Названия Bitrix могут сбивать с толку: **оба типа могут запускаться многократно**.

Различие заключается в расчёте следующего времени выполнения.

## 3.1. Периодический агент: `IS_PERIOD = Y`

Следующий запуск рассчитывается относительно **предыдущего запланированного времени**.

Пример:

- плановый запуск: 12:00;
- интервал: 1 час;
- фактический запуск: 12:20;
- следующая плановая отметка: 13:00.

Если агент сильно отстал от расписания, возможны повторные выполнения для наверстывания пропущенных интервалов. Детали обработки отставания зависят от реализации ядра.

Такой режим подходит, когда важна привязка к последовательности плановых временных отметок.

## 3.2. Непериодический агент: `IS_PERIOD = N`

Следующий запуск рассчитывается относительно **фактического выполнения**, а не предыдущей плановой отметки. По документации Bitrix Framework формула такая:

```text
next_exec = время окончания работы + interval
```

В аналогичном примере следующая отметка будет примерно в 13:20.

Этот вариант часто удобнее для задач вида:

> Выполнить работу, затем повторить её через заданный интервал.

> **Важно:** `IS_PERIOD = N` не означает «выполнить один раз». Однократность определяется возвращаемым значением агента.

# 📖 4. Что должен возвращать агент

Для повторного выполнения агент возвращает строку следующего вызова:

```php
return "\\MyCompany\\Project\\Agents::heartbeat();";
```

Для завершения работы и удаления записи агента:

```php
return "";
```

При штатной обработке ядром пустой результат означает, что продолжать выполнение этого агента не нужно.

Неявный `null`, например из-за отсутствующего `return`, также может привести к удалению агента. Поэтому возвращаемое значение должно быть явным.

## Базовый пример

```php
<?php

namespace MyCompany\Project;

class Agents
{
    public static function heartbeat(): string
    {
        \CEventLog::Add([
            "SEVERITY" => "INFO",
            "AUDIT_TYPE_ID" => "PROJECT_AGENT_HEARTBEAT",
            "MODULE_ID" => "main",
            "ITEM_ID" => __METHOD__,
            "DESCRIPTION" => "Агент выполнен: " . date("c"),
        ]);

        return "\\" . __METHOD__ . "();";
    }

    public static function oneTime(): string
    {
        // Однократная операция.

        return "";
    }
}
```

Начальный `\` в строке вызова явно указывает на полное имя класса.

# 📖 5. Загрузка класса агента

Регистрация агента **не регистрирует автозагрузку его класса**.

К моменту выполнения класс должен быть доступен.

## Вариант A. Класс находится в собственном модуле

При добавлении агента укажите настоящий ID модуля:

```php
\CAgent::AddAgent(
    "\\MyCompany\\MyModule\\Agents::execute();",
    "mycompany.mymodule",
    "N",
    3600
);
```

Загрузку классов должен обеспечивать модуль.

## Вариант B. Проектный класс вне модуля

Например, вы размещаете показанный выше класс в:

```text
/local/php_interface/lib/Agents.php
```

И регистрируете его загрузку в проектном `init.php`:

```php
<?php

\Bitrix\Main\Loader::registerAutoLoadClasses(
    null,
    [
        \MyCompany\Project\Agents::class =>
            "/local/php_interface/lib/Agents.php",
    ]
);
```

При регистрации агента `MODULE_ID` можно оставить пустым:

```php
""
```

> Автозагрузка должна работать и при загрузке сайта через CLI. Нельзя рассчитывать на подключение класса только из шаблона или компонента.

# 📖 6. Добавление агента через `CAgent`

Основной API:

```php
\CAgent::AddAgent(
    $name,
    $module = "",
    $period = "N",
    $interval = 86400,
    $datecheck = "",
    $active = "Y",
    $next_exec = "",
    $sort = 100,
    $user_id = false,
    $existError = true
);
```

## Основные параметры

| Параметр | Значение |
|---|---|
| `$name` | Строка вызова функции или метода |
| `$module` | ID модуля |
| `$period` | `Y` или `N`: правило расчёта следующего запуска |
| `$interval` | Интервал в секундах |
| `$datecheck` | Служебная дата проверки; обычно передают пустую строку |
| `$active` | Активность: `Y` или `N` |
| `$next_exec` | Дата следующего, в том числе первого, запуска |
| `$sort` | Сортировка |
| `$user_id` | Параметр идентификатора пользователя, не переключатель cron |
| `$existError` | Управление сообщением об уже существующем агенте |

**Аргумента `IS_CRON` у этого метода нет.**

## 6.1. Агент с интервалом один час

```php
<?php

$agentId = \CAgent::AddAgent(
    "\\MyCompany\\Project\\Agents::heartbeat();",
    "",       // MODULE_ID
    "N",      // IS_PERIOD
    3600,     // Интервал: один час
    "",       // DATE_CHECK
    "Y",      // ACTIVE
    "",       // NEXT_EXEC
    100       // SORT
);

if ($agentId === false) {
    throw new \RuntimeException(
        "Не удалось зарегистрировать агент"
    );
}
```

Пустой `NEXT_EXEC` не означает, что метод будет выполнен прямо внутри `AddAgent()`. Агент становится доступным для выполнения при последующей проверке.

## 6.2. Первый запуск через неделю

```php
<?php

$nextExec = new \Bitrix\Main\Type\DateTime();
$nextExec->add("7 days");

$agentId = \CAgent::AddAgent(
    "\\MyCompany\\Project\\Agents::heartbeat();",
    "",
    "N",
    86400,
    "",
    "Y",
    $nextExec->toString(),
    100
);
```

Первое выполнение планируется через неделю, последующие — с интервалом в сутки.

> Реальное начало выполнения может быть позже `NEXT_EXEC`: это зависит от момента проверки агентов.

## 6.3. Где регистрировать агент

Подходящие места:

- установка собственного модуля;
- миграция;
- отдельный административный скрипт, запускаемый один раз.

**Не нужно вызывать `AddAgent()` на каждом хите.**

Повторная установка должна учитывать уже существующую запись. Проверка наличия агента полезна, но сама по себе не заменяет защиту от конкурентного запуска установочных процедур.

# 📖 7. Поиск, изменение и удаление агента

Для этих операций используем публичный API `CAgent`.

> Не следует автоматически считать, что для каждого старого класса Bitrix существует аналогичная D7-сущность. В этом модуле не используется неподтверждённый API вида `Bitrix\Main\Agent::add()`.

## 7.1. Поиск

```php
<?php

$name = "\\MyCompany\\Project\\Agents::heartbeat();";

$result = \CAgent::GetList(
    ["ID" => "ASC"],
    [
        "NAME" => $name,
        "MODULE_ID" => "",
    ]
);

while ($agent = $result->Fetch()) {
    // Дополнительно проверяем точное совпадение строки вызова.
    if ($agent["NAME"] !== $name) {
        continue;
    }

    echo "ID агента: " . (int) $agent["ID"];
}
```

## 7.2. Изменение интервала

```php
<?php

$agentId = 123; // ID существующего агента.

\CAgent::Update(
    $agentId,
    [
        "AGENT_INTERVAL" => 7200,
    ]
);
```

**Изменение интервала не следует считать автоматическим переносом уже записанного `NEXT_EXEC`.**

Если нужно изменить и ближайший запуск, задайте его явно:

```php
<?php

$nextExec = new \Bitrix\Main\Type\DateTime();
$nextExec->add("2 hours");

\CAgent::Update(
    $agentId,
    [
        "AGENT_INTERVAL" => 7200,
        "NEXT_EXEC" => $nextExec->toString(),
    ]
);
```

## 7.3. Деактивация

```php
\CAgent::Update(
    $agentId,
    [
        "ACTIVE" => "N",
    ]
);
```

## 7.4. Удаление по ID

```php
\CAgent::Delete($agentId);
```

## 7.5. Удаление по строке вызова и модулю

```php
\CAgent::RemoveAgent(
    "\\MyCompany\\Project\\Agents::heartbeat();",
    ""
);
```

Используйте одинаковое написание строки вызова при регистрации, поиске и удалении агента.

# 📖 8. Передача параметров

Аргументы записываются непосредственно в строку вызова:

```php
\MyCompany\Project\Agents::processUser(123, 'email');
```

Для следующего выполнения агент должен вернуть строку с нужными параметрами.

## Пример метода

Этот метод можно добавить в класс `Agents`:

```php
public static function processUser(
    int $userId,
    string $channel
): string {
    $userResult = \CUser::GetByID($userId);
    $user = $userResult->Fetch();

    if (!$user) {
        // Пользователь удалён: продолжать работу агента не нужно.
        return "";
    }

    // Обработка пользователя.

    return "\\" . __METHOD__
        . "("
        . $userId
        . ", "
        . var_export($channel, true)
        . ");";
}
```

## Регистрация

```php
<?php

$userId = 123;
$channel = "email";

$name = "\\MyCompany\\Project\\Agents::processUser("
    . (int) $userId
    . ", "
    . var_export($channel, true)
    . ");";

\CAgent::AddAgent(
    $name,
    "",
    "N",
    3600
);
```

## Почему нельзя просто подставлять строку

Ненадёжный вариант:

```php
return __METHOD__ . "($userId, '$channel');";
```

Если значение содержит кавычку, выражение может стать некорректным. При недоверенных данных возможен риск внедрения PHP-кода.

**Правила:**

- числовые идентификаторы приводите к нужному типу;
- строковые аргументы формируйте через `var_export()`;
- не сохраняйте секреты и большие структуры в `NAME`;
- для сложных задач передавайте ID записи, а данные храните в БД.

# 📖 9. Настройка запуска через cron

## 9.1. Сначала выберите режим

В традиционной конфигурации Bitrix встречаются два сценария:

### Сценарий A. Разделённый режим

Обычно:

- непериодические агенты, `IS_PERIOD = N`, обрабатываются через cron;
- периодические агенты, `IS_PERIOD = Y`, остаются на хитах.

В этом режиме участвуют cron-настройки ядра и константы `BX_CRONTAB_SUPPORT`, `BX_CRONTAB`.

### Сценарий B. Все агенты через cron

На хитах автоматическая проверка отключается, а cron-скрипт запускает проверку всех агентов.

**Ниже рассматривается только сценарий B.** Не смешивайте его с настройками разделённого режима.

> Если сервер уже настроен через BitrixVM, панель хостинга или другой служебный скрипт, сначала проверьте действующую конфигурацию. Возможно, запуск агентов уже организован.

## 9.2. Отключение автоматической проверки на хитах

Следующий код выполняется **однократно в административном контексте с подключённым ядром**, например в установочной процедуре или миграции:

```php
<?php

use Bitrix\Main\Config\Option;

Option::set("main", "agents_use_crontab", "N");
Option::set("main", "check_agents", "N");
```

Здесь:

- `check_agents = N` отключает автоматическую проверку агентов на хитах;
- `agents_use_crontab = N` используется в рассматриваемой схеме, чтобы проверка не делила агентов по `IS_PERIOD`.

Это не универсальная настройка для любого cron-сценария.

> В этой конфигурации нельзя заранее включать `BX_CRONTAB_SUPPORT` через `dbconn.php`, `init.php` или другой подключаемый код: это может вернуть разделение агентов по типу.

Переключение выполняйте согласованно с настройкой cron, иначе между отключением хитов и запуском планировщика задачи перестанут выполняться.

## 9.3. Скрипт запуска

Например, вы можете создать:

```text
/local/cron/agents.php
```

Содержимое:

```php
<?php

if (PHP_SAPI !== "cli") {
    http_response_code(403);
    exit("CLI only");
}

$_SERVER["DOCUMENT_ROOT"] = "/var/www/site";
$DOCUMENT_ROOT = $_SERVER["DOCUMENT_ROOT"];

define("NO_KEEP_STATISTIC", true);
define("NOT_CHECK_PERMISSIONS", true);

require $_SERVER["DOCUMENT_ROOT"]
    . "/bitrix/modules/main/include/prolog_before.php";

set_time_limit(0);

// В рассматриваемой схеме до этой точки не должны быть включены
// константы, переключающие CheckAgents() в разделённый cron-режим.
\CAgent::CheckAgents();

// Эти константы определяются ПОСЛЕ проверки агентов.
define("BX_CRONTAB_SUPPORT", true);
define("BX_CRONTAB", true);

// Необязательно: обработка очереди почтовых событий.
// Не дублируйте её, если она уже запускается отдельным заданием.
// \CEvent::CheckEvents();

require $_SERVER["DOCUMENT_ROOT"]
    . "/bitrix/modules/main/include/epilog_after.php";
```

Замените `/var/www/site` на реальный корень установки.

**Почему важен порядок:** в традиционном механизме ядра cron-константы могут влиять на отбор агентов. В данной схеме они определяются после `CheckAgents()`, а не до него. Так же устроен штатный скрипт ядра `/bitrix/modules/main/tools/cron_events.php`: `CAgent::CheckAgents()`, затем `define("BX_CRONTAB_SUPPORT", true)`, `define("BX_CRONTAB", true)`, затем `CEvent::CheckEvents()`. Если хотите меньше расхождений с ядром — берите этот файл за основу; в конце он вызывает `CMain::FinalActions()`, а не подключает `epilog_after.php` напрямую.

Перед применением проверьте, что эти константы не определены ранее в конфигурации проекта.

## 9.4. Задание crontab

Запуск каждую минуту:

```bash
* * * * * /usr/bin/php /var/www/site/local/cron/agents.php >> /var/log/bitrix-agents.log 2>&1
```

Условия:

- путь к PHP должен соответствовать нужной CLI-версии;
- пользователь cron должен иметь необходимые права;
- каталог журнала должен существовать;
- нужно настроить ротацию журнала.

Если интервал проверки — одна минута, агент с интервалом 10 секунд не будет стабильно запускаться каждые 10 секунд.

## 9.5. Защита от наложения cron-процессов

При наличии `flock` можно использовать альтернативную запись:

```bash
* * * * * /usr/bin/flock -n /var/lock/bitrix-agents.lock /usr/bin/php /var/www/site/local/cron/agents.php >> /var/log/bitrix-agents.log 2>&1
```

Это **замена**, а не дополнительное расписание.

Пользователь cron должен иметь право создавать lock-файл.

`flock` предотвращает параллельный запуск именно этого скрипта с тем же lock-файлом. Он не заменяет идемпотентность бизнес-операций и не защищает от всех способов запуска той же задачи.

## 9.6. Проверка настройки

После переключения убедитесь, что:

1. cron действительно запускает скрипт;
2. CLI использует подходящую версию PHP и расширения;
3. классы агентов загружаются;
4. у контрольного агента обновляются `LAST_EXEC` и `NEXT_EXEC`;
5. агент выполняется без посещений сайта;
6. в журналах нет ошибок;
7. отсутствуют дублирующие задания cron.

# 📖 10. Обработка ошибок

Для современного PHP обычно следует перехватывать `\Throwable`, если вы намерены обработать и исключения, и ошибки вроде `TypeError`.

## Пример безопасной оболочки агента

Методы можно добавить в класс `Agents`:

```php
public static function safeExecute(): string
{
    $nextCall = "\\" . __METHOD__ . "();";

    try {
        self::doWork();
    } catch (\Throwable $error) {
        // Ошибка в логировании не должна скрыть исходный сбой.
        try {
            $logId = \CEventLog::Add([
                "SEVERITY" => "ERROR",
                "AUDIT_TYPE_ID" => "PROJECT_AGENT_ERROR",
                "MODULE_ID" => "main",
                "ITEM_ID" => __METHOD__,
                "DESCRIPTION" => get_class($error)
                    . ": "
                    . $error->getMessage(),
            ]);

            if (!$logId) {
                error_log(
                    "[Project agent] " . $error->getMessage()
                );
            }
        } catch (\Throwable $loggingError) {
            error_log(
                "[Project agent] " . $error->getMessage()
                . "; logging error: "
                . $loggingError->getMessage()
            );
        }
    }

    // В этом примере выбран повтор на следующем интервале.
    return $nextCall;
}

private static function doWork(): void
{
    // Ограниченный объём работы.
}
```

### Что важно понимать

- Этот пример сознательно сохраняет агент для повторного запуска.
- Для постоянной ошибки бесконечные повторы могут быть вредны.
- Критические сбои требуют уведомления и мониторинга.
- `Throwable` не гарантирует обработку любого аварийного завершения процесса.
- Не следует возвращать значение из `finally`: это может подавить исключение или перекрыть другой `return`.

Для разных ошибок нужна разная политика:

| Ошибка | Возможная реакция |
|---|---|
| Временная недоступность API | Повтор с задержкой |
| Неверные входные данные | Зафиксировать ошибку, прекратить обработку записи |
| Ошибка конфигурации | Уведомить администратора, приостановить задачу |
| Частично выполненная операция | Продолжить с сохранённой контрольной точки |

# 📖 11. Внешние HTTP-запросы

Этот код недостаточен:

```php
try {
    $data = file_get_contents($url);
} catch (\Exception $error) {
    // ...
}
```

При сетевой ошибке `file_get_contents()` обычно выдаёт предупреждение и возвращает `false`, а не выбрасывает исключение.

Для HTTP-запросов можно использовать `Bitrix\Main\Web\HttpClient`. Его `get()` возвращает тело ответа строкой или `false` при сетевой ошибке; **пустая строка ошибкой не является** — её проверяют отдельно. Исключений метод не бросает.

## Пример вспомогательного метода

```php
private static function fetchJson(string $url): array
{
    /*
     * Тайм-ауты задаются только опциями конструктора: методов
     * setTimeout()/setStreamTimeout() у HttpClient нет.
     */
    $http = new \Bitrix\Main\Web\HttpClient([
        'socketTimeout' => 5,
        'streamTimeout' => 15,
        'redirect' => true,
        'redirectMax' => 2,
    ]);

    $body = $http->get($url);

    if ($body === false) {
        throw new \RuntimeException(
            "Ошибка HTTP-запроса: "
            . implode("; ", $http->getError())
        );
    }

    $status = $http->getStatus();

    if ($status < 200 || $status >= 300) {
        throw new \RuntimeException(
            "Неуспешный HTTP-статус: " . $status
        );
    }

    $data = json_decode(
        $body,
        true,
        512,
        JSON_THROW_ON_ERROR
    );

    if (!is_array($data)) {
        throw new \RuntimeException(
            "Ожидался JSON-объект или массив"
        );
    }

    return $data;
}
```

Для production дополнительно нужны:

- проверка структуры ответа;
- ограничение объёма данных;
- обработка пагинации;
- политика повторов;
- соблюдение rate limit;
- безопасное хранение токенов;
- отсутствие секретов в логах.

Адрес внешнего сервиса не следует без проверки брать из пользовательского ввода.

# 📖 12. Ручной запуск

Метод агента можно вызвать напрямую:

```php
$result = \MyCompany\Project\Agents::heartbeat();
```

Но это **не эквивалент запуска через планировщик**.

Прямой вызов сам по себе не выполняет:

- проверку `NEXT_EXEC`;
- служебную обработку записи агента;
- обновление `LAST_EXEC` и `NEXT_EXEC`;
- применение возвращённой строки;
- удаление записи при возврате `""`.

Например:

```php
\MyCompany\Project\Agents::oneTime();
```

выполнит метод, но не удалит зарегистрированный агент только потому, что метод вернул пустую строку.

Для диагностики доступны список агентов в административной части и запуск cron-скрипта из CLI. Названия и возможности административных действий могут отличаться между версиями.

> `CAgent::CheckAgents()` проверяет набор подходящих агентов, а не запускает исключительно один выбранный метод.

# 📖 13. Надёжность фоновых задач

## 13.1. Ограничивайте объём работы

Не обрабатывайте миллион записей за один запуск.

Лучше:

1. выбрать ограниченную порцию;
2. обработать её;
3. сохранить прогресс;
4. продолжить при следующем вызове.

Размер порции подбирается по времени выполнения и нагрузке.

## 13.2. Делайте операции идемпотентными

Повтор одного действия не должен приводить к повторному нежелательному результату.

Например:

- повторный запуск не отправляет одно письмо дважды;
- повторная синхронизация не создаёт дубликат;
- повторная обработка платежа не списывает деньги повторно.

Используйте:

- уникальные ключи операций;
- статусы обработки;
- ограничения уникальности в БД;
- транзакции;
- идемпотентные API внешних систем.

**Нельзя рассчитывать на семантику «ровно один раз» только за счёт агента или cron.**

## 13.3. Учитывайте конкуренцию

Одна бизнес-операция может запускаться:

- несколькими cron-процессами;
- вручную;
- другим агентом;
- обработчиком события;
- внешним запросом.

Штатные механизмы планировщика не заменяют защиту самой бизнес-операции.

## 13.4. Следите за состоянием

Полезные сигналы:

- последнее успешное выполнение;
- длительность обработки;
- число ошибок;
- размер очереди;
- количество повторных попыток;
- просроченные задачи.

`LAST_EXEC` не следует считать универсальным подтверждением успешного бизнес-результата. Для критичных процессов фиксируйте успех отдельно.

## 13.5. Не логируйте лишнее

Не записывайте в логи:

- пароли;
- токены;
- полные персональные данные;
- содержимое чувствительных ответов API.

Для файловых журналов нужны ограничение доступа и ротация.

## 13.6. Когда агента недостаточно

Для длительных, ресурсоёмких или высоконагруженных процессов рассмотрите:

- отдельные CLI-команды;
- очередь задач;
- выделенные worker-процессы;
- внешний планировщик.

Агент может выступать инициатором обработки, но не обязан выполнять всю тяжёлую работу самостоятельно.

# 🎯 Вопросы для собеседования

## 1. Что такое агент в Bitrix?

Зарегистрированная задача, которую ядро вызывает при наступлении времени выполнения. Обычно это функция или статический метод, возвращающий строку следующего вызова либо пустую строку для завершения.

## 2. Чем запуск на хитах отличается от cron?

На хитах проверка зависит от обращений к сайту и может влиять на обработку HTTP-запроса. Cron запускает проверку независимо от посещений, но не гарантирует точное время или успешное завершение задачи.

## 3. Что означают `IS_PERIOD = Y` и `N`?

- `Y` — следующий запуск рассчитывается относительно предыдущего запланированного времени.
- `N` — относительно фактического выполнения.

Оба типа могут выполняться многократно.

## 4. Что должен возвращать агент?

Строку следующего вызова:

```php
return "\\" . __METHOD__ . "();";
```

Либо пустую строку:

```php
return "";
```

Пустая строка при штатной обработке ядром приводит к удалению агента.

## 5. Как добавить агент?

```php
\CAgent::AddAgent(
    "\\MyCompany\\Project\\Agents::heartbeat();",
    "",
    "N",
    3600,
    "",
    "Y",
    "",
    100
);
```

## 6. Есть ли у `AddAgent()` аргумент `IS_CRON`?

Нет. Девятый аргумент — `$user_id`, а не признак запуска через cron.

Режим выполнения задаётся конфигурацией механизма агентов и cron-окружения.

## 7. Можно ли передавать параметры?

Да. Они включаются в строку вызова. Числа нужно приводить к типам, строки — корректно сериализовать, например через `var_export()`.

## 8. Что произойдёт при необработанном исключении?

Штатное завершение агента будет нарушено. Не следует рассчитывать, что ядро всегда автоматически восстановит выполнение нужным образом: последствия зависят от версии и контекста.

Нужны обработка ожидаемых ошибок, логирование, политика повторов и мониторинг.

## 9. Равен ли прямой вызов метода запуску агента?

Нет. Прямой вызов не выполняет служебную обработку записи агента и не применяет возвращаемую строку к его расписанию.

## 10. Как изменить интервал?

```php
\CAgent::Update(
    $agentId,
    [
        "AGENT_INTERVAL" => 3600,
    ]
);
```

Если нужно изменить ближайшее время выполнения, отдельно задают `NEXT_EXEC`.

## 11. Как удалить агент?

```php
\CAgent::Delete($agentId);
```

Или:

```php
\CAgent::RemoveAgent(
    "\\MyCompany\\Project\\Agents::heartbeat();",
    ""
);
```

## 12. Почему cron не гарантирует выполнение?

Может не работать сам cron, PHP может завершиться ошибкой, БД или API могут быть недоступны, процесс может быть остановлен. Нужны контроль состояния и восстановление после сбоев.

# ⚠️ Частые ошибки

## 1. Забыли вернуть строку следующего вызова

```php
// ❌ Агент не возвращает продолжение.
public static function execute()
{
    self::doWork();
}
```

```php
// ✅ Продолжение задано явно.
public static function execute(): string
{
    self::doWork();

    return "\\" . __METHOD__ . "();";
}
```

## 2. Используют девятый аргумент как переключатель cron

```php
// ❌ true здесь не означает «запускать через cron».
\CAgent::AddAgent(
    "\\MyCompany\\Project\\Agents::heartbeat();",
    "",
    "N",
    3600,
    "",
    "Y",
    "",
    100,
    true
);
```

Правильно — настраивать cron-режим отдельно.

## 3. Считают `IS_PERIOD = N` однократным запуском

Непериодический агент может повторяться бесконечно, если возвращает строку следующего вызова.

Для однократного агента нужно вернуть `""`.

## 4. Выполняют слишком много работы

```php
// ❌ Перенос на cron не делает такую задачу безопасной.
self::processAllMillionRecords();
```

```php
// ✅ Ограниченный объём и сохранение прогресса.
self::processNextBatch();
```

## 5. Не проверяют результат сетевого запроса

`try/catch` сам по себе не заменяет проверку `false`, HTTP-статуса и содержимого ответа.

## 6. Не обеспечивают загрузку класса

Класс доступен в компоненте, но отсутствует при запуске из CLI.

Решение — корректная модульная или проектная автозагрузка.

## 7. Добавляют несколько cron-заданий

Несколько расписаний одного скрипта могут привести к наложению процессов.

Проверьте системный crontab, задания пользователя, панель хостинга и служебные настройки окружения.

## 8. Возвращают результат из `finally`

Это может скрыть исключение. Возвращайте строку после корректно завершённого `try/catch`.

## 9. Имя агента собирает вспомогательный метод

```php
// ❌ __METHOD__ внутри getAgentName() — это имя самого getAgentName().
public static function execute(): string
{
    self::doWork();

    return self::getAgentName();
}

private static function getAgentName(): string
{
    return __METHOD__ . '();';
}
```

Ядро запишет в `b_agent.NAME` строку `...::getAgentName();`. На следующем запуске оно вызовет геттер, тот вернёт эту же строку, и так каждый раз: `LAST_EXEC` обновляется, ошибок в журнале нет, `doWork()` не выполняется никогда.

```php
// ✅ Имя — константа класса, рабочий метод возвращает её.
public const AGENT_NAME = '\\MyCompany\\Project\\Agents::execute();';

public static function execute(): string
{
    self::doWork();

    return self::AGENT_NAME;
}
```

Проверка одна: посмотреть `NAME` в списке агентов после первого запуска. Если там имя метода, который вы не планировали вызывать, — это дефект. Живой прогон — `examples/module-1-3/task-agent-probe/`, разбор — `examples/module-1-3/control-task/`.

# 📚 Практические задачи

Каждая задача выдаётся вместе с эталонным решением. Код лежит в
`examples/module-1-3/`, README каждой папки объясняет поток выполнения,
альтернативы и границы применимости. Смысл не в копировании, а в способности
объяснить решение и изменить его под новое условие.

Общая рамка набора: агент всегда возвращает собственное имя, объём работы за
запуск ограничен, регистрация идемпотентна, имя агента — константа класса.
Отдельно про автозагрузку: регистрация агента не регистрирует его класс, и без
`Loader::registerAutoLoadClasses()` или PSR-4 из `/local/composer.json` агент
отработает из cron с `Class not found`.

## Задача 1. Очистка устаревших записей

Создайте агент, удаляющий записи проектного журнала старше 30 дней.

**Требования:**

- обрабатывать не больше заданного количества записей за вызов;
- использовать явно заданный срок хранения;
- логировать число удалённых записей;
- корректно переживать повторный запуск;
- не затрагивать записи новее границы хранения.

**Решение:** `examples/module-1-3/practice-1-log-cleanup/` — ORM-таблица
журнала, порционная выборка `ID` по `< CREATED_AT`, удаление по primary key,
бюджет времени, `flock` от параллельного запуска, JSONL-отчёт, `CEventLog`
только на ошибках.

**Что проверить в решении:**

- старые записи удаляются, свежие и запись ровно на границе остаются;
- повторный прогон удаляет 0 строк;
- `check.php` печатает «старые удалены, свежие и граница сохранены, повтор
  идемпотентен — ок».

## Задача 2. Отправка уведомлений из очереди

Создайте агент обработки собственной таблицы очереди.

**Требования:**

- статусы `new`, `processing`, `sent`, `error`;
- ограниченный размер порции;
- число попыток и время следующей попытки;
- защита от конкурентного захвата одной записи;
- восстановление зависших записей;
- определённая стратегия защиты от дублей.

**Важный нюанс:** статус `sent` в вашей системе не всегда означает фактическую доставку письма адресату.

**Решение:** `examples/module-1-3/practice-2-email-queue/` — атомарный захват
через `UPDATE ... WHERE STATUS='new'`, `ATTEMPTS` + `LOCKED_UNTIL` +
экспоненциальный backoff, `recoverStuck()` для строк, чей процесс умер,
`UNIQUE(DEDUP_KEY)` + обработка `DuplicateEntryException` в `enqueue()`.

**Что проверить в решении:**

- повторная постановка письма возвращает `duplicate: true` и не создаёт строку;
- зависшая строка возвращается в `new`, а с исчерпанными попытками уходит в
  `error`;
- при отсутствии почтового шаблона строки уходят в повтор, а не в `sent`.

## Задача 3. Синхронизация с внешним API

Создайте агент получения изменений из внешней системы.

**Требования:**

- тайм-ауты;
- проверка HTTP-статуса и JSON;
- обработка пагинации;
- сохранение контрольной точки;
- идемпотентное обновление записей;
- ограниченные повторные попытки;
- отсутствие токенов в логах.

**Решение:** `examples/module-1-3/practice-3-api-sync/` — `HttpClient` с
`socketTimeout`/`streamTimeout` из конструктора, разбор ответа с проверкой
структуры, цикл по `next_cursor`, запись порции и курсора одной транзакцией,
upsert по `UNIQUE(EXTERNAL_ID)`, подставной провайдер `demo-api.php` для
локального прогона.

**Что проверить в решении:**

- повторная обработка не создаёт дубликаты;
- временная ошибка не теряет прогресс: курсор остаётся на последней успешной
  странице;
- некорректный ответ (503, битый JSON, запись без `id`) фиксируется, а не
  роняет прогон;
- следующий запуск продолжает с сохранённой точки.

## Задача 4. Пробник механики

Проверить на своей сборке то, о чём говорит теория: подпись `AddAgent()`,
наличие методов `CAgent`, поведение при повторной регистрации, связь
`AGENT_INTERVAL` и `NEXT_EXEC`, дефект «имя агента из `__METHOD__`», разницу
между прямым вызовом метода и запуском агента.

**Решение:** `examples/module-1-3/task-agent-probe/` — скрипт печатает
фактическое состояние `b_agent` и снимает свои записи после прогона. Он не
вызывает `CheckAgents()`, чтобы не запускать чужие агенты инсталляции.

**Зачем:** две формулировки теории (`NEXT_EXEC` при `Update`, число строк при
повторной регистрации) зависят от версии ядра. Пробник либо подтверждает их,
либо показывает расхождение — и тогда верить надо выводу, а не тексту.

## Контрольное задание

`examples/module-1-3/control-task/` — агент очереди с шестью поведенческими
дефектами (`broken.php`), эталон (`fixed.php`) и разбор «ошибка → причина →
последствие → условие проявления → исправление». Эталон выдаётся сразу: задача
на чтение и объяснение, а не на угадывание.

## Дополнительно

`examples/module-1-3/example-file-log-cleanup/` — тот же набор требований
(срок хранения, отчёт, идемпотентность, блокировка) на файловой системе:
`lstat`, запрет симлинков, повторная проверка метаданных перед удалением. Это
не задача 1: там журнал в БД и порции строк.

## Критерии приёмки

Запуски и `curl`-сценарии — материал «по желанию», они не являются условием
зачёта. Зачёт — это:

- объяснить, почему `IS_PERIOD = N` не означает «один раз», и что вернёт агент
  для повтора и для завершения;
- объяснить, откуда берётся идемпотентность в каждой из трёх задач (фильтр
  `< cutoff`, `UNIQUE(DEDUP_KEY)`, `UNIQUE(EXTERNAL_ID)`);
- объяснить, что произойдёт с записью агента при необработанном исключении и
  при `return;`;
- изменить любое решение под новое условие: другой срок хранения, другой
  интервал backoff, другой лимит страниц — и назвать, что при этом сломается.

# Модуль 11.3: Интеграция с внешними системами через REST

## Теория

### Что такое интеграция с внешними системами

**Интеграция** — обмен данными между Bitrix24 и сторонней системой (ERP, 1С, склад, банк, логистика, маркетинговая платформа). Задача — синхронизировать состояние двух систем: чтобы заказ из CRM появился в учётной системе, а статус доставки вернулся обратно в сделку.

---

### Направления интеграции

| Направление | Что происходит | Инструменты |
|---|---|---|
| **Из Bitrix24 наружу** | Изменения в CRM → уведомление внешней системы | REST-вызовы из активити, события `onCrm*` на свой сервер |
| **В Bitrix24 извне** | Внешняя система → обновление карточек/сделок | Входящие вебхуки, события `onCrm*`, `bizproc.event.send` |
| **Двусторонняя** | Обе стороны синхронно/асинхронно меняются | Комбинация плюс очередь и маппинг ID |

---

### Архитектурные паттерны

#### 1. Прямой вызов из активити/робота

Активити само дёргает внешний API и возвращает результат. Подходит для **коротких** операций: получить курс валют, проверить ИНН, создать заявку.

**Минусы:** лимит 30 сек на handler, внешний API может тормозить/падать.

#### 2. Очередь + фоновая обработка

Активити только ставит задачу в очередь (БД/RabbitMQ/Redis), а отдельный worker её выполняет. Результат возвращается асинхронно через `bizproc.activity.completed` или `bizproc.event.send`.

**Плюсы:** надёжность, retry, не блокируем БП.
**Применять почти всегда**, если операция дольше пары секунд.

#### 3. Событийная модель (webhooks Bitrix24 → наше приложение)

Bitrix24 вызывает наш endpoint при событиях `onCrmDealUpdate`, `onCrmContactAdd`, `onTaskAdd` и т.д. Мы реагируем: синхронизируем наружу или пишем в сделку.

```php
// Регистрация события
CRest::call('event.bind', [
    'event' => 'onCrmDealUpdate',
    'handler' => 'https://myapp.com/webhook.php',
    'auth_type' => 0, // 0 — OAuth; 1 — входящий вебхук (application_token)
]);
```

Обработчик:
```php
// $_REQUEST['event'] = 'onCrmDealUpdate'
// $_REQUEST['data']['FIELDS']['ID'] = 123
// $_REQUEST['auth']['application_token'] — для проверки подлинности
```

#### 4. Планировщик (polling)

Крон раз в N минут опрашивает внешнюю систему и/или Bitrix24, сверяет данные. Дешёво и надёжно, но не realtime. Подходит для справочников и редко меняющихся данных.

---

### Авторизация на стороне внешней системы

- **OAuth 2.0** — стандарт для SaaS (Stripe, Google, Facebook). Приложение получает `access_token` + `refresh_token`, обновляет при истечении.
- **API-ключ / Bearer token** — большинство внутренних и B2B API. Ключ передаётся в заголовке `Authorization: Bearer ...` или в query.
- **Basic Auth / подпись запроса** — банки, старые ERP. Проверяйте, как именно формируется подпись (HMAC, JWT, RSA).
- **IP-whitelist** — дополнительная защита на стороне API.

**Принципиально:** секреты храните в конфиге/секрет-хранилище, а не в коде. Токены пользователей Bitrix24 — тоже.

---

### Паттерн «двусторонняя синхронизация»

Самый сложный кейс на собеседовании — объяснить, как не допустить зацикливания и конфликтов:

1. **Маппинг ID.** Таблица `bitrix_id ↔ external_id`. Без неё не понять, какую сущность обновлять.
2. **Источник истины.** Для каждого поля решаете, кто «главный». Например, товарный остаток — склад, скидка клиента — CRM.
3. **Timestamp / версия.** Храните `updated_at` обеих сторон — пишете только если входящая версия новее.
4. **Loop-prevention.** Внешнее событие, порождённое вашей же записью, не должно триггерить обратную запись. Помечайте: `sync_source = 'external'` / `'bitrix'`, и фильтруйте свои же события.
5. **Dead-letter queue.** Неудачные синхронизации в отдельную таблицу для повторной отправки.

---

### Идемпотентность

Внешний API или Битрикс может прислать событие дважды. Операция должна быть **идемпотентной**: повторный вызов не создаёт дубль и не портит данные.

Приёмы:
- `external_id` уникальный в вашей БД — при повторе просто `UPDATE`, а не `INSERT`.
- `idempotency_key` в заголовках (Stripe-style).
- Проверка «такая сущность уже создана» перед `crm.deal.add`.

---

### Rate limits Bitrix24

- ~2 запроса в секунду на приложение/вебхук.
- `batch` — до 50 команд в одном запросе.
- При массовых операциях — очередь + throttling, иначе 429.
- `user.velvetrope` или свой middleware для ограничения частоты.

---

### Типичный стек интеграции

```
Bitrix24 ──► активити/событие ──► ваш сервер
                                     │
                                     ▼
                              Очередь (RabbitMQ/Redis/БД)
                                     │
                                     ▼
                            Worker / cron
                                     │
                                     ▼
                            Внешний API (REST/SOAP/GraphQL)
                                     │
                                     ▼
                            Ответ → Bitrix24 (event.send / обновление поля)
```

### Вопросы для собеседования

**1. Чем синхронная интеграция через активити отличается от асинхронной через очередь?**
Синхронная — handler активити сам вызывает внешний API и сразу завершает БП. Быстро реализуется, но ограничена 30 сек и не устойчива к падению API. Асинхронная — активити ставит задачу в очередь и завершает приём, worker обрабатывает и будит БП. Надёжнее, но сложнее.

**2. Как не допустить дублирования сделок при интеграции?**
Хранить маппинг `bitrix_id ↔ external_id`, проверять `external_id` перед созданием. Использовать `crm.deal.list` с фильтром по пользовательскому полю `UF_EXTERNAL_ID` — если нашли, `update`, иначе `add`.

**3. Как избежать «петли» синхронизации?**
При записи в Bitrix помечать `UF_SYNC_SOURCE = 'external'` и наоборот. Обработчик событий проверяет это поле и игнорирует события, порождённые синхронизацией (или запоминает ID последних обновлённых нами сущностей и фильтрует их события).

**4. Что делать, если внешний API не отвечает?**
Timeout в клиенте (5–10 сек), retry с экспоненциальной задержкой, dead-letter queue для несработавших. Активити завершать ошибкой, чтобы БП мог ветвиться (например, уведомить администратора).

**5. Как организована авторизация?**
Зависит от API. Для SaaS — OAuth 2.0 с хранением `access_token`/`refresh_token` и авто-обновлением. Для B2B — API-ключ в конфиге. Никогда не хранить в коде или передавать через клиента.

**6. Как справляться с лимитами Bitrix24?**
Batch-запросы (до 50 команд), очередь исходящих вызовов, кэширование справочников, соблюдать rate limit ~2 rps. При 429 — повтор через паузу.

**7. Какая роль событий `onCrm*` в интеграции?**
Это webhook-и от Bitrix24 на ваш сервер. Подписываетесь через `event.bind`, получаете POST с `event` + `data`. Реагируете: пишете в свой API, обновляете карточку, будите триггер.

**8. Что такое application_token и зачем его проверять?**
Произвольная строка, которую приложение передаёт при `event.bind` и которая возвращается в `auth.application_token` при каждом вызове handler. Нужна, чтобы проверить, что запрос действительно от вашего портала Bitrix24, а не поддельный.

**9. Как синхронизировать справочники (пользователи, товары, статусы)?**
Polling кроном — самое дешёвое. Либо событийно: слушать изменения в обеих системах и пушить диф. Товары обычно polling, статусы — события.

**10. Что делать, если поле в CRM имеет другой тип, чем во внешней системе?**
Нормализация на стороне приложения: конвертация дат, перечислений (ENUM ↔ UF-поле-список), денег (копейки ↔ рубли), телефонов (E.164). Маппинг-таблица для значений списков.

### Частые ошибки

- ❌ **Синхронный вызов внешнего API из handler активити.** Таймауты, падение БП.
- ❌ **Нет маппинга ID.** Дубли, невозможно найти связанную сущность.
- ❌ **Петля синхронизации.** Событие от Bitrix → запись в API → событие API → запись в Bitrix → событие...
- ❌ **Отсутствие retry/dead-letter.** Одна сетевая ошибка = потерянные данные.
- ❌ **Секреты в коде.** Утечка в репо — публичный взлом.
- ❌ **Игнорирование идемпотентности.** Дубли документов/сделок.
- ❌ **Нет мониторинга очереди.** Задачи копятся, никто не замечает.

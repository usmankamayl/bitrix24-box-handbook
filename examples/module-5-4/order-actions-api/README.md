# Кейс 2: REST-эндпоинт ЛК — детали, повтор, отмена заказа

## Что решает

AJAX-действия в личном кабинете: получить детали заказа JSON'ом, повторить заказ в корзину, отменить. Главные риски — **IDOR** (подставил чужой `order_id` → чужой заказ), дубли позиций при повторе, отмена оплаченного заказа без возврата.

## Ключевые приёмы

1. **Проверка владельца — первая строка после `Order::load`.** `(int)$order->getUserId() !== (int)$USER->GetID()` → 403. Без этого — IDOR-критика.

2. **`check_bitrix_sessid()`** — защита от CSRF: чужая страница не сможет вызвать `cancel` от имени залогиненного пользователя.

3. **401 до всего, 403 на чужой, 404 на несуществующий.** Порядок важен: сначала auth, потом владелец, потом бизнес-правила — иначе утечём информацию о существовании чужих заказов.

4. **Повтор заказа — мердж в корзину, а не перезапись.** `getExistsItem` проверяет, есть ли товар уже в корзине — если есть, плюсуем количество, иначе дубли.

5. **`CUSTOM_PRICE = 'N'` при повторе** — цена пересчитывается по правилам (акции могли закончиться). Не копируем старую цену вслепую.

6. **Отмена ≠ возврат денег.** Бизнес-правило: оплаченный заказ нельзя отменить — это рефанд, а не cancel. Проверяем `isPaid()`, `isCanceled()`, статус `DE/DF`.

7. **`setField('CANCELED','Y') + setField('STATUS_ID','A') + save()`** — через D7-модель, поднимет `OnSaleOrderCanceled` для ERP/письма.

8. **`isSystem()` в shipment-коллекции.** У заказа есть системная отгрузка "пустая" — пропускаем её, иначе в JSON будет мусорная запись.

## Тестирование

- `curl` без `sessid` → 403.
- `curl` с чужим `order_id` → 403 (проверка владельца).
- Два `repeat` подряд → в корзине один товар с x2 quantity, не два одинаковых.
- Отмена `P` статуса → ошибка "оформите возврат".
- Отмена `N` → заказ в `A`, сработал `OnSaleOrderCanceled`.

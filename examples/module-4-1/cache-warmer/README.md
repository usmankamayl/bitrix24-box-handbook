# Задача 3: CacheWarmer — проактивный прогрев кеша

## Контекст

На проде после деплоя или очистки кеша первые пользователи "вычисляют" все страницы заново. При 1000 RPS это может уронить БД. Senior-решение — прогреть кеш самим.

## Принципы правильного прогрева

1. **Не прогревать ВСЁ** — только топ-N (1000 товаров, главная, популярные разделы). Прогрев 50к товаров бессмысленен — их и так будут запрашивать редко.

2. **Не через HTTP** — loopback-запросы долгие и могут упасть. Вызывай producer-функцию напрямую.

3. **Идемпотентность** — повторный запуск не должен ломать существующий кеш (наш `ProductRepository::getById` сам проверяет `initCache`).

4. **Блокировка** — только один процесс прогревает одновременно (lock через кеш).

5. **Мониторинг прогресса** — прогрев может идти 20 минут. Сохраняем `processed/total` в кеш, админка показывает "Прогрето 45%".

6. **Rate limiting** — `usleep(50000)` между пачками, чтобы не душить БД.

## Запуск

```bash
# CLI
php cache-warmer.php --type=products --limit=1000

# Cron
*/15 * * * * php /var/www/cache-warmer.php

# Через Bitrix-агент (в init.php)
\CAgent::AddAgent('\\Vendor\\Shop\\Cache\\runProductsWarmAgent();', 'vendor.shop', 'N', 3600);
```

## Вопросы на собеседовании

- "Как не дать пользователям ждать при первом хите после деплоя?" → cache warming
- "Почему нельзя прогревать через HTTP-запросы?" → loopback, лишняя нагрузка на веб-сервер, сессии
- "Как ограничить время работы агента-прогревателя?" → `--limit` + `set_time_limit`, мониторинг `max_execution_time`

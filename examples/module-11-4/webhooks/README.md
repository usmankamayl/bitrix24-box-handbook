# Вебхуки Bitrix24 — входящие и исходящие

Два демонстрационных сценария, которые часто спрашивают на собеседовании.

## Структура

- `inbound/create_lead.php` — использование входящего вебхука для создания лида
- `outbound/install.php` — привязка исходящего вебхука (`event.bind`)
- `outbound/handler.php` — обработчик события `onCrmDealAdd`

## Сценарий 1: Входящий вебхук (inbound)

Вызываем REST-методы извне без OAuth — просто POST'ом на URL с токеном.

**Настройка:**
1. Портал → Разработчикам → Входящий вебхук → права `crm`, `task`.
2. Копируете URL: `https://portal.bitrix24.ru/rest/1/TOKEN/`
3. В `create_lead.php` подставляете его в `WEBHOOK`.

**Использование:**
```bash
php create_lead.php
```

Создаёт лид, читает его, выводит список. Подходит для cron-скриптов и внутренних инструментов.

## Сценарий 2: Исходящий вебхук (outbound)

Bitrix24 сам шлёт POST на ваш сервер при событии.

**Настройка:**
1. Впишите `INBOUND_WEBHOOK` (с правами `event`, `crm`, `task`) в `install.php` и `handler.php`.
2. В `install.php` — реальный URL `handler.php`.
3. `php install.php` — событие привязано.

**Что делает handler:**
- Проверяет `application_token` — отсекает чужие запросы
- Быстро отвечает `200 OK` и закрывает соединение
- Дедупликация по `{event}:{dealId}:{ts}` — идемпотентность
- `crm.deal.get` → `tasks.task.add` — ставит задачу менеджеру о новой сделке

## Ключевые моменты для собеседования

- Входящий = вы звоните в Bitrix; исходящий = Bitrix звонит вам.
- `application_token` в payload — обязательная проверка.
- События не гарантируют доставку — для критичных данных polling.
- Делайте handler быстрым и идемпотентным.
- При `onAppUninstall` отписывайтесь от всех событий (`event.unbind`).

# Эталон: служебная точка входа

## Что копировать

```
local/ajax/deal-status.php   →  /local/ajax/deal-status.php
```

## Как проверить

1. Скопировать файл на коробку в `/local/ajax/deal-status.php`.
2. Убедиться, что модуль `crm` установлен и есть хотя бы одна сделка (ID смотри в
   `/crm/deal/`).
3. Авторизоваться в браузере под пользователем, у которого есть доступ к сделке.
   В DevTools → Application → Cookies скопировать **всю строку `Cookie`** —
   сессионная cookie (`BITRIX_SM_SESSID`) и есть авторизация. Одна
   `BITRIX_SM_LOGIN=admin` не авторизует: логин в cookie не заменяет сессию.
4. `sessid` взять из `bitrix_sessid()` на любой странице (например, добавить
   `<?=bitrix_sessid()?>` в шаблон или посмотреть скрытое поле формы).

### Матрица сценариев

| Сценарий | Ожидание |
|---|---|
| `GET` (авторизован или нет) | `405`, заголовок `Allow: POST` |
| `POST` без сессионной cookie | `401` |
| `POST` с сессией, но без `sessid` | `403` |
| Нет `deal_id`; массив (`deal_id[]=1`); текст; `0`; отрицательное; переполнение | `400` |
| Доступная сделка | `200`, в теле только `ID`, `TITLE`, `STAGE_ID` |
| Существующая недоступная сделка | `404` (тот же ответ, что и для несуществующей) |
| Несуществующая сделка | `404` |
| Превышение лимита | `429`, `Retry-After` равен секундам до конца минуты |
| Ошибка CRM / исключение | `500`, без трассировки и HTML в теле |
| Любой штатный ответ | ровно один JSON, без дописанного вывода |
| Параллельные запросы | лимит может слегка превышаться (неатомарный счётчик); сессия закрыта после проверок |

### curl

```bash
# 405 — метод не тот
curl -i "http://box.local/local/ajax/deal-status.php"

# 401 — без сессионной cookie
curl -i -X POST "http://box.local/local/ajax/deal-status.php" -d "deal_id=1"

# 403 — сессия есть, sessid нет
curl -i -X POST "http://box.local/local/ajax/deal-status.php" \
  -H "Cookie: <вся строка Cookie из DevTools>" -d "deal_id=1"

# 200 — с sessid
curl -i -X POST "http://box.local/local/ajax/deal-status.php" \
  -H "Cookie: <вся строка Cookie>" -d "sessid=<sessid>&deal_id=1"

# 404 — несуществующая или чужая сделка
curl -i -X POST "http://box.local/local/ajax/deal-status.php" \
  -H "Cookie: <вся строка Cookie>" -d "sessid=<sessid>&deal_id=999999"
```

Ожидаемо: во всех случаях `Content-Type: application/json`, тело — валидный JSON,
никакого HTML вокруг. В `200` — объект `deal` с `id`, `title`, `stage`.

## Почему так, а не иначе

- **`prolog_before.php`, а не `header.php`.** Шаблон не нужен: он добавил бы
  HTML-шапку в JSON-ответ и потратил рендер.
- **Константы до пролога.** `NO_KEEP_STATISTIC` / `STOP_STATISTICS` /
  `NO_AGENT_STATISTIC` читаются в прологе; объявленные после — не работают.
- **`RestartBuffer()` до заголовков и тела.** Пролог, `init.php` или
  `display_errors=On` могут оставить вывод; без сброса буфера он станет
  префиксом к JSON. Если вывод уже ушёл в сокет, сброс не поможет — поэтому
  ничего не печатаем раньше этой строки.
- **Порядок проверок: метод → лимит → авторизация → CSRF → валидация.**
  Если проверять CSRF до авторизации, неавторизованный клиент получает разные
  ответы на разные запросы и может перебирать. Если ставить лимит после
  авторизации, `401` и `403` не лимитируются — перебор `sessid` бесплатен.
- **404 вместо 403** для чужой сделки: не раскрываем существование объекта.
- **`FinalActions()` и никакого `exit`.** Она собирает буфер, отдаёт ответ и
  вызывает `Application::end()` → `terminate()`, где стоит `exit()`. Поэтому
  после `401/403/404` второй JSON в тело уйти не может — не потому, что мы
  поставили `exit`, а потому что ядро завершает процесс. Отдельный `exit` после
  неё — мёртвый код, который маскирует непонимание механизма.
- **`die()` вместо `FinalActions()`** ответ отдаст (ob-буферы сбрасывает
  shutdown-хендлер `PrologActions`), но эпилог этого запроса не выполнится:
  ни `OnAfterEpilog`, ни `session_write_close()`, ни background jobs
  (`check_events`), ни `ManagedCache::finalize()`. Это задержка побочных
  эффектов, а не потеря ответа — поэтому дефект живёт в проде незамеченным.
- **Закрытие сессии.** Для файловых сессий `Application::getInstance()->getSession()->save()`
  эквивалентен `session_write_close()` и снимает блокировку файла. При сессиях
  в БД/Redis и в режимах `readonly`/`virtual` поведение зависит от настроек —
  проверяйте под свою конфигурацию.
- **Лимит на `ManagedCache`, а не `Data\Cache`.** После успешного `initCache()`
  вызов `startDataCache()` возвращает `false`, `endDataCache()` ничего не
  пишет, и счётчик застревает на `1`. `ManagedCache::read()/get()/set()`
  позволяет перезаписать значение. Проверка неатомарна: при параллелизме лимит
  можно слегка превысить. Для денежных квот нужен атомарный `INCR` в Redis или
  счётчик в БД.
- **`filter_var` вместо `ctype_digit`.** `ctype_digit` пропускает длинную строку
  цифр, а `(int)` насыщает её до `PHP_INT_MAX`; `filter_var` с `min_range`/
  `max_range` отсекает переполнение.
- **`getList` с `select` вместо `getById()`.** `getById()` тянет всю строку,
  включая текстовые поля; для ответа нужны только `ID`, `TITLE`, `STAGE_ID`.

## Проверка прав

`CCrmDeal::CheckReadPermission($id, $userPermissions = null, $categoryId = null)` —
сигнатура стабильна в CRM 20.x–24.x, второй и третий аргументы опциональны.
Если в вашей сборке она иная, сверьтесь с `crm_deal.php`; логика «нет прав →
404» не меняется.

## Что добавить в реальном проекте

- Атомарный счётчик для строгого rate limit (Redis `INCR`/`EXPIRE` или таблица в БД).
- Идемпотентность для операций записи: ключ запроса в заголовке + таблица результатов.
- Проверка `Origin`/`Referer` для браузерных вызовов (в дополнение к `sessid`).
- Логирование в отдельный канал, а не в общий `AddMessage2Log`.
- Для инфраструктурных ошибок (fatal в прологе, падение PHP-FPM) — настроить
  JSON-ответ на уровне nginx/PHP; контракт эндпоинта их не покрывает.

# Задача 2. Смена стадии сделки — решение

## Задание

`/local/ajax/deal-stage.php`: POST-эндпоинт смены стадии сделки с полной
проверкой прав, кодами ответов и идемпотентностью.

## Файлы

```
local/ajax/deal-stage.php  →  /local/ajax/deal-stage.php
```

## Как проверить

Подставить свои cookie и `sessid` (взять из любой страницы: `<?=bitrix_sessid()?>`).

```bash
# 405 — GET
curl -i "http://box.local/local/ajax/deal-stage.php"

# 401 — без cookie
curl -i -X POST "http://box.local/local/ajax/deal-stage.php" \
  -d "deal_id=1&stage_id=WON&request_id=req-00000001"

# 403 — авторизован, без sessid
curl -i -X POST "http://box.local/local/ajax/deal-stage.php" \
  -b "<cookie>" -d "deal_id=1&stage_id=WON&request_id=req-00000001"

# 400 — неизвестная стадия
curl -i -X POST "http://box.local/local/ajax/deal-stage.php" \
  -b "<cookie>" -d "sessid=<sessid>&deal_id=1&stage_id=NOPE&request_id=req-00000001"

# 404 — чужая или несуществующая сделка
curl -i -X POST "http://box.local/local/ajax/deal-stage.php" \
  -b "<cookie>" -d "sessid=<sessid>&deal_id=999999&stage_id=WON&request_id=req-00000002"

# 200
curl -i -X POST "http://box.local/local/ajax/deal-stage.php" \
  -b "<cookie>" -d "sessid=<sessid>&deal_id=1&stage_id=WON&request_id=req-00000003"

# 200 повторно с тем же request_id — стадия не меняется второй раз,
# ответ тот же (из кеша идемпотентности)
curl -i -X POST "http://box.local/local/ajax/deal-stage.php" \
  -b "<cookie>" -d "sessid=<sessid>&deal_id=1&stage_id=WON&request_id=req-00000003"
```

Проверка идемпотентности глазами: после первого запроса смени стадию вручную в
карточке сделки, затем повтори запрос с тем же `request_id` — стадия **не**
перезапишется, вернётся сохранённый ответ.

## Почему решение такое

- **Метод проверяется первым.** GET на write-эндпоинт — это либо ошибка клиента,
  либо CSRF-проба; отвечаем `405` + `Allow: POST`, не раскрывая ничего.
- **`401` до `403`.** Сначала «кто ты», потом «докажи, что это твой запрос».
  Наоборот — утечка: неавторизованный видит, что эндпоинт живой и требует sessid.
- **`request_id` обязателен и валидируется по формату.** Свободная строка в
  ключе идемпотентности — это возможность забить кеш мусором.
- **`400` на неизвестную стадию, а не молчаливая запись.** Стадии — справочник;
  запись `STAGE_ID = 'WON '` (с пробелом) ломает воронку и отчёты.
- **`404` вместо `403`** для чужой сделки: `403` подтверждает существование
  объекта и позволяет перебором узнать, какие ID есть в системе.
- **`CCrmDeal::Update`, а не `DealTable::update`.** Прямой ORM-апдейт не
  запускает события CRM, роботов и бизнес-процессы: сделка «переедет» по
  стадии, но автоматизация не сработает. ORM уместен в миграциях и импорте,
  где автоматизация как раз не нужна.
- **`FinalActions()` + `exit`** — эпилог выполняется, почтовые события уходят;
  остановку скрипта гарантирует следующий за `FinalActions()` явный `exit`.

## Альтернативы и когда они лучше

| Вариант | Когда лучше | Цена |
|---|---|---|
| `CCrmDeal::Update()` (выбрано) | обычная работа с CRM | медленнее ORM, тянет события |
| `\Bitrix\Crm\DealTable::update()` | миграции, импорт, массовые правки | не запускает роботов, БП, историю |
| `\Bitrix\Crm\Service\Container::getInstance()->getFactory(...)` | смарт-процессы и универсальный код | сложнее, нужен ID типа |
| REST-метод `crm.deal.update` | внешняя интеграция, другой сервер | сетевой хоп, лимиты, вебхук-права |

## Edge cases

**Покрыто:**

- неверный метод, нет авторизации, нет sessid;
- массивы вместо строк (`deal_id[]=1`): без проверки `is_string` приведение
  даёт warning и `1` вместо ошибки;
- неизвестная стадия;
- несуществующая или чужая сделка;
- повторный запрос с тем же `request_id`;
- исключение при записи → `500` без деталей.

**Не покрыто (осознанно, для демо):**

- **Гонка двух одновременных запросов с разными `request_id`** на одну сделку:
  кеш не атомарен. В проде — `UNIQUE(request_id)` в таблице журнала плюс
  транзакция.
- **Ограничение частоты** — нет; в проде считать через кеш/Redis по пользователю.
- **Проверка `Origin`/`Referer`** — нет; `sessid` закрывает CSRF, но для
  браузерных вызовов полезно и это.
- **Аудит** — нет записи «кто, когда, из какой стадии в какую»; в CRM это даёт
  история сделки, для внешних вызовов нужен свой журнал.

## Что здесь важно понять, а не скопировать

- Идемпотентность — это про **ключ запроса**, а не про «повторить и проверить».
  Кеш — компромисс; настоящая гарантия — уникальный индекс в БД.
- `404` вместо `403` — не стилистика, а защита от перебора.
- `CCrmDeal::Update` vs ORM — выбор между «работает автоматизация» и
  «быстро и без побочных эффектов».

# Контрольное задание: пять дефектов в одном фрагменте

`broken.php` — дефектный фрагмент, `fixed.php` — эталон. Задание: найти пять
дефектов, объяснить последствие каждого и условия, при которых он проявляется.
Проверять по `fixed.php` и по этому разбору.

## Как проверить

1. `broken.php` → `/local/ajax/control-broken.php`.
2. `fixed.php` → `/local/ajax/control-fixed.php`.
3. Сравнить ответы:

```bash
# дефектный: HTML-шаблон вокруг JSON, статус 200 всегда
curl -i -X POST 'https://box.local/local/ajax/control-broken.php' \
     -d 'deal_id=12&stage_id=NEW'

# эталон: чистый JSON, корректный код ответа
curl -i -X POST 'https://box.local/local/ajax/control-fixed.php' \
     -d 'deal_id=12&stage_id=NEW&sessid=<sessid>'
```

## Пять дефектов

### 1. `header.php` вместо `prolog_before.php`

**Причина.** Фрагмент скопирован со страницы сайта, а не с точки входа API.

**Последствие.** В ответ попадает HTML шаблона: `<!DOCTYPE html>`, `<head>`,
меню, подвал. Клиент делает `JSON.parse` и падает на первом символе `<`. При
этом сервер отвечает `200`, поэтому в мониторинге ошибок нет — проблема видна
только в браузере.

**Условие проявления.** Всегда, на любом запросе. Плюс каждый запрос рендерит
шаблон — это оплаченное время и память на пустом месте.

**Исправление.** `prolog_before.php` вместо `header.php` и `footer.php`.

### 2. Константы определены после пролога

**Причина.** `define('NO_KEEP_STATISTIC', true)` и `STOP_STATISTICS` стоят после
`require header.php`.

**Последствие.** Пролог уже выполнился: статистика записана, модуль `statistic`
подключён. Константы прочитаны не были, поэтому эффекта нет — код создаёт
иллюзию оптимизации.

**Условие проявления.** Всегда. Заметно по времени отклика и по записям в
таблицах статистики.

**Исправление.** Все константы — до `require` пролога.

### 3. Нет проверки метода, авторизации и `sessid`

**Причина.** Фрагмент писался «чтобы работало», проверки отложены.

**Последствие.**
- `GET`-запрос тоже меняет стадию (нет `isPost()`) — изменение по ссылке, его
  проиндексирует любой краулер, который дёргает ссылки.
- Неавторизованный клиент меняет данные (нет `IsAuthorized()`).
- Любой внешний сайт отправляет POST от имени пользователя (нет `sessid`) —
  классический CSRF.

**Условие проявления.** CSRF — при переходе по чужой ссылке; `GET` — при
размещении URL в письме или на странице.

**Исправление.** Порядок: метод → авторизация → CSRF → валидация. В `fixed.php`
именно так.

### 4. `(int)$_POST['deal_id']` без валидации строки

**Причина.** Приведение воспринимается как проверка.

**Последствие.**
- `deal_id=12abc` → `12`: запрос уходит к реальной сделке №12.
- `deal_id[]=1` → warning и `1`.
- `deal_id` отсутствует → warning «undefined array key» и `0`, дальше запрос к
  `getById(0)`.

**Условие проявления.** При любом кривом вводе; в PHP 8 warning'и попадают в
вывод при `display_errors = On` и ломают JSON.

**Исправление.** Сначала тип (`is_string`), потом формат (`ctype_digit`), потом
длина (≤ 10 цифр для `int(11)`).

### 5. `die()` вместо `FinalActions()`

**Причина.** «Скрипт закончился — значит, всё сделано».

**Последствие.** Ответ клиент получит (ob-буферы сбрасывает shutdown-хендлер
`CMain::PrologActions()`), а эпилог Битрикса не выполнится:
- `OnEpilog`, `OnAfterEpilog` не вызываются;
- `session_write_close()` не выполняется в `terminate()`;
- background jobs (`check_events`, `check_agents`) не запускаются — почтовые
  события этого запроса остаются в `b_event` и уходят при следующем запросе
  или по крону (задержка, а не гарантированная потеря);
- `ManagedCache::finalize()` и закрытие соединений с БД не выполняются.

**Условие проявления.** Проявляется не сразу: письма «залипают», фоновые задачи
не выполняются. Обнаруживается при разборе «почему уведомление не пришло».

**Исправление.** `$APPLICATION->FinalActions()` собирает буфер, отправляет ответ
и завершает приложение: внутри `Application::end()` → `terminate()` стоит
`exit()`. Свой `exit` после неё не нужен — это мёртвый код.

## Что здесь важно понять, а не скопировать

1. **Порядок проверок — часть контракта.** Метод, потом личность, потом CSRF,
   потом данные. Другой порядок даёт либо оракул для перебора, либо CSRF-окно.
2. **`die()` не «быстрый выход», а пропуск эпилога.** Письма не теряются
   безвозвратно: они остаются в `b_event` и уходят при следующем запросе или
   агентом — то есть задерживаются. Разница видна только на побочных эффектах,
   поэтому дефект живёт годами.
3. **Константы читаются прологом, а не после него.** Место объявления — не
   стилистика, а работоспособность.
4. **`(int)` — приведение, а не валидация.** Это самая частая ошибка в
   Bitrix-коде: `(int)` на мусоре даёт валидный ID.

## Альтернативы

| Решение в эталоне | Альтернатива | Когда лучше |
|---|---|---|
| `CHTTP::SetStatus()` | `http_response_code()` | Вне Bitrix; внутри ядра `CHTTP` учитывает настройки и `RestartBuffer` |
| `FinalActions()` | `CMain::FinalActions()` через глобальный объект | Одно и то же; вызов через `$APPLICATION` читается короче |
| `ctype_digit` + `strlen` | `filter_var($id, FILTER_VALIDATE_INT)` | Когда нужен диапазон `min_range`/`max_range` одной строкой |
| Проверки в точке входа | Middleware/фасад `Bitrix\Main\Routing` | В новых проектах на D7-роутинге; в старых сайтах точка входа остаётся нормой |

## Не покрыто осознанно

- Идемпотентность и оптимистичная блокировка — это задачи 2 и 3 практики, в
  контрольном фрагменте их нет, чтобы не раздувать задание.
- Аудит изменений и уведомления — зависят от требований инсталляции.

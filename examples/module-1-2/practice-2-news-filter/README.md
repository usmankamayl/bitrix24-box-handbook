# Практика 2. Фильтр, сортировка и кеш `study:news.filtered`

Продолжение практики 1: тот же список, но с тремя источниками условий и
явной политикой кеширования для каждого.

## Установка

```bash
cp -r component "$DOCUMENT_ROOT/local/components/study/news.filtered"
cp page.php "$DOCUMENT_ROOT/study-news-filtered/index.php"
```

Требуется инфоблок с разделами (для выпадающего списка). Ссылки на детальную
страницу — из настроек инфоблока.

## Три источника условий

| Источник | Кто задаёт | Куда попадает | Влияние на кеш |
|---|---|---|---|
| `$arParams` (`IBLOCK_ID`, `SORT_FIELD`…) | разработчик | настройки компонента | автоматически: все параметры в ключе |
| `FILTER_NAME` → `$GLOBALS['arrFilter']` | код страницы, умный фильтр | массив фильтра | через `CACHE_FILTER` или отключение кеша |
| `q`, `section` в GET | посетитель | массив фильтра | через `CACHE_FILTER` или отключение кеша |

Ключевая развилка — как в стандартных компонентах:

```php
if (!$this->arParams['CACHE_FILTER'] && $this->hasUserOrExternalFilter($filter)) {
    $this->arParams['CACHE_TIME'] = 0;
}
```

`CACHE_FILTER = N` + непустой фильтр = кеша нет вообще. Это не «плохо», это
честно: иначе кеш первого посетителя с фильтром «А» отдаётся всем остальным.
`CACHE_FILTER = Y` кладёт нормализованный фильтр в `$additionalCacheID` и
плодит отдельную запись кеша на каждое сочетание условий — при большом числе
комбинаций это тысячи файлов, поэтому в каталоге для этого есть фасетный индекс
(модуль 3), а не кеш компонента на каждый чих.

## Что проверять в коде

1. **Валидация GET** — `getUserFilter()`. Порядок: тип (`is_string`) → формат
   (`ctype_digit`) → диапазон/длина (`mb_substr`). Массив в `q` (`?q[]=1`) и в
   `section` не приводит к warning и не попадает в фильтр.
2. **Имя внешнего фильтра** проверяется регуляркой. `$$filterName`-подстановка
   из параметра без проверки — это исполнение произвольной глобальной
   переменной и потенциальный обход: имя вида `arrFilter[IBLOCK_ID]=999`
   ломает выборку.
3. **Сброс пагинации** при смене фильтра: `FORM_URL` собирается через
   `GetCurPageParam('', ['PAGEN_1'])`.
4. **Стабильная сортировка**: если `SORT_FIELD` не `ID`, добавляется `ID => DESC`.
   Без этого при равных значениях поля страницы 1 и 2 могут пересекаться.
5. **`component_epilog.php`** живёт в папке шаблона, выполняется и на попадании
   в кеш и видит только ключи из `setResultCacheKeys()` — здесь `ITEMS_COUNT`.
6. **Экранирование** — `htmlspecialcharsbx()` в шаблоне, включая `action` формы
   и `href` сброса: URL приходит из текущего запроса.

## Эксперименты

| Действие | Ожидаемое поведение |
|---|---|
| Ввести `q` и открыть страницу дважды | при `CACHE_FILTER=Y` — попадание в кеш своего варианта |
| `CACHE_FILTER=N`, ввести `q` | кеш не создаётся (`CACHE_TIME` обнулён) |
| `?q[]=1` | фильтр игнорируется, ошибок нет |
| `?section=abc` | фильтр игнорируется |
| `?section=999999` | пустой список, кеш пустого результата |
| Задать `$GLOBALS['arrFilter']` на странице | условия добавляются к выборке |
| Сменить фильтр на 2-й странице | попадание на 1-ю страницу результата |

## Границы применимости

- Поиск по названию — `'%NAME'`. Это `LIKE '%…%'`: индекс не используется, на
  сотнях тысяч элементов нужен полнотекстовый поиск или фасетный индекс.
- `SECTION_ID` + `INCLUDE_SUBSECTIONS` работает для одного раздела. Множественный
  выбор разделов — `SECTION_ID => [1,2]` (массив) в том же ключе фильтра.
- Умный фильтр каталога (`bitrix:catalog.smart.filter`) сюда не подключён:
  это модуль 3, там другой контракт (`arrFilter` + `CACHE_FILTER` + фасеты).
- GET-фильтр без AJAX — осознанно: сначала рабочая серверная версия, потом
  прогрессивное улучшение (см. практику 3 про AJAX).

# Практика 3. Форма `study:feedback`

POST-форма без кеша: `sessid`, honeypot, подписанная метка времени, ограничение
частоты, капча, почтовое событие Bitrix, AJAX как прогрессивное улучшение.

## Установка

```bash
cp -r component "$DOCUMENT_ROOT/local/components/study/feedback"
cp page.php "$DOCUMENT_ROOT/study-feedback/index.php"
```

1. В `page.php` замените `EMAIL_TO`.
2. В админке: **Настройки → Настройки продукта → Почтовые события → Типы событий**
   создайте тип с кодом `STUDY_FEEDBACK` и почтовый шаблон для нужного сайта.
   Поля, доступные в шаблоне: `#NAME#`, `#EMAIL#`, `#PHONE#`, `#MESSAGE#`,
   `#EMAIL_TO#`.
3. Отправьте форму. Письмо попадает в очередь `b_event`; фактическая отправка —
   агент/`cron` (`/bitrix/modules/main/tools/cron_events.php`).

Капча в `page.php` выключена (`USE_CAPTCHA => 'N'`), чтобы пример запускался без
настройки GD. Включите `'Y'`, если в PHP есть GD и капча разрешена в настройках
модуля `main`.

## Порядок проверок (и почему именно такой)

```
POST
 ├─ 1. check_bitrix_sessid()        иначе любой сайт отправит форму за пользователя
 ├─ 2. honeypot                     дёшево, боты заполняют; ответ нейтральный
 ├─ 3. подпись метки времени         бот не может подписать, человек медленнее 3 сек
 ├─ 4. throttle по сессии            одна отправка в 30 сек
 ├─ 5. типы/длины/формат             до любых внешних вызовов
 ├─ 6. капча                         последней: не сжигаем её на мусорные данные
 └─ 7. Event::send() + isSuccess()
```

Проверка капчи до валидации полей — типичная ошибка: пользователь с опечаткой в
email теряет введённый код и получает новую картинку.

## Почему нет `mail()`

| `mail()` | `Event::send()` |
|---|---|
| заголовки собираются вручную | шаблон письма и заголовки — из админки |
| `From: noreply@$_SERVER['HTTP_HOST']` — хост из запроса, подделывается | домен из настроек сайта |
| UTF-8 тема требует ручного MIME-кодирования | кодировка из шаблона |
| нет журнала и повторной отправки | запись в `b_event`, повтор агентом |
| ошибка — только код возврата PHP | `Result` с ошибками |

`Event::send()` возвращает `AddResult`: успех означает «событие поставлено в
очередь», а не «письмо доставлено». Обещать пользователю доставку нельзя.

## Что проверять в коде

1. **`check_bitrix_sessid()`** до чтения данных. `isPost()` — не CSRF-защита.
2. **Чтение POST** — `readFormData()`: `getPost()` возвращает `array|string|null`,
   поэтому сначала `is_string()`, потом нормализация. `?name[]=1` не превращается
   в «Array» и не даёт warning.
3. **Honeypot** отвечает «спасибо» без письма. Сообщение «бот обнаружен» учит бота
   пропускать это поле.
4. **Метка времени подписана** `Signer` с солью: подделать нельзя, продлить тоже.
   Проверяются обе границы — «слишком быстро» и «слишком долго».
5. **Ограничение частоты** — по сессии. Это не защита от распределённого флуда
   (для него нужен уровень nginx/файрвола/капчи), но от повторной отправки
   одним браузером — работает.
6. **Длины полей** ограничены на сервере (`MAX_LEN`) и в разметке (`maxlength`).
   Без серверного лимита одно поле на 10 МБ = одно письмо на 10 МБ.
7. **Ошибки `Event::send()`** уходят в `AddMessage2Log`, пользователю — нейтральный
   текст. Текст исключения наружу не отдаётся.
8. **AJAX**: сервер выбирает JSON по `X-Requested-With`, а не по скрытому полю
   формы. При падении JS форма отправляется обычным POST (`form.submit()` в
   `catch`).

## Эксперименты

| Действие | Ожидаемое поведение |
|---|---|
| Отправить пустую форму | ошибки по обязательным полям, данные сохранены |
| Отправить быстрее 3 секунд | «Не удалось отправить форму», письма нет |
| Подождать 3 сек и отправить | письмо в `b_event` |
| Отправить дважды подряд | вторая попытка упирается в throttle |
| Удалить `sessid` из POST (DevTools) | «Сессия истекла» |
| Заполнить скрытое поле `_website` | «Спасибо», письма нет |
| Включить AJAX-ветку (без JS-ошибок) | JSON-ответ, капча обновляется |

## Границы применимости

- `$_SESSION`-throttle не работает при отключённых сессиях и не помогает против
  распределённого флуда.
- Капча Bitrix — базовая; на реальном проекте добавляют rate limit на nginx,
  honeypot-поля с неслучайными именами и проверку репутации IP.
- Персональные данные (имя, телефон, email) попадают в `b_event`: срок хранения
  и согласие на обработку — отдельная задача, код её не решает.

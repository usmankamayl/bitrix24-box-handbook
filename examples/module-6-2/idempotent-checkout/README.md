# Кейс 2: «Дубли заказов при двойном клике / ретрае платежа»

## Что показывает

Реальная проблема в проде: пользователь дважды кликает «Оформить» → два заказа. Платёжка шлёт webhook дважды → двойное письмо об оплате.

## Три уровня идемпотентности

```
Фронт (UX)    → кнопка disabled, REQUEST_ID в form-data
Сервер (API)  → acme_idempotency таблица, INSERT IGNORE
БД            → UNIQUE INDEX на REQUEST_ID (страховка)
Webhook (ПС)  → проверка isPayed() до setPaid()
```

### 1. `REQUEST_ID` — ключ идемпотентности

- Генерируется на фронте при открытии формы (UUID v4).
- Хранится в `acme_idempotency` — таблица, не кеш (переживает перезапуск, кластерная БД).
- `INSERT IGNORE` — атомарная проверка: если ключ есть — `affected_rows = 0`, значит дубль.

### 2. Статусы: `processing` / `done` / `failed`

- `processing` — ключ занят, заказ создаётся. Второй запрос видит это и ждёт/возвращает 202.
- `done` — заказ создан, возвращаем `ORDER_ID` без повторного создания.
- `failed` — ошибка при `save()`, ключ можно переиспользовать.

### 3. Webhook платёжной системы — `isPayed()` до `setPaid()`

```php
if ($payment->isPaid()) {
    http_response_code(200);
    die('already paid'); // это ОК, не ошибка
}
// только потом setPaid('Y') + save
```

**Почему 200, а не ошибка?** Если вернём 500 — ПС будет ретраить до таймаута. 200 + «already paid» = корректно обработано.

### 4. Подпись до всего остального

```php
$raw = file_get_contents('php://input'); // сырое тело!
$expected = hash_hmac('sha256', $raw, $secret);
hash_equals($expected, $post['signature']);
```

- `php://input`, не `$_POST` — распарсенные поля могут быть переупорядочены.
- `hash_equals` — защита от timing attack.

## Anti-pattern: «проверим в JS»

```javascript
// ❌ Недостаточно:
$('#submit').click(function() {
    $(this).prop('disabled', true);
});
```

Пользователь может перезагрузить страницу, открыть вторую вкладку, нажать back. JS — UX-защита, не безопасность.

## Senior-ответ на собеседовании

> «Идемпотентность на трёх уровнях: REQUEST_ID с фронта + таблица с UNIQUE INDEX — атомарная проверка через `INSERT IGNORE`. Для webhook — `isPayed()` до `setPaid`, и 200 OK даже на дубль. Отдельно статус `processing` — чтобы параллельные запросы с тем же ключом не создавали два заказа.»

## Что спросят

- «Почему `INSERT IGNORE`, а не `SELECT + INSERT`?» — race condition: между SELECT и INSERT два запроса могут пройти параллельно. `INSERT IGNORE` — атомарно.
- «Что если заказ создался, но `markDone` упал?» — заказ есть, ключ в `processing`. Retry приведёт к проверке статуса — можно либо найти заказ по `XML_ID`, либо дать ключу TTL.
- «Зачем `hash_equals`, а не `==`?» — `==` подвержен timing attack (время ответа зависит от префикса совпадения).

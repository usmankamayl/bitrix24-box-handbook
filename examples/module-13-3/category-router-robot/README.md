# REST-робот: перенос сделки в другую воронку по условию суммы

Робот (простое автоматическое действие на стадии), который переводит сделку
в указанную воронку и выбирает там подходящую стадию по семантике (`P` /
`S` / `F`), а не по жёстко зашитому `STAGE_ID`. Работает, только если сумма
сделки достигает заданного порога — пример того, как кастомная логика
расширяет штатных роботов без полноценного бизнес-процесса.

## Файлы

- `crest.php` — минимальный REST-клиент (вебхук-режим)
- `install.php` — скрипт регистрации робота через `bizproc.robot.add`
- `handler.php` — обработчик, который Bitrix24 дёргает при срабатывании робота

## Установка

1. Создайте входящий вебхук с правами `bizproc` и `crm`, укажите его в `crest.php` → `C_REST_WEB_HOOK_URL`.
2. Разместите `handler.php` на публичном сервере, подставьте его URL в `install.php` → `HANDLER`.
3. Запустите `install.php` один раз (в браузере или через `php install.php`) — он зарегистрирует робот в портале.
4. В интерфейсе Bitrix24: CRM → Автоматизация → на нужной стадии добавьте робот **"Перенести сделку в другую воронку"**, заполните параметры.

## Параметры робота

| Параметр | Тип | Назначение |
|---|---|---|
| `target_category_id` | int (обяз.) | ID воронки-получателя. `0` — воронка по умолчанию |
| `min_opportunity` | double | Минимальная сумма сделки; пусто — без условия |
| `target_stage_semantics` | string | `P` — в работе (по умолчанию), `S` — успешно, `F` — провалено |

## Ключевые моменты для собеседования

- **Робот ≠ custom activity.** Робот регистрируется через `bizproc.robot.add`, работает только в простом "выполнить действие" режиме, не возвращает OUTPUT-параметры для последующих шагов БП. Activity — через `bizproc.activity.add`, нужен для полноценного конструктора БП с ветвлением и возвратом переменных (см. `examples/module-11-1/`).
- **`CATEGORY_ID` и `STAGE_ID` меняются одним вызовом `crm.deal.update`.** Если поменять только `CATEGORY_ID`, старый `STAGE_ID` не существует в новой воронке — сделка "теряется" из канбана.
- **Стадия ищется по `SEMANTICS`, а не по `STAGE_ID`.** `STATUS_ID` вроде `C2:UC_8X3F2A` ломается при переименовании/перестройке стадий администратором; семантика `P`/`S`/`F` — нет.
- **Обработчик отвечает мгновенно и работает после `fastcgi_finish_request()`** — лимит ответа обработчика ~30 секунд, без этого сделка просто "зависнет" на шаге робота.

Подробный теоретический разбор — в `docs/module-13-3.md`.

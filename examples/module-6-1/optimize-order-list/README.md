# Задача 1: Оптимизация медленного списка заказов

## Что показывает

Классическая собеседовательная задача «страница грузится 8 секунд». Четыре подхода от худшего к хорошему:

| Подход | Запросов | Что делает |
|--------|----------|-----------|
| `getOrdersBad` | 120+ | `Order::load()` в цикле — N+1 |
| `getOrdersGood` | 3 | Один `getList` + два `batch-join` на связанные таблицы |
| `getOrdersCursor` | 1 | Курсорная пагинация вместо `OFFSET` |
| `getOrdersCached` | 0-3 | Кеш с тегами поверх оптимизированного запроса |

## Senior-инсайты

1. **`Order::load` в цикле — табу.** `load()` тянет все коллекции (корзину, свойства, оплаты, отгрузки). На 20 заказов — минимум 80 запросов.

2. **Кеш — последний шаг, не первый.** Закешировать N+1 = скрыть проблему. Оптимизируем запросы, *потом* добавляем кеш.

3. **OFFSET на большой таблице всё равно тормозит.** `LIMIT 20 OFFSET 40000` сканирует 40K строк чтобы их выкинуть. Курсор (`WHERE ID < :last_id`) — O(1).

4. **Тегированный кеш** — не просто TTL 5 минут, а тег `sale_order_u{userId}` который сбрасывается в `OnSaleOrderSaved`. Иначе пользователь увидит старый заказ после оплаты.

5. **`SqlTracker` — инструмент диагностики.** Всегда начинаем с `start()`/`getCounter()`/`getTime()`, а не с «наверное кеша не хватает».

## Как запустить

```bash
php optimize.php
```

Для теста сравнения: вызовите `getOrdersBad(1)` и `getOrdersGood(1)` с включённым `SqlTracker` — разница в 40 раз по запросам.

## Что спросят на собеседовании

- «Почему `Order::load` — это много запросов?» — потому что он собирает Order со всеми коллекциями (basket, payment, shipment, property, status history).
- «Почему `OFFSET 40000` медленный?» — скан 40000 строк индекса, которые потом отбрасываются.
- «Что такое курсорная пагинация?» — запоминаем ID последнего элемента, следующая страница = `WHERE ID < :last`.
- «Как инвалидировать кеш?» — тег + обработчик `OnSaleOrderSaved`, вызываем `clearByTag`.

  📄 topics/module-6-1.md — Теория

  ✅ Сильные стороны

  - Структура четкая: типы задач → разбор конкретных примеров → формула ответа
  - Реальный senior-подход: «диагноз перед лечением», а не «ставим Redis»
  - Практичные примеры кода в теории (короткие сниппеты для иллюстрации)
  - Таблица префиксов фильтра D7 — отличная шпаргалка

  ⚠️ Замечания

  1. Неточность в примере getList (строка 54)

  '%NAME' => 'тест'   // WRONG: даст `NAME LIKE '%тест%'`
  Проблема: Префикс % в Bitrix D7 работает не так. Это не LIKE, а MATCH для
  полнотекста. Для LIKE нужно:
  'NAME' => '%тест%'  // правильно для LIKE

  2. Противоречие в примере фильтрации (строки 39-49)

  'filter' => [
      'STATUS_ID' => 'N',
      '>=DATE_INSERT' => new \Bitrix\Main\Type\DateTime('-30 days'),
      '>PRICE' => 1000,
  ],
  Вопрос в строке 54: "почему >PRICE строкой '>'?"

  Ответ неполный. Надо объяснить: ключ в filter — это строка с префиксом.
  '>PRICE' — это ключ массива, а не "строка и число". Реальный код корректен, но
  объяснение может запутать.

  3. Неточность в описании fetchAll() (строка 56)

  Почему не `fetchAll()` на 5000? — memory limit
  Правильно, но неполно. fetchAll() загружает весь результат в массив сразу. На
  5000 строк × 10 полей × ~100 байт/поле = ~5MB — это еще норма. Проблема на
  действительно больших выборках (50K+). Стоит уточнить:

  ▎ «fetchAll() на большой выборке (десятки тысяч строк) съест память; 
  ▎ while(fetch()) — потоковая обработка»

  4. Пропущен важный момент про транзакции (строка 125)

  5. Когда нужна транзакция? — когда несколько пишущих операций должны быть
  атомарны
  Не хватает подводного камня: Транзакция в Bitrix начинается автоматически при
  вызове save() в D7. Явный $connection->startTransaction() нужен только если:
  - Несколько независимых save() должны быть атомарны
  - Legacy-код ($DB->Query)
  - Нужен SELECT ... FOR UPDATE

  Стоит добавить:

  ▎ «В D7 $order->save() уже внутри транзакции. Явный startTransaction() — когда
  ▎ несколько независимых записей или FOR UPDATE»

  📝 optimize-order-list/optimize.php

  ✅ Что хорошо

  - Четыре варианта от N+1 до кеша — отличная прогрессия
  - SqlTracker в начале — правильный подход
  - Курсорная пагинация — редко показывают, а это важно

  ⚠️ Баги и замечания

  1. NPE в getOrdersBad (строка 71-74)
  'CITY' => $order->getPropertyCollection()
      ->getItemByOrderPropertyCode('CITY')
      ->getValue(), // NPE если нет свойства
  Проблема: getItemByOrderPropertyCode вернет null, если свойства нет → NPE на
  getValue().

  Исправление:
  $cityProp =
  $order->getPropertyCollection()->getItemByOrderPropertyCode('CITY');
  'CITY' => $cityProp ? $cityProp->getValue() : '',

  2. Неверный фильтр в batch-загрузке свойств (строка 128-129)
  'filter' => [
      '=ORDER_ID' => $orderIds,
      'ORDER_PROPS.CODE' => 'CITY', // через связь к b_sale_order_props
  ],
  Проблема: ORDER_PROPS — это не связь в OrderPropsValueTable. Правильная связь:
  'ORDER_PROPERTY.CODE' => 'CITY'
  Или через явный runtime:
  'runtime' => [
      new Entity\ReferenceField(
          'PROP',
          \Bitrix\Sale\Internals\OrderPropsTable::class,
          ['=this.ORDER_PROPS_ID' => 'ref.ID'],
          ['join_type' => 'INNER']
      ),
  ],
  'filter' => [
      '=ORDER_ID' => $orderIds,
      'PROP.CODE' => 'CITY',
  ],

  3. Кеш-ключ небезопасен (строка 195)
  if ($cache->initCache($cacheTtl, $cacheKey, 'sale_orders', 'sale_order_u' .
  $userId)) {
  Проблема: Четвертый параметр initCache — это base_dir, а не тег. Теги
  регистрируются через registerTag. Код не работает как задумано.

  Исправление:
  if ($cache->initCache($cacheTtl, $cacheKey, 'sale_orders')) {
      return $cache->getVars();
  }
  (теги уже правильно регистрируются в startDataCache)

  📝 sql-interview-questions/sql_tasks.php

  ✅ Что хорошо

  - Пять типовых задач — отличный набор для собеседования
  - Бонусная задача "товар X без Y" — нестандартная, показывает глубину

  ⚠️ Баги и замечания

  1. Избыточная группировка в ЗАДАЧЕ 2 (строка 53)
  'group' => ['PRODUCT_ID', 'NAME'],
  Проблема: NAME — это поле из b_sale_basket, оно может различаться для одного
  PRODUCT_ID (например, если название товара менялось). Группировать надо только
  по PRODUCT_ID, а NAME брать через MIN() или MAX():
  'select' => [
      'PRODUCT_ID',
      'NAME' => new SqlExpression('MIN(NAME)'), // берем любое название
      'TOTAL_QTY' => new SqlExpression('SUM(QUANTITY)'),
      'TOTAL_SUM' => new SqlExpression('SUM(PRICE * QUANTITY)'),
  ],
  'group' => ['PRODUCT_ID'],

  2. Проблема с JOIN в ЗАДАЧЕ 3 (строки 64-82)
  'filter' => [
      'PROP_VALUE.ORDER_PROPS.CODE' => 'CITY',
      'PROP_VALUE.VALUE' => 'Москва',
  ],
  Проблема: Связь ORDER_PROPS в фильтре не работает без явного runtime. Код не
  выполнится.

  Исправление:
  'runtime' => [
      new Entity\ReferenceField(
          'PROP_VALUE',
          OrderPropsValueTable::class,
          ['=this.ID' => 'ref.ORDER_ID'],
          ['join_type' => 'INNER']
      ),
      new Entity\ReferenceField(
          'ORDER_PROP',
          \Bitrix\Sale\Internals\OrderPropsTable::class,
          ['=ref.PROP_VALUE.ORDER_PROPS_ID' => 'this.ID'],
          ['join_type' => 'INNER']
      ),
  ],
  'filter' => [
      'ORDER_PROP.CODE' => 'CITY',
      'PROP_VALUE.VALUE' => 'Москва',
  ],

  3. having с SqlExpression в массиве (строка 123)
  'having' => [new SqlExpression('COUNT(*) > 10')],
  Замечание: Работает, но неидиоматично. В Bitrix D7 having принимает массив
  фильтров, как и filter. Лучше:
  'having' => ['>ORDERS_COUNT' => 10],
  (после объявления ORDERS_COUNT в select)

  Но текущий вариант рабочий, просто менее читаемый.

  📝 find-the-bug/bugs.php

  ✅ Что хорошо

  - Все пять багов реальные и встречаются в проде
  - Исправления корректные
  - Комментарии объясняют почему это баг, а не просто «так делать нельзя»

  ⚠️ Замечания

  1. Проверка check_bitrix_sessid() избыточна для GET (строка 136)
  if (!check_bitrix_sessid()) {
      http_response_code(403);
      die('{"error":"sessid"}');
  }
  Проблема: CSRF-защита нужна только для изменяющих операций (POST/PUT/DELETE).
  В контексте GET-запроса ?id=123 это не нужно.

  Исправление:
  // CSRF только если это POST (изменение заказа)
  if ($_SERVER['REQUEST_METHOD'] === 'POST' && !check_bitrix_sessid()) {
      http_response_code(403);
      die('{"error":"sessid"}');
  }

  2. Недостаточная проверка авторизации (строка 130)
  if ($order->getUserId() !== $USER->GetID()) {
  Проблема: Что если $USER не авторизован? GetID() вернет null/false, и проверка
  пройдет для заказа гостя (USER_ID = null).

  Исправление:
  global $USER;
  if (!$USER->IsAuthorized()) {
      http_response_code(401);
      die('{"error":"unauthorized"}');
  }
  if ($order->getUserId() != $USER->GetID()) { // != а не !==, т.к. GetID() 
  может вернуть string
      http_response_code(403);
      die('{"error":"forbidden"}');
  }

  3. Неполное экранирование в legacy-коде (строка 172)
  $id = (int)$id; // приведение типа — минимум для числа
  Замечание: Правильно для чисел. Но комментарий «минимум» может ввести в
  заблуждение — для строк ForSql() недостаточно для полной безопасности (нужны
  prepared statements или ORM).

  Стоит уточнить:
  // Для чисел — (int), для строк — $DB->ForSql() + одинарные кавычки в запросе

# Задача 3: «Найди баг» — 5 классических ошибок

## Что показывает

Формат, который реально встречается на собеседовании: дают кусок кода, просят найти проблему. Каждый баг — плохой вариант + исправленный + объяснение.

| № | Баг | Последствие |
|---|-----|-------------|
| 1 | `Order::load()` в цикле | N+1 — 500+ запросов вместо 2 |
| 2 | `$order->save()` внутри `OnSaleOrderSaved` | Рекурсия / дедлок |
| 3 | Нет проверки владельца (`USER_ID`) | IDOR — чтение чужих заказов |
| 4 | Конкатенация `$_GET` в SQL | SQL-инъекция |
| 5 | Кеш без тегов | Устаревшие данные после изменения заказа |

## Senior-инсайты

1. **Баг 2 — самый коварный.** Код выглядит рабочим (сработает один раз без ошибки), а в проде на нагрузке — дедлок или StackOverflow при каскадных событиях. Правило: внутри `OnSale*Saved` никогда не вызывать `save()` той же сущности — только `CAgent` для отложенной работы.

2. **Баг 3 — не теоретический.** Реальная уязвимость из практики: порядковый `ID` в URL + отсутствие проверки владельца = перебор всех заказов.

3. **Баг 4 — даже если "ID из URL всегда число".** Нельзя полагаться на фронт — экранирование/приведение типа на бэке обязательно, даже для "очевидно безопасных" параметров.

4. **Баг 5 — незаметен в тестах, виден в проде.** На деве кеш короткий, не замечаем. В проде TTL 3600 — час "зависших" данных после оплаты.

## Как использовать

Каждый блок — отдельный пример. На собеседовании ожидают: сначала назвать проблему, потом объяснить **почему** это проблема (не просто "так не делают"), потом предложить исправление.

## Формула ответа для code review

1. Что не так — конкретно, со ссылкой на строку.
2. Почему это проблема — сценарий, при котором ломается.
3. Как исправить — рабочий вариант.
4. Как бы я это поймал — тест/код-ревью чеклист/линтер.

# Контрольное задание. Пять дефектов обработки ошибок

**Задание.** Эндпоинт `/local/ajax/request-close.php` принят на поддержку после
инцидента: «заявки закрываются, но письма не уходят, а иногда закрываются
дважды». В `broken.php` пять дефектов. Назвать все пять, объяснить последствие
и условие проявления каждого.

`broken.php` синтаксически валиден и запускается: дефекты поведенческие, а не
«класс не найден». Нумерации в коде нет — намеренно.

## Дефект 1. Проверка результата объектом

```php
if ($updateResult) {
```

**Причина.** `OrderTable::update()` возвращает объект `UpdateResult`. Объект в
PHP всегда `true`, независимо от `isSuccess()`.

**Последствие.** Ветка «успех» выполняется даже при проваленной записи: клиент
получает `200` и `success: true` на заявке, которая не закрыта. Письмо
клиенту (следующим шагом в реальном коде) уйдёт по несуществующему событию.

**Условие проявления.** Всегда, как только запись не удалась: нет строки,
ошибка валидации ORM, нарушение ограничения БД. То есть дефект виден только в
момент, когда что-то пошло не так, — и именно тогда он и вреден.

**Исправление.** `if ($updateResult->isSuccess())`.

## Дефект 2. `getErrors()[0]` без проверки успеха

```php
'notice' => $updateResult->getErrors()[0]->getMessage(),
```

**Причина.** У успешного результата массив ошибок пуст. В PHP 8 обращение к
`[0]` даёт warning «Undefined array key 0» и `null`, а `null->getMessage()` —
фатал.

**Последствие.** Каждый **успешный** вызов завершается `500` после того, как
данные уже записаны и транзакция закоммичена. Клиент повторяет запрос — заявка
закрывается второй раз, письмо уходит второй раз. Это ровно тот инцидент, из-за
которого файл попал на разбор.

**Условие проявления.** На любом успешном закрытии, то есть на штатном пути.

**Исправление.** `getErrors()` читают только внутри ветки `!isSuccess()`.
Сообщение об успехе собирается из `getData()`, а не из ошибок.

## Дефект 3. `catch (\Exception)` с проглатыванием

```php
} catch (\Exception $exception) {
    $errorMessage = $exception->getMessage();
}
```

**Причина.** Две ошибки в одной строке: тело `catch` не логирует и не
перебрасывает (ошибка теряется), а тип `\Exception` не покрывает `\Error` —
`TypeError`, `ValueError`, обращение к методу у `null` в PHP 8 в него не
попадают.

**Последствие.** Сбой БД превращается в «пустую строку в ответе»: в логе нет ни
следа, поддержка не может восстановить, что произошло. `TypeError` проходит мимо
`catch` и валит запрос с фаталом вне какой-либо обработки — с HTML-выводом
вместо JSON.

**Условие проявления.** Первое — при любом исключении, которое перехвачено;
второе — при ошибке типа в PHP 8 (например, `$updateResult` оказался `null` из-за
более раннего сбоя).

**Исправление.** `catch (\Throwable $e)` + запись в лог с `error_id` +
`throw` дальше или корректный ответ `500`. Молчащий `catch` недопустим:
«нет ошибки в логе» и «нет ошибки» — разные вещи.

## Дефект 4. Текст исключения в ответе клиенту

```php
'message' => $errorMessage,   // = $exception->getMessage()
```

**Причина.** `SqlException::getMessage()` содержит текст SQL и имя таблицы;
`ObjectPropertyException` — имя поля и сущности; любое исключение ядра — кусок
пути к файлу.

**Последствие.** Раскрытие структуры БД и кода любому, кто может отправить
запрос: имена таблиц, полей, версии, пути. Для атакующего это готовая карта,
для аудита — утечка.

**Условие проявления.** При любом исключении, дошедшем до `catch`; в проде это
редкие, но регулярные события (таймаут БД, битые данные).

**Исправление.** Клиенту — `code` и `error_id`; полный текст, класс и trace —
в лог. По `error_id` поддержка находит запись, клиент не видит внутренностей.

## Дефект 5. Транзакция без проверки результатов и без отката

```php
$connection->startTransaction();
try {
    $logResult = CloseLogTable::add([...]);   // результат не проверяется
    $updateResult = OrderTable::update([...]); // результат не проверяется
    $connection->commitTransaction();
} catch (\Exception $exception) { ... }        // rollback отсутствует
```

**Причина.** `startTransaction()` открывает транзакцию, но:
`commitTransaction()` стоит до проверки результатов обеих записей, а в `catch`
нет `rollbackTransaction()`.

**Последствие.** Два разных сценария:

1. **Ошибка ORM без исключения.** `add()`/`update()` вернули `Result` с ошибкой
   — код её не увидел и закоммитил транзакцию. В журнале запись есть, заявка не
   закрыта: «письма не уходят», данные рассинхронизированы.
2. **Исключение.** `catch` поймал, `rollback` не сделал — транзакция осталась
   открытой. Соединение закроет её откатом при завершении запроса, но это
   побочный эффект, а не гарантия: в CLI, в долгоживущем процессе и при пуле
   соединений поведение иное, а блокировки держатся до конца запроса.

**Условие проявления.** Первое — при любой ошибке записи, которая не является
исключением (частая ситуация в ORM, особенно с обработчиками `OnBeforeAdd`).
Второе — при любом исключении между `startTransaction()` и `commitTransaction()`.

**Исправление.** Проверять `isSuccess()` каждой записи и бросать исключение;
`commit` — последней строкой `try`; `catch (\Throwable)` → `rollback` → `throw`
(полная версия — `fixed.php`).

## Что осталось непокрытым и почему

- **Идемпотентность.** Повторный `POST` закроет заявку второй раз: проверки
  текущего статуса нет. Это не дефект обработки ошибок, а отсутствующее правило
  домена — разбирается в практиках 2 и 3.
- **Гонка двух одновременных запросов.** Оба прочитают `new`. Для этого нужен
  условный `UPDATE ... WHERE STATUS <> 'closed'` с проверкой числа строк.
- **Проверка владельца.** `AUTHOR_ID` не сверяется с `$USER`: любой
  авторизованный закроет чужую заявку по ID. Это дефект прав, а не обработки
  ошибок; в 1.7 он был отдельным пунктом.
- **Событие/письмо после закрытия.** В файле их нет; в реальном проекте их
  отправляют после `commit`, иначе подписчик увидит незакоммиченные данные.

## Как проверять

```bash
mysql -u root -p b24 < install.sql
```

1. `broken.php` → `/local/ajax/request-close.php`, `fixed.php` → тот же путь
   (заменяя друг друга), `OrderTable.php` и `CloseLogTable.php` →
   `/local/php_interface/classes/Requests/`.
2. Завести заявку: `INSERT INTO mycompany_request (TITLE, STATUS, AUTHOR_ID,
   UPDATED_AT) VALUES ('Тест', 'new', 1, NOW());`
3. `POST` с `id` этой заявки и `sessid`.

Ожидаемое: `broken.php` отвечает `500` с warning про `Undefined array key 0`
(дефект 2) при том, что заявка уже закрыта; `fixed.php` отвечает `200` и
закрывает ровно один раз.

## Что здесь важно понять, а не скопировать

1. Проверка результата — `isSuccess()`, и никак иначе.
2. Ошибки читают в ветке ошибки; на успехе их нет.
3. `catch` без лога — это не обработка, а удаление информации.
4. Наружу — код, внутрь — текст.
5. `commit` после проверок, `rollback` в `catch`, `\Throwable`, а не
   `\Exception`.

# Практика 3. Транзакция и граница `Result` / исключение

**Задача.** Перенести остаток между складами: списать, зачислить, записать
операцию в журнал — и сделать так, чтобы при сбое на любом шаге не осталось
«половины операции». Снаружи сервис возвращает `Result`, внутри работает
транзакция.

## Что делает код

`TransferService::transfer(int $productId, string $from, string $to, int $qty, string $opKey)`

| Шаг | Что происходит | Что будет при сбое |
|---|---|---|
| 1 | валидация: товар, количество, склады, длина ключа | `Result` с кодом, **до** БД и до транзакции |
| 2 | поиск журнала по `OP_KEY` | запись есть → успех с `duplicate: true` |
| 3 | `startTransaction()` | — |
| 4 | чтение склада-источника | нет строки → `STOCK_NOT_FOUND` |
| 5 | проверка остатка | меньше нужного → `INSUFFICIENT_STOCK` + `available`/`requested` |
| 6 | `update()` остатка + read-back | не сошлось → `STOCK_WRITE_FAILED` |
| 7 | врезка `afterDebit` (демо) | падение → исключение наверх, откат |
| 8 | чтение склада-назначения | **нет строки → `TRANSFER_TARGET_NOT_FOUND`, откат списания** |
| 9 | `update()` + read-back назначения | не сошлось → откат |
| 10 | `add()` в журнал | ошибка/исключение → `OPERATION_LOG_FAILED` / `OPERATION_IN_PROGRESS` |
| 11 | `commitTransaction()` | — |

Два контракта в одном методе — это и есть тема:

- **снаружи `Result`**: коды `INSUFFICIENT_STOCK`, `TRANSFER_TARGET_NOT_FOUND`, `STOCK_WRITE_FAILED`…;
- **внутри исключения**: каждый отказ шагов 4–10 бросает `TransferFailed`,
  который несёт готовый `Result`; `catch (TransferFailed)` делает откат и
  возвращает этот `Result`.

Третий вариант — «просто `return $result` из середины» — оставил бы транзакцию
открытой. `commitTransaction()` тогда не выполнится, соединение закроется
`ROLLBACK`-ом при завершении запроса, и это сработает не всегда: в CLI, в
долгоживущем воркере и при пуле соединений поведение другое. Тест на эту
ошибку не падает — падает биллинг.

## Структура и куда копировать

```
install.sql          ->  выполнить в БД инсталляции
StockTable.php       ->  /local/php_interface/classes/Stock/StockTable.php
StockLogTable.php    ->  /local/php_interface/classes/Stock/StockLogTable.php
TransferFailed.php   ->  /local/php_interface/classes/Stock/TransferFailed.php
TransferService.php  ->  /local/php_interface/classes/Stock/TransferService.php
check.php            ->  /local/tools/stock-transfer-check.php
```

Автозагрузка — PSR-4 из `/local/composer.json` (`"MyCompany\\":
"php_interface/classes/"`), как в практике 2. `check.php` умеет работать и без
неё: подключает классы напрямую, чтобы пример запускался в том виде, в каком
лежит.

## Запуск

```bash
mysql -u root -p b24 < install.sql
curl -s 'http://b24.local/local/tools/stock-transfer-check.php'
```

`check.php` работает только со своим товаром `PRODUCT_ID = 7777` и чистит его
записи перед прогоном.

  после успешного переноса                       WH-A=7  WH-B=3  журнал=1

  isSuccess=да data={"duplicate":true,"log_id":1,"quantity":3}
  после повтора (должно не измениться)           WH-A=7  WH-B=3  журнал=1

  isSuccess=нет codes=INSUFFICIENT_STOCK

  после отказа (транзакция не начиналась)        WH-A=7  WH-B=3  журнал=1

  isSuccess=нет codes=TRANSFER_TARGET_NOT_FOUND
  после отката (остаток A должен быть 7)         WH-A=7  WH-B=3  журнал=1

  исключение наверх: RuntimeException: Внешний сервис недоступен
  после отката (остаток A должен быть 7)         WH-A=7  WH-B=3  журнал=1

Смотреть надо на **сценарии 4 и 5**: остаток `WH-A` не изменился, хотя
списание уже было выполнено и подтверждено read-back. Это и есть транзакция.

## Почему решение такое

- **Идемпотентность на ключе операции, а не на «повезёт».** Retry после
  таймаута — нормальная ситуация (клиент не получил ответ). Повтор возвращает
  успех и `duplicate: true`, а не создаёт второй перенос.
- **`UNIQUE(OP_KEY)` в БД — вторая линия.** Проверка «операция уже была» и
  вставка не атомарны: между ними влезает параллельная транзакция. Индекс
  ловит эту гонку на уровне БД, а `writeLog()` обрабатывает и исключение, и
  `Result`-ошибку — разные версии ядра отдают по-разному.
- **Read-back внутри транзакции.** `isSuccess()` после `update()` означает «ORM
  не упала», а не «значение такое, как мы думаем». Пока транзакция открыта,
  проверка стоит одного `SELECT` и ничего не ломает.
- **`TransferFailed` несёт `Result`.** Иначе наверх пришлось бы бросать
  `\Exception('ошибка')` и терять коды, по которым транспорт строит HTTP-статус.
- **`catch (\Throwable)`, не `\Exception`.** Внутри транзакции `TypeError` из
  PHP 8 обязан откатить транзакцию так же, как `SqlException`.

## Альтернативы и когда они лучше

| Вариант | Когда лучше | Цена |
|---|---|---|
| `UPDATE ... SET QUANTITY = QUANTITY - :q WHERE QUANTITY >= :q` | высокие нагрузки, остатки — счётчик | нужен `queryExecute` и проверка числа затронутых строк; уходим от ORM |
| `SELECT ... FOR UPDATE` | несколько строк в одной операции | ORM не даёт блокировку «из коробки», нужен SQL |
| Отдельная таблица операций с `UNIQUE` до транзакции | идемпотентность на весь процесс | нужна уборка «подвисших» операций по таймауту |
| Очередь (агент/брокер) вместо синхронного переноса | операция длинная, внешние вызовы | eventual consistency, отдельная логика повторов |

Вложенные транзакции: `startTransaction()` внутри уже открытой — это
`SAVEPOINT`. Внутренний `rollbackTransaction()` откатит только до точки
сохранения; внешние изменения останутся. Поэтому «сервис на всякий случай
открывает транзакцию» — не защита для вызывающего, а её иллюзия.

## Непокрытые случаи

- **Гонка двух одновременных списаний.** Оба прочитали `QUANTITY = 10`, оба
  списали по 3 — итог 7 вместо 4. Read-back это не ловит (значение совпадает с
  ожидаемым в каждой транзакции). Лечится атомарным `UPDATE ... WHERE
  QUANTITY >= :q` или `FOR UPDATE` — тема модулей 2 и 13.
- **Долгая транзакция + внешний вызов.** Врезка `afterDebit` иллюстрирует, что
  вызов внешнего сервиса внутри транзакции держит блокировки и удлиняет её.
  В проде такие вызовы выносят за пределы транзакции (событие/очередь) или
  делают компенсацию.
- **`ddl` и MyISAM.** `install.sql` создаёт InnoDB; на MyISAM отката нет.
- **Отправка события после commit.** `OnAfterTransfer` здесь нет — в проекте
  событие шлют после `commit`, иначе подписчик увидит ещё не применённые данные.

## Что здесь важно понять, а не скопировать

1. Транзакция и `Result` — разные механизмы, и внутри транзакции `Result`
   превращается в исключение, а на границе — обратно.
2. `commit` — последняя строка `try`, после всех проверок; `rollback` — в
   `catch`, до `throw`.
3. Успешный `update()` не доказывает факт записи; проверять надо чтением, пока
   транзакция открыта.
4. Идемпотентность — это ключ операции в БД, а не `if` в коде.

## Ограничения

- Таблицы создаются `install.sql`, а не установщиком модуля: в проекте — миграция.
- `afterDebit` — демонстрационная врезка. В рабочем коде её место занимает
  вызов внешнего сервиса или события, и он должен быть либо до транзакции, либо
  через очередь.
- Идентификатор операции `$opKey` здесь приходит снаружи. В реальном API он
  генерируется клиентом (UUID) и хранится в `X-Idempotency-Key`; в 1.7–1.8 этого
  уровня нет — транспортная часть в практике 4.

# Практика 2. Доменный сервис с `Result`

**Задача.** Закрыть заявку: проверить права, допустимость перехода статуса,
идемпотентность и длину комментария — и вернуть `Result` с кодами, по которым
транспорт (форма, REST) сам решит, что показать пользователю и какой дать
HTTP-статус.

Домен — заявки. Сервис не знает ни про `$_POST`, ни про `header()`, ни про
шаблон: на входе `int`/`string`, на выходе `Result`.

## Что делает код

`OrderStatusService::closeRequest(int $requestId, int $userId, string $comment)`
— поток:

1. **Валидация примитивов.** `$requestId <= 0` → `REQUEST_ID_INVALID`. Пустой
   после `trim()` комментарий → `COMMENT_REQUIRED`. Длиннее 500 символов →
   `COMMENT_TOO_LONG` с `customData` (`max`, `actual`), чтобы клиент показал
   «501 из 500».
2. **Чтение заявки** через `OrderTable::getList()` с `limit => 1`. Строки нет →
   `REQUEST_NOT_FOUND`.
3. **Проверка владельца.** `AUTHOR_ID !== $userId` → в лог уходит запись о
   попытке, наружу — тот же `REQUEST_NOT_FOUND`. Снаружи «чужая» и
   «несуществующая» неотличимы: `403` подтвердил бы существование объекта.
4. **Идемпотентность отдельным кодом.** Уже закрыта → `ALREADY_CLOSED`, а не
   «успех» и не ошибка БД. Вызывающий должен отличать «я закрыл» от «закрыли до
   меня», иначе двойная отправка письма выглядит как штатная работа.
5. **Разрешённые переходы** — таблица `ALLOWED_TRANSITIONS`. Статус `archived`
   (данные из старой версии) → `STATUS_TRANSITION_DENIED` с `['from' => ...]`.
6. **Запись** через `OrderTable::update()`. `isSuccess() === false` → ошибки ORM
   переносятся в результат как есть, без переупаковки.
7. **Read-back.** После обновления строка читается снова и сверяется статус.
   `update()` умеет вернуть успех, не записав то, что мы ожидали; проверка
   факта — часть контракта сервиса. Не подтвердилось → `STORE_FAILED`.
8. **Успех** → `setData(['id', 'status', 'closed_at'])`.

Коды и их HTTP-смысл (сам статус ставит транспорт, практика 4):

| Код | HTTP | Когда |
|---|---|---|
| `REQUEST_ID_INVALID` | 400 | ID ≤ 0 или не число |
| `COMMENT_REQUIRED` | 422 | пустой комментарий |
| `COMMENT_TOO_LONG` | 422 | > 500 символов |
| `REQUEST_NOT_FOUND` | 404 | нет заявки или она чужая |
| `STATUS_TRANSITION_DENIED` | 409 | из текущего статуса закрыть нельзя |
| `ALREADY_CLOSED` | 409 | уже закрыта |
| `STORE_FAILED` | 500 | запись не подтвердилась чтением |

## Структура и куда копировать

```
install.sql              ->  выполнить в БД инсталляции
OrderTable.php           ->  /local/php_interface/classes/Requests/OrderTable.php
OrderStatusService.php   ->  /local/php_interface/classes/Requests/OrderStatusService.php
check.php                ->  /local/tools/requests-check.php
```

Автозагрузка — PSR-4 (как в 1.6), `/local/composer.json`:

```json
{
    "autoload": {
        "psr-4": {
            "MyCompany\\": "php_interface/classes/"
        }
    }
}
```

```bash
cd /local && composer dump-autoload
```

`Loader::registerNamespace()` здесь **не** используется: он приводит путь к
нижнему регистру, и файлы `OrderTable.php` на Linux не находятся (разбор — 1.6,
контрольное задание).

## Запуск и проверка

```bash
mysql -u root -p b24 < install.sql
curl -s 'http://b24.local/local/tools/requests-check.php'
```

`check.php` чистит только свои тестовые записи (`AUTHOR_ID` 9001/9002), создаёт
четыре заявки и прогоняет девять сценариев.

## Правильный вывод

| Сценарий | Успех | Коды |
|---|---|---|
| 1. своя заявка, `new` | да | — |
| 2. повторно та же заявка | нет | `ALREADY_CLOSED` |
| 3. чужая заявка | нет | `REQUEST_NOT_FOUND` |
| 4. несуществующий ID | нет | `REQUEST_NOT_FOUND` |
| 5. пустой комментарий | нет | `COMMENT_REQUIRED` |
| 6. комментарий 501 символ | нет | `COMMENT_TOO_LONG` |
| 7. своя заявка, `in_work` | да | — |
| 8. статус `archived` | нет | `STATUS_TRANSITION_DENIED` |
| 9. ID = 0 | нет | `REQUEST_ID_INVALID` |

В конце печатается состояние таблицы: у закрытых заявок заполнены `CLOSED_AT` и
`CLOSE_COMMENT`, у `archived` — нет.

## Почему решение такое

- **`Result`, а не исключения.** Все девять исходов — ожидаемые: пользователь
  может ввести пустой комментарий, заявку мог закрыть коллега, ID мог
  устареть во вкладке. Исключение здесь означало бы «500 на нормальное
  поведение пользователя».
- **Все проверки до записи, порядок — от дешёвых к дорогим.** Валидация
  примитивов не требует БД и отсекает мусор до запроса.
- **Один код — один смысл.** `ALREADY_CLOSED` отдельно от
  `STATUS_TRANSITION_DENIED`: клиенту в первом случае достаточно перечитать
  заявку, во втором — показать «из этого статуса нельзя».
- **`customData` вместо текста.** `['from' => 'archived']` и `['max' => 500]` —
  данные, из которых клиент строит UI. По тексту это делать нельзя: текст
  меняется и переводится.
- **Read-back.** Не паранойя: между `update()` и ответом клиенту нет ничего, что
  гарантировало бы фактическое состояние строки, кроме чтения.

## Альтернативы и когда они лучше

| Вариант | Плюс | Минус |
|---|---|---|
| Исключения на все отказы | короче запись | `try/catch` в каждом вызывающем, UI-ветки через исключения |
| Один код `FAILED` + текст | проще | клиент парсит текст, ломается при переводе |
| Проверка владельца в SQL (`filter: AUTHOR_ID = $userId`) | не читает чужую строку | нельзя отличить попытку доступа для лога; см. ниже |
| `update` без read-back | на один запрос меньше | не отличает «записалось» от «ORM не упала» |

Про фильтр владельца в SQL: оба варианта дают снаружи `REQUEST_NOT_FOUND`.
Вариант с фильтром дешевле и не тянет чужую строку в память; вариант с
проверкой в PHP позволяет записать в лог попытку доступа. В сервисе выбран
второй — из-за журналирования; при высокой нагрузке его меняют на первый.

## Покрытые и непокрытые случаи

Покрыто: пустой/длинный комментарий, неверный ID, отсутствие заявки, чужой
автор, повторное закрытие, запрещённый переход, неподтверждённая запись.

Не покрыто и почему:

- **Гонка двух одновременных закрытий.** Оба запроса прочитают `new`, оба
  сделают `update`. Второй получит `ALREADY_CLOSED` только если прочитает уже
  закрытую строку. Надёжно — `UPDATE ... WHERE STATUS <> 'closed'` с проверкой
  числа затронутых строк или `SELECT ... FOR UPDATE`; это тема модулей 2 и 13.
- **Права роли** (админ может закрывать чужие заявки). Здесь только владелец:
  `AccessDeniedException`/роли — модуль 7.
- **Транзакция.** Одна запись — транзакция не нужна. Две и больше — практика 3.

## Что здесь важно понять, а не скопировать

1. `Result` — контракт **слоя**, а не «контейнер для `try/catch`». Коды
   придумываются вместе с API, а не после.
2. «Чужой объект» и «нет объекта» — один ответ наружу, разный лог внутри.
3. `isSuccess()` после `update()` — необходимая, но недостаточная проверка.
4. Текст ошибки — для человека, код — для машины. Как только логика начинает
   смотреть на текст, контракт сломан.

## Ограничения

- `AddMessage2Log()` — legacy, но работает без настройки. В проекте с
  настроенным логгером (`Diag\Logger`, PSR-3-обёртки) заменяется на него.
- `mycompany_request` создаётся `install.sql`, а не миграцией модуля: в
  реальном проекте схема ставится установщиком модуля (`install/db/`) или
  миграцией, а не руками в БД.
- Комментарий хранится как есть (без `htmlspecialchars`): экранирование — при
  выводе, в контексте вывода.

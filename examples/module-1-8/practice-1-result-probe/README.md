# Практика 1. Проба `Result`, `Error`, исключений

**Задача.** Снять фактическое состояние механизма ошибок на своей версии ядра:
какие методы есть на самом деле, что вернёт `addErrors()` на массив строк,
чему равно `if ($result)`, что делает `Loader::includeModule()` с опечаткой,
считает ли ORM ошибкой `update()` по несуществующему ID.

## Что делает код

`probe.php` — один скрипт, двенадцать секций, текст `text/plain`:

| Секция | Что печатает | Что смотреть |
|---|---|---|
| 1. Окружение | `SM_VERSION`, `PHP_VERSION`, наличие классов | версия, от которой зависят выводы |
| 2. Матрица методов | `method_exists()` по `Result`, `Error`, `ErrorCollection` | `addData` — **нет**, `getErrorCollection` — с 15.5.9 |
| 3. `addErrors` | массив строк вместо `Error` | `TypeError`, а не «принял как есть» |
| 4. Truthiness | `(bool)$failed` для проваленного результата | `true` — отсюда дефект `if ($result)` |
| 5. `getErrors()[0]` | чтение первой ошибки у успешного результата | warning + фатал, а не `null` |
| 6. `setData` | два вызова подряд, правка копии `getData()` | второй массив заменил первый |
| 7. `Error` | код, `customData`, `__toString`, JSON, код-строка | код может быть строкой: `=== 0` не сработает |
| 8. `ErrorCollection` | `getErrorByCode()`, `isEmpty()`, `count()` | чего нет у `Result` |
| 9. Иерархия | `is_a()` для десяти пар класс-родитель | `SqlException` → `DB\Exception` → `SystemException` |
| 10. `Loader` | опечатка в имени модуля и пустая строка | `LoaderException`, а не `false` |
| 11. ORM | `update()` по ID, которого нет | `isSuccess() === true` при нуле строк |
| 12. Логирование | `AddMessage2Log`, `LOG_FILENAME`, `Diag\Logger` | чем логировать в твоей версии |

Скрипт ничего не пишет в БД: единственная запись — `update()` по ID
`2147483647` в `b_group`, где такой строки нет (0 затронутых строк). Все
спорные вызовы обёрнуты в `try/catch`: на другой версии ядра проба показывает
исключение, а не падает фаталом.

## Структура и куда копировать

```
probe.php   ->  /local/tools/result-probe.php
```

`/local/tools/` — не обязательный путь, но удобный: скрипт диагностический, в
роутинге не участвует.

## Запуск

```bash
curl -s 'http://b24.local/local/tools/result-probe.php'
```

или открыть в браузере (там же удобнее смотреть на `warning`-и).

## Что смотреть в выводе (правильные ответы)

| Проверка | Ожидаемо |
|---|---|
| `Result::addData` | `нет` — метода не существует ни в одной версии |
| `addErrors(['просто строка'])` | `TypeError: ... must be of type Bitrix\Main\Error, string given` |
| `(bool)$failed` | `true`, `isSuccess()` — `false` |
| `getErrors()[0]` у успешного | `Error: Undefined array key 0`, затем `Call to a member function getMessage() on null` |
| после двух `setData` | только второй массив |
| правка копии `getData()` | в результате ничего не поменялось |
| `getError()` при двух ошибках | сообщение **первой** |
| `json_encode($error)` | JSON-объект с сообщением и кодом (класс `JsonSerializable`) |
| `includeModule('iblok')` | `Bitrix\Main\LoaderException` |
| `update()` по чужому ID | `isSuccess() === true`, `getErrorMessages() === []` |

Если какая-то строка расходится с таблицей — это не ошибка в пробах, а
изменение ядра: правь теорию 1.8 и снимай `[проверить]`.

## Почему проба, а не «прочитать документацию»

Документация описывает последнюю версию, а в проекте может быть ядро трёхлетней
давности. `getErrorCollection()` появился в 15.5.9, `Error::createFromThrowable`
— заметно позже; код, написанный «по докам», падает на старом ядре фаталом
«call to undefined method», и это выясняется в проде. `method_exists()` в пробе
стоит ровно на этих границах.

Второе: поведение `update()` при нуле затронутых строк и `Loader` с опечаткой —
вещи, которые невозможно вывести из названия метода, и на них строится
неправильная логика. Один запуск снимает неопределённость на весь проект.

## Ограничения

- Проба не проверяет `getErrorCollection()` при пустом результате на всех
  версиях: на очень старых ядрах метода нет, и это видно в матрице.
- `b_group` выбран как таблица, которую в демо-инсталляции никто не меняет.
  На боевом проекте так делать не надо: диагностический скрипт не должен
  трогать данные вообще. Для боевой проверки — своя тестовая таблица.
- Скрипт доступен по URL: на боевом сайте его удаляют или закрывают
  `check_bitrix_sessid()` + правами администратора.

## Что здесь важно понять, а не скопировать

1. «Метод есть в документации» ≠ «метод есть на этом ядре».
2. `if ($result)` — не проверка успеха, а проверка «объект не `null`».
3. Ошибка в `Result` не делает результат «пустым»: `data` живёт отдельно.
4. Один и тот же API ядра может и возвращать `false`, и бросать исключение —
   `Loader::includeModule()` тому пример.

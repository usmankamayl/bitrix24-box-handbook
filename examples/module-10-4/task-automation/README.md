# Пример: Автоматизация задач в Bitrix24

## Описание

Два скрипта для работы с задачами через REST API (`tasks.task.*`):

- **create-task.php** — создание задачи с чек-листом, наблюдателями, дедлайном и привязкой к сделке CRM
- **report.php** — отчёт по просроченным задачам отдела с группировкой по исполнителям

## Файлы

| Файл | Что делает |
|------|-----------|
| `create-task.php` | Создаёт задачу → добавляет чек-лист через `batch` → пишет комментарий |
| `report.php` | Выбирает просроченные задачи → загружает имена пользователей → выводит сводку |

## Используемые методы REST API

### create-task.php

| Метод | Назначение |
|-------|------------|
| `tasks.task.add` | Создание задачи с полями `TITLE`, `RESPONSIBLE_ID`, `DEADLINE`, `UF_CRM_TASK`, `AUDITORS`, `TAGS` |
| `task.checklistitem.add` | Пункты чек-листа (через `batch` — 3 запроса в одном) |
| `task.commentitem.add` | Первый комментарий с инструкцией |

### report.php

| Метод | Назначение |
|-------|------------|
| `tasks.task.list` | Фильтр `<DEADLINE`, `!STATUS`, `RESPONSIBLE_ID` |
| `user.get` | Имена исполнителей для отчёта (через `batch`) |
| `batch` | Пагинация при >50 задачах + загрузка пользователей |

## Настройка

1. Создай входящий вебхук в Bitrix24: **Приложения → Вебхуки → Входящий вебхук**
   - Права: `task` (Задачи), `user` (Пользователи), `crm` (CRM)
   - Скопируй URL вида `https://portal.bitrix24.ru/rest/1/KEY/`

2. Открой оба файла и замени значения:

```php
define('WEBHOOK', 'https://your-portal.bitrix24.ru/rest/1/YOUR_WEBHOOK_KEY/');
define('RESPONSIBLE_ID', 15);  // ID исполнителя
define('AUDITOR_ID', 3);       // ID наблюдателя
define('DEAL_ID', 123);        // ID сделки для привязки
```

3. Для `report.php` укажи ID сотрудников отдела:

```php
$departmentUsers = [15, 16, 17, 18];
```

## Запуск

```bash
# Создать задачу
php create-task.php

# Отчёт по просроченным
php report.php
```

## Что демонстрирует

### create-task.php

- Правильный формат `DEADLINE` — ISO 8601 (`2026-11-15T18:00:00+03:00`)
- `UF_CRM_TASK` — всегда массив `['D_123']`, даже для одной сделки
- `TASK_CONTROL = 'Y'` — задача уйдёт на проверку постановщику (статус 4)
- `batch` для чек-листа — 3 `task.checklistitem.add` в одном HTTP-запросе
- `SORT_INDEX` с шагом 10 — позволяет вставлять пункты между существующими

### report.php

- Фильтр `'<DEADLINE' => $today` + `'!STATUS' => [5,6,7]` — только активные просроченные
- Пагинация: первая страница + `batch` для остальных при `total > 50`
- `array_column($tasks, 'responsibleId')` — сбор ID исполнителей
- Подсчёт дней просрочки через `DateTime::diff()->days`

## Частые ошибки (покрыты в коде)

| Ошибка | Как исправлено |
|--------|---------------|
| `UF_CRM_TASK` как строка | Всегда передаётся массив `['D_' . $id]` |
| `DEADLINE` в формате `дд.мм.гггг` | ISO 8601 через `DateTime::format('Y-m-d\TH:i:sP')` |
| `STATUS` как строка `'completed'` | Числовые коды `[5, 6, 7]` |
| Отсутствие обработки `error` | Проверка `$result['error']` после каждого вызова |
| 50 задач в `list` без пагинации | `batch` для страниц 2+ при `total > 50` |

## Для собеседования

- Чем `tasks.task.delegate` отличается от `update` с `RESPONSIBLE_ID`
- Что делает `TASK_CONTROL = 'Y'` и какой статус появляется
- Как `batch` экономит HTTP-запросы (до 50 команд за раз)
- Формат `UF_CRM_TASK` и префиксы `D_`, `C_`, `CO_`, `L_`
- Разница между `tasks.task.list` фильтрами `=`, `!`, `<`, `>`

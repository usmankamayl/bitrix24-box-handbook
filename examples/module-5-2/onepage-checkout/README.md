# Кейс 2: Кастомный чекаут — сборка заказа через Order API

## Что решает

Стандартный компонент `sale.order.ajax` закрывает 80% проектов, но как только нужен нестандартный одностраничный чекаут (своя вёрстка, свой шаг-степпер, другая логика выбора доставки/оплаты) — приходится собирать `Sale\Order` вручную. Это ровно то место, где чаще всего ловят баги на реальных проектах: заказ "создаётся", но с нулевой суммой, пустыми свойствами или без отгрузки. Кейс показывает правильный, воспроизводимый порядок сборки.

## Структура

```
onepage-checkout/
├── checkout.php                # обработчик сабмита формы — создаёт заказ
├── events.php                  # OnSaleOrderSaved — постановка письма в очередь
├── lib/
│   ├── OrderBuilder.php        # сборка Order из корзины + данных формы
│   └── OrderMailAgent.php      # асинхронная отправка письма агентом
└── README.md
```

## Ключевые приёмы (на что обратить внимание на собеседовании)

1. **Порядок вызовов — не случайный, а обязательный.**
   `Order::create` → `setPersonTypeId` → `setBasket` → свойства → отгрузка → оплата → `save()`.
   - Тип плательщика — до свойств: `PropertyValueCollection` зависит от `PERSON_TYPE_ID`, обратный порядок стирает уже введённые значения.
   - Оплата — после отгрузки: `order->getPrice()` должен уже включать стоимость доставки, иначе `SUM` платежа будет занижен.

2. **Обязательность свойств проверяется руками.** `PropertyValue::setValue()` не валидирует `REQUIRED` — пустое обязательное поле "успешно" запишется, если явно не проверить `isRequired()` после простановки значений.

3. **`isNew()` в `OnSaleOrderSaved` отличает создание от любого другого сохранения.** Событие срабатывает и на смену статуса, и на правку в админке — без проверки письмо "заказ оформлен" будет дублироваться.

4. **Письмо — через агента, а не синхронно в `checkout.php`.** `CEvent::Send` с реальным SMTP может занять секунды; клиент, только что оплативший заказ, не должен ждать этого на редиректе. Агент ставится с задержкой 5 секунд и возвращает `''` (одноразовый запуск — см. модуль 1.3).

5. **`PropertyValueCollection::getUserEmail()`** — готовый метод коллекции свойств для получения email покупателя, не нужно вручную искать свойство по `TYPE => 'EMAIL'`.

## Как использовать

1. Подключить `events.php` в `/local/php_interface/init.php`.
2. Разместить `checkout.php` и `lib/` как обработчик формы, например `/cart/checkout-submit.php`.
3. Форма отправляет `POST`: `PERSON_TYPE_ID`, `DELIVERY_ID`, `PAY_SYSTEM_ID`, `PROPERTIES[ID свойства]`, `sessid`.
4. Убедиться, что в `SALE_NEW_ORDER` (Настройки → Почтовые события) есть шаблон письма, иначе `CEvent::Send` просто не найдёт событие.

## Возможные вопросы на собеседовании по этому коду

- Почему `setPersonTypeId` нельзя вызвать после заполнения свойств? *(набор свойств пересчитывается под новый тип плательщика — уже введённые значения теряются)*
- Что произойдёт, если `Delivery\Services\Manager::getById` вернёт несуществующую службу? *(`OrderBuilder` вернёт `Result` с ошибкой до вызова `order->save()` — заказ не создастся в неконсистентном состоянии)*
- Почему письмо не отправляется прямо в `checkout.php` после `$order->save()`? *(синхронный SMTP-запрос в ответе на чекаут — лишняя задержка и точка отказа; агент развязывает это по времени)*
- Как отличить "заказ только что создан" от "заказ пересчитан после смены статуса" в `OnSaleOrderSaved`? *(`$order->isNew()`)*
- Что будет, если у пользователя не настроено ни одной доступной доставки для его региона? *(`DELIVERY_ID` не пройдёт `getById`/будет недоступен для фильтрации по зоне — проверка зон делается до рендера формы, вне скоупа этого файла)*

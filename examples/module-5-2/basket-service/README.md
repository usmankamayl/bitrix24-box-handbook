# Кейс 1: Сервис корзины — add/update/remove, купоны, мердж при логине

## Что решает

Типичный антипаттерн в проектах на Bitrix — логика корзины размазана по ajax-файлам: в одном месте `CSaleBasket::Add`, в другом прямой `UPDATE b_sale_basket`, купоны применяются где-то ещё. Это ломает резервы, события и правила скидок, а тестировать такой код невозможно. Решение — вынести всю логику в один сервисный класс, работающий **только** через объектную модель `Sale\Basket`, а ajax-файл сделать тонким роутером.

## Структура

```
basket-service/
├── basket.php              # AJAX-роутер: add / update / remove / coupon / summary
├── events.php               # OnBeforeUserLogin + OnUserLogin — перенос анонимной корзины
├── lib/
│   └── BasketService.php    # вся бизнес-логика корзины
└── README.md
```

## Ключевые приёмы (на что обратить внимание на собеседовании)

1. **Только `Basket::createItem()` + `save()`, никогда `b_sale_basket` напрямую.** Иначе не сработают проверка остатков, события `OnSaleBasketItem*`, резервирование и пересчёт купонов — корзина "есть в базе", но система её не видит как валидную.

2. **Мердж корзины анонима — это перенос `BasketItem`, а не смена `FUSER_ID`.** Прямая правка `FUSER_ID` в строках `b_sale_basket` оставляет резервы привязанными к старому fuser'у. `mergeAnonymousBasket()` создаёт новые позиции в целевой корзине и удаляет исходную.

3. **Анонимный `FUSER_ID` нужно поймать ДО авторизации.** См. `events.php`: `OnBeforeUserLogin` фиксирует `Sale\Fuser::getId()` в `$GLOBALS`, а `OnUserLogin` уже использует это значение. Если читать `Sale\Fuser::getId()` прямо в `OnUserLogin`, можно получить fuser, уже привязанный к залогиненному пользователю, — анонимная корзина будет потеряна.

4. **Легковесный пролог для ajax.** `basket.php` не подключает `header.php` целиком (шаблон, меню, компоненты страницы), а использует `prolog_before.php` напрямую — для экшена "+1 в корзине", который может вызываться десятки раз за визит, это заметная экономия.

5. **Цена не доверяет клиенту.** `addProduct()`/`updateQuantity()` принимают от фронта только `productId`/`quantity` — итоговая цена всегда берётся из `Sale\Basket`/`BasketItem` после `save()`, а не из тела запроса.

6. **Купон проверяется "по факту применения", а не по коду ответа.** `DiscountCouponsManager::add()` молча игнорирует невалидный код — поэтому после `save()` код явно проверяет, попал ли купон в список применённых (`DiscountCouponsManager::get()`).

## Как использовать

1. Подключить `events.php` в `/local/php_interface/init.php`.
2. Разместить `basket.php` и `lib/` там, откуда фронт будет их вызывать (например, `/local/ajax/basket.php`).
3. Пример запроса с фронта:

```js
fetch('/local/ajax/basket.php', {
    method: 'POST',
    headers: {'Content-Type': 'application/x-www-form-urlencoded'},
    body: new URLSearchParams({
        action: 'add',
        productId: 101,
        quantity: 2,
        sessid: BX.bitrix_sessid(),
    }),
}).then(r => r.json()).then(data => console.log(data));
```

4. Проверить мердж: добавить товар анонимно, авторизоваться существующим пользователем с непустой корзиной — товары должны объединиться по `PRODUCT_ID` с суммированием количества.

## Возможные вопросы на собеседовании по этому коду

- Почему `addProduct` возвращает всю сводку корзины, а не просто `true`? *(Фронту не нужен лишний round-trip за `summary` после каждой мутации — отдаём актуальное состояние сразу.)*
- Что будет, если вызвать `applyCoupon` дважды с одним кодом? *(Явная проверка `in_array` до `DiscountCouponsManager::add` — не дублируем код и не тратим лишний `save()`.)*
- Почему `mergeAnonymousBasket` удаляет исходную корзину, а не оставляет её "на всякий случай"? *(Висящая fuser-корзина — мусор в `b_sale_fuser`/`b_sale_basket`, который никогда не будет использован повторно, т.к. анонимная кука уже заменена сессией авторизованного пользователя.)*
- Почему `basket.php` не использует полный `header.php`? *(Для частых мелких ajax-запросов полная загрузка шаблона — лишняя нагрузка; `prolog_before.php` даёт доступ к ядру, модулям и сессии без рендеринга страницы.)*
- Как защититься от гонки, если пользователь кликает "+1" быстро несколько раз подряд? *(Вне скоупа примера, но правильный ответ — троттлинг на фронте + идемпотентность на бэке, либо блокировка позиции корзины на время `save()`.)*

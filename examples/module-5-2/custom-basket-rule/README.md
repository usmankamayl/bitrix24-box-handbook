# Кейс 3: Кастомное правило «каждый N-й товар дешевле» + аудит скидок

## Что решает

Классический вопрос на собеседовании: *«как сделать скидку "купи 2 — третий бесплатно/дешевле", если стандартные правила корзины такого не умеют?»*. В модуле описан легаси-путь через `CSaleActionCtrl` (регистрация через `OnCondSaleActionsControlBuildList`/`OnCondSaleControlBuildList`) — это даёт скидку в стандартном интерфейсе администратора «Скидки» наравне с остальными. Но для нетривиальной логики (именно N-я *единица*, а не N-я позиция) эта legacy-подсистема слабо документирована и жёстко завязана на формат `b_sale_discount`.

Здесь показан практический D7-альтернативный путь: явный калькулятор + прямая простановка `CUSTOM_PRICE` на `BasketItem` до `basket->save()`. Это тот же принцип, что использует внутри себя `ActionDiscountCalculator`, но без привязки к UI управления скидками.

## Структура

```
custom-basket-rule/
├── demo.php                            # применить правило к текущей корзине (runnable)
├── events.php                          # OnSaleOrderSaved — аудит применённых скидок
├── lib/
│   ├── NthItemDiscountCalculator.php   # чистая математика скидки (без Bitrix\Sale)
│   ├── NthItemDiscountRule.php         # применение правила к Sale\Basket
│   └── DiscountAuditLog.php            # запись в лог событий Bitrix
└── README.md
```

## Как считается скидка

`NthItemDiscountCalculator::calculateUnitPrice($basePrice, $quantity, $everyNth, $percent)`:

- при `everyNth = 3`, `quantity = 7` — скидка применится к `intdiv(7, 3) = 2` единицам;
- `PRICE` в `b_sale_basket` хранится **за единицу**, а не суммой по строке — поэтому возвращается усреднённая цена: `(полных_юнитов × basePrice + скидочных_юнитов × discountedPrice) / quantity`;
- пример: `basePrice = 100`, `quantity = 6`, `everyNth = 3`, `percent = 50` → 2 единицы по 50, 4 по 100 → средняя цена `(4×100 + 2×50) / 6 ≈ 83.33`.

## Ключевые приёмы (на что обратить внимание на собеседовании)

1. **Почему не `CSaleActionCtrl`.** Легаси-API синхронизируется с 1С, завязан на админку «Скидки» и плохо подходит, когда правило — чисто программная бизнес-логика, которую нетехнический сотрудник не должен и не может менять руками. Явный калькулятор — предсказуемее, тестируется юнит-тестами и не зависит от внутренностей `discount.php` конкретной версии ядра. Это честный trade-off, а не "не осилили legacy API" — на собеседовании стоит показать именно осознанность выбора.

2. **`CUSTOM_PRICE = 'Y'`** — обязателен при ручной простановке `PRICE`, иначе при следующем пересчёте корзины (`basket->refresh()`, смена валюты, применение купона) цена будет молча заменена обратно на стандартную.

3. **Идемпотентность.** `apply()` сравнивает новую цену с текущей и трогает позицию только при реальном изменении — иначе при каждом вызове (а он может происходить на каждое добавление в корзину) `basket->save()` считает позицию "изменённой" и лишний раз гоняет пересчёт правил корзины.

4. **Аудит через `OnSaleOrderSaved`, а не через движок скидок.** Раз скидка не проходит через `sale.discount`, в стандартных отчётах по скидкам её не видно. `events.php` явно логирует, в каких заказах она была применена — для финансового контроля.

## Как использовать

1. Подключить `events.php` в `/local/php_interface/init.php`.
2. Встроить вызов в сервис корзины: в `BasketService::addProduct()`/`updateQuantity()` (Кейс 1) добавить `(new NthItemDiscountRule($eligibleIds))->apply($basket);` непосредственно перед `$basket->save()`.
3. Для отдельной проверки — запустить `demo.php` с реальными ID товаров из каталога вместо `[101, 205]`.

## Возможные вопросы на собеседовании по этому коду

- Почему `PRICE` — это средняя цена за единицу, а не просто цена последней "скидочной" единицы? *(В `b_sale_basket` нет понятия "эта единица дороже, эта дешевле" — одна строка корзины имеет одну цену за единицу, поэтому для корректной суммы (`PRICE × QUANTITY`) цену нужно усреднять)*
- Что будет, если товар уже участвует в стандартной скидке корзины (например, по купону)? *(Порядок применения становится критичным: если наш калькулятор сработает после купона — он перезапишет его эффект, если до — купон отработает по уже сниженной `PRICE`. Нужно явно решать на уровне бизнес-логики, в каком порядке суммировать скидки — в примере оставлено как точка для обсуждения)*
- Почему `apply()` не вызывает `basket->save()` сам? *(Разделение ответственности: калькулятор меняет поля, а решение "когда сохранять" — у вызывающего кода, который может объединить это с другими изменениями корзины в один `save()`)*
- Почему для аудита используется `AddMessage2Log`, а не просто запись в HL-блок? *(Для MVP/примера достаточно лога событий Bitrix — в реальном проекте с требованием отчётности это действительно стоит вынести в отдельную таблицу/HL-блок с фильтрами в админке)*

# Односторонняя синхронизация сделок Bitrix24 → AmoCRM

Сделки, созданные/изменённые в Bitrix24 CRM, асинхронно реплицируются в
AmoCRM. Bitrix24 выступает единственным источником истины (односторонняя
синхронизация, см. теорию в `docs/module-13-2.md`), поэтому конфликтов
встречных изменений не возникает.

## Файлы

- `schema.sql` — `entity_mapping` (соответствие ID Bitrix24 ↔ AmoCRM) и `sync_queue` (очередь задач)
- `config.php` — токен AmoCRM и подключение к БД
- `EntityMapper.php` — поиск/сохранение соответствия ID + хэша последнего отправленного состояния
- `SyncQueue.php` — постановка задач в очередь, выборка ожидающих, учёт попыток
- `AmoCrmClient.php` — минимальный REST-клиент AmoCRM (create/update/find по кастомному полю)
- `SyncService.php` — идемпотентная синхронизация одной сделки (ядро модуля)
- `event_handler.php` — обработчики `OnAfterCrmDealAdd`/`OnAfterCrmDealUpdate`: только `enqueue()`, без сетевых вызовов
- `agent.php` — крон-агент Bitrix24: разбирает очередь, вызывает `SyncService`, обрабатывает ошибки

## Установка

1. Выполните `schema.sql` в своей БД.
2. В `config.php` укажите `AMOCRM_DOMAIN`, `AMOCRM_ACCESS_TOKEN` и `AMOCRM_BITRIX_ID_FIELD_ID` (ID текстового кастомного поля, заранее созданного в AmoCRM для сделок — Настройки → Поля сделок).
3. Подключите `event_handler.php` в `init.php` вашего локального модуля (или зарегистрируйте обработчики через `CEventManager::RegisterEventHandler` в install-скрипте модуля).
4. Зарегистрируйте `agent.php` агентом: `CAgent::AddAgent('\\processDealSyncQueueAgent();', '', 'N', 60);`

## Почему событие не вызывает AmoCRM напрямую

Если бы `event_handler.php` сам делал HTTP-запрос к AmoCRM, таймаут или
недоступность AmoCRM заблокировали бы сохранение сделки в самом Bitrix24
(пользователь увидит зависшую форму). Вместо этого обработчик только кладёт
запись в `sync_queue` — лёгкая операция с БД, доли миллисекунды. Сетевой
вызов выполняется отдельно, крон-агентом, вне контекста пользовательского
запроса.

## Почему синхронизация идемпотентна

`SyncService::syncDeal()` перед созданием сделки в AmoCRM сначала ищет её
там по кастомному полю `bitrix_deal_id`, в которое при создании всегда
записывается ID исходной сделки. Если прошлая попытка создания упала по
таймауту уже **после** того, как AmoCRM фактически создал запись — повторный
запуск задачи найдёт эту запись и свяжет её, вместо того чтобы создать
дубль.

## Ключевые моменты для собеседования

- Таблица `entity_mapping` с двумя уникальными индексами (`uniq_bitrix`, `uniq_external`) физически не даёт привязать одну сделку Bitrix24 к двум записям AmoCRM и наоборот.
- `last_synced_hash` экономит лимит запросов AmoCRM: если содержимое синхронизируемых полей не изменилось, `UPDATE` не отправляется вообще.
- `sync_queue.attempts` + `markFailed(maxAttempts: 5)` — задача не ретраится бесконечно; после исчерпания попыток остаётся в статусе `failed` для ручного разбора, а не теряется молча.
- Обработчик события CRM и фактическая отправка во внешнюю систему разнесены по времени — это стандартный паттерн "событие ставит задачу, агент её выполняет" (тот же принцип, что в [1.3](../../../docs/module-1-3.md)).

Подробный теоретический разбор — в `docs/module-13-2.md`.

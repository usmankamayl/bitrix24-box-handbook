# Практика 1. Агент очистки устаревших записей журнала

**Задача.** Агент удаляет записи проектного журнала старше 30 дней: не больше
заданного числа за вызов, с явным сроком хранения, логом числа удалённых,
корректным повтором и без посягательств на свежие записи.

## Что делает код

Поток одного запуска:

| Шаг | Что происходит | Что будет при сбое |
|---|---|---|
| 1 | `execute()` вызывает `run()` | исключение ловится в `execute()` — агент не исчезает |
| 2 | считается граница `cutoff = now − 30 дней` | — |
| 3 | берётся `flock` на `/local/var/agents/log-cleanup.lock` | блокировку держит другой процесс → отчёт `skipped_locked`, возврат имени агента |
| 4 | выборка `ID` по `< CREATED_AT`, `ORDER BY ID`, `LIMIT 200` | ошибка БД → в отчёт, выход с именем агента |
| 5 | по строкам `LogTable::delete($id)` | ошибка на конкретной строке → `failed++`, остальные удаляются |
| 6 | если порция была полной — следующая, но не больше 10 порций и 20 секунд | — |
| 7 | отчёт дописывается в `log-cleanup.jsonl`; ошибки дублируются в `CEventLog` | сбой записи отчёта не влияет на возврат имени |

Почему порядок именно такой:

- **Сначала блокировка, потом выборка.** Иначе два процесса (cron и ручной
  прогон) выбирают одни и те же ID, первый удаляет, второй получает ошибки
  «строки нет» и пишет их в журнал как сбои.
- **Удаление по primary key, а не `DELETE ... WHERE CREATED_AT < X`.** Так
  видно, сколько именно строк удалено (`deleted`), а ошибка одной строки не
  отменяет весь пакет.
- **Порции + бюджет времени.** Один запуск не должен занимать процесс
  минутами: агент работает в том числе внутри HTTP-запроса на хитах, где это
  время видит посетитель.
- **`< cutoff`, а не `<=`.** Строка ровно на границе срока считается «не
  старше» и остаётся. Это осознанное решение, а не случайность: граница
  проверяется сценарием 4 в `check.php`.

## Структура и куда копировать

```
install.sql        ->  выполнить в БД инсталляции
LogTable.php       ->  /local/php_interface/classes/Agents/LogTable.php
LogCleanupAgent.php ->  /local/php_interface/classes/Agents/LogCleanupAgent.php
install.php        ->  /local/tools/practice-1-log-cleanup/install.php
check.php          ->  /local/tools/practice-1-log-cleanup/check.php
```

Автозагрузка — та же, что в 1.6: PSR-4 из `/local/composer.json`
(`"MyCompany\\": "php_interface/classes/"`), а если Composer в демо не настроен
— `Loader::registerAutoLoadClasses()` в `/local/php_interface/init.php`.
`check.php` умеет работать и без неё: подключает классы напрямую.

## Запуск

```bash
mysql -u root -p b24 < install.sql
cp -r practice-1-log-cleanup <DOCUMENT_ROOT>/local/tools/
# браузером под администратором:
#   https://site/local/tools/practice-1-log-cleanup/install.php  -> «Зарегистрировать агента»
php -f <DOCUMENT_ROOT>/local/tools/practice-1-log-cleanup/check.php
```

`install.php` — только администратор, изменение только по `POST` и только с
валидным `sessid`; повторный заход дубликат не создаёт.

  после запуска: старше срока: 0   не старше: 3

## Почему решение такое

**Порционность вместо одного большого `DELETE`.** `DELETE FROM log WHERE
CREATED_AT < X` в MySQL держит блокировки на все удаляемые строки, пишет
огромный undo-лог и может держать репликацию. Порция по 200 строк с
ограничением времени дешевле и предсказуемее; остаток дочищается следующим
запуском.

**`IS_PERIOD = N`.** Агенту не нужна привязка к календарной сетке: «раз в час
от факта выполнения» — ровно то поведение, которое ожидается от уборки.

**`AGENT_NAME` как константа.** Одна строка на регистрацию, поиск и удаление.
Ошибка «имя собрано из `__METHOD__` в другом методе» — самый частый дефект
агентов (разбор — `../control-task/`), константа его исключает.

**`execute()` возвращает имя при любом исходе.** `return;` (null) или
исключение наружу означают, что агент удалён или его расписание не
пересчитано — уборка тихо перестаёт работать.

## Альтернативы и когда они лучше

| Вариант | Когда лучше | Цена |
|---|---|---|
| `DELETE ... WHERE CREATED_AT < X LIMIT 200` (MySQL) | журнал в миллионы строк, нужен один запрос на порцию | диалект-специфично, нет поштучного учёта ошибок |
| Партиционирование по дате + `DROP PARTITION` | журнал — главная таблица нагрузки | схема БД и миграции сложнее, нужен DBA |
| Отдельная таблица-архив вместо удаления | данные нужны для разбора инцидентов | растёт вторая таблица, нужен свой срок |
| `\Bitrix\Main\AgentTable` (D7) для чтения | нужен `select`/`filter` по агентам в своём коде | для регистрации всё равно legacy `CAgent` |

## Покрытые edge cases

- журнал пуст → `stop_reason = empty`, ошибок нет;
- второй прогон → 0 удалений;
- строка ровно на границе срока → остаётся;
- параллельный запуск → второй процесс выходит по блокировке;
- ошибка удаления одной строки → остальные удалены, `failed` и текст ошибки в отчёте;
- ошибка записи отчёта → не влияет на возврат имени агента;
- битый UTF-8 в сообщении журнала → `JSON_INVALID_UTF8_SUBSTITUTE`.

## Непокрытое и границы применимости

- `flock` защищает только при общем локальном диске. На нескольких серверах
  (веб-кластер, отдельная cron-машина) нужен распределённый lock: `GET_LOCK()`
  в MySQL или блокировка в отдельной таблице.
- Отчёт в JSONL растёт бесконечно: нужен `logrotate` (шаблон — в
  `../example-file-log-cleanup/README.md`).
- Срок хранения — константа класса. Для «разного срока для разных `CODE`»
  нужна таблица политик, а не правка кода.
- `CEventLog` пишется только при ошибках: успешные ежедневные сводки остаются
  в JSONL, иначе журнал событий забьётся.

## Что здесь важно понять, а не скопировать

1. Агент — не демон. Он выполняется, когда сработала проверка агентов, и
   уходит вместе с процессом. Всё, что должно пережить запуск, лежит в БД или
   в файле.
2. «Ограничить работу за вызов» — это два разных лимита: количество строк и
   время. Один без другого не спасает.
3. Идемпотентность здесь получается не из кода, а из условий запроса:
   `< cutoff` + удаление по ключу. Повторный запуск просто не находит целей.
4. Блокировка — про производительность и чистоту отчётов, а не про
   корректность: даже без неё данные не испортятся.

# Агент очистки старых логов для Bitrix Framework

## 📋 Описание

Агент автоматически удаляет файлы логов старше 30 дней из каталога `/upload/logs/`. Решение предназначено для небольших и средних проектов и включает:

- штатную регистрацию через `CAgent`;
- автозагрузку класса агента;
- проверку путей и запрет символических ссылок;
- блокировку параллельного запуска через `flock`;
- изоляцию ошибок по каждому файлу;
- запись отчётов в JSONL вне document root;
- уведомления администратору через `CAdminNotify`;
- режим `dry-run` для безопасной проверки перед удалением.

---

## 🗂 Структура проекта

```text
/local/
├── php_interface/
│   ├── init.php                              # Регистрация автозагрузки
│   └── lib/
│       └── MyCompany/
│           └── Agents/
│               └── CleanOldLogsAgent.php     # Класс агента
└── tools/
    └── clean-old-logs/
        └── install.php                       # Установщик агента
```

Служебный каталог (вне document root):

```text
/var/lib/bitrix/clean-old-logs/
├── cleanup.lock      # Файл блокировки
└── agent.jsonl       # Журнал отчётов (JSONL)
```

## ✅ Требования

- PHP 8.2 или выше;
- Bitrix Framework с модулем `main`;
- права на запись в `/upload/logs/` и `/var/lib/bitrix/clean-old-logs/`;
- веб-сервер и CLI должны использовать одну версию PHP;
- каталог `/upload/logs/` должен быть выделен исключительно для логов, подлежащих очистке.

## 🚀 Установка

### Шаг 1. Разместите файлы

Скопируйте файлы в соответствии со структурой выше:

- `CleanOldLogsAgent.php` → `/local/php_interface/lib/MyCompany/Agents/CleanOldLogsAgent.php`
- `install.php` → `/local/tools/clean-old-logs/install.php`

### Шаг 2. Настройте автозагрузку

Добавьте в существующий `/local/php_interface/init.php` следующий фрагмент (не перезаписывая остальное содержимое):

```php
<?php

use Bitrix\Main\Loader;

Loader::registerAutoLoadClasses(
    null,
    [
        \MyCompany\Agents\CleanOldLogsAgent::class
            => '/local/php_interface/lib/MyCompany/Agents/CleanOldLogsAgent.php',
    ]
);
```

Если `init.php` уже содержит открывающий `<?php`, второй добавлять не нужно.

### Шаг 3. Создайте служебный каталог

Выполните на сервере (замените пользователя и группу на реальные):

```bash
sudo install -d \
  -m 0700 \
  -o www-data \
  -g www-data \
  /var/lib/bitrix/clean-old-logs
```

Каталог должен быть доступен на запись пользователю, от которого работает PHP и cron. Предпочтительно, чтобы PHP-FPM и cron работали от одного пользователя.

### Шаг 4. Подготовьте каталог логов

Убедитесь, что `/upload/logs/`:

- существует;
- не является символической ссылкой;
- доступен PHP на чтение и удаление файлов;
- содержит только те файлы, которые разрешено удалять.

**Доступ к каталогу по HTTP должен быть запрещён.** Нахождение внутри `/upload/` не делает логи приватными.

### Шаг 5. Зарегистрируйте агент

Откройте в браузере (под администратором):

```text
https://ваш-сайт.ru/local/tools/clean-old-logs/install.php
```

Установщик:

- доступен только администратору;
- изменяет состояние только по `POST`;
- проверяет CSRF-токен;
- проверяет автозагрузку и каталоги;
- не создаёт дубликат при повторной установке.

После успешной регистрации **удалите установщик** или закройте к нему доступ на уровне веб-сервера.

## ⚙️ Настройка параметров

Параметры задаются константами в классе `CleanOldLogsAgent`:

```php
public const DAYS_TO_KEEP = 30;                // Срок хранения в днях
public const LOGS_DIR = '/upload/logs';        // Каталог логов относительно DOCUMENT_ROOT
public const RUNTIME_DIR = '/var/lib/bitrix/clean-old-logs'; // Служебный каталог
```

- `DAYS_TO_KEEP` — файлы с `mtime` старше указанного количества дней удаляются.
- `LOGS_DIR` — каталог, в котором выполняется очистка.
- `RUNTIME_DIR` — абсолютный путь вне document root для журнала и блокировки.

## 🎯 Использование

### Проверка без удаления (dry-run)

Выполните в доверенном контексте с подключённым Bitrix (например, через CLI-скрипт или временный административный скрипт):

```php
\MyCompany\Agents\CleanOldLogsAgent::execute(true);
```

Файлы не удаляются. Отчёт записывается в `/var/lib/bitrix/clean-old-logs/agent.jsonl`.

### Обычный запуск

```php
\MyCompany\Agents\CleanOldLogsAgent::execute();
```

После выполнения агент возвращает строку:

```php
\MyCompany\Agents\CleanOldLogsAgent::execute();
```

что обеспечивает его повторный запуск через механизм агентов.

### Проверка зарегистрированного агента

```php
<?php

use MyCompany\Agents\CleanOldLogsAgent;

$result = \CAgent::GetList(
    ['ID' => 'ASC'],
    ['NAME' => CleanOldLogsAgent::AGENT_NAME]
);

while ($agent = $result->Fetch()) {
    if ($agent['NAME'] !== CleanOldLogsAgent::AGENT_NAME) {
        continue;
    }

    echo '<pre>';
    echo htmlspecialcharsbx(
        print_r(
            [
                'ID' => $agent['ID'],
                'ACTIVE' => $agent['ACTIVE'],
                'IS_PERIOD' => $agent['IS_PERIOD'],
                'AGENT_INTERVAL' => $agent['AGENT_INTERVAL'],
                'LAST_EXEC' => $agent['LAST_EXEC'],
                'NEXT_EXEC' => $agent['NEXT_EXEC'],
            ],
            true
        )
    );
    echo '</pre>';
}
```

После выполнения через механизм агентов поле `NAME` должно оставаться равным:

```php
\MyCompany\Agents\CleanOldLogsAgent::execute();
```

Именно эта проверка обнаруживает ошибку с возвратом имени метода.

## ⏰ Настройка cron

В этом решении **нет выдуманного поля `IS_CRON`**. Агент регистрируется штатно. Способ вызова механизма агентов — на хитах или через cron — настраивается на уровне проекта.

Для production:

1. Используйте схему переноса агентов на cron, соответствующую установленной версии Bitrix.
2. Запускайте общий обработчик достаточно часто, обычно раз в минуту.
3. Не меняйте глобальную схему выполнения агентов только ради этой задачи без проверки остальных агентов.
4. Оставьте этому агенту интервал `86400` и `IS_PERIOD = N`.

**Интервал `86400` означает «примерно раз в сутки», а не строго «каждый день в 02:00».** Если требуется точное календарное расписание, лучше отдельно спроектировать запуск через системный планировщик и не дублировать его активным агентом.

## 📊 Логирование и мониторинг

### Журнал агента

Отчёты записываются в JSONL-файл:

```text
/var/lib/bitrix/clean-old-logs/agent.jsonl
```

Пример одной строки (отформатирован для чтения):

```json
{
  "event": "clean_old_logs",
  "dry_run": false,
  "days_to_keep": 30,
  "examined": 14,
  "skipped": 10,
  "eligible_count": 4,
  "eligible_bytes": 10485760,
  "deleted_count": 4,
  "deleted_bytes": 10485760,
  "error_count": 0,
  "errors": [],
  "eligible_size": "10 MiB",
  "deleted_size": "10 MiB"
}
```

### Журнал событий Bitrix

При ошибках создаётся запись в журнале событий Bitrix:

- тип события: `CLEAN_LOGS_AGENT`;
- уровень: `ERROR`.

Просмотр: **Настройки → Журнал событий**.

### Уведомления администратору

При ошибках создаётся уведомление в административной панели с постоянным тегом `mycompany_clean_old_logs_error`. Одно уведомление на запуск, а не на каждый проблемный файл. Уведомление не зависит от почтовых шаблонов.

### Ротация журнала

Настройте `logrotate` для `agent.jsonl`. Пример:

```text
/var/lib/bitrix/clean-old-logs/agent.jsonl {
    daily
    rotate 14
    compress
    missingok
    notifempty
    su www-data www-data
    create 0600 www-data www-data
}
```

**Файл `cleanup.lock` не нужно ротировать или удалять во время работы**: удаление lock-файла может нарушить взаимное исключение процессов.

## 🛡 Безопасность

- Удаляются **все обычные файлы** непосредственно из `/upload/logs/`, если их `mtime` старше 30 × 24 часов.
- Подкаталоги и символические ссылки пропускаются.
- `/upload/logs/` должен быть выделенным каталогом логов, без пользовательских загрузок.
- Служебные журналы и блокировка находятся **вне document root**.
- Проверяются канонические пути через `realpath()`, запрещаются симлинки.
- Перед удалением выполняется повторная проверка метаданных (`lstat`, сравнение `dev/ino/mode/mtime/ctime/size`).
- Доступ к `/upload/logs/` по HTTP должен быть запрещён.
- Права на служебный каталог должны быть ограничены.

Это не защита от произвольного изменения файловой системы злоумышленником: каталог должен иметь корректные права доступа. Проверки путей и метаданных уменьшают риски, но не устраняют все возможные TOCTOU-гонки.

## 🧪 Тестирование

### Минимальный набор проверок

| Сценарий | Ожидаемый результат |
|---|---|
| Файл старше 30 дней | Удалён |
| Файл младше 30 дней | Сохранён |
| Файл ровно на границе срока | Сохранён (условие `>= cutoff`) |
| Подкаталог | Не затронут |
| Симлинк | Пропущен |
| Один файл удалить нельзя | Остальные обработаны, ошибка отражена |
| Каталог отсутствует | Предсказуемый результат без поломки расписания |
| Не работает отправка почты | Агент корректно завершает выполнение |
| Повторный запуск через Bitrix | Класс загружается, возвращается правильное имя |
| Повторная установка | Не создаёт дубликат |

### Проверка после исправления `File::delete()`

Для одного подходящего файла размером 1024 байта:

| Сценарий | `eligible_count` | `deleted_count` | `deleted_bytes` | `error_count` |
|---|---:|---:|---:|---:|
| Успешное удаление | 1 | 1 | 1024 | 0 |
| Исключение при удалении | 1 | 0 | 0 | 1 |
| Dry-run | 1 | 0 | 0 | 0 |

## 🧹 Удаление агента

1. Удалите агент через административную панель: **Настройки → Инструменты → Агенты**.
2. Или программно:

```php
\CAgent::RemoveAgent(
    \MyCompany\Agents\CleanOldLogsAgent::AGENT_NAME,
    ''
);
```

3. Удалите файлы:

```text
/local/php_interface/lib/MyCompany/Agents/CleanOldLogsAgent.php
/local/tools/clean-old-logs/install.php
```

4. Удалите регистрацию автозагрузки из `init.php`.
5. При необходимости удалите служебный каталог:

```bash
sudo rm -rf /var/lib/bitrix/clean-old-logs
```

## 🐛 Решение проблем

### Агент не запускается

- Проверьте, что агент активен в административной панели.
- Убедитесь, что автозагрузка класса работает в CLI.
- Проверьте журнал `agent.jsonl` и журнал событий Bitrix.
- Убедитесь, что механизм агентов вообще выполняется (хиты или cron).

### Ошибка «Класс агента не загружается»

- Проверьте регистрацию в `init.php`.
- Убедитесь, что путь к файлу класса указан верно.
- Проверьте, что `init.php` подключается в CLI-контексте.

### Файлы не удаляются

- Проверьте права на `/upload/logs/`.
- Убедитесь, что путь не является симлинком.
- Проверьте, что файлы старше 30 дней по `mtime`.
- Посмотрите `error_count` и `errors` в `agent.jsonl`.

### Ошибка «Служебный каталог отсутствует»

- Создайте `/var/lib/bitrix/clean-old-logs/` с правами на запись.
- Убедитесь, что путь не является симлинком.
- Проверьте, что каталог находится вне document root.

### Уведомления не приходят

- Уведомления в административной панели работают через `CAdminNotify` и не зависят от почты.
- Если уведомлений нет, проверьте журнал событий Bitrix и `error_log`.

## 📌 Ограничения

- `Directory::getChildren()` формирует список элементов. Для каталога с сотнями тысяч или миллионами файлов этот вариант нужно заменить на потоковый или пакетный обход.
- `deleted_bytes` — **суммарный размер удалённых файлов**, а не гарантия немедленного освобождения диска. Если другой процесс держит удалённый файл открытым, ОС может освободить место позже.
- Почта намеренно не включена в базовый вариант: для неё нужны настроенные тип события, шаблон, сайт, получатель и ограничение повторных отправок. Уведомление в административной панели работает без зависимости от почтовых шаблонов.
- Конкретную конфигурацию cron нужно проверять на версии Bitrix проекта, а не представлять данный README как универсальный рецепт.

# Практика 3. Агент синхронизации с внешним API

**Задача.** Агент получает изменения из внешней системы: тайм-ауты, проверка
HTTP-статуса и JSON, пагинация, сохранение контрольной точки, идемпотентное
обновление записей, ограниченные повторы, отсутствие токенов в логах.

## Что делает код

| Шаг | Что происходит | Что будет при сбое |
|---|---|---|
| 1 | читается контрольная точка `CODE = demo.items` | строки нет → создаётся с пустым курсором |
| 2 | `buildUrl()`: базовый адрес из опции + `limit` + `cursor` | адрес не задан → отчёт с ошибкой, без падений |
| 3 | `HttpClient`: `socketTimeout=3`, `streamTimeout=8`, 2 редиректа | сеть → до 2 попыток на страницу |
| 4 | `get()` вернул `false` → исключение с `getError()` | повтор, затем ошибка в отчёт |
| 5 | HTTP-статус вне 2xx или пустое тело → исключение | повтор, затем ошибка |
| 6 | `json_decode` с `JSON_THROW_ON_ERROR`, проверка `items[]` | битый JSON → ошибка в отчёт |
| 7 | нормализация каждой записи: `id` обязателен, `title`, `changed_at` | запись без `id` → `skipped++`, страница обрабатывается |
| 8 | транзакция: upsert по `EXTERNAL_ID` **и** запись курсора | любая ошибка → `rollback`, курсор не сдвинулся |
| 9 | `next_cursor = null` → `completed = true`, курсор обнуляется | — |
| 10 | не больше 5 страниц и 20 секунд за запуск | `stop_reason = page_limit` / `time_budget` |

Почему именно так:

- **Тайм-ауты в конструкторе `HttpClient`.** У класса нет `setTimeout()`; опции
  называются `socketTimeout` и `streamTimeout` и передаются массивом в
  конструктор.
- **`get()` возвращает `false`, а не бросает.** `try/catch` вокруг вызова без
  проверки результата не ловит сетевую ошибку — она приходит предупреждением и
  `false`.
- **Курсор в той же транзакции, что данные.** Иначе «курсор сохранён, данные
  нет» означает потерянную страницу: следующий запуск начнёт после неё.
- **Повторы на страницу, а не на прогон.** Пять упавших страниц не должны
  исчерпывать бюджет попыток всего прогона.
- **`UNIQUE(EXTERNAL_ID)`.** Идемпотентность синхронизации — это индекс в БД,
  а не проверка «есть ли уже такая запись» в коде.

## Правильный вывод

```
1. Полная синхронизация (две страницы)
  pages=2 fetched=4 created=3 updated=0 skipped=1 completed=да stop=completed
  курсор: было (пусто) -> стало (пусто)
  строк в локальной таблице: 3

2. Повторный прогон (идемпотентность)
  pages=2 fetched=4 created=0 updated=3 skipped=1 completed=да stop=completed
  строк в локальной таблице: 3

3. Ошибка провайдера (HTTP 503 на первой странице)
  pages=0 fetched=0 created=0 updated=0 skipped=0 completed=нет stop=error
  ошибки: RuntimeException: Страница не получена за 2 попытки: HTTP-статус 503
  контрольная точка: pages_done 0 -> 0

4. Прогресс сохраняется: точка после первой страницы, вторая падает
  pages=0 ... stop=error
  курсор после сбоя: p2 (ожидается p2)

5. Продолжение с сохранённой точки
  pages=1 fetched=2 created=1 updated=0 skipped=1 completed=да stop=completed
  строк в локальной таблице: 1 (ожидается 1: вторая страница)

Проверки
  пагинация, идемпотентность и контрольная точка работают — ок
```

## Почему решение такое

**Курсор от провайдера, а не `updated_at > last_run`.** Фильтр по времени
теряет записи, изменённые во время прогона, и зависит от часов сервера.
Курсор — единственный источник истины о том, что уже прочитано.

**Транзакция на страницу, а не на весь прогон.** Прогон может занять
несколько страниц и быть прерванным; фиксация постранично оставляет
осмысленную точку восстановления.

**Обрезка курсора в отчёте.** Курсор нередко содержит подписанный токен
(`?cursor=eyJhbGciOi...`), поэтому в JSONL попадает только начало, а сам адрес
API не пишется вовсе.

**Токен заголовком, а не в query.** URL попадает в `access.log` веб-сервера,
прокси и журналы ошибок; заголовок `Authorization` — меньше.

## Альтернативы и когда они лучше

| Вариант | Когда лучше | Цена |
|---|---|---|
| Провайдер отдаёт `updated_at`-фильтр и `updated_at` возрастает | простой API без курсоров | нужна гарантия монотонности и синхронизация часов |
| Вебхуки вместо опроса | нужна секундная реакция | нужен публичный endpoint, проверка подписи, повторная доставка |
| REST-провайдер через `Bitrix\Main\Web\HttpClient` + очередь (practice-2) | много объектов, разная скорость обработки | инфраструктура очереди |
| `\Bitrix\Main\Web\Json` вместо `json_decode` | нужен `Json::decode` с контролем кодировки | поведение на битом UTF-8 отличается, `JSON_THROW_ON_ERROR` понятнее |
| Пакетный upsert (`INSERT ... ON DUPLICATE KEY UPDATE`) | тысячи записей на страницу | SQL под конкретный движок, ORM не даёт |

## Покрытые edge cases

- две страницы, `next_cursor = null` на последней → `completed`;
- повторный прогон → 0 созданных, все обновлены, дублей нет;
- запись без `id` → `skipped`, страница не падает;
- HTTP 503 → 2 попытки, `stop_reason = error`, исключение не выходит наружу;
- сбой после первой страницы → курсор остаётся `p2`, следующий запуск
  продолжает с него;
- адрес API не задан → понятная ошибка в отчёте;
- пустой ответ и битый JSON → разные сообщения об ошибке.

## Непокрытое и границы применимости

- **Тайм-аут и пауза между повторами.** `usleep(300ms)` внутри агента
  допустим только потому, что агент работает из cron. На хитах это время ждёт
  посетитель — там повторы надо выносить в очередь.
- **Лимит страниц vs. большой бэклог.** Если провайдер отдаёт миллион записей,
  5 страниц за запуск — это месяцы. Нужен отдельный worker/CLI и прогресс в
  `SyncStateTable`, а не агент.
- **Нет удаления.** Записи, пропавшие на стороне провайдера, остаются
  локально. Для полной синхронизации нужен режим «полный проход + удаление
  отсутствующих» с отдельным курсором.
- **Нет проверки структуры каждого поля.** Валидируется только `id`/`title`;
  для строгого контракта нужен JSON Schema или явный валидатор.
- **Токен в опциях.** `Option` хранит значение в `b_option` открытым текстом —
  это уровень «не в логах», а не «защищено». Для секретов коробки нужен
  `.settings.php`/переменные окружения и ограничение прав на файл.

## Что здесь важно понять, а не скопировать

1. `HttpClient::get()` не бросает исключений: основная ошибка здесь — `catch`
   вокруг вызова без проверки `false`.
2. Контрольная точка — часть транзакции с данными. Иначе синхронизация
   «перепрыгивает» страницу и теряет её навсегда.
3. Идемпотентность живёт в схеме БД (`UNIQUE`), а не в `if (уже есть)`.
4. Пагинация заканчивается не «когда пусто», а по явному признаку
   (`next_cursor = null`): пустая страница может быть и в середине.

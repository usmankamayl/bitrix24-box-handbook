# Практика 2. Агент разбора очереди писем

**Задача.** Агент обрабатывает собственную таблицу очереди: статусы
`new`/`processing`/`sent`/`error`, ограниченная порция, число попыток и время
следующей попытки, защита от конкурентного захвата, восстановление зависших
строк, определённая стратегия против дублей.

## Что делает код

Поток одного запуска:

| Шаг | Что происходит | Что будет при сбое |
|---|---|---|
| 1 | `execute()` → `run()` | исключение ловится, имя агента всё равно возвращается |
| 2 | `recoverStuck()`: `processing` с истёкшим `LOCKED_UNTIL` → `new`, а с исчерпанными попытками → `error` | ошибка БД → отчёт, выход |
| 3 | выборка одного `ID` со `STATUS='new'` и наступившим `NEXT_ATTEMPT_AT` | кандидатов нет → `stop_reason = empty` |
| 4 | `claim()`: `UPDATE ... SET STATUS='processing', ATTEMPTS=ATTEMPTS+1 WHERE ID=? AND STATUS='new'` | обновлено 0 строк → `contended++`, строка чужая |
| 5 | `Event::send()` | исключение или `false` → `fail()` |
| 6 | успех: `STATUS='sent'`, `SENT_AT`, снят `LOCKED_UNTIL` | — |
| 7 | неудача: `ATTEMPTS < 5` → `new` + `NEXT_ATTEMPT_AT` (60·2ⁿ, потолок 3600); иначе `error` + `CEventLog` | — |
| 8 | шаги 3–7 повторяются до 20 писем или 20 секунд | — |
| 9 | отчёт в `email-queue.jsonl` | сбой записи не влияет на возврат имени |

Почему захват именно такой:

- **Условный `UPDATE`, а не «прочитали и обновили».** Между `SELECT` и
  `UPDATE` строку может забрать второй процесс. Условие `WHERE STATUS='new'`
  делает захват атомарным на уровне БД: `UPDATE` либо обновит одну строку и
  вернёт 1 в `getAffectedRowsCount()`, либо не обновит ничего.
- **`LOCKED_UNTIL` вместо «навсегда processing».** Процесс может умереть между
  захватом и отправкой (таймаут, OOM, перезапуск php-fpm). Без TTL такая
  строка не вернётся никогда.
- **Статус `sent` ставится после `Event::send()`, а не до.** Обратный порядок
  («пометили, потом отправили») теряет письма при падении процесса.
- **`UNIQUE(DEDUP_KEY)` + обработка `DuplicateEntryException`.** Проверка
  «есть ли такое письмо» до `INSERT` не защищает от гонки; уникальный индекс
  защищает.

`sent` = «письмо передано в почтовую подсистему Bitrix» (запись в `b_event`).
Фактическую доставку подтверждает SMTP-сервер, и до `b_event.SUCCESS_EXEC = Y`
строка `sent` ничего не гарантирует.

Отдельно про контракт `Event::send()`: в новых сборках он возвращает `AddResult`
(объект), в старых — ID или `false`. Объект всегда truthy, поэтому «проверка
`if (!$result)`» на новом ядре не ловит неуспех: нужен `isSuccess()` у
результата. В `EmailQueueAgent::send()` проверяются оба контракта — пример не
должен зависеть от версии.

## Правильный вывод

```
1. Постановка в очередь (идемпотентность по DEDUP_KEY)
  первый вызов:    id=1 duplicate=нет
  повторный вызов: id=1 duplicate=да
  строк с префиксом demo.queue.: 3 (ожидается 3)

2. Первый прогон агента
  candidates=3 claimed=3 sent=3 retried=0 dead=0 contended=0 stop=empty
  new=0  processing=0  sent=3  error=0  ...

3. Второй прогон сразу после первого
  candidates=0 claimed=0 sent=0 retried=0 stop=empty
```

Если шаблон письма не создан, `Event::send()` вернёт `false` и вывод будет
другим — `sent=0 retried=3`, у строк появится `NEXT_ATTEMPT_AT` через 60
секунд. Это тоже правильный вывод: агент не падает, а переносит попытку.

## Почему решение такое

**Порция в 20 писем и 20 секунд.** Агент на хитах работает внутри запроса
посетителя; отправка 500 писем в одном запросе — это таймаут, а не рассылка.

**Интервал агента 60 секунд.** Письмо в очереди должно уйти за минуты, а не за
час. Цена — частые проверки; при пустой очереди это один дешёвый `SELECT`.

**Повтор с экспоненциальной задержкой.** Мгновенные повторы добивают падающий
SMTP; линейная задержка даёт «шторм» через равные интервалы. Потолок в час
ограничивает и то, и другое.

**Отдельный статус `error` вместо бесконечных повторов.** Письмо, которое
падает 5 раз, — это проблема данных или шаблона, а не сети; его должен увидеть
человек, а очередь должна идти дальше.

## Альтернативы и когда они лучше

| Вариант | Когда лучше | Цена |
|---|---|---|
| `b_event` + `CEvent::CheckEvents()` без своей очереди | письма с шаблонами и штатные уведомления | нет своих статусов, нет dedup-ключа, нет управления попытками |
| `\Bitrix\Main\Mail\Sender` + `Bitrix\Sender` (маркетинг) | массовые рассылки с сегментами | тяжёлый модуль, рассчитан на кампании, а не на транзакционные письма |
| Очередь во внешнем брокере (RabbitMQ) | несколько серверов, высокий поток | инфраструктура, свой consumer, деплой |
| `SELECT ... FOR UPDATE` вместо условного `UPDATE` | сложная логика выбора строки | держит блокировку на время отправки, второй процесс ждёт |
| Блокировка `GET_LOCK()` на имя очереди | один обработчик на всю очередь, MySQL | не работает на другом движке БД |

## Покрытые edge cases

- повторная постановка того же письма → `duplicate: true`, новой строки нет;
- гонка двух постановок → второй `INSERT` ловится по `DuplicateEntryException`;
- зависшая строка с `LOCKED_UNTIL` в прошлом → возвращается в `new`;
- зависшая строка с `ATTEMPTS >= MAX` → `error`, а не бесконечный цикл;
- два процесса одновременно → один получает `claimed`, второй `contended`;
- `Event::send()` вернул неуспешный результат (нет шаблона) → повтор, а не «sent»;
- `Event::send()` бросил исключение → то же;
- очередь пуста → `stop_reason = empty`, ошибок нет.

## Непокрытое и границы применимости

- Строка, у которой процесс жив, но завис (медленный SMTP дольше
  `LOCK_TTL_SECONDS`), будет захвачена повторно → письмо может уйти дважды.
  Правильное решение — увеличить TTL и/или хранить `WORKER_ID` и сверять его
  при завершении.
- Нет приоритетов: `ORDER BY ID` = FIFO. Для транзакционных писем впереди
  маркетинговых нужен `PRIORITY` и соответствующий индекс.
- Нет ограничения на размер `BODY`: мегабайтное письмо в очереди — проблема
  `max_allowed_packet`. В проде тело хранят в файле/на диске, а в строке —
  ссылку и хеш.
- `sent` не равно «доставлено»; для реального контроля нужен разбор
  `b_event.SUCCESS_EXEC`/ bounce-ов.

## Что здесь важно понять, а не скопировать

1. «Защита от конкурентного захвата» — это одно условие в `WHERE`, а не
   `flock` на файле и не `sleep`.
2. Состояние строки — часть контракта. Если статус ставится до выполнения
   работы, система врёт о себе.
3. Очередь без восстановления зависших строк теряет письма молча: `processing`
   выглядит как «в работе», а работы нет.
4. Нельзя смешивать два смысла слова «отправлено»: передано в подсистему и
   доставлено получателю.

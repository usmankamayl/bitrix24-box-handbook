# Защищённый обработчик входящих событий от OAuth-приложения

Endpoint, который принимает события от Bitrix24 и проверяет их подлинность
по связке `member_id` + `application_token`, а не только по одному из них.
Пример того, что на собеседовании называют "обработчик не должен принимать
чужие запросы".

## Файлы

- `config.php` — подключение к БД с таблицей `app_installations`
- `handler.php` — сам обработчик (двухуровневая проверка + рутинг событий)

## Установка

1. Требуется таблица `app_installations` из `examples/module-13-1/` (поле `application_token` заполняется при `ONAPPINSTALL`).
2. Зарегистрируйте `handler.php` как обработчик события через `event.bind` или в настройках приложения.

## Как это работает

```
POST → handler.php
  │
  ├─ member_id из auth находим в app_installations (status=active)
  │   └─ не нашли → 403 "unknown member_id"
  │
  ├─ application_token из auth сверяем с сохранённым hash_equals()
  │   └─ не совпал → 403 "token mismatch"
  │
  └─ оба признака сошлись → обработка события
```

## Ключевые моменты для собеседования

- **`member_id` не секретен** — его можно подобрать или узнать из адреса портала, поэтому одной его проверки недостаточно. Но в связке с `application_token` он подтверждает, что запрос от конкретного установленного портала, а не от чужого.
- **`hash_equals()` вместо `==`** — защита от timing-атаки (злоумышленник не сможет подобрать токен по времени ответа сервера). Мелочь, но маркер зрелого ответа.
- **IP-фильтрация — неправильный механизм.** IP-адреса Bitrix24 не документированы как надёжный источник доверия и могут меняться; `application_token` — единственный официальный способ подтвердить подлинность запроса от OAuth-приложения.
- **`status = "active"` в запросе** — уже удалённое приложение не должно принимать события от этого портала, даже если member_id/app_token технически совпадают.

Подробный теоретический разбор — в `topics/module-13-4.md`, задача 3.

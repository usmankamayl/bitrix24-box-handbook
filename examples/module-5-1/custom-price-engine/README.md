# Кейс 3: Кастомный ценовой движок «Партнёр» через OnGetOptimalPrice

## Что решает

Часто на собеседовании спрашивают: *«заказчик хочет, чтобы у партнёров определённого уровня была своя наценка на разные категории товаров — как сделать без форка ядра каталога?»*. Решение — не плодить ещё один тип цены (`b_catalog_group`) на каждую комбинацию категория×партнёр (их может быть сотни), а **перехватить итоговый расчёт цены** через событие `OnGetOptimalPrice` и применить правило наценки динамически.

## Структура

```
custom-price-engine/
├── events.php                       # регистрация обработчика события
├── lib/
│   ├── PartnerPriceCalculator.php   # сам обработчик OnGetOptimalPrice
│   └── PartnerMarkupTable.php       # доступ к правилам наценки (HL-блок)
├── install/
│   └── install_hlblock.php          # одноразовое создание HL-блока с полями
└── README.md
```

## Модель данных

HL-блок `PartnerCategoryMarkup`:

| Поле | Тип | Смысл |
|---|---|---|
| `UF_SECTION_ID` | integer | ID раздела каталога |
| `UF_USER_GROUP_ID` | integer | ID группы пользователей («Партнёр 1 уровня» и т.д.) |
| `UF_MARKUP` | double | Процент наценки, например `12.5` |

Правило «раздел × группа → наценка» — гибкая связная сущность, которую удобно редактировать через стандартный список HL-блока в админке, не трогая код.

## Ключевые приёмы (на что обратить внимание на собеседовании)

1. **Точка расширения — `OnGetOptimalPrice`, а не правка `CCatalogProduct`.** Это единственное официальное место, где можно модифицировать уже посчитанную (с учётом скидок, валюты, типа цены) итоговую цену, не трогая ядро модуля `catalog`.

2. **Группы-партнёры и наценки конфигурируются, а не хардкодятся.** ID партнёрских групп — в настройках модуля (`Option::get`), правила наценки — в HL-блоке. Разработчик не нужен, чтобы завести новую партнёрскую группу или поменять процент.

3. **Раздел для SKU берём у родителя.** Торговые предложения обычно не привязаны к разделам витрины напрямую — типичная ошибка новичка: искать `IBLOCK_SECTION_ID` у самого SKU и получать `null`.

4. **Правило «максимальная наценка» при пересечении групп.** Если пользователь состоит в нескольких партнёрских группах с разными правилами на один раздел — бизнес-логика явно фиксирует, какая наценка побеждает (здесь — большая), а не «первая попавшаяся», что было бы недетерминированным багом.

5. **Кэш на время хита.** `PartnerPriceCalculator::$requestCache` — чтобы при выводе списка из 50 товаров не делать 50 отдельных походов в HL-блок для одного и того же раздела/группы без необходимости (хотя `PartnerMarkupTable::getMarkup` и так дешёвый точечный запрос, кэш страхует от списков с повторным рендером одного товара, напр. в блоке «похожие»).

## Как использовать

1. Выполнить `install/install_hlblock.php` один раз (через `php_command_line.php` в админке или `php -f` из CLI с подключённым прологом).
2. Подключить `events.php` в `/local/php_interface/init.php`.
3. В настройках модуля `bitrix_course` (или через `Option::set` напрямую) задать `partner_group_ids`, например `'7,9'`.
4. Добавить строки в HL-блок `PartnerCategoryMarkup`, например: раздел 12, группа 7, наценка 15.0.
5. Проверить: `CCatalogProduct::GetOptimalPrice($productId, 1, [7])` должен вернуть цену, увеличенную на 15% для товаров из раздела 12.

## Возможные вопросы на собеседовании по этому коду

- Почему наценка не реализована через ещё один тип цены (`CATALOG_GROUP_ID`)? *(комбинаторный взрыв: N разделов × M партнёрских групп = N×M типов цен в админке — немасштабируемо и неюзабельно)*
- Что если у товара вообще нет цены в базовом типе? *(`$price['PRICE']` будет пустым — `empty()`-проверка в начале обработчика просто ничего не сделает, наценка на 0 не имеет смысла)*
- Как протестировать обработчик без реального фронта? *(вызвать `CCatalogProduct::GetOptimalPrice()` напрямую в консоли `php_command_line.php` с разными `$arUserGroups`)*
- Как быть с кешированием компонента каталога, если цена теперь зависит от группы пользователя? *(кеш обязан учитывать группу в `CACHE_GROUPS`/ключе кеша, иначе партнёр увидит кешированную розничную цену — явная ловушка, которую стоит проговорить)*

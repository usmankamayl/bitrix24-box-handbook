# Массовый импорт лидов из CSV с батчами и защитой от дублей

Консольный скрипт для разового или регулярного импорта лидов из CSV-файла
в CRM: батч-запросы (до 50 команд за HTTP-вызов), идемпотентность при
повторном запуске и проверка дублей по email перед созданием.

## Файлы

- `crest.php` — REST-клиент с поддержкой `callBatch()`
- `leads.csv` — пример входного файла
- `import.php` — сам скрипт импорта (CLI)
- `mapping.json` — создаётся автоматически при первом запуске (прогресс)

## Запуск

```bash
php import.php leads.csv
```

В `crest.php` предварительно укажите входящий вебхук
`C_REST_WEB_HOOK_URL` с правами `crm`.

## Как это работает

1. Скрипт читает CSV и `mapping.json` (если уже есть) — строки, чей
   `external_id` уже встречается в mapping, пропускаются сразу: это и
   есть идемпотентность при повторном запуске после сбоя.
2. Оставшиеся строки режутся на батчи по 50.
3. **Шаг 1 батча** — один вызов `batch` с командами
   `crm.duplicate.findbycomm` по email для всех строк батча разом.
4. **Шаг 2 батча** — для строк без найденного дубля формируется второй
   `batch`-вызов с командами `crm.lead.add`.
5. После каждого батча `mapping.json` перезаписывается на диск —
   если скрипт упадёт посередине (сеть, лимит, ошибка PHP), прогресс не
   теряется и следующий запуск продолжит с необработанных строк.
6. `sleep(1)` между батчами — не упираться в rate limit вебхука
   (см. модуль 8.3).

## Почему мэппинг в файле, а не кастомное поле в Bitrix

Для учебного примера идемпотентность реализована через локальный
`mapping.json` — это проще для демонстрации и не требует предварительной
настройки пользовательских полей. В продакшене обычно дополнительно
заводят поле `UF_CRM_EXTERNAL_ID` на лиде и пишут туда `external_id` —
тогда сопоставление "наша система ↔ Bitrix" видно прямо в CRM, а не
только в файле на сервере импорта.

## Ключевые моменты для собеседования

- Прямой цикл `crm.lead.add` по одному вызову на запись упёрся бы в
  rate limit на тысячах строк — отсюда batch по 50 команд.
- Идемпотентность достигается сохранением внешнего ключа
  (`external_id`) к ID созданной записи — без этого повторный запуск
  после сбоя создаст полные дубли.
- Проверка дублей (`crm.duplicate.findbycomm`) выполняется **до**
  создания, а не чисткой дублей после — дешевле и безопаснее.
- Прогресс пишется на диск после каждого батча, а не в конце скрипта —
  иначе обрыв на 999-й из 1000 строк потеряет весь прогресс.

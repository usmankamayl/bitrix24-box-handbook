# Контрольное задание: пять дефектов инициализации

Файлы: `broken.php` (`/local/php_interface/init.php`), `composer.json` того же
проекта, эталон — `fixed.php`.

Задание: назвать все пять дефектов, последствие каждого и условия, при которых
дефект проявляется. Полный ответ — не «так не пишут», а «при X будет Y, потому
что Z».

## Ответ

### 1. Собственный глобальный автозагрузчик с `include`

```php
spl_autoload_register(function ($class) {
    $path = $_SERVER['DOCUMENT_ROOT'] . '/local/php_interface/classes/'
        . str_replace('\\', '/', $class) . '.php';
    include $path;
});
```

**Причина.** Автор не знал, что PSR-4 из `composer.json` уже покрывает
`MyCompany\*`, и добавил «быстрый» загрузчик.

**Последствие.** Два независимых эффекта:

- `include` без `file_exists` на первом же промахе даёт
  `Fatal error: Failed opening required '.../classes/Some/Class.php'` — и,
  что важнее, **обрывает цепочку**: этот загрузчик стоит в стеке до
  `Composer\Autoload\ClassLoader`, поэтому классы, которые нашлись бы у
  Composer, до него уже не дойдут;
- путь собирается из строки имени класса без валидации. `class_exists($x)` и
  `unserialize()` вызывают автозагрузчик с произвольной строкой, поэтому
  `class_exists('../../../../etc/passwd')` — это `include` файла за пределами
  каталога классов. Классический local file inclusion через автозагрузку.

**Исправление.** Удалить. Если свой обработчик действительно нужен (например,
классы в нижнем регистре вне PSR-4) — `Loader::registerHandler(callable)`,
внутри цепочки ядра, с проверкой `is_file()` и валидацией имени по
`[a-zA-Z0-9_\\/]`.

### 2. `registerNamespace` для каталога с CamelCase-файлами

```php
Loader::registerNamespace('MyCompany\\Legacy', '.../classes/Legacy');
```

**Причина.** `registerNamespace` принимают за PSR-4. Это не так: `Loader`
приводит путь к нижнему регистру.

**Последствие.** `MyCompany\Legacy\OldHelper` ищется в
`classes/legacy/oldhelper.php`. На Windows находит `classes/Legacy/OldHelper.php`
и всё «работает»; на Linux в проде — `Class not found`. Диагностика занимает
часы, потому что на машине разработчика ошибка не воспроизводится.

**Исправление.** Либо переименовать файлы в нижний регистр (тогда работает и
`Loader`), либо перевести namespace на PSR-4 в Composer — он ищет файл по имени
класса без изменения регистра.

### 3. Безусловный `require` автозагрузчика Composer

```php
require_once $_SERVER['DOCUMENT_ROOT'] . '/local/vendor/autoload.php';
```

**Причина.** «Composer же всегда установлен».

**Последствие.** Деплой без `composer install` (или `vendor/` не в git, или
папка не скопирована) — `Fatal error` на этапе 6 пролога, то есть **до**
`header.php`. Браузер получает пустую страницу без текста ошибки; сообщение
есть только в `error_log`/`php_errorlog`. Классический «белый экран» после
переезда.

**Исправление.**

```php
$autoload = Loader::getDocumentRoot() . '/local/vendor/autoload.php';
if (is_file($autoload)) {
    require_once $autoload;
}
```

Если зависимости критичны — не молчать, а отдавать понятную ошибку
(`CHTTP::SetStatus('503 Service Unavailable')` + запись в лог), но не фатал
до шаблона.

### 4. Проверка прав в теле `init.php`

```php
if (!$USER->IsAuthorized()) {
    return;
}
```

**Причина.** Ошибочное представление, что `init.php` подключается «когда всё
готово». Он подключается на шаге 6 пролога, а `$USER` создаётся на шаге 9.

**Последствие.** На PHP 8 `$USER` в этот момент — неинициализированная
переменная: `Error: Call to a member function IsAuthorized() on null`, страница
падает целиком. Если же ядро к этому моменту успело определить `$USER`
(старые сборки), срабатывает вторая часть дефекта: `return` выходит из
`init.php` и **отменяет все регистрации ниже** — карта классов, обработчики
событий, константы. Сайт живёт, но без половины логики; искать причину будут
в обработчиках, а не в `init.php`.

**Исправление.** В теле `init.php` — только регистрации и константы. Проверка
прав — внутри обработчика события или в точке входа, где `$USER` уже есть.
Защита от прямого вызова файла — `defined('B_PROLOG_INCLUDED')`.

### 5. Класс объявлен в двух источниках

`composer.json` содержит `autoload.files` с `Pricing/Calculator.php`, и тут же
`registerAutoLoadClasses` регистрирует тот же `MyCompany\Pricing\Calculator`
картой.

**Причина.** Проект переводили на Composer и не убрали старую регистрацию.

**Последствие.**

- `files` — eager-подключение: файл читается и компилируется на **каждом**
  запросе, включая AJAX и REST, независимо от того, нужен класс или нет;
- карта и `files` расходятся в путях (абсолютный `/local/...` против
  относительного в `composer.json`), поэтому один и тот же класс может быть
  включён из двух файлов — `Fatal error: Cannot declare class`;
- при разборе бага непонятно, кто включает файл: `grep` по классу даёт две
  записи, и обе «правильные».

**Исправление.** Один источник истины. Классы — только PSR-4; `autoload.files`
оставить для функций и констант, карту — для того, что не описывается ни
модульным префиксом, ни PSR-4.

## Модификация (проверка понимания)

Условие меняется: проект переезжает в `/local/modules/mycompany.pricing/` как
отдельный модуль. Что из пяти исправлений остаётся, что переписывается, а что
исчезает совсем?

Ожидаемый ответ: пункт 5 исчезает (класс уходит в `lib/`, Composer его больше
не касается), пункт 2 исчезает вместе с `registerNamespace` (модульный префикс
и конвенция нижнего регистра), пункт 1 остаётся запрещённым, пункты 3 и 4 не
зависят от места кода. Регистрация в `init.php` заменяется на
`Loader::includeModule('mycompany.pricing')` в точках использования.

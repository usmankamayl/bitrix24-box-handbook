# Task Request — Request, валидация и JSON-ответ

Материал подраздела **1.7** (`Application`, `Context`, `Request`, `Response`).
Здесь три файла, которые закрывают один и тот же путь с разными контрактами:

| Файл | Путь в проекте | Что показывает |
|---|---|---|
| `search.php` | `/search/index.php` | GET-параметр, проверка типа, поиск по инфоблоку, экранирование в выводе |
| `registration-form.php` | `/register/index.php` | POST-форма, `check_bitrix_sessid()`, `Result` с несколькими ошибками |
| `RegistrationValidator.php` | `/local/php_interface/classes/Forms/RegistrationValidator.php` | валидация на массиве, без HTML и без БД |
| `json-endpoint.php` | `/local/api/registration.php` | JSON-тело, CSRF без `$_POST`, статус и `Content-Type` |

## Как поставить

1. `RegistrationValidator.php` → `/local/php_interface/classes/Forms/RegistrationValidator.php`.
2. В `/local/php_interface/init.php` — автозагрузка:

```php
\Bitrix\Main\Loader::registerNamespace(
    'MyCompany\Forms',
    __DIR__ . '/classes/Forms'
);
```

3. `search.php` → `/search/index.php`; в нём заменить `$iblockId = 5` на свой инфоблок.
4. `registration-form.php` → `/register/index.php`.
5. `json-endpoint.php` → `/local/api/registration.php`.

## Что здесь важно понять

- **`Request` — источник данных, а не фильтр.** `getQuery()`/`getPost()` не
  проверяют ни тип, ни формат. `?q[]=1` вернёт массив, `?q=` — пустую строку,
  отсутствие параметра — `null`. Все три случая надо разобрать явно.
- **Проверка типа до приведения.** `(int)'12abc'` даёт `12`, `(int)[]` — `1`.
  Поэтому `filter_var(..., FILTER_VALIDATE_INT)` на строке, а не приведение.
- **Валидация не экранирует.** `htmlspecialchars()` на входе — это ошибка слоя:
  в БД попадут HTML-сущности, и в шаблоне они будут экранированы второй раз.
  Валидатор нормализует (trim, lowercase email, чистка телефона), экранирование
  делает шаблон.
- **`Result` вместо исключений для ожидаемых ошибок.** Пользователь не ввёл
  email — это не исключительная ситуация. `Result` собирает все ошибки сразу,
  а не первую; клиент получает коды (`EMAIL_INVALID`), а не текст для парсинга.
- **`check_bitrix_sessid()` работает с `$_POST`/`$_GET`.** В JSON-эндпоинте
  sessid приходит в теле или заголовке — сравниваем с `bitrix_sessid()` через
  `hash_equals()`.
- **`%NAME` — оператор, а не часть значения.** `LIKE` с обеих сторон добавляет
  API; вписывать `%` в значение руками — двойной `%%`.
- **`nTopCount`/`limit` обязательны.** `GetList` без ограничения на каталоге
  в 50 000 элементов — это таймаут, а не «медленная страница».
- **JSON-ответ — это статус + `Content-Type` + тело.** `Json::encode()` сам по
  себе ответом не является; заголовки ставятся до первого вывода.
- **`NO_KEEP_STATISTIC`** для эндпоинта, который вызывается часто и не является
  страницей: иначе каждый вызов пишет статистику. `NOT_CHECK_PERMISSIONS`
  здесь **не** ставится: ослаблять проверки в публичной точке входа нельзя.

## Ограничения

- **Нет сохранения.** Валидные данные никуда не пишутся: слой репозитория —
  тема модуля 2. Показывать «сохранение» через `CIBlockElement::Add()` в
  примере про Request было бы смешением тем.
- **Нет пагинации** в поиске: только `nTopCount`. Для реального каталога —
  `CIBlockResult::NavStart` или постраничная навигация компонента.
- **HTML-описание из инфоблока выводится как есть.** Это доверенный контент
  админки; если в него попадает пользовательский ввод — нужен санитайзер.
- **Валидатор без юнит-тестов.** Он для них и написан (принимает массив,
  возвращает `Result`), но тесты — тема модуля 6.
- **CSRF-токен в JSON-теле** — упрощение. В реальных SPA токен часто отдают
  отдельным эндпоинтом и передают заголовком; механика проверки та же.

## Что было исправлено в предыдущей версии примеров

Старый набор (в `examples/module-1-1/task-3`) смешивал слои и учил неверному.
Расхождения, из-за которых он переписан:

| Было | Стало |
|---|---|
| `htmlspecialchars()` на входе, `strip_tags()` в валидаторе | валидатор нормализует, шаблон экранирует |
| `is_numeric()` + `(int)` для числа | `filter_var(FILTER_VALIDATE_INT)` с диапазоном |
| `$request->get()` без проверки типа | `getQuery()`/`getPost()` + `is_string()` |
| экранирование `$searchQuery` до поиска (LIKE по сущностям `&quot;`) | поиск по сырому значению, экранирование только при выводе |
| вывод ошибок из валидатора через `ShowError()` внутри класса | ошибки возвращаются `Result`, выводит шаблон |
| `jsonResponse()` с `die()` внутри класса валидатора | отдельный эндпоинт, статус и заголовки явно |
| `echo` без экранирования в ORM-примерах | вывод через `htmlspecialcharsbx()` |
| `Bitrix\Main\Entity\ExpressionField` (legacy namespace) | примеры ORM убраны в модуль 2, где им место |

# Контрольное задание: пять дефектов эндпоинта

Файлы: `broken.php` (`/local/ajax/request-status.php`), эталон — `fixed.php`.

Задание: назвать все пять дефектов, последствие каждого и условия, при которых
дефект проявляется. Ответ в формате «при X будет Y, потому что Z», а не «так не
пишут».

## Ответ

### 1. `(int)$_REQUEST['id']` — источник и приведение

```php
$id = (int)$_REQUEST['id'];
```

**Причина.** Автор читает «что-нибудь, где-нибудь»: `$_REQUEST` — это смесь
GET/POST/Cookie, состав которой задаётся `variables_order`/`request_order` в
`php.ini`. Приведение `(int)` выбран как «очистка».

**Последствие.** Два независимых эффекта:

- `$_REQUEST` включает cookie (на типовой конфигурации) — значит значение
  приходит от клиента в любом виде, включая `Cookie: id=42`;
- `(int)` не проверяет, а обрезает: `'12abc'` → `12`, `' 12'` → `12`, `[]` → `1`,
  `'1e3'` → `1`. Ошибка ввода молча превращается в валидный чужой идентификатор.

**Исправление.** `$request->getPost('id')` → `is_string()` →
`filter_var(..., FILTER_VALIDATE_INT, ['options' => ['min_range' => 1]])` →
`400`, если `false`.

### 2. `htmlspecialchars()` на входе

```php
$comment = htmlspecialchars(trim((string)($_POST['comment'] ?? '')));
```

**Причина.** «Экранируем всё, что приходит от пользователя» — привычка,
перенесённая из статей про безопасность.

**Последствие.** В БД лежит `&quot;кавычки&quot;` и `&lt;тег&gt;`. Дальше три
проблемы: шаблон экранирует повторно (`&amp;quot;` на экране), поиск и отчёты
ищут по сущностям, а не по тексту, а при выгрузке в CSV/JSON клиент получает
испорченные данные. XSS при этом не закрыт: экранирование имеет смысл только в
конкретном контексте вывода (`href`, JS, атрибут), а не «вообще».

**Исправление.** Хранить нормализованное значение (`trim`, ограничение длины),
экранировать при выводе — `htmlspecialcharsbx()` в HTML-шаблоне.

### 3. `isAjaxRequest()` вместо CSRF

```php
if (!...getRequest()->isAjaxRequest()) {
    die('AJAX only');
}
```

**Причина.** Заголовок `X-Requested-With` принят за признак «свой клиент».

**Последствие.** Заголовок ставит клиент. Сторонняя страница отправляет форму
на этот URL — браузер жертвы прикладывает cookie сессии, `check_bitrix_sessid()`
нигде не вызывается, статус заявки меняется. Классический CSRF. Дополнительно:
`isAjaxRequest()` в части ядер смотрит ещё и на `bxajaxid`, то есть поведение
зависит от версии.

**Исправление.** `check_bitrix_sessid()` (для JSON — сравнение
`hash_equals()` с `bitrix_sessid()` из тела или заголовка). `isAjaxRequest()`
остаётся диагностическим признаком, не защитой.

### 4. `echo` до `header()` и `die()` в середине логики

```php
if (!in_array($status, $allowedStatuses, true)) {
    echo 'Неверный статус';
    die();
}
// ...
header('Content-Type: application/json');
```

**Причина.** Ответ собран «по ходу»: каждая ветка печатает сама.

**Последствие.** Три эффекта:

- к моменту `header('Content-Type: ...')` тело уже отправлено — заголовок не
  встанет, PHP выдаст `Cannot modify header information — headers already sent`;
- клиент получает `200 OK` с текстом ошибки: интеграция считает, что статус
  изменён;
- `die()` не доводит эпилог: статистика, `OnEpilog`, отложенные события не
  выполняются. Письма и события копятся до следующего запроса.

**Исправление.** Одна функция `respond(int $status, array $payload)`: сначала
`http_response_code()` и `header()`, потом тело, `exit` — в конце. Ветки не
печатают, а возвращают.

### 5. Нет проверки владельца: горизонтальный доступ

```php
['IBLOCK_ID' => $iblockId, 'ID' => $id]
```

**Причина.** `CREATED_BY` выбран в `Select`, но нигде не сравнивается с текущим
пользователем. Заодно нет проверки авторизации вообще — эндпоинт работает и для
гостя.

**Последствие.** Любой, кто знает или перебирает `id`, меняет статус чужой
заявки. Это не «недостающая фича», а дыра: `id` — последовательное число,
перебор идёт за минуты.

**Исправление.** `CREATED_BY = $userId` в фильтре и `404`, если элемент не
найден: чужая заявка неотличима от несуществующей, существование объекта не
подтверждается. `403` здесь был бы утечкой.

## В эталоне дополнительно

- Порядок проверок: **метод → кто → CSRF → данные → объект → запись.**
  Метод отсекает мусор дешевле всего, права — до обращения к БД.
- `NOT_CHECK_PERMISSIONS` не ставится: в публичной точке входа он отключает
  проверки, а не ускоряет код.
- Ошибка записи — `500` и строка в лог (`AddMessage2Log`), без деталей в ответе.
- Комментарий ограничен по длине: без лимита в `PREVIEW_TEXT` уезжает мегабайт.

## Чего в этом задании нет

- **ORM.** Эталон остался на `CIBlockElement` — задача про слой входа, а не про
  переписывание на D7 (модуль 2). Ошибка `Update()` не даёт кодов причин, в
  отличие от `Result` у ORM; для этого задания достаточно `bool`.
- **Идемпотентности.** Повторный POST применит тот же статус ещё раз — для
  «установить статус» это безвредно, для «добавить комментарий» уже нет.
- **Проверки прав на уровне модуля.** `CIBlockElement::Update` уважает права
  инфоблока, но полагаться только на это нельзя: у администратора прав больше,
  чем у владельца заявки.

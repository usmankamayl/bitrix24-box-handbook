# Task Context Probe — что ядро реально собрало в Context/Request

Материал подраздела **1.7**. Один файл, одна цель: заменить в голове
«документация говорит» на «вот вывод моей версии ядра».

| Файл | Путь в проекте | Что показывает |
|---|---|---|
| `probe.php` | `/local/tools/context-probe.php` | классы контекста, матрицу методов, снимок `$_GET`, источники значений, заголовки, тело, файлы |

## Как поставить

1. Скопировать `probe.php` в `/local/tools/context-probe.php` (каталог создать).
2. Открыть `http://<сайт>/local/tools/context-probe.php?probe_a=1`.

Страница администратора не нужна, авторизация не нужна: скрипт только читает
текущий запрос и ничего не пишет. На боевом сайте — удалить после снятия
вывода: он показывает структуру запроса, включая наличие заголовков.

`NO_KEEP_STATISTIC` стоит: диагностический вызов не должен попадать в
статистику. `NOT_CHECK_PERMISSIONS` **не** стоит — ослаблять проверки в
публичной точке входа нельзя даже в инструменте.

## Три запроса, которые проверяют разное

```bash
# 1. query + cookie
curl -s 'http://b24.local/local/tools/context-probe.php?probe_a=1&probe_both=from_query' \
     -b 'probe_cookie=cookie_value'

# 2. POST: probe_both задан и в query, и в теле
curl -s -X POST -d 'probe_both=from_post&probe_only_post=1' \
     'http://b24.local/local/tools/context-probe.php?probe_a=1&probe_both=from_query'

# 3. JSON-тело и ajax-заголовок
curl -s -X POST -H 'Content-Type: application/json' \
     -H 'X-Requested-With: XMLHttpRequest' \
     -d '{"probe_both":"from_json"}' \
     'http://b24.local/local/tools/context-probe.php'
```

## Что смотреть в выводе

| Секция | На что смотреть | Правильный вывод |
|---|---|---|
| 1. Кто есть кто | `CMain === Application?` | `false`: это разные объекты, живущие одновременно |
| 2. Методы | строки `нет` | в твоей версии часть API отсутствует: `getCulture()`, `isHttps()`, `getHeaders()` появлялись в разных версиях |
| 3. Снимок | `getQuery(probe_a)` до и после правки `$_GET` | одинаковые; `probe_injected` → `null` |
| 4. Источники | `get()` для `probe_both` | `from_query`; порядок источников — деталь реализации, на него не опираются |
| 5. Заголовки | `Content-Type`, `Authorization` | `HTTP_CONTENT_TYPE` пуст, значение лежит в `CONTENT_TYPE`; `Authorization` может быть пуст целиком |
| 7. Тело | оба чтения `php://input` | совпали; для `multipart/form-data` второе чтение пустое |
| 8. Файлы | `error = UPLOAD_ERR_NO_FILE` | «нет файла» — код ошибки, а не пустой `tmp_name` |
| 9. Сессия/язык/сайт | классы | имена классов в разных ядрах отличаются — это и есть ответ на `[проверить]` |

## Почему так, а не «просто `var_dump($request)`»

- **`method_exists` вместо вызова.** Скрипт не падает с fatal на версии ядра,
  где метода нет: он печатает, чего нет. Так и должно выглядеть
  версионно-зависимое исследование.
- **Сравнение до/после.** «Request — снимок» — утверждение о поведении, а не о
  коде. Оно проверяется правкой `$_GET` после старта контекста.
- **Никаких секретов.** Вывод не содержит значений cookie сессии, только
  наличие/длину. Скрипт можно запускать на демо без последствий.

## Ограничения

- **CLI здесь не проверяется.** В `php -f` контекста HTTP нет; проверка —
  отдельная задача, и в ней `getQuery()` всегда `null`.
- **Мультисайтовость не разбирается.** `getSite()` печатается как класс, без
  переключения сайтов.
- **`get()` — не рекомендация.** Таблица источников показывает поведение
  конкретной версии; в коде всё равно вызываются `getQuery()`/`getPost()`.
- **Прокси-заголовки не проверяются.** `X-Forwarded-For` подставляет клиент;
  доверие к нему — вопрос конфигурации веб-сервера, а не ядра.

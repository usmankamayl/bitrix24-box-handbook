# Task Template Copy — правка стандартного компонента без правки `/bitrix/`

**Задача 3.** До тебя правили `template.php` компонента `bitrix:main.feedback`
прямо в `/bitrix/components/bitrix/`. После обновления правки исчезли. Нужно
восстановить их «правильно» и объяснить цену решения.

Здесь лежит только вторая половина решения — код. Первая половина (процедура
поиска фактического шаблона, проверка кеша, запись в README проекта) в разделах
ниже: она важнее кода, потому что копия не туда — это тот же баг, но позже.

## Что в примере

```
local/templates/.default/components/bitrix/main.feedback/feedback-custom/
├── template.php         копия .default с четырьмя правками
├── result_modifier.php  нормализация REQUIRED_FIELDS для шаблона
└── lang/ru/template.php подписи (заказчик меняет текст здесь, а не в HTML)
```

Куда копировать на сайте:

```bash
T=/путь/до/сайта
cp -r local/templates/.default "$T/local/templates/"        # если шаблона .default в /local нет
```

Вызов компонента на странице — с именем нового шаблона:

```php
$APPLICATION->IncludeComponent(
    'bitrix:main.feedback',
    'feedback-custom',
    [
        'EVENT_NAME'      => 'FEEDBACK_FORM',
        'EMAIL_TO'        => 'info@example.com',
        'REQUIRED_FIELDS' => ['NAME', 'MESSAGE'],   // EMAIL убран из обязательных
        'USE_CAPTCHA'     => 'N',
    ],
    false
);
```

`USE_CAPTCHA => 'N'` — осознанный дефект демо: без капчи форма собирает спам.
В рабочем варианте капча остаётся (`'Y'`), а её блок в шаблоне уже написан.

## Шаг 1. Какой шаблон фактически используется

Порядок поиска для `bitrix:main.feedback` с шаблоном `feedback-custom`:

1. `/local/templates/<шаблон сайта>/components/bitrix/main.feedback/feedback-custom/`
2. `/bitrix/templates/<шаблон сайта>/components/bitrix/main.feedback/feedback-custom/`
3. `/local/templates/.default/components/bitrix/main.feedback/feedback-custom/`
4. `/bitrix/templates/.default/components/bitrix/main.feedback/feedback-custom/`
5. `/local/components/bitrix/main.feedback/templates/feedback-custom/`
6. `/bitrix/components/bitrix/main.feedback/templates/feedback-custom/`

Плюс шаблон на уровне компонента (пункты 5–6) — это «шаблон рядом с
компонентом», а не в шаблонах сайта. Частая причина «я скопировал, а ничего не
изменилось»: копия лежит в `.default`, а сайт работает на другом шаблоне.

Проверка на живой странице, а не по памяти:

```php
// в тело шаблона сайта или в отладочную точку
echo '<pre>' . htmlspecialcharsbx(print_r($APPLICATION->GetTemplatePath(), true)) . '</pre>';
// путь к шаблону конкретного компонента — в result_modifier.php:
echo '<pre>' . htmlspecialcharsbx($this->GetFolder()) . '</pre>';
```

`$this->GetFolder()` в шаблоне компонента возвращает фактический каталог
шаблона. Это единственный ответ, который не врёт: остальное — догадки.

Ещё один способ, быстрее: временно сломать файл (`die('marker')`) и посмотреть,
откуда пришёл маркер. Так же находят, откуда грузится `.css`.

## Шаг 2. Копия шаблона, а не правка

```bash
# 1. база — оригинал из ядра, а не перепечатка по памяти
cp -r bitrix/components/bitrix/main.feedback/templates/.default \
      local/templates/.default/components/bitrix/main.feedback/feedback-custom

# 2. правки — только те, что просил заказчик
#    поле EMAIL убрано, подписи в lang/, id/for, экранирование

# 3. дифф должен показать ровно эти правки
diff -u bitrix/components/bitrix/main.feedback/templates/.default/template.php \
        local/templates/.default/components/bitrix/main.feedback/feedback-custom/template.php
```

Копирование оригинала первым шагом — не формальность. Если начать с чистого
файла, теряются мелочи контракта: скрытые поля (`PARAMS_HASH`), порядок
валидации, обработка `$arResult['ERRORS']`, `component_epilog`. Форма при этом
«выглядит рабочей» и молча не отправляет письма.

## Шаг 3. Когда копировать шаблон уже недостаточно

Правка `template.php` меняет только разметку. Как только заказчик просит
**логику** (другое письмо, запись в свою таблицу, проверка прав, смена
получателя по домену) — копируется компонент:

```bash
cp -r bitrix/components/bitrix/main.feedback local/components/mycompany/feedback
```

Дальше — четыре обязательных правки, иначе копия не заработает или затрёт ядро:

| Что | Почему |
|---|---|
| `local/components/mycompany/feedback/` — свой namespace (`mycompany`), **не** `bitrix` | копия в `/local/components/bitrix/...` перекрывает ядро для всего сайта: обновление компонента вы не получите, но и «откатить» нечем |
| класс в `class.php`/`component.php` переименован, если имя совпадает с ядровым | два класса с одним именем — фатал `Cannot redeclare class` при подключении обоих |
| `.description.php`: `NAME`, `DESCRIPTION` — со своим префиксом | иначе в списке компонентов две одинаковые строки и путаница навсегда |
| вызовы поменять на `mycompany:feedback` | старый вызов продолжит работать с ядровым компонентом, и правки «не применятся» |

Дальше компонент живёт своей жизнью: **исправления ядра в него не приходят**.
Это и есть цена, её пишут в README проекта.

`bitrix:main.feedback` — компонент без `class.php` (логика в `component.php`).
Для копии это значит: копируется целиком, включая `component.php`, и правится
именно он. У компонентов на классах (`catalog.section` и т.п.) копия правит
`class.php` и namespace класса.

## Шаг 4. Кеш и `result_modifier`/`component_epilog`

Что проверить после копии:

1. **Кеш компонента.** Если в вызове `CACHE_TYPE => 'A'`, старый HTML останется
   до истечения TTL. Сброс: `/bitrix/admin/cache.php` или кнопка «Сбросить кеш»
   в шаблоне сайта. Это не баг — это забытый сброс.
2. **`result_modifier.php`** выполняется **только при промахе кеша**. Если
   в нём что-то меняли и «изменения не видны» — сначала сброс кеша.
3. **`component_epilog.php`** выполняется **всегда**, в том числе при попадании
   в кеш; `$arParams`/`$arResult` из шаблона в него не переносятся автоматически
   (нужен `$this->SetResultCacheKeys()` в `result_modifier`). Поэтому состояние
   шаблона не хранят в `$arResult` «на потом для эпилога».
4. **Композит.** Композитный кеш хранит итоговый HTML; изменения в шаблоне
   видны после сброса композитного кеша, а не обычного.

## Цена правки: что ломается вместе с полем

Поле `EMAIL` в `main.feedback` — не просто поле. Компонент использует
`user_email` как адрес отправителя/`Reply-To` письма. Если поле удалено:

- менеджер не может ответить кнопкой «Ответить» — письмо приходит «от сайта»;
- если `EMAIL` остался в `REQUIRED_FIELDS`, форма молча не проходит валидацию
  (поле обязательно, но его нет в разметке) — классический «отправляю, ничего
  не происходит»;
- шаблон и вызов компонента надо менять **вместе**: `REQUIRED_FIELDS` без
  `EMAIL` и шаблон без `user_email`.

Поэтому в примере `REQUIRED_FIELDS => ['NAME', 'MESSAGE']`. Правильный ответ
заказчику в 8 из 10 случаев: «поле оставляем, но делаем необязательным и меняем
подпись» — а не «удаляем».

## Что здесь важно понять, а не скопировать

1. **Копия шаблона ≠ копия компонента.** Первое дёшево и почти всегда
   достаточно; второе — форк, который надо обслуживать.
2. **Путь шаблона проверяют на живой странице** (`$this->GetFolder()`), а не
   восстановлением порядка поиска по памяти.
3. **Оригинал — источник истины.** Копия делается `cp`, а не перепечаткой: цена
   перепечатки — потерянные скрытые поля и неработающая форма.
4. **`/bitrix/` чист.** Критерий приёмки: `git status -- bitrix/` пуст или файлы
   совпадают с дистрибутивом. Это проверяется до и после.

## Проверка

1. `git status -- bitrix/` — пусто (или diff с дистрибутивом).
2. Форма отправляется: письмо приходит на `EMAIL_TO`, в теле — имя и текст.
3. Пустое имя при `REQUIRED_FIELDS => ['NAME']` — ошибка выводится **в шаблоне**,
   а не «ничего не происходит».
4. Сброс кеша компонента — правки на месте.
5. `<script>alert(1)</script>` в имени после отправки — в письме и на странице
   текст, не выполнение.

## Ограничения примера

- Один компонент (`main.feedback`). Для комплексных компонентов (`catalog`,
  `news.list`) порядок тот же, но добавляется кеширование по `SEF_URL` и
  `result_modifier` в комплексном шаблоне.
- Шаблон `.default` в примере — копия; если в вашей сборке он отличается,
  различия в диффе будут не четыре, а больше. Смотрите на смысл правок.
- Компонент копируется командой, но файлы копии здесь не приводятся: копия по
  определению — исходник ядра, переписывать его в примере бессмысленно и вредно
  (он разойдётся с версией сайта).

# Task Code Review — восемь дефектов и эталон

**Задача 5.** Код пришёл на ревью. Нужно найти проблемы и объяснить каждую в
формате «ошибка → причина → последствие → исправление», отдельно отметив, что
ломает безопасность, что производительность, что поддерживаемость.

```
review.php    код как пришёл (не запускать)
fixed.php     эталон после ревью → /local/pages/report.php
```

Ожидание в задании — «не менее шести». Здесь восемь; ниже — все восемь с
классификацией, а в конце — «что здесь нельзя починить заменой на D7».

## 1. Нет проверки прав

**Ошибка.** Страница отдаёт отчёт любому посетителю: ни `$USER->IsAuthorized()`,
ни проверки группы, ни `CheckModuleRight`.

**Причина.** Права проверяют в точке входа, а не в меню и не «скрытой ссылкой».

**Последствие.** `Безопасность.` Отчёт по ценам и товарам открыт по прямому URL;
поисковик проиндексирует, если страница не закрыта `robots.txt`. Скрытая ссылка
в админке защитой не является — URL утекает из логов, закладок, истории
браузера.

**Исправление.** Проверка до подключения шаблона и до запроса к данным:
`if (!$USER->IsAdmin()) { \CHTTP::SetStatus('403 Forbidden'); ... }`. Для
страницы внутри админки — `$APPLICATION->GetGroupRight('iblock')`. `403` здесь
корректен: страница — не объект, скрывать её существование нечего.

## 2. `$_GET` без `isset`, типа и валидации

**Ошибка.** `$from = $_GET['from'];` — массив при `?from[]=1`, warning при
отсутствии параметра, произвольная строка при `?from=foo`.

**Причина.** `$_GET` — нетипизированный пользовательский ввод.

**Последствие.** `Безопасность + поддерживаемость.` Массив в фильтре ломает
построение запроса (`Array to string conversion`), пустой параметр даёт warning
в лог на каждый хит и `LIKE`/`>=` с пустой строкой. SQL-инъекции здесь нет:
`CIBlockElement::GetList` параметризует значения — важно не преувеличивать.
Но невалидная дата молча меняет смысл отчёта, и никто этого не замечает.

**Исправление.** `Context::getCurrent()->getRequest()->getQuery('from')`,
`is_string()`, разбор через `DateTimeImmutable::createFromFormat('!Y-m-d', …)`
с проверкой обратного форматирования, осмысленный дефолт, обмен `from/to`, если
пришли в обратном порядке.

## 3. Запись файла в публичный `/upload/` на GET-запрос

**Ошибка.** `file_put_contents(DOCUMENT_ROOT . '/upload/report.csv', …, FILE_APPEND)`.

**Причина.** Смешаны чтение (страница) и запись (побочный эффект), а каталог
выбран первый попавшийся.

**Последствие.** `Безопасность + производительность.` Четыре проблемы в одной
строке: (а) `/upload/` отдаётся веб-сервером напрямую — отчёт доступен по
`/upload/report.csv` вообще без авторизации; (б) GET с побочным эффектом
пишется краулерами и префетчерами — файл растёт от чужого трафика; (в) нет
`LOCK_EX`, параллельные запросы перемешивают строки; (г) результат записи не
проверяется — «отчёт есть» превращается в «отчёта нет» без ошибки.

**Исправление.** Файл не нужен: CSV собирается в памяти и отдаётся в поток
(`php://output` + `fputcsv` + `Content-Disposition`), побочных эффектов нет,
права проверяются на входе. Если файл действительно нужен (большие выгрузки) —
он пишется **вне** `DOCUMENT_ROOT`, по POST с `sessid`, с `LOCK_EX` и
проверкой результата.

## 4. Нет ограничения выборки

**Ошибка.** Четвёртый параметр `GetList` — `false`.

**Причина.** «Работает же» на демо с 20 элементами.

**Последствие.** `Производительность.` Полный обход инфоблока на каждый хит:
время и память линейны по размеру каталога. На 50k элементов страница уходит в
таймаут или `memory_limit`, при этом в отчёт попадает всё — то есть вывод
бесполезен.

**Исправление.** `['nPageSize' => 50, 'iNumPage' => $page]` для страницы и
`['nTopCount' => 5000]` для экспорта — с явным сообщением, что выгрузка
ограничена.

## 5. XSS в выводе

**Ошибка.** `echo $el['NAME'] . ' — ' . $el['PROPERTY_PRICE_VALUE']`.

**Причина.** Имена элементов приходят из контента, а не из кода.

**Последствие.** `Безопасность.` Элемент с именем `<script>…</script>` или
`<img onerror=…>` выполняет код в браузере администратора — то есть в сессии,
у которой есть доступ к админке. Это не «косметика».

**Исправление.** `htmlspecialcharsbx()` на каждом значении при выводе. Не в
фильтре и не при сохранении: экранирование зависит от контекста, и в JSON/SQL
оно другое.

## 6. `prolog_before.php` без `prolog.php`

**Ошибка.** Подключён только `prolog_before.php`; `prolog.php`/`epilog.php` нет.

**Причина.** Скрипт вырос из «быстрого probe» и остался скриптом.

**Последствие.** `Поддерживаемость.` Нет шаблона сайта: `$APPLICATION->SetTitle('Отчёт')`
не выводится никуда (`<title>` формируется в `header.php`), нет стилей и
навигации, страница выглядит как дамп. Плюс не работают штатные механизмы
шаблона: `AddChainItem`, буферизация, композит.

**Исправление.** `prolog_before.php` (логика) → `prolog.php` (шаблон) →
`epilog.php`. Строка `SetTitle` остаётся до `prolog.php` — это обязательный
порядок, иначе заголовок не попадёт в `<title>`.

## 7. Фильтр по `DATE_ACTIVE_FROM` и закрытый интервал

**Ошибка.** `'>=DATE_ACTIVE_FROM' => $from`, `'<=DATE_ACTIVE_FROM' => $to`.

**Причина.** Взято первое похожее на «дату» поле.

**Последствие.** `Поддерживаемость.` Две ошибки. Первая: `DATE_ACTIVE_FROM` —
дата **начала активности**, у элемента может быть пустой (тогда он всегда
выпадает) и не совпадает с датой создания. Отчёт «за период» по умолчанию
означает «созданные за период». Вторая: `to` — дата без времени, `<=` по
`00:00:00` отсекает весь последний день, и пользователь видит «за 1-е — 31-е,
а 31-го пусто».

**Исправление.** `>=DATE_CREATE` от `from 00:00:00` и `<DATE_CREATE` от
`to + 1 день 00:00:00` — полуоткрытый интервал. Для «даты активности» нужен
отдельный отчёт и отдельная формулировка в интерфейсе.

## 8. Модуль не подключён

**Ошибка.** Нет `Loader::includeModule('iblock')` (в исходнике вообще нет
подключения модуля).

**Причина.** На стенде разработчика `iblock` установлен и подключается
автоматически другими страницами.

**Последствие.** `Поддерживаемость.` На чистой странице или на редакции без
модуля — фатал «Class "CIBlockElement" not found». Ошибка воспроизводится
только у клиента и только иногда — худший класс дефектов.

**Исправление.** `if (!Loader::includeModule('iblock')) { 500 + понятный текст }`
до первого обращения к API.

## Что здесь нельзя починить заменой на D7

Соблазн ответить «перепишем на ORM» — и это неверный ответ:

1. **`PROPERTY_PRICE`.** В ORM свойства не выбираются без join; понадобится
   `ElementPropertyTable`/`PropertyIndex`, а формат результата изменится.
   Задача ревью — исправить дефекты, а не сменить контракт выдачи.
2. **`PROPERTY_PRICE_VALUE` и `Fetch()`.** Это контракт legacy-выборки.
   `ElementTable` вернёт `PROPERTY_PRICE` как поле-объект или массив другой
   формы — весь код вывода и CSV меняется вместе с ним.
3. **`DATE_ACTIVE_FROM` vs `DATE_CREATE`.** Это решение о смысле отчёта, а не
   о технологии: ORM точно так же позволит выбрать неверное поле.
4. **Права, CSRF, экранирование, лимиты.** От выбора API не зависят вообще.
   D7-код с `echo $name` — такая же уязвимость.

Вывод, который и проверяется на защите: **ревью — про дефекты, а не про версию
API.**

## Проверка

1. Обычный пользователь → `403`, данных нет.
2. `?from=2024-13-45` → дефолтный период, без warning в логе.
3. `?from[]=1&to[]=2` → дефолтный период, без warning.
4. `?from=2024-01-01&to=2024-01-31` → записи за 31-е включительно.
5. `?export=csv` → файл скачивается, в `/upload/` ничего не появляется.
6. Элемент с `NAME = <script>alert(1)</script>` → текст на странице, скрипта нет.
7. Заголовок вкладки браузера = «Отчёт за период» (работает `prolog.php`).
8. На инсталляции без `iblock`: понятная ошибка `500`, не фатал с классом.

## Ограничения

- `$USER->IsAdmin()` — демо-уровень прав. В проекте — права на инфоблок/модуль
  или отдельная группа отчётности.
- `CHTTP::SetStatus()` — legacy, но это штатный способ выставить статус в
  прологе; `http_response_code()` до `prolog.php` тоже работает, однако ядро
  может перезаписать статус в `epilog_after`.
- Экспорт не ограничен по времени: 5000 строк `CIBlockElement` тянет несколько
  секунд. Для больших выгрузок — агент + файл вне `DOCUMENT_ROOT`.
- Нет тестов: проверка — чек-лист выше.

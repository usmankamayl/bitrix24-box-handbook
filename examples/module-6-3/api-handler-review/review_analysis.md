# Code Review #2: Разбор «плохого» REST-эндпоинта повтора заказа

## Найденные проблемы (7 штук)

### Критичные

| № | Проблема | Сценарий | Исправление |
|---|----------|----------|--------------|
| 1 | **Нет проверки владельца заказа — IDOR** | Любой авторизованный пользователь подставляет чужой `order_id` → получает копию чужого заказа с чужим адресом/телефоном в своей корзине | `(int)$order->getUserId() !== $userId` → 403 |
| 2 | **`$_REQUEST['order_id']` без приведения типа** | Передача массива/строки вместо числа — неожиданное поведение `Order::load()` | `(int)($_REQUEST['order_id'] ?? 0)` |
| 3 | **Копирование старой цены с `CUSTOM_PRICE='Y'`** | Акция закончилась/цена выросла — пользователь оформляет заказ по устаревшей цене, магазин теряет деньги | Не ставим `CUSTOM_PRICE` — цена пересчитывается по актуальным правилам |

### Архитектурные

| № | Проблема | Сценарий | Исправление |
|---|----------|----------|--------------|
| 4 | **Сразу создаётся новый `Order`, минуя checkout** | Пропускается проверка наличия на складе, актуальности доставки/оплаты, валидация свойств | Мердж в активную корзину (`Basket::loadItemsForFUser`), оформление — через обычный checkout |
| 5 | **Нет мерджа — дубли при повторном вызове** | Пользователь нажал «Повторить» дважды → два одинаковых товара вместо одного с quantity×2 | Проверка `getProductId()` в текущей корзине перед `createItem` |
| 6 | **Синхронная отправка письма** | SMTP недоступен → весь repeat падает с 500, хотя корзина уже наполнена | Письмо убрано — репит это не заказ, письмо уйдёт при реальном оформлении |
| 7 | **Silent fail при ошибке `save()`** | `{"error":"save failed"}` — разработчик через месяц не поймёт, что упало | Логирование деталей в файл + безопасное сообщение пользователю |

## Главный архитектурный вопрос

«Повтор заказа» — это создание **нового независимого заказа** (клон) или **наполнение текущей корзины** для обычного оформления?

- **Клон заказа** — опасно: обходит проверки наличия/актуальности доставки/валидации свойств, которые проходит обычный checkout.
- **Наполнение корзины** (правильный подход) — пользователь довозит свой обычный checkout-flow, где все проверки стандартные.

Большинство реальных магазинов делают **второй вариант** — он у vas уже был описан в `examples/module-5-4/order-actions-api/README.md`.

## Как отвечать на собеседовании

> «Первое и критичное — нет проверки владельца заказа, это IDOR: подставил чужой `order_id` — получил чужие данные в своей корзине. Второе — копируется старая цена с `CUSTOM_PRICE='Y'`, то есть пользователь получает заказ по неактуальной цене. Третье — архитектурная проблема: эндпоинт сразу создаёт новый заказ, обходя обычный checkout с его проверками наличия и валидацией. Правильно — мерджить товары в текущую корзину и дать пользователю пройти обычное оформление.»

## Что спросят

- «Почему `CUSTOM_PRICE` не должен копироваться?» — потому что акция могла закончиться; при повторе цена должна пересчитываться заново по актуальным правилам.
- «Чем плохо создание нового `Order` напрямую?» — обходит валидацию наличия товара, актуальности способа доставки, свойств заказа — всё то, что делает стандартный checkout.
- «Как избежать дублей при повторном repeat?» — проверка существующей позиции в корзине по `PRODUCT_ID` перед добавлением новой.

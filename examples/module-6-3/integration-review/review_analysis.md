# Code Review #3: Разбор «плохой» интеграции с API доставки

## Найденные проблемы (8 штук)

### Критичные (безопасность и корректность)

| № | Проблема | Сценарий | Исправление |
|---|----------|----------|--------------|
| 1 | **API-ключ захардкожен в коде** | Код попадёт в git — ключ утекает в репозиторий. Ротация требует деплой. | `Option::get` — настройка модуля, меняется в админке без релиза |
| 2 | **Синхронный `curl_exec` в `OnSaleOrderSaved`** | HTTP-запрос длится внутри транзакции сохранения заказа: транзакция держит блокировки, а внешний API может отвечать секунды/не отвечать вообще | HTTP уходит в outbox-workflow, событие делает только `INSERT` в очередь |
| 3 | **Нет таймаута у `curl`** | API курьерской службы повис — запрос висит бесконечно, блокирует транзакцию и держит PHP-процесс | `CURLOPT_CONNECTTIMEOUT => 3`, `CURLOPT_TIMEOUT => 5` |
| 4 | **`save()` внутри `OnSaleOrderSaved` → рекурсия** | `setField` → `save()` → снова `OnSaleOrderSaved` → бесконечный цикл или deadlock | Сохранение результата делает worker, а не обработчик события |
| 5 | **Webhook без проверки подписи** | Любой может отправить поддельный статус «доставлен» на любой заказ | `hash_hmac` + `hash_equals` по сырому телу запроса |

### Надёжность

| № | Проблема | Сценарий | Исправление |
|---|----------|----------|--------------|
| 6 | **Нет retry и circuit breaker** | API курьера лежит 1 час — все события теряются, заявки не создаются, никто не узнает | Outbox с retry + backoff; circuit breaker не долбит мёртвый сервис |
| 7 | **Нет `Idempotency-Key` при создании заявки** | Worker сделал retry → две заявки на доставку вместо одной | Заголовок `Idempotency-Key: shipment_{order_id}` — дедупликация на стороне курьера |
| 8 | **Нет идемпотентности в webhook** | Повторный webhook с тем же статусом → лишний `save()` → лишние события | Сравнение текущего `DELIVERY_STATUS` с пришедшим перед `save()` |

## Ключевые правила интеграции с внешним API

- **Секреты — в `Option`, не в коде.** Git-история ≠ криптосторож; ключ должен меняться без деплоя.
- **HTTP в событии — нет.** Транзакция заказа не должна ждать внешний API. Событие → `INSERT` в очередь.
- **Таймаут — всегда.** `curl` без `CURLOPT_TIMEOUT` — это процесс, который может висеть вечно.
- **Подпись webhook — до любых действий.** Без неё любой может прислать поддельный статус.
- **`save()` внутри события — нельзя.** Это рекурсия/дедлок; изменения делает worker.
- **Идемпотентность — обязательно.** `Idempotency-Key` при создании; проверка «уже такой статус» при приёме webhook.
- **Retry + circuit breaker.** Retry для временных сбоев, breaker — чтобы не долбить мёртвый API каждым заказом.

## Как отвечать на собеседовании

> «Критичное — синхронный curl без таймаута внутри `OnSaleOrderSaved`: транзакция заказа ждёт внешний API, при зависании всё падает. Плюс `save()` в событии — рекурсия. Плюс API-ключ захардкожен — утечка в git. Плюс webhook без подписи — подделка статусов. Правильно: событие ставит задачу в outbox, отдельный worker делает HTTP с таймаутом, retry через backoff, circuit breaker, `Idempotency-Key`, подпись через `hash_hmac` по сырому телу.»

## Что спросят

- «Чем circuit breaker отличается от retry?» — retry делает повторную попытку сразу; circuit breaker при N сбоях перестаёт пытаться вообще, чтобы не добивать упавший сервис.
- «Зачем `Idempotency-Key`, если есть retry?» — retry делает новый HTTP-запрос, без ключа курьерская служба создаст две заявки.
- «Почему 200, а не 404 при неизвестном `order_id` в webhook?» — иначе сервис будет ретраить бесконечно на заказ, которого у нас никогда не было.

# Code Review #1: Разбор «плохого» компонента

## Найденные проблемы (8 штук)

### Критичные (ломается/уязвимость)

| № | Проблема | Сценарий | Исправление |
|---|----------|----------|-------------|
| 1 | **LocalRedirect без `die()`** | Редирект выполняется, но код продолжает работать → запросы к БД для неавторизованного | `die()` после `LocalRedirect` |
| 2 | **Ключ кеша одинаковый для всех** | `'order_list'` — все пользователи видят заказы первого, кто открыл страницу | Ключ по `user_id`: `'order_list_u' . $userId` |
| 3 | **Кеш без тегов** | Заказ изменился → пользователь видит старые данные до TTL (3600 сек) | `startTagCache` + `registerTag('sale_order_u' . $userId)` |
| 4 | **SQL-инъекция (косвенная)** | `$row['STATUS_ID']` в запрос без экранирования — хоть и число, но привычка опасна | D7 ORM `getList` или `(int)` приведение |

### Производительность

| № | Проблема | Сценарий | Исправление |
|---|----------|----------|-------------|
| 5 | **N+1: 4 запроса в цикле** | 20 заказов × 4 запроса = 80+ запросов → 8 секунд | 3 batch-запроса всего |
| 6 | **`$DB->Query` вместо D7** | Нет кеширования результата, нет ORM-связей, сложнее поддерживать | `Order::getList`, `BasketTable::getList` |

### Архитектура

| № | Проблема | Сценарий | Исправление |
|---|----------|----------|-------------|
| 7 | **Бизнес-логика в компоненте** | Скидка 10% — хардкод, не тестируется, не переиспользуется | `DiscountService` — отдельный класс |
| 8 | **CAN_CANCEL — бизнес-правило в данных** | Логика "какие заказы можно отменить" в массиве для шаблона | Отдельный метод `getCancelableOrderIds()` |

## Сравнение «до/после»

| Метрика | До | После |
|---------|-----|-------|
| Запросов на страницу | ~80 | 3 |
| Кеш | Общий ключ, без тегов | По `user_id`, с тегами |
| IDOR | Нет проверки (только `IsAuthorized`) | Проверка `USER_ID` в фильтре |
| Безопасность SQL | Конкатенация | ORM / приведение типов |
| Тестируемость | Нет (всё в компоненте) | `DiscountService` — отдельный класс |

## Как отвечать на собеседовании

> «Первое — `LocalRedirect` без `die()` — запросы к БД выполняются даже для неавторизованного. Второе — ключ кеша `'order_list'` одинаковый для всех — пользователь А увидит заказы пользователя Б. Третье — N+1: 4 запроса в цикле, на 20 заказов — 80 запросов. Четвёртое — бизнес-логика (скидка) в компоненте — хардкод, не тестируется. Как перепишу: `Order::getList` с `filter` по `USER_ID`, два batch-запроса для товаров и городов, кеш с тегами, `DiscountService` вынесу.»

## Что спросят

- «Почему `die()` после `LocalRedirect`?» — `LocalRedirect` отправляет заголовок `Location`, но PHP продолжает выполняться до конца скрипта.
- «Почему кеш по `user_id`?» — иначе все видят одни и те же данные (первого, кто открыл страницу).
- «Что такое `setResultCacheKeys`?» — указывает, какие ключи `arResult` кешировать. Без неё кешируется весь `arResult`, включая объекты (опасно).
